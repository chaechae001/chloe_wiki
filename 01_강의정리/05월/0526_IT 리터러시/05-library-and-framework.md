# 라이브러리와 프레임워크 — 바퀴를 다시 발명하지 않는 법

> 차트를 직접 0부터 그리고, 로그인 기능을 처음부터 짜고, 관리자 페이지를 손수 만든다면 며칠이 걸립니다. 그런데 개발자는 이걸 몇 줄로 끝내기도 합니다. 비결이 바로 라이브러리와 프레임워크입니다.

`웹의역사` · `라이브러리` · `패키지` · `프레임워크` · `코드재사용` · `Django` · `버전관리`

## 핵심요약

- 웹은 자료 공유를 위해 시작되어, 점점 커지고 복잡해지며 **재사용 가능한 코드의 필요성**을 키웠다.
- **라이브러리**는 자주 쓰는 코드(기능)를 모아 둔 도구 모음으로, 가져다 선언해 쓴다.
- 라이브러리는 **패키지**라고도 불리며, 오픈소스로 활발히 공유된다.
- **프레임워크**는 코드를 작성하기 위한 **틀(구조)** 을 제시해, 정해진 규칙 위에서 개발하게 한다.
- 라이브러리와 API는 "재사용"이라는 공통점이 있지만, API는 **네트워크·통신**을 통해 기능을 제공한다는 차이가 있다.
- 라이브러리·프레임워크는 **버전이 계속 바뀌므로**, 버전 차이로 코드가 깨질 수 있음을 늘 염두에 둔다.

## 개념별 정리

### 웹의 역사 — 왜 도구가 필요해졌나

**1. 정의**
웹(World Wide Web)은 연구자들끼리 자료를 공유하기 위해 시작된 기술입니다. 창시자 팀 버너스리는 HTML·CSS·HTTP·URL 등 현대 웹의 초석이 되는 기술을 개발하고, 이를 대중에게 무료로 공개했습니다.

**2. 왜 필요한가?**
웹이 점점 커지고 복잡해지면서, 같은 코드를 반복해서 짜는 비효율이 커졌습니다. 협업 프로젝트도 많아져 **구조화된 체계**가 필요해졌습니다. 라이브러리·프레임워크는 이 흐름에서 등장합니다.

**3. 예시 — 점점 커지는 웹**

```text
초기 웹:  자료 공유용 단순 페이지 (세계 최초 웹사이트)
        │  반복적으로 자주 쓰이는 코드들이 쌓임
        ▼
현재 웹:  크고 복잡한 서비스 → 재사용 + 구조화된 체계 필요
```

**4. 헷갈리기 쉬운 점**
웹의 역사를 단순 교양으로 보기 쉽지만, "왜 라이브러리·프레임워크가 생겼는가"라는 **필요의 맥락**을 보여주는 배경입니다.

**5. 한 줄 정리**
웹이 커질수록 "반복을 줄이고 구조를 잡는" 도구의 필요성이 커졌다.

### 라이브러리 (Library)

**1. 정의**
반복해서 자주 사용하는 코드 모음, 일종의 코드로 이루어진 도구 모음입니다. 다른 말로 **패키지(package)** 라고도 부릅니다.

**2. 왜 필요한가?**
코드의 역사가 쌓이며 "자주 쓰게 되는 기능"이 생깁니다. 이를 한 곳에 모아 두고, 필요할 때 **선언해서 가져다 쓰면** 매번 새로 만들 필요가 없습니다. 오픈소스 영역에서도 활발히 생산·공유됩니다.

**3. 예시 — 대표 라이브러리**

```text
- Chart.js  : 색과 데이터 수치만 선언하면 복잡한 차트를 쉽게 그려줌
- Passport.js : 로그인·회원가입 관리 구현을 쉽게 도와줌
              (소셜 로그인도 간편하게, 카카오·네이버용도 존재)
- Pandas    : 데이터 분석·가공을 쉽게 처리
```

예를 들어 막대그래프(Bar chart)를 직접 그리려면 복잡하지만, Chart.js는 데이터와 색만 선언하면 그려줍니다.

**4. 헷갈리기 쉬운 점**
"라이브러리를 쓰면 무조건 좋다"는 오해가 있습니다. 적절하지 못한 사용은 오히려 **성능을 저하**시킬 수 있습니다. 검증된 라이브러리를 잘 골라 쓰는 것도 개발자의 능력입니다.

**5. 한 줄 정리**
라이브러리는 자주 쓰는 기능을 모아 둔 도구 상자로, 가져다 선언해 쓴다.

> 비유: 요리할 때 직접 만들지 않고 사 오는 **양념·소스 세트**입니다. 필요할 때 꺼내 쓰면 시간이 크게 절약됩니다.

### 라이브러리 vs API

**1. 정의**
둘 다 "재사용 가능한 코드"를 활용한다는 공통점이 있습니다. 차이는 제공 방식입니다.

**2. 왜 필요한가?**
비슷해 보이는 두 개념을 구분해야, "이건 가져와 쓰는 도구인지, 통신으로 호출하는 기능인지"를 헷갈리지 않습니다.

**3. 예시 — 공통점과 차이점**

```text
공통점 : 재사용 가능한 코드의 반복적 활용
차이점 : API는 네트워크·통신을 통해 기능을 제공
```

- 라이브러리: 내 프로젝트 안으로 **가져와** 선언해 사용.
- API: 네트워크 너머의 기능을 **호출**해 사용.

**4. 헷갈리기 쉬운 점**
라이브러리는 보통 내 코드 안에서 직접 부르고, API는 통신을 거쳐 외부 기능을 부릅니다. "가져오기 vs 호출하기"로 기억하면 좋습니다.

**5. 한 줄 정리**
라이브러리는 가져와 쓰는 도구, API는 통신으로 불러 쓰는 기능이다.

### 프레임워크 (Framework)

**1. 정의**
프로그램을 효율적으로 짜기 위한 **틀(Frame)** 입니다. 빵 모양을 찍는 틀처럼, 코드를 작성하기 위한 구조를 미리 제시합니다.

**2. 왜 필요한가?**
공통된 규칙(틀)을 따르면 협업에 매우 유리하고, 개발자는 틀을 짜는 대신 **핵심 로직에 집중**할 수 있습니다. 언어별로 다양한 프레임워크가 있고, 각각 제공하는 도구가 다릅니다.

**3. 예시 — Django**

```text
Django (파이썬 기반 웹 프레임워크)
- 파이썬으로 웹 페이지를 만들 때 사용
- 보통 직접 만들어야 하는 관리자 페이지를,
  상당한 수준으로 기본 제공 → 제작 부담을 덜어줌
```

**4. 헷갈리기 쉬운 점**
**라이브러리 vs 프레임워크**가 가장 헷갈립니다. 라이브러리는 "내가 필요할 때 꺼내 쓰는 도구", 프레임워크는 "정해진 틀 안에서 내가 코드를 채우는 구조"입니다. 주도권의 방향이 다릅니다.

**5. 한 줄 정리**
프레임워크는 정해진 틀을 제공하고, 개발자는 그 틀 안을 채운다.

> 비유: 붕어빵으로 보면, **붕어빵 틀이 프레임워크**(모양을 잡아줌), **반죽·팥 같은 재료가 라이브러리**(가져다 넣는 것)입니다. 틀이 형태를 정하고, 나는 그 안을 채웁니다.

### 버전 관리 주의

**1. 정의**
라이브러리·프레임워크는 계속 업데이트되며 버전이 바뀝니다. 버전이 달라지면 같은 코드가 동작하지 않을 수 있습니다.

**2. 왜 필요한가?**
오래된 책이나 옛 강의 영상을 따라 할 때 코드가 안 되는 일이 흔한데, 대부분 **버전 불일치** 때문입니다. 이를 알면 불필요한 좌절을 줄일 수 있습니다.

**3. 한 줄 정리**
도구의 버전이 바뀌면 코드가 깨질 수 있으니, 버전을 늘 확인한다.

> 비유: 같은 레시피라도 오븐 모델(버전)이 바뀌면 온도·시간이 달라져 결과가 달라지는 것과 같습니다.

## 코드로 보기 — 라이브러리 vs 프레임워크, 주도권의 방향

개념 중심 글이라, 두 도구의 차이를 비교표와 구조도로 정리합니다.

```text
[라이브러리] 내가 도구를 부른다 (내가 주도)
   내 코드 ──── 필요할 때 호출 ───▶ 라이브러리 기능
   예) "여기서 차트 그려줘" → Chart.js 호출

[프레임워크] 틀이 내 코드를 부른다 (틀이 주도)
   프레임워크(틀) ──── 정해진 자리에서 ───▶ 내 코드 실행
   예) 정해진 구조의 빈칸에 내 로직을 채워 넣음
```

| 구분 | 라이브러리 | 프레임워크 |
| --- | --- | --- |
| 비유 | 양념·재료 / 붕어빵 반죽 | 붕어빵 틀 |
| 주도권 | 내가 필요할 때 호출 | 틀이 흐름을 주도 |
| 자유도 | 높음(원하는 부분만 사용) | 정해진 규칙을 따름 |
| 강점 | 가볍게 기능 추가 | 협업·구조화에 유리 |
| 예시 | Chart.js, Passport.js, Pandas | Django |

**무엇을 보기 위한 비교인가**
"둘 다 코드를 재사용한다"는 점에서 헷갈리는 라이브러리와 프레임워크를, **주도권의 방향**으로 갈라 보기 위한 것입니다.

**해석**
내가 도구를 부르면 라이브러리, 틀이 내 코드를 부르면 프레임워크입니다. 이 한 끗이 둘을 가르는 핵심입니다.

**실무 연결**
- 검증된 라이브러리를 적절히 고르는 것은 생산성과 직결됩니다(잘못 쓰면 성능 저하).
- 협업 프로젝트에서는 공통 규칙(프레임워크)을 따르는 것이 유지보수·분업에 유리합니다.

3. 옛날 강의를 따라 했더니 코드가 안 됐다면, 가장 먼저 의심해 볼 원인은 무엇일지 적어보세요.

## 헷갈리기 쉬운 포인트

- **라이브러리 vs 프레임워크**: 내가 도구를 호출 vs 틀이 내 코드를 호출(주도권 방향).
- **라이브러리 vs API**: 가져와 쓰는 도구 vs 통신으로 호출하는 기능.
- **라이브러리 = 패키지**: 같은 대상을 부르는 다른 이름.
- **최신 = 항상 안전**은 아님: 버전 차이로 기존 코드가 깨질 수 있음.

**복습 질문 및 답변**

- (기본) 자주 쓰는 코드를 모아 둔 도구 모음을 무엇이라 하나?
  → 라이브러리(=패키지).
- (이해확인) 라이브러리와 API의 가장 큰 차이는?
  → API는 네트워크·통신을 통해 기능을 제공한다는 점. 라이브러리는 가져와 직접 호출함.
- (응용) "붕어빵 틀과 반죽" 비유로 프레임워크와 라이브러리를 구분해 설명한다면?
  → 틀(프레임워크)이 전체 모양과 흐름을 정하고, 나는 그 안에 반죽·재료(라이브러리)를 가져다 채워 넣는다.

## 한 줄 정리

> 라이브러리는 가져다 쓰는 도구 상자, 프레임워크는 그 위에서 개발하는 틀이며, 둘 다 "바퀴를 다시 발명하지 않게" 도와주되 버전 변화에는 늘 주의한다.
