# 프론트엔드·백엔드와 REST API — 화면 뒤에서 벌어지는 일

> 같은 로그인 버튼인데, 누르면 "환영합니다"가 뜨기도 하고 "비밀번호가 틀렸어요"가 뜨기도 합니다. 화면(프론트엔드)과 서버(백엔드)는 이때 정확히 어떤 말(메서드)을 주고받고 있을까요?

`프론트엔드` · `백엔드` · `UIUX` · `반응형` · `HTTP메서드` · `CRUD` · `API` · `RESTAPI` · `Analytics` · `SEO`

## 핵심요약

- **프론트엔드**는 사용자가 처음 만나는 화면, **백엔드**는 서버 측에서 비즈니스 로직을 처리하는 쪽이다.
- 프론트엔드의 핵심은 **UI(화면 구성)** 와 **UX(사용 경험)**, 그리고 다양한 화면을 커버하는 **반응형**이다.
- 프론트와 백엔드가 주고받는 통신 함수가 **HTTP 메서드**: GET·POST·PUT/PATCH·DELETE.
- 이 네 가지는 데이터의 **읽기·생성·수정·삭제(CRUD)** 와 짝을 이룬다.
- **API**는 프로그램끼리 대화하도록 도와주는 일이고, **REST API**는 "약속된 주소(URI)에 기능을 매핑한" 설계 방식이다.
- 서비스를 키우려면 **사용자 행동 분석(Analytics)** 과 **검색 노출(SEO)** 도 함께 고려한다.

## 개념별 정리

### 프론트엔드 (Front-end / 클라이언트)

**1. 정의**
서비스에서 사용자가 처음 만나는 화면이자, 서비스의 의도대로 사용자를 이끄는 영역입니다. 서버 기능과 무관하게 단독으로 동작하는 기능(예: 카메라 촬영)도 포함합니다.

**2. 왜 필요한가?**
기능이 아무리 좋아도 화면이 불편하면 사용자가 떠납니다. 보이는 품질(사용성·디자인)이 곧 서비스의 첫인상이기 때문입니다.

**3. 예시 — 프론트엔드의 주요 특징**

```text
1) UI/UX        : 화면과 사용자 경험 구성
2) 독립적 기능  : 서버 없이도 동작하는 기능(예: 카메라 촬영)
3) 통신 기능    : 서버에 요청을 보내기 위한 기능
4) Analytics    : 사용자 패턴 분석을 위한 측정 코드
```

**4. 헷갈리기 쉬운 점**
"프론트엔드 = 디자인"으로 좁게 보기 쉽지만, 디자인뿐 아니라 서버에 요청을 보내는 통신, 사용자 행동을 측정하는 분석까지 포함하는 넓은 영역입니다.

**5. 한 줄 정리**
프론트엔드는 사용자를 만나는 화면이자, 서버와 대화를 시작하는 입구다.

> 비유: 매장의 쇼윈도와 출입문입니다. 보기 좋아야 들어오고(UI/UX), 문이 잘 열려야 안(서버)으로 연결됩니다.

### UI와 UX, 그리고 반응형

**1. 정의**
- **UI(User Interface)**: 사용자가 만나는 화면, 디자인적 요소를 담은 면. 실무에선 GUI(그래픽 기반 UI)를 그냥 UI라 부르는 경우가 많습니다.
- **UX(User Experience)**: 서비스 성격에 맞춰 사용자에게 편리한 경험을 제공하는 것.
- **반응형 화면**: PC·태블릿·모바일 등 다양한 크기의 스크린을 하나의 설계로 커버하는 방식.

**2. 왜 필요한가?**
같은 기능도 어떤 흐름(UX)과 어떤 화면(UI)으로 주느냐에 따라 사용 편의가 크게 달라집니다. 또 사용자의 기기가 제각각이라 반응형이 필요합니다.

**3. 예시 — 같은 목적, 다른 UX 흐름**

```text
흐름 A: 로그인 → 메인화면 → 메뉴 탐색 → 기능 → 카메라 촬영
흐름 B: 로그인 → 메인화면 하단 버튼 → 카메라 촬영
```

둘 다 "카메라 촬영"이 목적이지만, 흐름 B가 더 적은 단계로 도달합니다. 서비스 성격에 맞는 흐름을 고르는 게 UX입니다.

**4. 헷갈리기 쉬운 점**
**UI는 화면(보이는 것), UX는 경험(흐름·느낌)** 입니다. 예쁜 화면(UI)이 곧 좋은 경험(UX)은 아닙니다. 반응형에서는 작은 화면에서의 정보 손실도 함께 고려해야 합니다.

**5. 한 줄 정리**
UI는 무엇을 보여줄지, UX는 어떻게 느끼게 할지를 다룬다.

> 비유: UI는 식당의 그릇과 플레이팅, UX는 입장부터 계산까지의 전체 동선과 기분입니다.

### HTTP 메서드 (GET · POST · PUT/PATCH · DELETE)

**1. 정의**
프론트엔드와 백엔드가 주고받는 통신 함수들입니다. 각각 데이터를 다루는 역할이 정해져 있습니다.

**2. 왜 필요한가?**
"이 요청이 정보를 읽으려는 건지, 새로 만들려는 건지, 고치려는 건지, 지우려는 건지"를 명확히 구분해야 서버가 올바르게 처리합니다.

**3. 예시 — 메서드별 역할**

| 메서드 | 하는 일 | 일상 예시 |
| --- | --- | --- |
| **GET** | 기존 정보·페이지를 읽어온다 | 로그인 후 "○○님 환영합니다" 페이지, 상품 상세 페이지 |
| **POST** | 정보를 저장·전달하기 위해 서버에 보낸다 | 명함정보(이름·회사·전화번호) 저장 |
| **PUT / PATCH** | 기존 정보의 내용을 수정한다 | 명함정보 수정, 비밀번호 변경 |
| **DELETE** | 저장된 정보를 삭제한다 | 명함정보 삭제, 서비스 계정 탈퇴 |

**4. 헷갈리기 쉬운 점**
- **GET vs POST**: GET은 "읽어오기", POST는 "보내서 저장하기". 로그인 후 내 이름을 화면에 불러오는 건 GET, 회원정보를 처음 저장하는 건 POST입니다.
- **PUT vs PATCH**: 둘 다 수정용입니다. PUT은 보안적으로 이슈가 생길 수 있어, 보완해서 나온 것이 PATCH라고 이해하면 됩니다(부분 수정에 PATCH를 많이 씀).

**5. 한 줄 정리**
GET=읽기, POST=만들기, PUT/PATCH=고치기, DELETE=지우기.

> 비유: 게시판으로 보면 글 보기(GET), 글 쓰기(POST), 글 수정(PUT/PATCH), 글 삭제(DELETE)와 똑같습니다.

### CRUD — 메서드의 또 다른 이름

**1. 정의**
데이터를 다루는 네 가지 기본 동작 **Create(생성)·Read(읽기)·Update(수정)·Delete(삭제)** 의 앞 글자입니다. HTTP 메서드와 자연스럽게 짝지어집니다.

**2. 왜 필요한가?**
거의 모든 서비스 기능은 결국 이 네 동작의 조합입니다. CRUD로 보면 복잡한 기능도 단순하게 분해됩니다.

**3. 예시 — 메서드와 CRUD 매핑**

```text
POST   →  Create (생성)
GET    →  Read   (읽기)
PUT/PATCH → Update (수정)
DELETE →  Delete (삭제)
```

**4. 헷갈리기 쉬운 점**
CRUD는 데이터 관점의 용어, HTTP 메서드는 통신 관점의 용어입니다. 같은 동작을 부르는 두 이름이라고 보면 됩니다.

**5. 한 줄 정리**
모든 서비스 기능은 결국 만들고·읽고·고치고·지우는 CRUD로 환원된다.

### API와 REST API

**1. 정의**
- **API(Application Programming Interface)**: 프로그램끼리(코드끼리) 대화하도록 도와주는 일, 즉 네트워크를 통한 기능 호출입니다.
- **REST API**: 약속된 주소(**URI**)마다 기능(함수)을 매핑해 둔 설계 방식입니다.

**2. 왜 필요한가?**
서로 다른 프로그램이 기능을 빌려 쓰려면 "이 주소로 요청하면 이 기능이 돈다"는 약속이 필요합니다. REST는 그 약속을 깔끔하게 정리한 규칙입니다.

**3. 예시 — 로그인 API와 GET API**

```text
[로그인 API]
클라이언트 ── 아이디/비밀번호 전송(POST) ──▶ 서버
endpoint: shoppingmall.com/login
→ 로그인 정보 DB 조회 → 로그인 성공 응답

[GET API: 국가별 페이지]
같은 회사 사이트라도 주소(국가코드)만 바꾸면 다른 정보를 가져온다.
  ...example.com/kr/  → 한국어 사이트 정보
  ...example.com/jp/  → 일본어 사이트 정보
```

여기서 요청이 도착하는 그 주소를 **Endpoint**라고 합니다.

**4. 헷갈리기 쉬운 점**
- **URI vs URL**: URL은 우리가 흔히 쓰는 웹사이트 주소를 뜻하고, URI는 그보다 더 넓은 "자원 식별자" 개념입니다. "URI가 URL보다 더 큰 개념"이라고 기억하면 됩니다.
- **API vs REST API**: API는 큰 개념(기능 호출), REST API는 그 API를 설계하는 한 가지 방식입니다.

**5. 한 줄 정리**
API는 프로그램끼리의 대화 창구이고, REST API는 그 창구를 "주소 = 기능"으로 약속한 방식이다.

> 비유: 식당 메뉴판과 같습니다. "1번 주소 = 비빔밥, 2번 주소 = 냉면"처럼 주소(번호)마다 받을 수 있는 기능(메뉴)이 정해져 있습니다.

### Open API

**1. 정의**
누구나 활용할 수 있도록 공개된 API입니다. 예를 들어 행정안전부가 제공하는 주소 조회 Open API를 활용해 "주소 찾기" 기능을 만들 수 있습니다.

**2. 왜 필요한가?**
이미 잘 만들어진 기능(지도·주소·날씨 등)을 직접 개발하지 않고 가져다 쓰면, 시간과 비용을 크게 아낄 수 있습니다.

**3. 한 줄 정리**
Open API는 공개된 기능 창구로, 잘 만든 기능을 빌려와 내 서비스에 붙이는 통로다.

### 사용자 분석(Analytics)과 검색엔진 최적화(SEO)

**1. 정의**
- **Analytics**: 트래픽·방문자 수·클릭 등 사용자 행동을 측정·분석하는 것. 대표적으로 Google Analytics가 있습니다.
- **SEO(Search Engine Optimization)**: 검색엔진이 내 페이지를 잘 찾아 상위에 노출하도록 최적화하는 것. Search Console 같은 도구로 노출 상태를 점검합니다.

**2. 왜 필요한가?**
UI/UX 개선은 직감이 아니라 **데이터(트래킹·통계)** 로 판단해야 합니다. A안·B안을 동시에 노출해 클릭률 등을 비교하는 **A/B 테스트**가 대표적입니다. 또 아무리 좋은 서비스도 검색에서 안 보이면 사용자가 찾아오기 어렵기 때문에 SEO가 필요합니다.

**3. 예시 — 데이터 기반 의사결정 흐름(의사코드)**

```text
A안 노출 그룹 → 클릭률 측정
B안 노출 그룹 → 클릭률 측정
if  B안 클릭률 > A안 클릭률:
        B안 채택
else:
        A안 유지
```

**4. 헷갈리기 쉬운 점**
"분석은 분석가만의 일"이 아닙니다. 내가 만든 페이지가 있어야 분석 실습이 가능하므로, 기획·마케팅·개발 모두에게 기본 역량에 가깝습니다. 또한 접근성(예: 색각 이상 사용자 고려)도 더 많은 사용자를 포용하는 중요한 설계 요소입니다.

**5. 한 줄 정리**
Analytics는 "사용자가 어떻게 쓰는지"를 보고, SEO는 "사용자가 어떻게 찾아오는지"를 챙긴다.

> 비유: Analytics는 매장에 단 CCTV(동선 파악), SEO는 큰길에 세운 간판(찾아오게 하기)입니다.

## 코드로 보기 — REST API: 주소에 기능을 매핑하다

이 글도 개념 중심이라, REST API의 핵심 아이디어를 구조도로 정리합니다.

```text
프론트엔드(요청)                         백엔드(응답)
   GET  ───────────────────────────────▶  GET
              │                              │
              └──── 약속된 주소(URI) ─────────┘
                    example.com/courses/info

핵심: 약속된 주소(URI)마다 기능(함수)이 매핑되어 있고,
      프론트가 GET으로 요청하면 백엔드도 반드시 GET으로 호응한다.
```

메서드 짝 맞추기 규칙:

```text
프론트 요청    →   백엔드 응답
GET           →   GET
POST          →   POST
PUT/PATCH     →   PUT/PATCH
DELETE        →   DELETE
```

**무엇을 하기 위한 구조인가**
"어떤 주소로 어떤 메서드 요청을 보내면 어떤 기능이 돌아오는지"를 미리 약속해, 프론트와 백엔드가 따로 개발해도 서로 맞물리게 하기 위한 것입니다.

**해석**
프론트가 GET으로 요청하면 백엔드도 GET으로 응답해야 합니다. 약속이 어긋나면 통신이 깨지거나 잘못된 동작이 일어납니다.

**실무 연결**
- 기획자가 이 규칙을 모르고 설계하면, 개발 단계에서 재작업이 커질 수 있습니다. 요즘은 기획자가 API 설계서를 함께 작성하기도 합니다.
- "피그마로 디자인 설계 → API 설계서 작성 → 개발"로 이어지는 협업 흐름의 중심에 REST API가 있습니다.

## 헷갈리기 쉬운 포인트

- **GET vs POST**: 읽어오기 vs 보내서 저장하기.
- **PUT vs PATCH**: 둘 다 수정. PATCH는 PUT의 보안 이슈를 보완한 쪽으로 부분 수정에 많이 쓰임.
- **UI vs UX**: 보이는 화면 vs 사용 경험(흐름).
- **API vs REST API**: 기능 호출이라는 큰 개념 vs 그것을 "주소=기능"으로 설계한 방식.
- **URI vs URL**: URI가 더 큰 개념, URL은 우리가 흔히 쓰는 웹 주소.

- [ ] UI와 UX의 차이를 예시로 들 수 있다.
- [ ] GET·POST·PUT/PATCH·DELETE의 역할을 각각 말할 수 있다.
- [ ] HTTP 메서드와 CRUD를 짝지을 수 있다.
- [ ] REST API에서 "주소(URI)=기능"의 의미를 안다.
- [ ] Analytics와 SEO가 왜 필요한지 설명할 수 있다.

**복습 질문 및 답변**

- (기본) 기존에 저장된 정보를 읽어오는 HTTP 메서드는?
  → GET.
- (이해확인) REST API에서 URI가 하는 역할은?
  → 약속된 주소마다 기능(함수)을 매핑해, 그 주소로 요청하면 정해진 기능이 동작하게 하는 것.
- (응용) UI는 좋은데 UX가 나쁜 서비스의 예를 하나 들고, 왜 그런지 설명한다면?
  → 화면은 예쁘지만(UI) 원하는 기능까지 단계가 너무 많아 흐름이 불편한(UX) 경우 등. 보이는 품질과 사용 경험은 별개이기 때문.

## 한 줄 정리

> 프론트엔드와 백엔드는 약속된 주소(REST API)와 메서드(GET·POST·PUT/PATCH·DELETE)로 대화하며, 좋은 서비스는 그 위에 분석(Analytics)과 노출(SEO)까지 챙긴다.
