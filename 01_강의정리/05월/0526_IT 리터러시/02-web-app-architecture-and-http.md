# 웹·앱 서비스의 구조와 통신 — HTTP, WAS, 그리고 동기/비동기

> 카카오톡 메시지를 보내면 상대에게 도착하고, 배달앱에서 주문하면 사장님 화면에 뜹니다. 멀리 떨어진 기기들이 어떻게 이렇게 정확히 "대화"할까요? 그 약속의 이름이 바로 **통신**입니다.

`통신` · `HTTP` · `프로토콜` · `JSON` · `XML` · `WAS` · `동기` · `비동기` · `요청과응답`

## 핵심요약

- 통신이란 **컴퓨터 간의 대화(Communication)** 이고, 기본 원칙은 **1요청 1응답**이다.
- 웹 주소 앞의 `http`는 **HyperText Transfer Protocol**, 즉 "약속된 형식으로 문자를 주고받는 방식"이다.
- 주고받는 데이터는 **JSON·XML** 같은 정해진 형태로 담기며, 이를 풀어 읽는 과정을 **파싱(Parsing)** 이라 한다.
- 웹 서비스의 일반 구조는 **클라이언트 → 웹 서버 → 백엔드 동작 코드 → 데이터베이스**로 이어진다(WAS).
- **동기**는 결과를 받을 때까지 기다리며 함께 움직이는 방식, **비동기**는 결과와 상관없이 다른 일을 진행하는 방식이다.
- 동기/비동기는 좋고 나쁨이 아니라 **상황에 맞게 선택**하는 것이다.

## 개념별 정리

### 통신 (Communication)

**1. 정의**
서로 다른 기기가 약속된 규칙에 따라 정보를 주고받는 것입니다. 컴퓨터와 컴퓨터, 스마트폰과 서버, 내 폰과 친구 폰(메신저) 사이의 "대화"라고 보면 됩니다.

**2. 왜 필요한가?**
혼자 도는 프로그램이 아니라 "연결된 서비스"를 이해하려면, 데이터가 어디서 어디로 흐르는지 알아야 하기 때문입니다.

**3. 예시 — 1요청 1응답**

```text
배달앱  ── "후라이드 치킨 주문" (요청) ──▶  치킨집
배달앱  ◀─ "주문 OK! 20분 기다려줘~" (응답) ─  치킨집
```

내가 한 번 요청하면, 상대가 한 번 응답합니다. 이 단순한 규칙이 통신의 기본입니다.

**4. 헷갈리기 쉬운 점**
"요청만 보내면 알아서 다 된다"고 생각하기 쉽지만, 통신은 **요청과 응답이 짝을 이루는 대화**입니다. 응답이 없으면 통신이 끊긴 것입니다.

**5. 한 줄 정리**
통신은 기기 사이의 대화이며, 1요청에 1응답이 기본 원칙이다.

> 비유: 가게에 "주문이요!"라고 외치면(요청) "네, 20분요!"라고 답이 오는(응답) 것과 같습니다.

### HTTP (HyperText Transfer Protocol)

**1. 정의**
웹 주소 맨 앞에 붙는 그 `http`입니다. 네 글자를 풀면 이렇게 됩니다.

- **H**yper — 연결된
- **T**ext — 문자를
- **T**ransfer — 전송하는
- **P**rotocol — 약속(규칙)

즉, "약속된 방식으로 문자를 주고받는 통신 규칙"입니다.

**2. 왜 필요한가?**
기기·운영체제·웹 브라우저가 제각각이어도 똑같이 통신하려면, 모두가 따르는 **공통 규칙(프로토콜)** 이 필요합니다. HTTP가 바로 그 공통 규칙입니다.

**3. 예시**
HTTP는 운영체제(Windows/Mac)나 브라우저(크롬/사파리)가 달라도, 약속된 형태이기만 하면 문자로 통신할 수 있게 해줍니다.

**4. 헷갈리기 쉬운 점**
"프로토콜"이라는 말이 어렵게 느껴지지만, 사전적으로는 "정한 규칙·약속"일 뿐입니다. HTTP = 웹에서 데이터를 주고받기로 한 약속, 정도로 이해하면 충분합니다.

**5. 한 줄 정리**
HTTP는 "연결된 문자를 약속대로 주고받자"는 웹 통신의 공통 규칙이다.

> 비유: 나라가 달라도 통하는 만국 공통 교통 신호등과 같습니다. 모두가 빨강=정지로 약속했기에 어디서든 통합니다.

### 주고받는 데이터의 형태 — JSON·XML과 파싱

**1. 정의**
통신으로 오가는 데이터는 아무렇게나가 아니라 정해진 형태에 담깁니다. 대표적인 형태가 **JSON**과 **XML**이고, 받은 데이터를 풀어서 필요한 부분을 꺼내 쓰는 과정을 **파싱(Parsing)** 이라고 합니다.

**2. 왜 필요한가?**
"이름은 여기, 전화번호는 여기"처럼 형태가 정해져 있어야 받는 쪽이 헷갈리지 않고 데이터를 꺼내 쓸 수 있습니다.

**3. 예시 — JSON으로 표현한 명함 정보**

```json
{
  "id": 1,
  "name": "홍길동",
  "company": "(주)예시",
  "phone": "010-1234-5678"
}
```

같은 정보를 XML 형태로도 표현할 수 있습니다.

```xml
<CD>
  <TITLE>Sample Title</TITLE>
  <ARTIST>Sample Artist</ARTIST>
  <COUNTRY>KR</COUNTRY>
  <PRICE>10.20</PRICE>
  <YEAR>1990</YEAR>
</CD>
```

받은 JSON을 파싱하면, "이 명함의 이름은 홍길동, 회사는 (주)예시"처럼 항목별로 꺼내 쓸 수 있습니다.

**4. 헷갈리기 쉬운 점**
JSON과 XML은 "데이터를 담는 그릇"일 뿐, 데이터 그 자체가 아닙니다. 같은 내용을 그릇만 바꿔 담은 것이라고 보면 됩니다.

**5. 한 줄 정리**
JSON·XML은 데이터를 약속된 형태로 담는 그릇이고, 파싱은 그 그릇을 열어 내용을 꺼내는 일이다.

> 비유: 택배 상자(JSON/XML)에 송장 규격이 정해져 있어야, 받는 사람이 어디에 무엇이 들었는지 바로 알 수 있는 것과 같습니다.

### WAS 구조 (Web Application Server)

**1. 정의**
일반적인 웹 애플리케이션 서버의 기본 구조로, 요청이 처리되는 길을 정리한 것입니다.

**2. 왜 필요한가?**
하나의 요청이 화면에서 데이터베이스까지 어떤 부품들을 거치는지 알아야, 문제가 생겼을 때 어디를 봐야 할지 감이 옵니다.

**3. 예시 — 요청이 흘러가는 길**

```text
클라이언트            Web Server          Back-end           DataBase
(웹 브라우저,    ─▶  (http 통신)  ─▶   (동작 코드)  ─▶   (각종 정보 저장)
 스마트폰)
        ◀──────────────  응답(Response)  ──────────────
        요청(Request)
```

클라이언트가 요청하면 웹 서버가 받고, 백엔드 코드가 처리해 데이터베이스와 주고받은 뒤, 그 결과가 다시 클라이언트로 응답됩니다. 여기서도 **1요청 1응답** 원칙은 그대로입니다.

**4. 헷갈리기 쉬운 점**
"서버는 하나의 덩어리"라고 생각하기 쉽지만, 실제로는 웹 서버·백엔드 코드·데이터베이스 등 여러 부품이 협력합니다.

**5. 한 줄 정리**
WAS는 "요청 → 웹 서버 → 백엔드 코드 → DB → 응답"으로 이어지는 한 줄의 처리 흐름이다.

> 비유: 패스트푸드 주문대(클라이언트) → 주문 접수(웹 서버) → 주방 조리(백엔드) → 식자재 창고(DB)로 이어지는 동선과 같습니다.

### 동기(Synchronous)와 비동기(Asynchronous)

**1. 정의**
- **동기**: 통신의 결과와 함께 움직임 (결과가 올 때까지 기다림)
- **비동기**: 통신의 결과와 상관없이 움직임 (기다리지 않고 다른 일 진행)

**2. 왜 필요한가?**
어떤 작업은 "끝날 때까지 기다려야" 안전하고(예: 결제·시스템 업데이트), 어떤 작업은 "기다리면 답답"해서(예: 영상 보며 댓글 달기) 동시에 진행하는 게 낫기 때문입니다.

**3. 예시**

```text
[동기]   강의 목록 → 상세 페이지로 이동      (페이지가 바뀔 때까지 기다림)
[비동기] 영상 시청 + 댓글 작성 동시에 진행   (서로 기다리지 않음)
```

게임 다운로드가 끝날 때까지 화면이 멈춰 있으면 동기적으로 느껴지고, 유튜브를 보면서 댓글을 다는 것은 비동기적으로 느껴집니다.

**4. 헷갈리기 쉬운 점**
"비동기가 무조건 좋다"는 오해가 흔합니다. 시스템 업데이트처럼 **순서가 중요한 작업은 동기 방식이 더 안전**할 수 있습니다. 둘은 우열이 아니라 선택의 문제입니다.

**5. 한 줄 정리**
동기는 "끝까지 기다리기", 비동기는 "기다리지 않고 동시에" — 상황에 맞게 고른다.

> 비유: 동기는 한 명씩 차례로 들어가는 1인 진료실, 비동기는 번호표를 뽑고 자리에서 다른 일을 보다가 호출되면 들어가는 방식입니다.

## 코드로 보기 — 요청 하나가 응답이 되어 돌아오기까지

개념 중심 글이라, 통신의 전체 동선을 흐름도로 정리합니다.

```text
[1] 클라이언트가 요청(Request)         예) "내 명함정보 저장해줘" (POST)
        │  http 통신(약속된 형식)
        ▼
[2] 웹 서버가 요청을 받음
        │
        ▼
[3] 백엔드 코드가 처리, Hypertext 파싱 후 저장 공간을 찾아 전달
        │
        ▼
[4] 데이터베이스에 정보 저장
        │
        ▼
[5] 처리 결과가 응답(Response)으로 클라이언트에 돌아옴   ← 1요청 1응답 완성
```

**무엇을 하기 위한 흐름인가**
"화면에서 누른 버튼 하나"가 서버와 DB를 거쳐 다시 화면으로 돌아오는 전체 경로를 한눈에 보기 위한 것입니다.

**해석**
사용자는 1·5단계(요청과 응답)만 체감하지만, 그 사이엔 항상 2~4단계의 처리가 숨어 있습니다. 화면이 "잠깐 멈춤"처럼 느껴진다면 이 처리가 진행 중일 수 있습니다.

**실무 연결**
- 기획자가 이 흐름을 이해하면, "이 버튼은 어떤 요청을 보내고 무엇을 응답받아야 하는지"를 설계서에 정확히 적을 수 있습니다.
- 동기/비동기 선택은 사용자 체감 속도와 직결되므로, 서비스 기획·UX 판단에 바로 쓰입니다.

## 헷갈리기 쉬운 포인트

- **동기 vs 비동기**: 결과를 기다림 vs 기다리지 않음. 비동기가 항상 우월한 게 아니라 상황에 따라 다름.
- **JSON vs XML**: 같은 데이터를 담는 서로 다른 그릇. 형태만 다를 뿐 역할은 같음.
- **요청(Request) vs 응답(Response)**: 보내는 쪽 vs 돌려주는 쪽. 1요청 1응답으로 짝을 이룸.
- **웹 서버 vs 데이터베이스**: 통신을 받아 처리하는 부품 vs 데이터를 보관하는 부품.

## 한 줄 정리

> 웹 서비스는 약속된 규칙(HTTP)으로 1요청 1응답을 주고받는 대화이며, 그 대화를 동기로 기다릴지 비동기로 흘려보낼지는 상황에 따라 고른다.
