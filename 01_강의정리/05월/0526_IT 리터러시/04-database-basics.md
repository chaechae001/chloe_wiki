# 데이터베이스의 모든 것 — 저장·검색·수정·삭제로 보는 데이터 창고

> 은행앱에서 결제 내역을 조회하고, 도서관에서 책을 검색하고, 쇼핑몰에서 품절을 확인하는 일. 전부 어딘가에 잘 정리된 "데이터 창고"가 있기에 가능합니다. 그 창고의 이름이 데이터베이스(DB)입니다.

`데이터베이스` · `테이블` · `Query` · `CRUD` · `논리삭제` · `DBMS` · `관계형` · `NoSQL` · `데이터타입`

## 핵심요약

- 데이터베이스는 **기록하고 조합하는 모든 데이터의 총합**, 즉 잘 분류해 저장해 둔 창고다.
- 기본 기능은 네 가지: **저장(Insert)·검색(Select/Find)·수정(Update)·삭제(Delete)** = CRUD.
- 데이터는 **테이블(행·열)** 형태로, 분류하기 좋게 정리되어 저장된다.
- 데이터베이스에 내리는 명령어를 **Query(쿼리)** 라고 한다.
- 삭제에는 진짜 지우는 방식과, 지운 것처럼 표시만 하는 **논리삭제**가 있다.
- DB를 운영·관리하는 소프트웨어가 **DBMS**, 종류는 크게 **관계형(RDB)** 과 **NoSQL**로 나뉜다.

## 개념별 정리

### 데이터베이스란?

**1. 정의**
기록하고 조합하는 모든 데이터를 모아 둔 총합입니다. 핵심은 그냥 쌓는 게 아니라 **분류하기 좋게 저장**한다는 점입니다.

**2. 왜 필요한가?**
서비스가 다루는 정보(회원·상품·주문 등)는 잘 정리되어 있어야 빠르게 찾고 바꿀 수 있습니다. "서비스를 어떻게 운영할 것인가"의 핵심 요소가 바로 데이터 구조입니다.

**3. 예시 — 일상 속 데이터베이스**

```text
은행 결제내역 조회
1단계: 은행앱 열기
2단계: 은행 서버에 내 계좌정보로 접속
3단계: 접속정보 확인 → 내 계좌정보 데이터베이스 검색
4단계: 원하는 결제내역 확인
```

통장의 입·출금 기록, 도서관의 도서 검색도 모두 데이터베이스 활용 사례입니다.

**4. 헷갈리기 쉬운 점**
데이터베이스는 "데이터를 많이 쌓아 둔 것"이 아니라 "**분류하기 좋게** 쌓아 둔 것"입니다. 정리 없이 쌓기만 하면 찾을 수 없습니다.

**5. 한 줄 정리**
데이터베이스는 잘 분류해 저장한 데이터 창고다.

> 비유: 도서관입니다. 책(데이터)을 그냥 쌓아두지 않고 분류 기호로 정리해 두기에 원하는 책을 금방 찾습니다.

### 기본 기능 — 저장·검색·수정·삭제 (CRUD)

**1. 정의**
데이터베이스의 네 가지 기본 동작입니다.

- **저장(Insert)**: 새 데이터를 넣음 (상품 정보, 사진·가격·상세설명 등)
- **검색(Select/Find)**: 특정 조건으로 데이터를 찾음
- **수정(Update)**: 저장된 데이터의 값을 바꿈
- **삭제(Delete)**: 데이터를 지움

**2. 왜 필요한가?**
서비스의 거의 모든 기능(상품 등록·조회·매진 처리·환불 등)이 이 네 동작의 조합으로 이루어지기 때문입니다.

**3. 예시 — 쇼핑몰 상품 테이블**

| 상품번호 | 상품종류 | 가격 |
| --- | --- | --- |
| 1 | 상의 | 50000 |
| 2 | 청바지 | 80000 |
| 3 | 신발 | 70000 |
| 4 | 벨트 | 10000 |

여기서 신상품을 넣으면 저장(Insert), "가격 낮은 순/추천상품"으로 찾으면 검색(Select), 품절 상태를 바꾸면 수정(Update), 더 이상 안 파는 상품을 빼면 삭제(Delete)입니다.

**4. 헷갈리기 쉬운 점**
검색은 단순히 "다 보여주기"가 아니라 **특정 조건으로 분류해 꺼내기**입니다. "신상품 입고", "핫딜", "가격 낮은순" 같은 키워드가 모두 검색 조건입니다.

**5. 한 줄 정리**
데이터베이스는 결국 넣고(저장)·찾고(검색)·고치고(수정)·빼는(삭제) 네 가지로 돌아간다.

### 테이블과 데이터 타입

**1. 정의**
데이터를 **행과 열**로 분류해 저장한 형태가 테이블입니다. 그리고 각 칸에 들어가는 값에는 정해진 **데이터 타입**이 있습니다.

**2. 왜 필요한가?**
"가격에는 숫자, 이름에는 문자, 매진 여부에는 참/거짓"처럼 타입을 정해 두어야 데이터가 일관되게 관리되고 계산·검색이 정확해집니다.

**3. 예시 — 컴퓨터의 데이터 타입**

| 구분 | 타입 | 설명 |
| --- | --- | --- |
| 숫자 | Int, Float, Double | 정수, 소수 형태 숫자 |
| 문자 | String | 문자열(이름, 주소 등) |
| 문자 | Boolean | 참/거짓 형태의 데이터 |
| 시간 | Time / Datetime | 날짜·시간 형태 |

회원정보 테이블이라면 이름(String), 아이디(String), 주소(String)처럼 칸마다 타입이 정해집니다.

**4. 헷갈리기 쉬운 점**
숫자처럼 보여도 타입은 문자일 수 있습니다(예: 전화번호 "010..."). 계산이 필요하면 숫자, 단순 표시면 문자로 두는 식으로 목적에 맞게 정합니다.

**5. 한 줄 정리**
테이블은 행·열로 정리한 표, 데이터 타입은 각 칸에 담길 값의 종류다.

> 비유: 엑셀 시트와 같습니다. 시트(테이블)의 각 열에 "여긴 숫자, 여긴 날짜"라고 형식을 정해두는 것과 같습니다.

### Query (쿼리)

**1. 정의**
데이터베이스에 내리는 **명령어**입니다. "이 조건으로 찾아줘", "이 값을 바꿔줘" 같은 요청을 쿼리로 전달합니다.

**2. 왜 필요한가?**
사람이 직접 창고를 뒤지는 게 아니라, 명령(쿼리) 한 줄로 원하는 데이터를 정확히 꺼내거나 바꾸기 위해서입니다.

**3. 예시 — 신상품 조회 흐름(의사 쿼리)**

```text
[신상품 테이블]  →  [조회]  →  [결과]
- 신상품만 저장    - 전체 목록 조회    - 조회 결과 반환

의사 쿼리(개념): "신상품 테이블에서 전체 목록을 가져와라"
정렬 예: "최신 등록순으로 20개만" / "8~10월 상품만"
```

**4. 헷갈리기 쉬운 점**
쿼리는 "잘 쓰는 것"으로 끝이 아니라, **성능을 고려해 쓰는 것**이 핵심입니다. 같은 결과라도 어떻게 쿼리하느냐에 따라 속도가 크게 달라질 수 있습니다.

**5. 한 줄 정리**
쿼리는 데이터베이스에게 건네는 정확한 주문서다.

> 비유: 도서관 사서에게 "1990년대 출간, 제목에 '바다' 들어간 책 찾아주세요"라고 적어 건네는 신청서와 같습니다.

### 정렬과 논리삭제

**1. 정의**
- **정렬**: 특정 값을 기준으로 데이터 순서를 맞추는 것(예: 최신순, 가격순).
- **논리삭제**: 데이터를 실제로 지우지 않고, "삭제됨"으로 표시만 해 두는 방식.

**2. 왜 필요한가?**
정렬은 사용자가 원하는 순서로 보여주기 위해, 논리삭제는 기록을 남겨야 하거나 복구 가능성을 위해 필요합니다. 예를 들어 "매진"은 상품을 지우는 게 아니라 상태를 표시하는 쪽이 안전합니다.

**3. 예시 — 매진 처리(논리삭제)**

| 상품번호 | 상품종류 | 가격 | 매진 |
| --- | --- | --- | --- |
| 1 | 상의 | 50000 | False |
| 2 | 청바지 | 80000 | False |
| 3 | 신발 | 70000 | **True** |
| 4 | 벨트 | 10000 | False |

신발이 매진되어도 행을 지우지 않고 `매진 = True`로 표시만 합니다. 데이터(상품 정보)는 남기고, 노출만 제어하는 것입니다.

**4. 헷갈리기 쉬운 점**
**물리삭제 vs 논리삭제**: 물리삭제는 데이터를 실제로 제거, 논리삭제는 표시만 바꿈. 매진·탈퇴 같은 경우 기록 보존을 위해 논리삭제를 자주 씁니다.

**5. 한 줄 정리**
정렬은 보여줄 순서를 정하고, 논리삭제는 "지운 척" 표시로 데이터를 보존한다.

### DBMS와 데이터베이스의 종류 (RDB vs NoSQL)

**1. 정의**
- **DBMS(Database Management System)**: 데이터베이스 운영·관리를 위한 소프트웨어.
- **관계형(RDB)**: 표(테이블)들을 고유값으로 연결해 관리하는 방식.
- **NoSQL**: 기록이 단순하고 대용량 처리에 유리한 비정형 방식.

**2. 왜 필요한가?**
데이터의 성격에 따라 알맞은 DB를 골라야 하기 때문입니다. 연결이 중요한 데이터는 관계형, 단순·대용량은 NoSQL이 유리할 수 있습니다.

**3. 예시 — DBMS 종류와 관계형 vs NoSQL**

| DBMS 예시 | 분류 |
| --- | --- |
| MySQL · MariaDB · PostgreSQL · Oracle | 관계형(RDB) |
| MongoDB · Elasticsearch | NoSQL |
| ChromaDB 등 | Vector DB(LLM/RAG용, 성장 단계) |

관계형은 **Primary Key(고유값)** 를 활용해 테이블을 연결합니다. 예를 들어 "B신발을 구매한 A고객"을 표현할 때, 신발 데이터와 고객 데이터를 키로 연결합니다. NoSQL은 기록이 단순해 대용량 처리에 강점이 있습니다.

**4. 헷갈리기 쉬운 점**
"DB = SQL"은 아닙니다. 관계형 외에 NoSQL, 그리고 LLM·검색에 쓰이는 Vector DB도 있습니다. 정답이 하나가 아니라 **상황에 맞는 선택**입니다. 참고로 여러 DB의 현황·순위는 DB-Engines 같은 사이트에서 비교해 볼 수 있습니다.

**5. 한 줄 정리**
DBMS는 데이터베이스를 운영하는 관리 프로그램이고, RDB·NoSQL 등은 데이터 성격에 따라 고르는 종류다.

> 비유: 창고를 운영하는 관리 시스템(DBMS) 위에, 물건 성격에 맞는 정리 방식(관계형=라벨로 연결, NoSQL=대량 적재)을 고르는 셈입니다.

## 코드로 보기 — DB가 우리 화면까지 오는 과정

개념 중심 글이라, 데이터가 화면까지 도달하는 동선을 흐름도로 정리합니다.

```text
[웹 브라우저/스마트폰]
        │  ① 서버 조회 요청
        ▼
[웹 서버]
        │  ② DB query 조회
        ▼
[데이터베이스]  ── ③ 조회 결과 ──▶ [웹 서버]
                                        │  ④ 조회 결과를 전달
                                        ▼
                              [웹 브라우저/스마트폰]에 표시
```

서버 오류의 종류도 함께 알아두면 좋습니다.

```text
- 트래픽 과부하 : 동시 접속(통신량)이 너무 많아 서버가 감당 못 함
- 백엔드 코드 버그
- DB 접속 오류  : 서버엔 접속되지만 DB와의 연결이 안 되는 경우
```

**무엇을 하기 위한 흐름인가**
"검색 한 번"이 서버와 DB를 거쳐 다시 내 화면으로 돌아오는 전체 경로를 보기 위한 것입니다.

**해석**
같은 "안 보임"이라도 원인은 다릅니다. 트래픽 때문일 수도, DB 연결 문제(서버는 살아있지만 DB와 단절)일 수도 있습니다. 구조를 알면 어디가 막혔는지 짐작할 수 있습니다.

**실무 연결**
- 백엔드에서 중요한 건 기능 구현보다 **속도·지연·과부하 대응**입니다. 그래서 쿼리 성능·인덱싱·알고리즘(B-Tree, Hash 등)을 고려한 설계가 강조됩니다.
- 프로젝트 완성 후엔 동시 접속자 수 기준 성능 테스트로 "몇 명까지 안정적인지"를 말할 수 있어야 합니다.

## 헷갈리기 쉬운 포인트

- **저장(Insert) vs 수정(Update)**: 새로 넣기 vs 기존 값 바꾸기.
- **물리삭제 vs 논리삭제**: 실제로 지우기 vs "삭제됨" 표시만 하기.
- **관계형(RDB) vs NoSQL**: 키로 연결·정형 vs 단순·대용량 비정형.
- **DBMS vs 데이터베이스**: 운영·관리하는 소프트웨어 vs 실제 데이터가 담긴 저장소.

- (이해확인) 매진 처리를 논리삭제로 하는 이유는?
  → 상품 정보를 지우지 않고 상태(매진 = True)만 바꿔, 데이터를 보존하면서 노출만 제어하기 위해.
- (응용) 같은 "조회가 안 됨"이라도 트래픽 과부하와 DB 접속 오류는 어떻게 다른가?
  → 트래픽 과부하는 동시 접속이 너무 많아 서버가 감당 못 하는 것, DB 접속 오류는 서버엔 접속되지만 DB와의 연결이 끊긴 것.

## 한 줄 정리

> 데이터베이스는 분류해 저장한 데이터 창고이며, 저장·검색·수정·삭제(CRUD)와 쿼리로 다루고, 데이터 성격에 따라 관계형·NoSQL 등 알맞은 종류를 고른다.
