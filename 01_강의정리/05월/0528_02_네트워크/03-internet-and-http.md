# 인터넷과 HTTP — 웹 브라우저와 서버는 어떤 규칙으로 대화할까?

> 주소창에 `https://...`를 치고 엔터를 누르면, 내 브라우저와 저 멀리 서버는 정해진 절차로 묻고 답합니다. 그 약속이 HTTP이고, 답장 앞에 붙는 숫자(200·404·500)가 상태코드입니다.

`프로토콜` `TCP/IP` `캡슐화` `HTTP` `상태코드` `CRUD` `CORS`

## 핵심요약
- **프로토콜**은 통신에 필요한 형식·약속·규칙을 정의한 것이다.
- 데이터를 보낼 때 각 계층이 정보를 덧붙이는 것이 **캡슐화**, 받을 때 벗기는 것이 **역캡슐화**다.
- **HTTP**는 웹에서 데이터를 주고받는 규칙으로, **무상태(stateless)** · **클라이언트–서버** 모델을 따른다.
- HTTP **메서드**(GET·POST·PUT·DELETE)는 데이터 처리 기본 동작인 **CRUD**(생성·조회·수정·삭제)와 짝을 이룬다.
- **상태코드**는 응답 앞머리 숫자로, 백단위로 의미가 갈린다: 2xx 성공 / 3xx 리다이렉션 / 4xx 클라이언트 오류 / 5xx 서버 오류.
- **CORS**는 서로 다른 출처(Origin) 간 요청을 허용하는 정책이고, 기본 정책인 **SOP**는 같은 출처만 허용한다.

---

## 통신의 약속 — 프로토콜

### 프로토콜(Protocol)
**1. 정의**
프로토콜은 **통신에 필요한 형식·약속·규칙을 정의한 것**입니다. 신호 처리법, 오류 처리, 암호, 인증, 주소 등을 포함합니다.

**2. 왜 필요한가?**
서로 다른 제조사의 기기들이 대화하려면 "이런 형식으로 보내고, 이런 순서로 답하자"는 공통 규칙이 있어야 합니다. 그래서 원활한 통신을 위해서는 프로토콜을 **통일**하는 것이 좋습니다.

**3. 예시 — 프로토콜이 규정하는 3요소**

| 요소 | 규정하는 것 |
| --- | --- |
| 구문(Syntax) | 데이터의 형식·부호화·신호 레벨 |
| 의미(Semantics) | 효율적·정확한 전송을 위한 제어 정보 |
| 시간(Timing) | 통신 속도·순서 제어 |

**4. 헷갈리기 쉬운 점**
프로토콜은 특정 프로그램이 아니라 **"약속" 그 자체**입니다. 복잡한 네트워크 시스템을 여러 프로토콜의 조합으로 단순화한 것을 **네트워크 아키텍처**라고 부릅니다(복잡한 건축물을 뼈대로 단순화하듯).

**5. 한 줄 정리**
프로토콜은 "어떻게 주고받을지"를 미리 정한 통신 규칙이다.

> 비유: 같은 언어와 예절을 정해 두는 것 — 그래야 처음 보는 사람과도 대화가 됩니다.

---

### 캡슐화(Capsulation)와 역캡슐화(Decapsulation)
**1. 정의**
데이터가 계층을 내려가며 각 계층의 제어 정보(헤더)를 **덧붙이는 것이 캡슐화**, 받는 쪽에서 계층을 올라가며 그 정보를 **벗겨 내는 것이 역캡슐화**입니다.

**2. 왜 필요한가?**
각 계층이 자기 일에 필요한 정보(예: 전송 계층은 포트, 네트워크 계층은 IP)를 챙겨 넣어야, 데이터가 정확히·순서대로 도착하고 오류를 검사할 수 있습니다.

**3. 예시**
```text
[보낼 때 — 캡슐화: 정보를 덧붙임]
유저 데이터
유저 데이터 + 응용 헤더
유저 데이터 + 응용 헤더 + TCP 헤더
유저 데이터 + 응용 헤더 + TCP 헤더 + IP 헤더  → 전송

[받을 때 — 역캡슐화: 거꾸로 벗김]
... → IP 헤더 제거 → TCP 헤더 제거 → 응용 헤더 제거 → 유저 데이터
```

**4. 헷갈리기 쉬운 점**
"데이터에 뭔가를 자꾸 붙이면 손해 아닌가?" 싶지만, 이 헤더들이 있어야 길 찾기·오류 검출·순서 맞추기가 가능합니다. 받는 쪽에서 정확히 같은 순서로 벗겨 내기 때문에 원본 데이터는 그대로 복원됩니다.

**5. 한 줄 정리**
보낼 때 겹겹이 포장(캡슐화), 받을 때 겹겹이 개봉(역캡슐화).

> 비유: 택배를 여러 겹 포장해 보내고(캡슐화), 받는 사람이 겉 상자부터 차례로 뜯는 것(역캡슐화)과 같습니다.

## 신뢰의 한 쌍 — TCP와 IP (TCP/IP)

오늘날 인터넷의 토대가 되는 통신 규약 묶음이 **TCP/IP**입니다. 디바이스를 연결하는 프로토콜의 집합이며, 데이터 패킷을 올바른 위치로 전송해 다른 컴퓨터와 통신하게 합니다.

- **TCP(Transmission Control Protocol)**: 데이터 전송을 위한 **연결지향** 프로토콜. ① **신뢰성**(적극적 수신·재전송), ② **흐름 제어**(보내는 양 조절), ③ **다중화**(여러 연결 동시 유지)를 제공합니다.
- **IP(Internet Protocol)**: 인터넷/로컬 네트워크를 통해 전송되는 **데이터 형식을 관리하는 규칙 집합**입니다.

> TCP의 신뢰성과 연결 방식, UDP와의 비교, 그리고 IP의 특징은 [주요 프로토콜](04-core-protocols.md) 글에서 더 자세히 다룹니다.

여기에 더해, 회사 안에서만 쓰는 **인트라넷**(내부 직원만 접근하는 사설망, 주목적은 보안), 협력사·고객까지 일부 열어 주는 **엑스트라넷**도 같은 인터넷 기술 위에서 접근 범위만 달리한 개념입니다.

## 웹의 대화 규칙 — HTTP

### HTTP(Hyper Text Transfer Protocol)
**1. 정의**
HTTP는 **인터넷에서 데이터를 주고받을 수 있는 프로토콜**입니다. 전통적인 **클라이언트–서버 모델**을 따르며, 서버가 이전 상태를 기억하지 않는 **무상태(stateless)** 프로토콜입니다.

**2. 왜 필요한가?**
웹 브라우저(클라이언트)가 "이 페이지 주세요"라고 요청하고 서버가 응답하는, 웹의 가장 기본적인 대화가 모두 HTTP로 이루어집니다.

**3. 예시 — HTTP 요청 메시지 구조**
```http
GET /index.html HTTP/1.1      ← Start Line (요청라인)
Host: www.example.com         ← Header (생략 가능)
Accept: text/html
                              ← Empty Line (공백라인)
(여기에 Message Body)          ← 본문 (있을 수도, 없을 수도)
```
HTTP 구조는 **Start Line → Header → Empty Line → Message Body** 순서입니다. 헤더는 요청·응답에 대한 부가 정보를 담으며 `이름: 값` 쌍으로 적습니다.

**4. 헷갈리기 쉬운 점**
**무상태(stateless)** 가 핵심입니다. HTTP 자체는 "당신이 방금 로그인했는지" 같은 상태를 기억하지 않습니다. 그래서 로그인 유지를 위해 **쿠키·세션·토큰** 같은 보조 장치가 따로 필요합니다(→ [⑤ 웹 보안과 인증](05-web-security-and-auth.md)).

**5. 한 줄 정리**
HTTP는 웹에서 요청–응답으로 데이터를 주고받는, 상태를 기억하지 않는 규칙이다.

> 비유: 매번 처음 보는 직원에게 주문하는 패스트푸드 카운터 — 직원은 당신을 기억하지 못하므로(무상태), 멤버십 카드(쿠키)를 따로 내밀어야 합니다.

---

### HTTP 메서드와 CRUD
**1. 정의**
메서드는 "서버에 무엇을 해 달라"는 동작 지정입니다. 이는 대부분의 소프트웨어가 가진 기본 데이터 처리 기능 **CRUD**와 짝을 이룹니다.

**2. 왜 필요한가?**
같은 주소라도 "읽을지, 새로 만들지, 고칠지, 지울지"를 구분해야 서버가 알맞게 처리합니다.

**3. 예시 — 메서드 ↔ CRUD 대응**

| 메서드 | 역할 | CRUD |
| --- | --- | --- |
| GET | 자료를 **조회**할 때 | Read |
| POST | 자료를 **등록**할 때 | Create |
| PUT | 자료의 **수정**을 요청할 때 | Update |
| DELETE | 자료의 **삭제**를 요청할 때 | Delete |

**4. 헷갈리기 쉬운 점**
GET과 POST를 혼동하기 쉽습니다. GET은 "주세요(조회)", POST는 "이거 받아 주세요(등록)"입니다. 로그인 폼처럼 데이터를 서버로 보내는 동작은 GET이 아니라 POST가 어울립니다.

**5. 한 줄 정리**
GET·POST·PUT·DELETE는 곧 Read·Create·Update·Delete다.

## 응답의 첫인사 — 상태코드(Status Code)

상태코드는 **클라이언트의 요청에 대한 서버의 응답 상태**를 숫자로 알려 줍니다. 예를 들어 어떤 페이지에 접속(GET)이 잘 되면 `200`이 옵니다. **백(100)단위로 큰 의미가 갈린다**는 점만 잡으면 외우기 쉽습니다.

| 분류 | 의미 | 한 줄 요약 | 대표 코드 |
| --- | --- | --- | --- |
| **1xx** | 정보(Information) | 요청을 받았고 처리를 계속함 | 100 Continue, 101 Switching Protocol |
| **2xx** | 성공(Successful) | 요청을 성공적으로 받고 처리함 | 200 OK, 201 Created, 204 No Content |
| **3xx** | 리다이렉션(Redirection) | 요청 완료를 위해 추가 조치가 필요 | 301 Moved Permanently, 302 Found, 304 Not Modified |
| **4xx** | 클라이언트 오류(Client Error) | 요청 문법이 잘못됐거나 처리할 수 없음 | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests |
| **5xx** | 서버 오류(Server Error) | 유효한 요청인데 서버가 충족 실패 | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

실무 감각으로는 이렇게 기억하면 충분합니다.

- **200대** = 성공.
- **400대** = "당신(클라이언트) 쪽 요청에 문제" — 권한 없음(403), 경로 잘못(404) 등.
- **500대** = "서버 쪽 문제" — 점검 중이거나 장애.

> 자주 보는 404("페이지를 찾을 수 없음")는 4xx라서 **요청한 경로의 문제**, 503("서비스 점검 중")은 5xx라서 **서버의 문제**임을 코드만 보고도 구분할 수 있습니다.

## 출처의 경계 — CORS와 SOP

### SOP(Same-Origin Policy)와 CORS(Cross-Origin Resource Sharing)
**1. 정의**
- **SOP**: 자신과 **동일한 출처(Origin)** 에서만 데이터를 요청·응답하도록 하는 기본 보안 정책.
- **CORS**: 서로 **다른 출처 간**에도 요청과 응답을 허용하도록 열어 주는 정책.

**2. 왜 필요한가?**
악성 사이트가 내가 로그인한 다른 사이트의 데이터를 함부로 가져가지 못하도록, 브라우저는 기본적으로 같은 출처만 허용(SOP)합니다. 하지만 현대 웹은 여러 도메인의 API·폰트·이미지를 끌어와야 하므로, 안전하게 예외를 허용하는 규칙(CORS)이 필요합니다.

**3. 예시 — "출처(Origin)"의 구성**
```text
https://www.example.com:182/category/blog/index.html
  └─프로토콜─┘ └─호스트(도메인)─┘ └포트┘ └── 경로 ──┘

출처(Origin) = 프로토콜(Scheme) + 호스트(Host) + 포트(Port)
```
**이 세 가지(프로토콜·호스트·포트)가 모두 같아야 "같은 출처"** 입니다.

**4. 헷갈리기 쉬운 점 — Same Origin vs Same Site**
- **Same Origin(같은 출처)**: 프로토콜·호스트·포트가 **모두** 일치해야 함. `http`와 `https`만 달라도, 포트만 달라도, 서브도메인만 달라도 → 다른 출처.
- **Same Site(같은 사이트)**: **도메인만 같으면** 같은 사이트로 봄(서브도메인·포트·일부 차이는 무관).

| 기준 URL: `https://www.example.com:448` | Same Origin? | Same Site? |
| --- | --- | --- |
| `https://login.example.com:448` (서브도메인만 다름) | ✗ cross-origin | ✓ same-site |
| `http://www.example.com:448` (프로토콜만 다름) | ✗ cross-origin | ✗ cross-site |
| `https://www.example.com:70` (포트만 다름) | ✗ cross-origin | ✓ same-site |
| `https://www.example.com:448` (완전 일치) | ✓ same-origin | ✓ same-site |

CORS 요청에는 안전한 **Simple Request**(GET/POST/HEAD + 허용된 Content-Type)와, 먼저 `OPTIONS`로 "보내도 안전한지" 미리 확인하는 **Preflight Request**가 있습니다. Preflight는 cross-origin 요청이 유저 데이터에 영향을 줄 수 있으므로 본 요청 전에 미리 확인하는 절차입니다.

**5. 한 줄 정리**
SOP는 "같은 출처만", CORS는 "다른 출처도 안전하게 허용".

> 비유: 기본적으로 우리 집 사람만 들이는 게 SOP, 신원 확인을 거쳐 손님도 들이는 게 CORS입니다.

## 코드로 보기 — HTTP 요청과 응답 한 쌍

```http
# ── 요청(Request): 브라우저 → 서버 ──
GET /products/42 HTTP/1.1
Host: shop.example.com
Accept: application/json

# ── 응답(Response): 서버 → 브라우저 ──
HTTP/1.1 200 OK
Content-Type: application/json

{ "id": 42, "name": "키보드", "price": 39000 }
```

**코드목적**
"42번 상품 정보를 조회(GET·Read)"하는 가장 단순한 웹 통신 한 사이클을 보여 줍니다.

**해석**
요청의 첫 줄(Start Line)이 메서드와 경로를, 응답의 첫 줄이 **상태코드(200 OK)** 를 알려 줍니다. 만약 42번 상품이 없다면 응답은 `404 Not Found`, 서버가 점검 중이면 `503`이 됩니다. 코드만 보고도 "요청 문제냐, 서버 문제냐"를 가릴 수 있습니다.

**실무 연결**
API를 호출하거나 웹 서비스를 디버깅할 때, 개발자 도구의 Network 탭에서 보게 되는 모습이 바로 이것입니다. 메서드·상태코드·헤더 세 가지만 읽을 줄 알아도 대부분의 문제 원인을 빠르게 좁힐 수 있습니다.

## 직접 해보기
1. 평소 자주 쓰는 사이트에서 브라우저 개발자 도구(F12) → Network 탭을 열고, 요청 하나의 **메서드와 상태코드**를 확인해 보기.
2. `200`, `301`, `404`, `503`을 보고 각각 "성공/리다이렉션/클라이언트 오류/서버 오류" 중 무엇인지 즉답해 보기.
3. `https://www.example.com`과 `https://api.example.com`이 Same Origin인지 Same Site인지 판별하고 이유 적기.

## 헷갈리기 쉬운 포인트
- **GET vs POST**: 조회(Read) vs 등록(Create). 데이터를 서버로 보내는 동작은 보통 POST.
- **4xx vs 5xx**: 클라이언트(요청) 문제 vs 서버 문제.
- **Same Origin vs Same Site**: 프로토콜·호스트·포트 전부 일치 vs 도메인만 일치.
- **SOP vs CORS**: 기본 차단 정책 vs 안전하게 열어 주는 정책.
- **캡슐화 vs 역캡슐화**: 보낼 때 헤더 추가 vs 받을 때 헤더 제거.

**복습 질문 및 답변**

- (기본) HTTP가 "무상태(stateless)"라는 것은 무슨 뜻인가요?
  - 서버가 이전 요청의 상태(로그인 여부 등)를 기억하지 않는다는 뜻입니다. 그래서 쿠키·세션·토큰이 필요합니다.
- (이해확인) 404와 500의 차이를 한 문장으로 설명하면?
  - 404는 클라이언트가 요청한 경로의 문제(4xx), 500은 서버 내부의 문제(5xx)입니다.
- (응용) 프론트엔드에서 다른 도메인의 API를 호출했더니 브라우저가 막았습니다. 어떤 정책 때문이며, 무엇으로 해결할까요?
  - 기본 정책인 SOP 때문입니다. 서버에서 CORS를 허용하도록 설정하면 다른 출처 간 요청을 주고받을 수 있습니다.

## 한 줄 정리
> HTTP는 웹 브라우저와 서버가 요청–응답으로 대화하는 무상태 규칙이며, 메서드(=CRUD)·상태코드(2xx~5xx)·출처 정책(SOP/CORS)만 읽을 줄 알아도 웹 통신의 80%가 보인다.
