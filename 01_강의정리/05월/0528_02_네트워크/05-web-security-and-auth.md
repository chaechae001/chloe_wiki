# 웹 보안과 인증 — 서버는 어떻게 "당신"을 기억하고 지킬까?

> HTTP는 방금 로그인한 사람도 기억하지 못합니다(무상태). 그런데 우리는 한 번 로그인하면 페이지를 옮겨도 로그인 상태가 유지됩니다. 이 마법의 정체가 쿠키·세션·토큰이고, 비밀번호를 안전하게 지키는 장치가 해시와 암호화입니다.

`인증` `인가` `해시` `쿠키` `세션` `토큰` `JWT` `캐시`

## 핵심요약
- **인증(Authentication)** 은 "누구인지" 확인, **인가(Authorization)** 는 "무엇을 할 수 있는지" 확인이다.
- **해시**는 임의 길이 데이터를 고정 길이의 값으로 바꾸는 **단방향**(되돌릴 수 없는) 변환이다 — 비밀번호 저장의 핵심.
- 무상태 HTTP에서 로그인을 유지하려고 **쿠키(클라이언트 저장)** 와 **세션(서버 저장)** 을 쓴다.
- **토큰**과 **JWT**는 서버가 상태를 저장하지 않고도 사용자를 식별하게 해 준다.
- **캐시**는 자주 쓰는 데이터를 가까운 곳에 미리 둬서 속도·비용을 아끼는 기법이고, 이를 전 세계로 펼친 것이 **CDN**이다.

---

## 누구인가, 무엇을 할 수 있는가 — 인증과 인가

### 인증(Authentication)과 인가(Authorization)
**1. 정의**
- **인증**: **사용자의 신원을 검증**하는 과정("당신이 정말 그 사람인가?").
- **인가**: 인증된 사용자가 **어떤 자원에 접근할 수 있는지**를 확인하는 과정("그 일을 할 권한이 있는가?").

**2. 왜 필요한가?**
승인되지 않은 접근·오용·변조로부터 시스템을 지키려면, 먼저 "누구인지" 확인하고(인증) 그다음 "무엇까지 허용할지"를 정해야(인가) 합니다.

**3. 예시 — 대표적인 인증 방식**

| 인증 방식 | 내용 |
| --- | --- |
| 비밀번호 | 가장 많이 쓰이는 인증 요소 |
| 일회용 핀(OTP) | 단일 세션·거래에 한해 접근 허용 |
| 인증 앱 | 외부 기관을 통해 보안 코드 생성(예: 휴대폰 인증서) |
| 생체 인식 | 지문·얼굴 등(예: Face ID, 지문 인식) |

**4. 헷갈리기 쉬운 점 — 인증 vs 인가**

| 구분 | 인증(Authentication) | 인가(Authorization) |
| --- | --- | --- |
| 기능 | 자격(신원) 증명 확인 | 권한 허가/거부 |
| 사용자가 볼 수 있나? | O | X |
| 사용자가 바꿀 수 있나? | 부분적으로 가능 | 불가능 |
| 데이터 전송 | ID 토큰 | 액세스 토큰 |

순서가 핵심입니다. **인증이 먼저(누구인지), 인가가 나중(무엇을 할지).** 로그인은 됐는데(인증 OK) 관리자 페이지는 막히는 경우(인가 X)가 그 예입니다.

**5. 한 줄 정리**
인증은 "신원 확인", 인가는 "권한 확인"이다.

> 비유: 회사 출입증으로 건물에 들어가는 것이 인증, 그 출입증으로 들어갈 수 있는 층이 정해진 것이 인가입니다.

암호 기법도 함께 봐 둡니다. 정보를 의도하지 않은 사람이 알아볼 수 없는 형태로 바꾸는 것을 **암호화**, 되돌리는 것을 **복호화**라 합니다. 암호 기법에는 되돌릴 수 없는 **단방향(해시)** 과, 되돌릴 수 있는 **양방향**(대칭키·공개키 방식)이 있습니다.

## 비밀번호를 지키는 법 — 해시(Hash)

### 해시함수와 해시값
**1. 정의**
**해시**는 단방향 암호화 기법으로, 임의 길이의 데이터를 **고정된 길이의 암호화된 문자열로 바꿔 버리는 것**입니다. 이때 쓰는 함수가 **해시함수**, 결과값이 **해시값**입니다.

**2. 왜 필요한가?**
사이버 범죄·해킹으로 정보 유출이 늘면서, 민감한 정보를 그대로 저장하면 위험합니다. 비밀번호를 **해시값으로 저장**하면, 설령 유출돼도 원래 비밀번호를 알아내기 어렵습니다.

**3. 예시 — 해시의 흐름**
```text
입력값(긴 데이터)  ──[ 해시함수 ]──▶  해시값(짧고 고정 길이)

"mypassword123"   ──[ SHA-256 ]──▶  "ef797c8118f02d..."(256비트 고정)
"mypassword124"   ──[ SHA-256 ]──▶  "9f1c8a47b0e3...."(전혀 다른 값!)
```

**4. 헷갈리기 쉬운 점 — 단방향성**
해시는 **되돌릴 수 없습니다(역산 불가).** 입력 → 해시값은 쉽지만, 해시값 → 입력은 사실상 불가능합니다. 그래서 서버는 비밀번호 원문을 모른 채, 로그인 시 입력값을 똑같이 해시해서 저장된 해시값과 **비교만** 합니다.

**5. 한 줄 정리**
해시는 "되돌릴 수 없게 고정 길이로 바꾸기" — 비밀번호 저장의 표준이다.

> 비유: 과일을 갈아 주스로 만드는 것과 같습니다. 주스(해시값)에서 원래 과일(원문)을 복원할 수는 없지만, 같은 과일을 갈면 늘 같은 주스가 나옵니다.

해시함수의 두 갈래도 알아 둡니다.
- **암호화 해시함수**: 해시값으로 입력값을 알아내기 어렵다는 점(단방향성)을 이용 — 예: MD5, SHA.
- **비암호화 해시함수**: 같은 해시값을 갖는 다른 입력이 없다는 성질로 **무결성 검증**용 — 예: CRC, Checksum.

암호화 해시함수의 핵심 특징은 **단방향성**, **충돌 저항성**(같은 해시값을 내는 두 입력을 찾기 어려움), **역상 저항성**(해시값으로 입력을 찾기 어려움)입니다. 또한 작은 입력 변화가 결과를 완전히 바꾸는 **눈사태 효과**, 거대한 데이터의 무결성을 작은 값으로 보장하는 **압축 효과**가 있습니다.

> 대표 알고리즘: MD5(128비트), SHA-1(160비트), SHA-2/SHA-3 계열 등.

## 무상태 HTTP에서 로그인을 유지하기 — 쿠키와 세션

### 쿠키(Cookie)
**1. 정의**
쿠키는 **서버가 사용자 브라우저로 전송하는 작은 데이터**입니다. HTTP는 상태를 기억하지 않으므로(stateless), 쿠키로 "이전에 본 사람"이라는 정보를 클라이언트에 남깁니다.

**2. 왜 필요한가?**
매번 처음 보는 사람처럼 대하면 로그인 유지·맞춤 추천이 불가능합니다. 쿠키가 그 "기억"을 대신해 줍니다(유튜브 추천 영상도 쿠키를 활용).

**3. 예시 — 쿠키의 작동원리**
```text
1. 브라우저 ── HTTP 요청 ───────────▶ 서버
2. 브라우저 ◀─ 쿠키를 헤더에 담아 응답 ─ 서버   (Set-Cookie)
3. 브라우저 ── 쿠키 포함해 재요청 ─────▶ 서버   (다음부터 자동 첨부)
4. 브라우저 ◀─ 응답(쿠키 업데이트 시) ── 서버
```

**4. 헷갈리기 쉬운 점 — 특징과 한계**
쿠키는 **클라이언트에 저장**되고, 한 개당 약 **4KB**, 도메인당·전체 개수 제한이 있습니다(브라우저 종료 시 기본 삭제되는 것은 세션 쿠키). 클라이언트에 저장되는 만큼 **민감 정보를 그대로 담으면 보안 위험**이 있고, 용량 제한도 있습니다.

**5. 한 줄 정리**
쿠키는 "클라이언트에 저장하는 작은 기억"이다.

> 종류: 브라우저가 열려 있는 동안만 유효한 **세션 쿠키**, 만료일까지 디스크에 저장되는 **영구 쿠키**가 있습니다.

### 세션(Session)
**1. 정의**
세션은 **웹 사이트의 여러 페이지에 걸쳐 사용되는 사용자 정보를 (서버에) 저장하는 방법**입니다. 즉 **서버에 저장되는 쿠키(= 세션 쿠키)** 개념입니다.

**2. 왜 필요한가?**
민감한 정보를 클라이언트(쿠키)에 두는 게 불안하니, 서버에 두고 클라이언트에는 **고유 Session ID** 만 주는 방식이 더 안전합니다.

**3. 예시 — 세션 작동원리**
```text
1. 요청           브라우저 ───────▶ 서버
2. 세션 ID 생성                     서버
3. 응답(세션 쿠키 포함) 브라우저 ◀── 서버
4. 세션 쿠키 저장  브라우저
5. 재요청(세션 쿠키 포함) 브라우저 ─▶ 서버
6. 클라이언트 인증                  서버
7. 응답           브라우저 ◀────── 서버
```

**4. 헷갈리기 쉬운 점 — 쿠키 vs 세션**

| 구분 | 쿠키 | 세션 |
| --- | --- | --- |
| 저장 위치 | 클라이언트 | 웹 서버 |
| 리소스 | 클라이언트 자원 | 서버 자원 |
| 속도 | 세션보다 빠름 | 쿠키보다 느림 |
| 보안 | 세션보다 약함 | 쿠키보다 안전 |
| 용량 | 제한 있음(개당 4KB 등) | 서버가 허용하는 한 제한 없음 |

세션은 더 안전하지만, **서버 자원을 쓰므로** 사용자가 많아지면 속도 저하·**오버헤드**(부가적 처리 부담)가 생길 수 있습니다.

**5. 한 줄 정리**
쿠키는 클라이언트에, 세션은 서버에 — 빠름 vs 안전의 선택이다.

## 서버 부담을 더는 식별 방법 — 토큰과 JWT

### 토큰(Token)과 JWT(JSON Web Token)
**1. 정의**
- **토큰**: 서버가 각 클라이언트를 정확히 구별할 수 있도록, 유니크한 정보를 담은 **암호화 데이터**.
- **JWT**: 클라이언트와 서버 사이에서 **권한을 위해 사용하는 토큰**으로, JSON 데이터를 Base64 URL-safe로 인코딩해 직렬화한 것.

**2. 왜 필요한가?**
세션은 서버가 모든 로그인 상태를 기억해야 해서 부담이 큽니다. 토큰/JWT는 **서버가 상태를 저장하지 않고도**(토큰 안에 정보가 들어 있어) 사용자를 식별할 수 있어, 서버를 늘리기(확장) 쉽습니다.

**3. 예시 — JWT의 구조**
```text
JWT = Header . Payload . Signature

aaaaaa.bbbbbb.cccccc
  │       │       └ Signature: 개인키로 서명 → 전송 중 변조 안 됐는지 확인
  │       └ Payload: 토큰 발급자·유효기간·사용자 권한 등 데이터
  └ Header: 토큰 유형 + 서명 알고리즘

# Header 예시
{ "alg": "HS256", "typ": "JWT" }
# Payload 예시
{ "sub": "1234567890", "name": "John Doe", "iat": 1516239022 }
```

**4. 헷갈리기 쉬운 점 — 장점과 위험**
JWT는 용량이 작아 빠르게 전달되고, 서버가 토큰을 따로 저장·확인할 필요가 없습니다. 다만 **단일 키가 유출되면 시스템 전체가 위험**해지고, 한 번 발급된 토큰은 만료 전까지 강제로 무효화하기 어렵습니다. 이를 보완하려고 **Refresh Token**을 함께 씁니다.

**5. 한 줄 정리**
토큰/JWT는 "서버가 기억하지 않아도 되는 신분증"이다.

> **Refresh Token 보완책**: 짧은 만료의 **Access Token**(예: 몇 분)과 긴 만료의 **Refresh Token**(예: 1~2주)을 함께 발급해, Access Token이 만료되면 Refresh Token으로 새 Access Token을 받습니다. 짧은 수명으로 탈취 위험을 줄이면서 사용자는 자주 로그인하지 않아도 됩니다.

> 비유: 출입증(Access Token)은 자주 갱신해야 하지만, 그 갱신을 자동으로 해 주는 정기권(Refresh Token)이 있는 셈입니다.

## 빠르게, 가깝게 — 캐시(Cache)와 CDN

### 캐시(Cache)와 캐싱(Caching)
**1. 정의**
캐시는 **자주 필요한 데이터·값의 복사본을 임시로 저장해 두는 곳**이고, 그렇게 저장해 두고 꺼내 쓰는 기법이 **캐싱**입니다. 오래 걸리는 작업의 결과를 저장해 시간·비용을 아낍니다.

**2. 왜 필요한가?**
매번 원본(느린 디스크·먼 서버·무거운 계산)에서 가져오면 느립니다. 결과를 가까운 빠른 곳(주로 RAM)에 두면 응답이 훨씬 빨라집니다.

**3. 예시 — 캐싱 작동 방식**
```text
클라이언트 ─── 요청 ───▶ [캐시 확인]
                          ├─ 있으면(Hit):  캐시에서 즉시 반환 (빠름)
                          └─ 없으면(Miss): 원본에서 가져와 캐시에 저장 후 반환
```

**4. 헷갈리기 쉬운 점 — 캐시 vs 쿠키**

| 구분 | 캐시 | 쿠키 |
| --- | --- | --- |
| 정의 | 웹 페이지 요소를 저장하는 임시 저장소 | 정보를 저장하기 위해 서버가 보내는 작은 파일 |
| 목적 | 페이지를 빠르게 렌더링하도록 도움 | 사용자 인증을 도움 |
| 삭제 | 보통 사용자가 직접 수동 삭제 | 만료 기간이 있어 시간 지나면 자동 삭제 |
| 예시 | 오디오·비디오·이미지 파일 등 | 로그인 정보, 방문 기록 |

캐시는 **속도**, 쿠키는 **기억(인증)** 이 목적이라는 점이 갈립니다.

**5. 한 줄 정리**
캐시는 "가까운 곳에 미리 둔 복사본"으로 속도를 번다.

> 비유: 멀리 있는 본점(원본 서버) 대신 가까운 동네 지점(캐시)에서 받으면 빠르듯, 자주 찾는 데이터를 가까이 둡니다.

### CDN(Content Delivery Network)
CDN은 **고용량 데이터를, 이용자가 어디에 있든 안정적으로 전송**해 주는 기술입니다. 전 세계에 캐시 서버를 두고, 사용자와 가까운 서버에서 콘텐츠를 내려보냅니다.

- **장점**: 장거리 로딩 속도 개선·안정적 콘텐츠 제공, 자체 인프라 투자 없이 글로벌 서비스 가능 → 비용 절감.
- **단점**: 특정 지역만 타깃하는 서비스엔 불필요한 연결 지점이 늘 수 있고, 캐시 서버가 부실하면 **SPOF(단일 장애점)** 위험.
- **활용**: 콘텐츠 캐시 서버, 클라우드 스토리지, 멀티미디어 스트리밍 등.

> 캐시가 "한 서버 안의 빠른 저장"이라면, CDN은 그 캐시를 **전 세계 곳곳에 펼쳐 둔 것**입니다.

## 코드로 보기 — 로그인 상태를 유지하는 두 가지 방식

```http
# ── 방식 A) 세션 + 쿠키 (서버가 상태를 기억) ──
# 로그인 성공 후 서버 응답:
HTTP/1.1 200 OK
Set-Cookie: SESSIONID=abc123; HttpOnly       # 서버가 세션 ID만 내려 줌
# 이후 모든 요청에 쿠키가 자동 첨부 → 서버가 SESSIONID로 사용자 식별

# ── 방식 B) JWT (서버가 상태를 저장하지 않음) ──
HTTP/1.1 200 OK
{ "accessToken": "aaaaaa.bbbbbb.cccccc" }    # 토큰 안에 사용자 정보가 들어 있음
# 이후 요청 헤더에 토큰을 실어 보냄:
Authorization: Bearer aaaaaa.bbbbbb.cccccc
```

**코드목적**
"한 번 로그인하면 다음 요청부터 자동으로 인증되는" 두 가지 대표 방식을 나란히 비교합니다.

**해석**
방식 A는 서버가 세션을 들고 있고 클라이언트엔 **ID만** 줍니다(안전하지만 서버 자원 소모). 방식 B는 토큰 자체에 정보가 들어 있어 서버가 기억하지 않아도 됩니다(확장에 유리하지만 토큰 탈취·만료 관리가 과제). 어느 쪽이든 비밀번호는 **해시값**으로 저장되어 원문이 노출되지 않습니다.

**실무 연결**
로그인 기능을 설계할 때 "세션 기반이냐, 토큰(JWT) 기반이냐"는 가장 먼저 마주치는 결정입니다. 서비스 규모·보안 요구·서버 확장 계획에 따라 선택이 달라지며, 이 글의 비교표가 그 판단의 기준이 됩니다.

## 헷갈리기 쉬운 포인트
- **인증 vs 인가**: 누구인지(먼저) vs 무엇을 할 수 있는지(나중).
- **해시 vs 암호화**: 해시는 단방향(복원 불가), 암호화는 양방향(복호화 가능).
- **쿠키 vs 세션**: 클라이언트 저장(빠름·덜 안전) vs 서버 저장(안전·자원 소모).
- **세션 vs JWT**: 서버가 상태를 기억 vs 토큰에 정보를 담아 서버 부담 ↓.
- **캐시 vs 쿠키**: 속도용 임시 저장소 vs 인증·기억용 작은 데이터.

- [ ] 해시가 단방향이라는 의미와, 비밀번호 저장에 쓰는 이유를 안다.
- [ ] 쿠키와 세션의 저장 위치·보안 차이를 말할 수 있다.
- [ ] JWT의 세 부분(Header·Payload·Signature)을 떠올릴 수 있다.
- [ ] Refresh Token이 해결하는 문제를 설명할 수 있다.
- [ ] 캐시와 CDN의 관계를 설명할 수 있다.

**복습 질문 및 답변**

- (기본) 비밀번호를 안전하게 저장할 때 쓰는, 되돌릴 수 없는 변환을 무엇이라 하나요?
  - 해시(단방향 암호화)입니다.
- (이해확인) 쿠키와 세션은 각각 어디에 저장되며, 보안 면에서 어느 쪽이 더 안전한가요?
  - 쿠키는 클라이언트, 세션은 서버에 저장됩니다. 민감 정보를 서버에 두는 세션이 더 안전합니다.
- (응용) JWT 기반 인증에서 토큰 탈취 위험을 줄이면서 사용자가 자주 로그인하지 않게 하려면 어떤 보완책을 쓸까요?
  - 짧은 만료의 Access Token과 긴 만료의 Refresh Token을 함께 발급해, 만료 시 Refresh Token으로 새 Access Token을 재발급합니다.

## 한 줄 정리
> 인증(누구인지)·인가(무엇을 할지)를 기반으로, 무상태 HTTP에서는 쿠키·세션·토큰(JWT)으로 로그인을 유지하고, 해시·암호화로 데이터를 지키며, 캐시·CDN으로 빠르게 전달한다.
