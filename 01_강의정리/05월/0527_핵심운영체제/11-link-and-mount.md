# 링크와 마운트 — 바로가기의 원리와 장치를 연결하는 작업

> 바탕화면의 '바로가기'를 지워도 원본은 멀쩡합니다. 왜 그럴까요? 또 USB를 꽂으면 컴퓨터가 어떻게 그걸 '내 장치'로 인식할까요? 이 두 질문의 답이 바로 링크와 마운트입니다.

`inode` `심볼릭링크` `하드링크` `바로가기` `마운트` `lsblk` `파일시스템`

## 핵심요약

- 리눅스에서 모든 파일과 디렉터리는 고유한 **inode**를 가지며, inode에는 파일에 대한 모든 정보(유형·권한·시간·저장 블록 위치 등)가 기록된다.
- **심볼릭 링크**는 원본 파일의 '경로'를 가리키는 바로가기로, 자신만의 별도 inode를 가진다.
- **하드 링크**는 원본과 '같은 inode'를 공유하는 바로가기다.
- 그래서 원본을 지웠을 때 심볼릭 링크는 끊어지고, 하드 링크는 그대로 쓸 수 있다.
- 링크는 같은 데이터를 여러 위치에서 쓰는 것처럼 보이게 하면서도 디스크 용량은 한 번만 차지한다.
- **마운트**는 물리적인 저장 장치를 특정 디렉터리에 연결해 운영체제가 인식·접근하게 만드는 작업이다.
- 윈도우는 드라이브 문자(C:, D:)로 자동 마운트하고, 리눅스는 `/` 아래 디렉터리에 마운트한다.

## 개념별 정리

### inode (index-node)

**1. 정의**
inode는 하나의 파일에 대한 모든 정보를 기록해 두는 곳입니다. 파일 유형, 접근 권한, 시간 정보, 그리고 파일이 실제로 저장된 블록 위치까지 담겨 있습니다. 리눅스는 각 inode에 번호를 부여하고, 모든 파일과 디렉터리는 자신만의 고유한 inode를 가집니다.

**2. 왜 필요한가?**
파일 이름은 사람이 부르기 편하라고 붙인 꼬리표일 뿐, 컴퓨터가 파일을 찾을 때 진짜로 기준 삼는 것은 inode 번호입니다. inode가 있어야 "이 파일이 디스크 어디에 있고, 누가 접근할 수 있는지"를 한곳에서 관리할 수 있습니다.

**3. 예시**
원본 파일 `F1.txt`를 열면, 그 이름은 inode 번호(예: 12351)를 가리키고, 그 inode가 다시 하드디스크의 실제 저장 위치를 가리킵니다.

```text
F1.txt  →  inode 12351  →  하드디스크(파일이 저장된 블록 위치)
```

**4. 헷갈리기 쉬운 점**
파일 '이름'과 파일 '실체'는 다릅니다. 이름은 inode를 가리키는 라벨이고, 파일의 진짜 정보와 위치는 inode가 들고 있습니다. 앞 글의 색인 할당에서 "블록 번호를 인덱스 블록에 모아 둔다"는 이야기와 이어지는 개념입니다.

**5. 한 줄 정리**
inode는 파일의 모든 정보가 담긴 '신분증'이고, 파일 이름은 그 신분증을 가리키는 꼬리표입니다.

### 심볼릭 링크 (Symbolic link)

**1. 정의**
원본 파일의 '경로'를 가리키는 바로가기입니다. 링크 파일 자신도 별도의 inode를 가집니다.

**2. 왜 필요한가?**
바로가기를 만들어 두면 깊은 경로에 있는 파일을 짧은 이름으로 빠르게 실행할 수 있고, 같은 데이터를 여러 위치에서 쓰는 것처럼 다룰 수 있습니다. 바로가기를 실행하면 곧 그 원본 파일을 실행하는 것과 같습니다.

**3. 예시**
`sl_F1.txt`는 자기만의 inode(예: 34151)를 가지지만, 그 안에는 "원본 파일의 경로"가 적혀 있습니다.

```text
sl_F1.txt  →  inode 34151  →  "원본 파일의 경로"
```

**4. 헷갈리기 쉬운 점**
심볼릭 링크는 경로를 가리키기 때문에, 원본이 삭제되거나 경로가 바뀌면 링크가 끊어집니다. 반면 링크 파일을 수정하면 (살아 있는 동안에는) 원본 내용도 똑같이 수정됩니다.

**5. 한 줄 정리**
심볼릭 링크는 '주소(경로)를 적어 둔 바로가기'라서, 원본이 사라지거나 이사 가면 길을 잃습니다.

### 하드 링크 (Hard link)

**1. 정의**
원본과 '같은 inode'를 공유하는 바로가기입니다. 별도 경로를 거치지 않고 곧장 같은 실체를 가리킵니다.

**2. 왜 필요한가?**
원본 파일을 이동하거나 삭제해도 하드 링크는 그대로 쓸 수 있어야 할 때 유용합니다. 같은 inode를 공유하므로 둘은 사실상 같은 파일의 두 이름인 셈입니다.

**3. 예시**
`hl_F1.txt`는 원본과 동일한 inode(예: 12351)를 가리키고, 그 inode가 하드디스크의 실제 위치로 이어집니다.

```text
hl_F1.txt  →  inode 12351 (원본과 같은 inode 공유)  →  하드디스크
```

**4. 헷갈리기 쉬운 점**
하드 링크는 경로가 아니라 inode 자체를 공유하기 때문에, 원본을 지우거나 옮겨도 멀쩡합니다. 단, 링크를 수정하면 원본도 같이 수정됩니다(같은 실체를 보고 있으니 당연합니다).

**5. 한 줄 정리**
하드 링크는 '같은 파일에 붙인 또 하나의 이름표'라서, 원본을 지워도 살아남습니다.

### 마운트 (Mount)

**1. 정의**
물리적인 저장 장치를 특정 디렉터리에 연결하는 작업입니다. 새 장치를 쓰려면 반드시 마운트가 필요하며, 요즘 운영체제는 대부분 이를 자동으로 해 줍니다.

**2. 왜 필요한가?**
운영체제가 장치를 '인식'해야 그 안의 파일 시스템에 접근할 수 있습니다. 마운트는 바로 그 인식·연결 작업입니다. USB·CD·외장하드 등 대부분의 저장장치가 대상입니다. 우리가 평소에 마운트를 의식하지 못하는 이유는, 운영체제가 자동으로 해 주기 때문입니다.

**3. 예시**
- **윈도우**: 각 장치를 드라이브 문자에 자동 마운트합니다(C: 하드디스크, D: USB, E: CD/DVD 등).
- **리눅스**: `/`(root) 아래에 `/bin`, `/dev`, `/etc`, `/usr` 같은 디렉터리가 있고, 예를 들어 두 번째 하드디스크를 `/data1`이라는 디렉터리(마운트 포인트)에 연결합니다.

**4. 헷갈리기 쉬운 점**
마운트는 '복사'가 아니라 '연결'입니다. 장치의 내용을 옮겨 오는 게 아니라, "이 디렉터리로 들어가면 그 장치를 쓸 수 있다"고 길을 터 주는 것입니다.

**5. 한 줄 정리**
마운트는 저장 장치를 폴더 하나에 '연결해' 운영체제가 쓸 수 있게 만드는 작업입니다.

## 코드로 보기 — 링크 만들기와 장치 마운트

슬라이드에 등장한 실제 셸 명령으로 정리합니다.

```bash
# 심볼릭 링크 생성: 원본의 '경로'를 가리키는 바로가기
ln -s [원본파일] [심볼릭 링크 파일]

# 하드 링크 생성: 원본과 '같은 inode'를 공유하는 바로가기
ln [원본파일] [하드 링크 파일]

# 연결된 장치 목록 확인: NAME(장치 이름) / TYPE(Disk·Part) / MOUNTPOINT(마운트 위치)
lsblk -p

# 장치를 디렉터리에 마운트: -t 로 파일 시스템 유형 지정(예: ext4)
sudo mount [옵션] [장치] [디렉터리]
```

심볼릭 링크와 하드 링크의 차이를 표로 비교하면 다음과 같습니다.

| 항목 | 심볼릭 링크 | 하드 링크 |
| --- | --- | --- |
| inode | 별도의 inode를 가짐 | 원본과 같은 inode 공유 |
| 가리키는 대상 | 원본 파일의 '경로' | 원본과 같은 '실체(inode)' |
| 원본 삭제·이동 시 | 링크가 끊어짐 | 그대로 사용 가능 |
| 링크 수정 시 | 원본도 함께 수정됨 | 원본도 함께 수정됨 |
| 생성 명령 | `ln -s` | `ln` |

**코드목적**
바로가기(링크)를 만들고, 컴퓨터에 연결된 저장 장치를 확인해 원하는 디렉터리에 연결(마운트)하기 위한 명령들입니다.

**해석**
`ln -s`는 경로를 적어 둔 바로가기를, `ln`은 같은 실체를 공유하는 바로가기를 만듭니다. `lsblk -p`로 장치의 이름·유형·마운트 위치를 한눈에 확인한 뒤, `sudo mount`로 장치를 특정 디렉터리에 연결합니다. 링크를 쓰면 대량 데이터를 일일이 복사하지 않고도, 여러 위치에 같은 데이터가 있는 것처럼 쓰면서 디스크 용량은 한 번만 차지합니다(예: `/code/my1/data`와 `/code/my2/dataset`가 모두 실제 위치인 `/data1/dataset`을 심볼릭 링크로 가리키는 구조). 단, 어느 쪽을 수정하든 원본이 함께 바뀐다는 점은 유의해야 합니다.

**실무 연결**
구글 코랩에서 구글 드라이브를 연동할 때 "드라이브 마운트"라는 표현이 그대로 등장합니다. 이때 하는 일이 바로 이 마운트 개념입니다. 또 용량이 큰 데이터셋을 여러 작업 폴더에서 공유할 때, 복사 대신 링크를 거는 방식이 저장 공간과 동기화 면에서 유리합니다.

## 헷갈리기 쉬운 포인트

- **심볼릭 링크 vs 하드 링크**: 별도 inode로 '경로'를 가리킴(원본 삭제 시 끊김) vs 같은 inode를 '공유'함(원본 삭제 시 유지).
- **파일 이름 vs inode**: 사람이 부르는 꼬리표 vs 파일의 실제 정보·위치를 담은 신분증.
- **마운트 vs 복사**: 장치를 디렉터리에 '연결' vs 내용을 '옮겨 담기'.

**복습 질문 및 답변**

- (기본) inode에는 어떤 정보가 담겨 있나요?
  → 파일 유형, 접근 권한, 시간 정보, 파일이 저장된 블록 위치 등 파일에 대한 모든 정보가 담겨 있다.
- (이해 확인) 원본 파일을 삭제하면 심볼릭 링크와 하드 링크는 각각 어떻게 되나요?
  → 심볼릭 링크는 경로가 사라져 끊어지고, 하드 링크는 같은 inode를 공유하므로 그대로 쓸 수 있다.
- (응용) 큰 데이터셋을 여러 작업 폴더에서 함께 쓰고 싶을 때 복사 대신 링크를 쓰는 이유는?
  → 여러 위치에 같은 데이터가 있는 것처럼 쓰면서도 디스크 용량은 한 번만 차지하기 때문. 단, 한쪽을 수정하면 원본도 함께 바뀐다는 점은 유의해야 한다.

## 한 줄 정리

> 링크는 inode를 매개로 한 '바로가기'(경로를 가리키는 심볼릭, 실체를 공유하는 하드)이고, 마운트는 물리 장치를 디렉터리에 연결해 운영체제가 쓸 수 있게 만드는 작업이다.
