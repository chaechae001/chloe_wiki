# 모델별 특성 엔지니어링 — 모델이 데이터를 보는 방식이 다르다

> 같은 데이터라도 선형모델, 거리 기반 모델, 트리는 서로 다른 눈으로 봅니다. 그래서 필요한 전처리도 달라집니다.

`특성엔지니어링` · `스케일링` · `로그변환` · `상호작용항` · `모델별전처리`

## 핵심요약

- 특성 엔지니어링은 기존 컬럼으로 모델이 더 잘 배우는 새 특성을 만들거나 변환하는 작업이다.
- 선형·로지스틱 회귀는 스케일·선형 관계에 민감해 스케일링, 로그변환, 상호작용항이 중요하다.
- KNN·거리 기반 모델은 스케일이 큰 특성이 거리를 지배하므로 표준화·정규화가 핵심이다.
- 트리 계열은 스케일에 둔감한 대신, 좋은 분할 후보(범주 인코딩·의미 있는 파생변수)가 중요하다.
- 전처리가 항상 성능을 올리는 것은 아니며, 모델 성격에 맞지 않으면 오히려 성능이 떨어질 수 있다.

## 1. 특성 엔지니어링이란

### 1) 정의

특성 엔지니어링(feature engineering)은 원본 데이터의 컬럼을 가공·조합·변환해 모델이 패턴을 더 잘 학습하도록 돕는 특성을 만드는 작업입니다. 새 데이터를 수집하지 않고 기존 컬럼만으로도 많은 것을 할 수 있습니다.

### 2) 왜 필요한가

모델은 주어진 특성의 표현 방식에 크게 좌우됩니다. 같은 정보라도 어떻게 표현하느냐에 따라 학습 난이도가 달라집니다. 예를 들어 한쪽으로 치우친(왜도가 큰) 금액 데이터는 로그변환하면 분포가 완만해져 선형모델이 다루기 쉬워집니다.

### 3) 핵심 흐름 재구성 — 모델별 전략

모델이 데이터를 보는 방식이 다르기 때문에, 중요한 특성 엔지니어링도 모델마다 다릅니다.

| 모델 계열 | 중요한 특성 엔지니어링 | 이유 |
|---|---|---|
| 선형회귀·로지스틱 회귀 | 스케일링, 로그변환, 상호작용항, 다중공선성 관리 | 계수·규제가 스케일에 민감하고 선형 관계를 가정 |
| KNN·거리 기반 | 표준화/정규화, 불필요한 특성 제거 | 거리 계산에서 큰 스케일 특성이 전체 거리를 지배 |
| 트리·랜덤포레스트·GBM | 범주 인코딩, 결측 처리, 의미 있는 비닝·파생변수 | 스케일에 둔감하지만 좋은 분할 후보가 필요 |
| 나이브 베이즈 | 분포 가정에 맞는 변환, 희소 범주 정리 | 가정(Gaussian/Multinomial 등)과 입력 표현이 직결 |
| 신경망 | 스케일링, 임베딩, 안정적 수치 범위 | 최적화·gradient 안정성에 큰 영향 |
| 시계열 | lag, rolling mean/std, 미래 정보 제거 | 시간 순서와 누수 방지가 핵심 |

### 4) 쉬운 예시

키를 cm로, 몸무게를 kg로 재면 몸무게 숫자가 훨씬 큽니다. 거리 기반 모델(KNN)은 이 큰 숫자에 끌려다녀 키를 거의 무시합니다. 표준화로 두 특성의 스케일을 맞추면 비로소 공평하게 반영됩니다. 반면 트리는 "키 ≤ 170?"처럼 임곗값으로만 나누므로 단위 크기에 흔들리지 않습니다.

### 5) 한 줄 정리

> 특성 엔지니어링은 모델의 성격에 맞춰야 하며, 만능 전처리는 없다.

## 2. tips 데이터로 만드는 파생 특성

### 1) 코드 예시

새 데이터를 더하지 않고 기존 컬럼만으로 특성을 만듭니다(공개용 seaborn `tips`).

```python
import numpy as np, seaborn as sns

tips = sns.load_dataset('tips').copy()

# 왜도가 큰 금액을 완만하게: 로그변환
tips['log_total_bill'] = np.log1p(tips['total_bill'])

# 1인당 결제 금액 (의미 있는 파생변수)
tips['bill_per_person'] = tips['total_bill'] / tips['size']

# 인원이 4명 이상인지 (비닝 → 0/1)
tips['large_party'] = (tips['size'] >= 4).astype(int)

# 금액과 인원의 상호작용항
tips['bill_x_size'] = tips['total_bill'] * tips['size']

# 범주형 원-핫 인코딩
tips = pd.get_dummies(tips, columns=['day', 'time', 'smoker'], drop_first=True)

print("기본 특성 수: 2  →  엔지니어링 후 특성 수:", 
      len([c for c in tips.columns if c not in ['tip', 'tip_rate', 'high_tip']]))
```

이렇게 하면 `total_bill`, `size` 두 개였던 기본 특성이 로그변환·1인당 금액·구간화·상호작용·원-핫까지 더해져 여러 개로 늘어납니다.

### 2) 각 파생 특성의 의도

- `log_total_bill`: 큰 금액의 영향을 완만하게 만들어 선형모델의 가정에 맞춤.
- `bill_per_person`: 절대 금액보다 "1인당 얼마"가 더 의미 있을 수 있음.
- `large_party`: 연속값을 의미 있는 구간(0/1)으로 나눔.
- `bill_x_size`: 두 변수의 결합 효과(상호작용)를 명시적으로 표현.
- 원-핫 인코딩: 요일·시간대·흡연 여부 같은 범주를 모델이 읽을 수 있는 숫자로 변환.

## 3. 전처리가 항상 좋은 건 아니다

### 1) 왜 중요한가

특성 엔지니어링을 "무조건 하면 좋다"고 생각하기 쉽지만, 모델과 데이터에 따라 효과가 갈립니다. 강의 실습에서 기본 특성 vs 엔지니어링 특성으로 여러 모델을 비교한 결과, 모델별로 방향이 달랐습니다.

- **선형회귀**: 로그변환·상호작용항을 더한 엔지니어링 특성에서 오차(RMSE)가 개선되는 경향.
- **KNN**: 스케일링을 적용하면 개선되지만, 특성을 무작정 늘리면 오히려 성능이 떨어지기도 함(차원이 늘며 거리 계산이 흐려짐).
- **트리**: 스케일링·로그변환의 효과가 거의 없음. 트리는 임곗값 분할이라 단조 변환에 둔감하기 때문.

### 2) 결과 해석

같은 파생 특성이 선형모델에는 도움이 되고 트리에는 무의미할 수 있습니다. 그래서 "어떤 모델을 쓸 것인가"를 먼저 정하고, 그 모델이 데이터를 보는 방식에 맞춰 전처리를 설계해야 합니다.

### 3) 한 줄 정리

> 좋은 전처리는 모델 성격에 맞춘 전처리이며, 같은 변환도 모델에 따라 약이 되기도 독이 되기도 한다.

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| 선형모델 vs 트리의 스케일 민감도 | 선형·거리 모델은 스케일에 민감 vs 트리는 임곗값 분할이라 둔감 |
| 표준화 vs 정규화 | 평균 0·표준편차 1로 맞춤 vs 0~1 범위로 압축 |
| 로그변환 vs 스케일링 | 왜도(치우침)를 완화 vs 값의 범위/단위를 맞춤 |
| 원-핫 인코딩 vs 라벨 인코딩 | 범주를 여러 0/1 열로 vs 하나의 정수로. 순서 없는 범주엔 원-핫 |
| 특성 추가 = 성능 향상? | 항상 아님. 모델·차원에 따라 오히려 악화 가능 |

### 복습 질문 및 답변

**Q1. 트리 모델에는 왜 스케일링이 거의 필요 없나?**

<details>
<summary>답</summary>

트리는 "특성 값 ≤ 임곗값?"이라는 대소 비교로 분할한다. 스케일링은 값의 순서를 바꾸지 않으므로 분할 지점의 상대 관계가 그대로 유지되어, 결과에 거의 영향이 없다.

</details>

**Q2. KNN에서 스케일링을 빼먹으면 무슨 일이 생기나?**

<details>
<summary>답</summary>

KNN은 특성 간 거리로 이웃을 찾는다. 스케일이 큰 특성이 거리 값을 지배해, 스케일이 작은 특성은 사실상 무시된다. 그래서 표준화·정규화로 스케일을 맞추는 것이 필수다.

</details>

**Q3. 상호작용항(예: bill × size)은 왜 만드는가?**

<details>
<summary>답</summary>

두 특성이 함께 작용할 때 생기는 효과를 선형모델이 스스로 잡아내기 어렵기 때문이다. 곱한 항을 명시적으로 특성에 추가하면 그 결합 효과를 모델이 직접 학습할 수 있다.

</details>

## 한 줄 정리

> 특성 엔지니어링은 모델이 데이터를 보는 방식에 맞춰 설계해야 하며, 선형·거리 모델은 스케일링이, 트리는 좋은 분할 후보가 핵심이다.
