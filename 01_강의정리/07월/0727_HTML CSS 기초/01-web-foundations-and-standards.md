# 웹의 구성 요소와 품질 기준 — 정보·표현·동작을 나누어 설계하기

> 웹페이지는 화면에 보이는 한 장이지만, 그 안에서는 정보와 디자인과 동작이 서로 다른 책임을 맡습니다.
> 세 역할을 구분하고 공통 규칙을 지키면 더 많은 사람이 더 다양한 환경에서 같은 정보를 이용할 수 있습니다.

`HTML` · `CSS` · `JavaScript` · `웹 접근성` · `크로스 브라우징`

## 핵심요약

- HTML은 콘텐츠의 의미와 문서 구조를 표현한다.
- CSS는 HTML에 색상·간격·배치 같은 시각적 표현을 적용한다.
- JavaScript는 사용자 입력에 반응하고 화면의 상태를 바꾸는 동작을 담당한다.
- 웹 표준과 접근성을 지키면 특정 환경이나 사용 방식에 갇히지 않는 페이지를 만들 수 있다.
- 정보와 표현을 분리하면 같은 내용을 여러 화면에 재사용하고 변경 비용을 줄일 수 있다.

## 1. HTML·CSS·JavaScript의 역할

### 1) 정의

웹 브라우저는 여러 종류의 코드를 읽어 하나의 화면으로 조합합니다. 그중 HTML은 "무엇이 있는가", CSS는 "어떻게 보이는가", JavaScript는 "어떻게 반응하는가"를 주로 설명합니다.
이 구분은 절대적인 벽이라기보다 각 기술이 가장 잘 담당하는 책임을 나타냅니다.

| 기술 | 주된 질문 | 대표 역할 |
|---|---|---|
| HTML | 이 정보는 무엇인가? | 제목, 문단, 목록, 링크 같은 구조 |
| CSS | 이 정보를 어떻게 보여 줄까? | 색상, 글꼴, 간격, 정렬, 레이아웃 |
| JavaScript | 어떤 사건에 어떻게 반응할까? | 클릭 처리, 상태 변경, 데이터 갱신 |

### 2) 왜 필요한가

세 책임이 한곳에 뒤섞이면 작은 변경도 다른 부분을 뜻밖에 깨뜨릴 수 있습니다. 예를 들어 메뉴의 색만 바꾸려는데 HTML 문구까지 여러 곳에서 수정해야 한다면 유지보수가 어렵습니다.
반대로 HTML 구조가 분명하면 CSS를 교체해도 정보의 의미는 남고, JavaScript가 없어도 핵심 내용을 읽을 수 있습니다. 역할 분리는 협업에서도 중요합니다.
기획한 정보 구조, 시각 디자인, 상호작용 로직을 서로 독립적으로 검토할 수 있기 때문입니다.
### 3) 핵심 흐름 재구성

브라우저가 페이지를 만드는 흐름은 다음처럼 이해할 수 있습니다.

1. HTML을 읽어 제목·문단·버튼 같은 문서 구조를 만든다.
2. CSS 규칙을 찾아 각 요소의 모양과 배치를 계산한다.
3. 계산된 결과를 화면에 그린다.
4. JavaScript를 실행해 클릭이나 입력 같은 사건을 기다린다.
5. 상태가 바뀌면 필요한 부분을 다시 계산하고 그린다.

HTML이 먼저 정보의 뼈대를 제공한다는 점이 중요합니다. 뼈대가 의미 있게 작성되어야 스타일을 끄거나 동작이 실패한 상황에서도 콘텐츠가 남습니다.
### 4) 쉬운 예시

카페 메뉴판을 떠올려 봅시다. 메뉴명과 가격의 분류는 HTML, 글자 크기와 색상은 CSS, 품절 메뉴를 누르면 안내가 나타나는 기능은 JavaScript에 해당합니다.
메뉴판의 색이 바뀌어도 음료 이름이 음료라는 사실은 달라지지 않습니다. 바로 이 차이가 정보와 표현을 나누는 이유입니다.
### 5) 코드 예시

다음 예시는 같은 소개 카드를 세 기술이 나누어 완성하는 최소 구조입니다.

```html
<article class="profile-card">
  <h2>주말 독서 모임</h2>
  <p>함께 읽고 생각을 나누는 작은 모임입니다.</p>
  <button type="button" id="join-button">관심 표시</button>
</article>

<style>
  .profile-card {
    max-width: 320px;
    padding: 20px;
    border: 1px solid #cbd5e1;
    border-radius: 12px;
  }
</style>

<script>
  const button = document.querySelector('#join-button');   button.addEventListener('click', () => {
    button.textContent = '관심 있음';
  });
</script>
```

예상 렌더링은 제목, 설명, 버튼이 들어 있는 테두리 카드입니다. 버튼을 누르기 전에는 `관심 표시`, 누른 뒤에는 `관심 있음`이라는 문구가 보입니다.
### 6) 헷갈리는 점

HTML도 `style` 속성을 통해 모양을 바꿀 수 있고, JavaScript도 스타일을 직접 수정할 수 있습니다. 그러나 "할 수 있다"와 "주된 책임으로 삼는다"는 다릅니다.
반복되는 시각 규칙은 CSS에 두고, JavaScript는 상태를 나타내는 클래스나 속성을 바꾸는 방식이 읽기 쉽습니다.
### 7) 한 줄 정리

> HTML은 의미, CSS는 표현, JavaScript는 동작을 중심으로 맡을 때 페이지의 구조와 변경 이유가 선명해진다.
## 2. 웹 표준·접근성·크로스 브라우징

### 1) 정의

웹 표준은 브라우저와 개발자가 공통으로 이해할 수 있도록 정한 기술 규칙과 권장 방식입니다. 웹 접근성은 신체 조건, 감각, 입력 장치와 관계없이 정보와 기능을 이용할 수 있게 만드는 품질 기준입니다.
크로스 브라우징은 서로 다른 브라우저와 기기에서도 핵심 내용과 기능이 안정적으로 동작하도록 확인하고 보완하는 과정입니다. 세 개념은 목표가 다르지만 서로 연결됩니다.
표준적인 코드는 브라우저가 예측 가능하게 해석하기 쉽고, 의미 있는 구조는 보조 기술이 내용을 이해하는 데 도움이 됩니다.
### 2) 왜 필요한가

사용자는 모두 같은 화면과 입력 장치를 쓰지 않습니다. 누군가는 키보드만 사용하고, 누군가는 화면 낭독기로 제목과 링크를 탐색합니다.
작은 휴대전화, 큰 모니터, 오래된 브라우저처럼 실행 환경도 다양합니다. 따라서 "내 화면에서 보인다"는 확인만으로 품질을 판단할 수 없습니다.
웹의 기본 약속을 지키면 특정 사용자나 특정 프로그램에만 맞춘 우연한 성공을 줄일 수 있습니다.
### 3) 핵심 흐름 재구성

품질을 점검할 때는 다음 순서가 실용적입니다.

1. 유효하고 의미 있는 HTML로 정보 구조를 세운다.
2. 이미지와 입력 요소에 텍스트 대안을 제공한다.
3. 키보드만으로 링크와 버튼을 사용할 수 있는지 확인한다.
4. CSS가 없어도 콘텐츠 순서가 이해되는지 살핀다.
5. 화면 폭을 바꾸고 둘 이상의 브라우저에서 핵심 기능을 시험한다.
6. 지원하지 않는 기능이 있어도 기본 정보는 남도록 대체 경로를 둔다.

이 흐름은 마지막에 오류를 고치는 절차가 아니라 처음부터 설계에 포함해야 할 기준입니다.
### 4) 쉬운 예시

공공건물의 출입구를 생각해 봅시다. 표준은 문의 위치와 문 여는 방식에 관한 공통 약속이고, 접근성은 계단 외에 경사로와 안내 표지를 마련하는 일에 가깝습니다.
크로스 브라우징은 비 오는 날이나 큰 짐을 든 상황에서도 실제로 출입할 수 있는지 여러 조건에서 시험하는 과정과 닮았습니다.
### 5) 코드 예시

이미지는 보이는 모양뿐 아니라 의미를 전달해야 합니다.

```html
<a class="story-link" href="/stories/garden">
  <img
    src="images/community-garden.webp"
    alt="주민들이 함께 가꾸는 작은 텃밭"
  >
  <span>공동 텃밭 이야기 읽기</span>
</a>
```

이미지가 로드되지 않거나 화면을 보지 않고 탐색해도 `alt`와 링크 문구가 목적을 전달합니다. 링크 자체의 텍스트가 충분히 구체적이므로 "여기를 클릭"보다 이동 결과를 예측하기 쉽습니다.
### 6) 헷갈리는 점

모든 이미지의 `alt`를 길게 쓰는 것이 접근성은 아닙니다. 정보를 전달하는 이미지는 목적을 설명하고, 장식뿐인 이미지는 빈 대체 텍스트를 사용해 불필요한 낭독을 줄입니다.
또한 여러 브라우저에서 픽셀 하나까지 완전히 같아야 크로스 브라우징이 성공하는 것은 아닙니다. 핵심 정보와 기능이 동등하게 제공되는지가 먼저입니다.
### 7) 한 줄 정리

> 좋은 웹 품질은 한 환경의 완벽한 모양보다 다양한 환경에서 같은 정보와 기능에 도달할 수 있는가로 판단한다.
## 3. 정보와 표현의 분리

### 1) 정의

정보와 표현의 분리는 콘텐츠의 의미를 HTML에, 반복되는 시각 규칙을 CSS에 두는 설계 원칙입니다. 예를 들어 "이 문장은 경고다"라는 의미는 클래스 이름이나 구조로 표현하고, 빨간색과 테두리는 CSS가 결정합니다.
### 2) 왜 필요한가

페이지가 늘어나면 같은 디자인을 수십 번 수정해야 할 수 있습니다. 공통 CSS를 사용하면 규칙 한 곳을 바꾸어 관련 요소를 함께 갱신할 수 있습니다.
HTML도 색상 지시가 줄어들어 내용의 구조를 읽기 쉬워집니다.
### 3) 핵심 흐름 재구성

정보와 표현을 나누는 간단한 기준은 "이 값이 콘텐츠의 의미인가, 현재 디자인의 선택인가"를 묻는 것입니다.

- 제목이라는 의미는 HTML 태그로 표현한다.
- 주의가 필요한 상태는 의미 있는 이름으로 표시한다.
- 글자색과 여백은 CSS 규칙으로 관리한다.
- 동작 상태는 JavaScript가 클래스나 속성으로 알린다.
- CSS는 그 상태에 맞는 시각적 결과를 그린다.

### 4) 쉬운 예시

책의 원고와 편집 디자인을 나누는 것과 같습니다. 본문이 어느 장의 제목인지는 원고의 구조이고, 제목을 파란색 28픽셀로 보이게 하는 것은 편집 디자인입니다.
표지 디자인을 바꾸더라도 원고의 장 순서는 유지되어야 합니다.
### 5) 코드 예시

```html
<p class="notice" data-level="important">
  신청 마감일이 가까워졌습니다.
</p>
```

```css
.notice[data-level="important"] {
  padding: 12px;
  border-left: 4px solid #b91c1c;
  background-color: #fff1f2;
}
```

HTML은 중요 공지라는 상태를 담고, CSS는 그 상태를 어떻게 보일지 결정합니다.
### 6) 헷갈리는 점

외부 CSS를 쓰는 것만으로 자동으로 책임 분리가 완성되지는 않습니다.

`red-big-box`처럼 현재 모양을 그대로 이름 붙이면 디자인 변경 때 의미가 어색해집니다.

`notice`나 `featured-card`처럼 역할과 상태를 드러내는 이름이 변경에 강합니다.

### 7) 한 줄 정리

> HTML에는 변하지 않는 의미를, CSS에는 바뀔 수 있는 표현 규칙을 두면 재사용과 유지보수가 쉬워진다.
## 코드로 보기 — 스타일이 없어도 이해되는 알림 카드

```html
<section class="event-card" aria-labelledby="event-title">
  <h2 id="event-title">동네 영화 상영회</h2>
  <p>토요일 오후 4시에 시작합니다.</p>
  <a href="/events/movie-night">상세 일정 보기</a>
</section>

<style>
  .event-card {
    max-width: 28rem;
    padding: 1rem;
    border: 1px solid #94a3b8;
    background: #f8fafc;
  }   .event-card a:focus-visible {
    outline: 3px solid #2563eb;
    outline-offset: 3px;
  }
</style>
```

### 코드 목적

HTML만 읽어도 정보의 제목, 설명, 이동 경로가 분명하고 CSS는 가독성과 키보드 초점을 보완하는 구조를 만듭니다.
### 코드 흐름

1. `section`이 하나의 행사 정보를 묶는다.
2. `aria-labelledby`가 영역과 제목을 연결한다.
3. 링크 문구가 이동할 정보의 내용을 구체적으로 설명한다.
4. CSS가 카드 모양과 키보드 초점 표시를 더한다.

### 예상 렌더링 및 실행 결과

```text
동네 영화 상영회
토요일 오후 4시에 시작합니다.
[상세 일정 보기]
```

키보드의 Tab 키로 링크에 이동하면 파란색 윤곽선이 나타납니다.
### 결과 해석

CSS를 제거해도 제목과 문단과 링크의 순서는 그대로 남습니다. 즉 시각적 카드가 없어져도 행사 정보와 이동 목적을 이해할 수 있습니다.
### 실무 연결

공지 목록, 상품 카드, 대시보드 요약처럼 반복되는 구성 요소는 이 방식으로 만들면 테마를 바꾸기 쉽습니다. 접근성 점검과 반응형 디자인도 의미 있는 HTML 뼈대 위에서 더 안정적으로 수행할 수 있습니다.

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| HTML vs CSS | HTML은 정보의 의미와 구조, CSS는 그 정보의 시각적 표현 |
| CSS vs JavaScript | CSS는 상태를 보이게 하고, JavaScript는 사건을 처리해 상태를 바꿈 |
| 웹 표준 vs 웹 접근성 | 표준은 공통 기술 규칙, 접근성은 다양한 사용자가 정보와 기능에 도달하도록 하는 품질 |
| 접근성 vs 크로스 브라우징 | 접근성은 사용 방식의 다양성, 크로스 브라우징은 실행 환경의 다양성에 초점 |
| 인라인 스타일 vs 외부 스타일 | 요소에 직접 쓰면 즉시성이 높고, 별도 규칙으로 관리하면 재사용과 변경이 쉬움 |

**Q1. HTML이 시각적 결과가 아니라 의미를 담당해야 하는 이유는 무엇인가요?**
<details>
<summary>답</summary>

화면 모양은 기기나 테마에 따라 바뀌지만 정보의 역할은 유지되어야 하기 때문입니다. 의미 있는 구조는 검색 도구와 보조 기술에도 콘텐츠 관계를 전달합니다.
</details>

**Q2. 표준을 지키면 모든 브라우저의 화면이 완전히 같아지나요?**
<details>
<summary>답</summary>

그렇지는 않습니다. 브라우저별 렌더링 차이는 남을 수 있습니다. 표준 준수의 핵심은 코드를 예측 가능하게 해석하게 하고 핵심 정보와 기능의 차이를 줄이는 것입니다.
</details>

**Q3. JavaScript 오류가 발생해도 사용자가 핵심 정보를 얻도록 하려면 어떻게 설계해야 하나요?**

내용과 기본 이동 경로를 HTML에 먼저 작성하고, JavaScript는 추가 편의 기능으로 얹습니다. 그러면 동작 코드가 실패해도 문서와 링크는 남습니다.
</details>
