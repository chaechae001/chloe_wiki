# 포매터·린터와 AI 코드 리뷰

> 자동화 도구는 코드 스타일을 빠르게 맞추고 반복 실수를 찾아 주지만, 코드가 올바른 문제를 풀고 있는지까지 보증하지는 않습니다.

`Black` · `Ruff` · `isort` · `static analysis` · `AI code review`

## 핵심요약

- Black은 공백·줄바꿈 같은 코드 모양을 일관된 형식으로 정리하는 포매터다.
- Ruff는 규칙 위반과 잠재 문제를 탐지하는 린터이며, 일부 항목은 자동으로 수정할 수 있다.
- isort는 import 문을 그룹과 순서에 맞게 정리한다.
- 자동화 도구는 역할이 다르므로 결과 메시지와 변경 내용을 확인하고 함께 사용해야 한다.
- AI가 만든 코드도 하드코딩, 전역 변수, 긴 함수, 중복, 모호한 이름을 사람이 최종 검토해야 한다.

## 1. 포매터와 린터의 역할

### 1) 정의

포매터(formatter)는 실행 의미를 유지하면서 코드의 **표현 형식**을 일정하게 바꾸는 도구입니다. 린터(linter)는 코드를 실행하기 전에 규칙 위반, 사용하지 않는 요소, 잠재 오류처럼 점검 가능한 문제를 찾아 알려 주는 도구입니다.

둘 다 코드 품질 자동화에 사용되지만 질문이 다릅니다.

| 도구 유형 | 핵심 질문 | 대표 결과 |
|---|---|---|
| 포매터 | 코드를 같은 스타일로 읽을 수 있는가? | 공백·들여쓰기·줄바꿈 정리 |
| 린터 | 정적으로 찾을 수 있는 문제나 규칙 위반이 있는가? | 진단 위치와 규칙 코드 표시 |
| import 정리 도구 | import가 예측 가능한 순서로 배치됐는가? | 그룹화·정렬 |

### 2) 왜 필요한가

여러 사람이 같은 저장소를 수정하면 개인마다 줄바꿈과 따옴표, import 순서가 달라질 수 있습니다. 이런 차이를 사람이 반복해서 고치면 리뷰 시간이 스타일 논쟁에 쓰이고, 실제 로직 문제를 놓치기 쉽습니다.

자동화 도구를 사용하면 다음 효과를 기대할 수 있습니다.

- 반복적인 스타일 정리를 빠르게 수행합니다.
- 리뷰에서 로직과 설계에 더 집중할 수 있습니다.
- 파일마다 다른 형식이 누적되는 것을 줄입니다.
- 일부 단순 규칙 위반을 작성 단계에서 발견합니다.

하지만 도구 통과는 “버그가 없다”는 인증이 아닙니다. 요구사항 오해, 잘못된 계산식, 부적절한 예외 복구, 복잡한 책임 분리는 별도 검토가 필요합니다.

### 3) 핵심 흐름 재구성

기본적인 자동 정리 흐름은 다음처럼 이해할 수 있습니다.

```text
코드 작성
  ↓
포매터로 표현 형식 통일
  ↓
import 순서 정리
  ↓
린터로 문제 탐지·일부 수정
  ↓
변경 내용과 로직을 사람이 검토
```

실제 순서는 팀 설정에 따라 달라질 수 있습니다. 중요한 것은 각 도구가 바꾼 내용을 확인하고, 같은 규칙을 반복해서 적용해도 추가 변경이 없는 안정된 상태를 만드는 것입니다.

### 4) 쉬운 예시

문서 편집에서 맞춤법 검사와 서식 통일을 떠올려 봅시다. 제목 크기와 줄 간격을 통일해도 내용의 주장이 사실이 되는 것은 아닙니다. 맞춤법 오류가 없다고 논리적인 글이 보장되는 것도 아닙니다.

코드 포매터와 린터도 같습니다. 읽기 방식을 통일하고 일부 문제를 찾지만, 프로그램의 목적과 결과는 사람이 검증해야 합니다.

### 5) 코드 예시

다음 코드는 실행될 수 있지만 import 순서와 공백이 일관되지 않고, 사용하지 않는 import도 포함합니다.

```python
import sys
import json


def build_message(name: str, count: int) -> str:
    return f"{name}: {count}"


print(build_message("sample", 3))
```

린터는 사용하지 않는 `sys`, `json`을 지적할 수 있습니다. 포매터는 함수와 인수 주변의 공백·줄바꿈을 통일합니다. import 정리 도구는 남아 있는 import를 정해진 순서로 배치합니다.

도구를 적용한 뒤 불필요한 import를 제거하면 핵심 코드는 다음처럼 남습니다.

```python
def build_message(name: str, count: int) -> str:
    return f"{name}: {count}"


print(build_message("sample", 3))
```

```text
sample: 3
```

출력은 같지만 독자는 프로그램에 실제로 필요한 요소만 보게 됩니다.

### 6) 헷갈리는 점

린터의 자동 수정 옵션이 모든 진단을 고치는 것은 아닙니다. 의미를 바꿀 가능성이 있거나 사람이 판단해야 하는 항목은 진단만 제공할 수 있습니다.

또한 도구마다 담당 범위가 겹치는 경우가 있습니다. 같은 코드를 서로 다른 방식으로 계속 바꾼다면 개인이 임의로 순서를 바꾸기보다 팀의 실행 순서와 설정을 하나로 맞춰야 합니다.

### 7) 한 줄 정리

> 포매터는 표현을 통일하고 린터는 정적 문제를 찾지만, 프로그램의 의미와 요구사항은 사람이 검증한다.

## 2. Black·Ruff·isort 사용 흐름

### 1) 정의

- **Black**: 파이썬 코드를 일관된 형식으로 다시 배치하는 포매터
- **Ruff**: 코드 규칙을 검사하고 일부 항목을 자동 수정하는 린터
- **isort**: 표준 라이브러리, 외부 패키지, 프로젝트 모듈 등의 import 순서를 정리하는 도구

### 2) 왜 필요한가

각 도구의 목적을 구분하면 결과를 잘못 해석하는 일을 줄일 수 있습니다. 예를 들어 Black을 실행한 뒤 진단이 없다고 해서 사용하지 않는 변수가 사라지는 것은 아닙니다. Ruff가 경고를 모두 없앴다고 해서 줄바꿈 형식이 팀 기준과 일치한다고 단정할 수도 없습니다.

### 3) 핵심 흐름 재구성

한 파일을 대상으로 각 역할을 확인하는 명령은 다음과 같습니다.

```bash
black --check app.py
isort --check-only app.py
ruff check app.py
```

- `black --check`: 파일을 바꾸지 않고 포맷 변경이 필요한지 확인합니다.
- `isort --check-only`: import 순서가 기준과 맞는지 확인합니다.
- `ruff check`: 규칙 위반 위치와 내용을 진단합니다.

실제로 정리하려면 다음처럼 실행할 수 있습니다.

```bash
black app.py
isort app.py
ruff check --fix app.py
```

자동 수정 후에는 변경된 코드를 다시 읽고 테스트해야 합니다. 특히 `--fix`는 “수정 가능한 진단을 처리하라”는 뜻이지 “프로그램의 모든 품질 문제를 해결하라”는 뜻이 아닙니다.

### 4) 쉬운 예시

Black은 책의 글꼴과 문단 간격을 통일하는 편집자, isort는 참고문헌을 정해진 기준으로 배열하는 정리자, Ruff는 반복 표현과 규칙 위반을 표시하는 교정자에 가깝습니다.

세 역할을 거쳐도 글의 결론이 타당한지는 저자가 확인해야 합니다. 코드에서는 그 역할을 테스트와 코드 리뷰가 맡습니다.

### 5) 코드 예시

```bash
# 1. 파일을 바꾸지 않고 상태 확인
black --check app.py
isort --check-only app.py
ruff check app.py

# 2. 필요한 항목 정리
black app.py
isort app.py
ruff check --fix app.py

# 3. 다시 검사
black --check app.py
isort --check-only app.py
ruff check app.py
```

마지막 검사에서 추가 진단이나 변경 요구가 없다면 **설정된 자동 규칙 범위**를 통과한 것입니다. 기능이 정확하다는 뜻은 아니므로 입력·출력 테스트와 사람의 검토가 뒤따라야 합니다.

### 6) 헷갈리는 점

도구를 설치했다고 자동으로 실행되는 것은 아닙니다. 개발 흐름에서 명령을 직접 실행하거나 편집기의 저장 동작과 연결하는 등 일관된 실행 지점이 필요합니다.

저장 시 자동 실행은 빠른 피드백을 주지만, 큰 변경이 갑자기 적용될 수 있습니다. 처음 도입할 때는 작은 파일에서 결과를 확인하고 팀 규칙을 합의하는 편이 안전합니다.

### 7) 한 줄 정리

> Black·Ruff·isort는 서로 다른 반복 작업을 맡으며, 검사 후 변경 내용과 기능을 다시 확인해야 완전한 흐름이 된다.

## 3. AI 생성 코드를 검토하는 기준

### 1) 정의

AI 코드 리뷰는 생성된 코드가 문법상 실행되는지만 보는 것이 아니라, 프로젝트 규칙과 요구사항, 유지보수 기준에 맞는지 사람이 확인하는 과정입니다.

AI는 일반적인 패턴을 빠르게 제시할 수 있지만, 프로젝트가 가진 실제 경로 규칙, 설정 정책, 성능 요구, 실패 처리 원칙을 모두 알고 있다고 가정할 수 없습니다.

### 2) 왜 필요한가

코드 생성 요청을 반복하고 기능을 확장하다 보면 앞뒤 스타일이 달라지거나 같은 로직이 여러 곳에 복제될 수 있습니다. 실행에 성공하더라도 다음과 같은 문제가 남을 수 있습니다.

- 경로·임계값 같은 값이 코드 곳곳에 하드코딩됨
- 전역 변수를 여러 함수가 직접 변경함
- 한 함수가 읽기·변환·저장·출력까지 모두 담당함
- 비슷한 로직이 여러 파일에 중복됨
- `data`, `tmp`, `result2`처럼 의미가 약한 이름이 사용됨

### 3) 핵심 흐름 재구성

AI 생성 코드는 다음 순서로 검토하면 빠뜨림을 줄일 수 있습니다.

1. **목적 확인**: 요구한 문제를 실제로 해결하는가?
2. **입출력 확인**: 정상 입력과 빈 입력, 잘못된 입력의 결과가 명확한가?
3. **구조 확인**: 함수가 한 가지 책임에 집중하는가?
4. **중복 확인**: 같은 규칙이 여러 곳에 복사되지 않았는가?
5. **상태 확인**: 전역 변수와 숨은 변경이 과도하지 않은가?
6. **이름 확인**: 변수와 함수가 역할을 설명하는가?
7. **자동 검사**: 포매터와 린터 결과를 확인했는가?
8. **기능 검증**: 대표 입력으로 실행하고 결과를 해석했는가?

### 4) 쉬운 예시

자동 번역문이 문법적으로 자연스럽더라도 제품 용어와 계약 조건까지 정확하다고 단정할 수 없습니다. 분야의 맥락을 아는 사람이 최종 문장을 검토해야 합니다.

AI 코드도 같은 방식으로 봐야 합니다. 자동 검사 결과는 중요한 단서지만, 요구사항과 업무 의미를 아는 개발자의 판단을 대체하지 않습니다.

### 5) 코드 예시

다음 함수는 여러 책임이 섞여 있고 값이 하드코딩되어 있습니다.

```python
def process(items: list[int]) -> None:
    selected = [item for item in items if item >= 70]
    print(",".join(str(item) for item in selected))
```

기준값과 계산, 출력 책임을 분리하면 의도가 더 선명해집니다.

```python
def select_scores(scores: list[int], minimum: int) -> list[int]:
    return [score for score in scores if score >= minimum]


def format_scores(scores: list[int]) -> str:
    return ",".join(str(score) for score in scores)


selected_scores = select_scores([65, 72, 90], minimum=70)
print(format_scores(selected_scores))
```

```text
72,90
```

기준값이 호출부에 드러나고, 선택 로직과 표현 로직을 각각 테스트할 수 있습니다. 다만 함수가 매우 작고 다시 쓰이지 않는 상황이라면 반드시 둘로 나눠야 하는 것은 아닙니다. 분리는 변경 이유와 재사용 필요를 기준으로 판단합니다.

### 6) 헷갈리는 점

긴 함수라고 모두 나쁜 것은 아니며, 짧은 함수라고 모두 좋은 것도 아닙니다. 한 함수가 여러 책임을 섞고 있는지, 이름으로 목적을 설명할 수 있는지, 독립적으로 검증할 수 있는지가 더 중요한 기준입니다.

AI에게 “깨끗하게 고쳐 줘”라고 다시 요청하는 것만으로 검토가 끝나지 않습니다. 수정 결과가 요구사항을 유지하는지 비교하고, 사람이 이해하지 못한 코드는 그대로 반영하지 않아야 합니다.

### 7) 한 줄 정리

> AI 생성 코드의 최종 품질은 자동 수정 횟수가 아니라, 요구사항·구조·실패 흐름을 이해한 사람의 검토로 결정된다.

## 코드로 보기 — 자동 검사와 사람 검토를 한 흐름으로 묶기

```bash
# 자동화 도구가 확인할 영역
black --check service.py
isort --check-only service.py
ruff check service.py

# 기능 확인은 별도로 실행
python service.py
```

검토할 코드:

```python
def summarize(values: list[int], minimum: int) -> str:
    selected = [value for value in values if value >= minimum]
    return f"count={len(selected)}, total={sum(selected)}"


print(summarize([3, 8, 12], minimum=8))
```

```text
count=2, total=20
```

### 코드 목적

스타일·정적 규칙 검사와 기능 결과 확인이 서로 다른 단계임을 보여 줍니다.

### 코드 흐름

1. Black으로 표현 형식이 기준과 맞는지 확인합니다.
2. isort로 import 순서를 확인합니다.
3. Ruff로 정적으로 찾을 수 있는 문제를 확인합니다.
4. 코드를 직접 실행해 대표 입력의 결과를 확인합니다.
5. 마지막으로 함수 이름, 기준값, 빈 입력의 의미를 사람이 검토합니다.

### 실행 결과 해석

입력 `[3, 8, 12]`에서 기준 `8` 이상인 값은 `8`, `12` 두 개이므로 개수는 2, 합은 20입니다. 자동 검사에 진단이 없더라도 “기준 이상”이 업무 요구와 맞는지, 빈 목록에서 `total=0`을 반환하는 정책이 적절한지는 사람이 판단해야 합니다.

### 실무 연결

자동 검사를 코드 작성 직후에 실행하면 단순 스타일 문제를 초기에 줄일 수 있습니다. 리뷰에서는 하드코딩된 정책, 예외 경계, 함수 책임, 실제 출력 의미에 더 집중할 수 있습니다. AI가 초안을 만든 경우에도 같은 품질 게이트를 적용해야 합니다.

1. Black, Ruff, isort의 역할을 각각 한 문장으로 구분해 보세요.
2. `ruff check --fix app.py`가 성공했습니다. 이 결과만으로 기능이 정확하다고 볼 수 없는 이유를 설명해 보세요.
3. AI가 만든 함수에 하드코딩된 경로, 전역 상태 변경, 80줄짜리 처리 흐름, 중복 코드가 함께 있습니다. 어떤 순서로 검토하고 개선할지 제안해 보세요.

<details>
<summary>정답 보기</summary>

1. Black은 코드 형식을 통일하고, Ruff는 정적 규칙 위반과 잠재 문제를 찾으며 일부를 수정하고, isort는 import 문을 정렬합니다.
2. 자동 수정은 Ruff가 알고 있는 규칙 중 안전하게 고칠 수 있는 범위만 처리합니다. 요구사항이 맞는지, 계산 결과가 정확한지, 예외 정책이 적절한지는 실행과 테스트, 사람의 검토가 필요합니다.
3. 먼저 함수의 목적과 입출력 요구를 확인합니다. 그다음 경로와 정책값을 외부에서 주입할 수 있게 만들고, 전역 상태를 매개변수와 반환값으로 바꾸며, 책임이 다른 처리 단계를 분리합니다. 중복 로직은 공통 함수로 모은 뒤 자동 검사와 대표 입력 테스트로 동작을 다시 확인합니다.

</details>

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| 포매터 vs 린터 | 코드 표현을 자동 정리 vs 규칙 위반과 잠재 문제를 진단 |
| Black vs isort | 전체 코드의 형식 통일 vs import 문 정렬에 집중 |
| `ruff check` vs `ruff check --fix` | 문제를 보고만 함 vs 안전하게 고칠 수 있는 일부 항목까지 수정 |
| 자동 검사 통과 vs 기능 정확성 | 설정된 정적 규칙 만족 vs 요구사항과 실행 결과까지 올바름 |
| AI 코드 생성 vs AI 코드 검토 | 초안을 빠르게 만드는 일 vs 맥락·구조·결과를 검증하는 일 |

### 복습 질문 및 답변

**Q1. 포매터를 사용하면 코드 리뷰가 필요 없어지나요?**

<details>
<summary>답</summary>

아닙니다. 포매터는 표현 형식을 통일할 뿐입니다. 계산이 요구사항에 맞는지, 함수 책임이 적절한지, 실패를 안전하게 처리하는지는 리뷰와 테스트가 필요합니다.

</details>

**Q2. 자동 수정 옵션은 언제 특히 조심해야 하나요?**

<details>
<summary>답</summary>

도구를 처음 도입하거나 한 번에 많은 파일을 바꿀 때입니다. 작은 범위에서 변경 내용을 확인하고, 테스트를 실행하며, 팀에서 같은 설정과 실행 순서를 사용해야 합니다.

</details>

**Q3. AI가 만든 코드가 실행도 되고 린터도 통과한다면 무엇을 더 봐야 하나요?**

<details>
<summary>답</summary>

요구한 문제를 실제로 해결하는지, 경계 입력과 실패 흐름이 안전한지, 정책값이 하드코딩되지 않았는지, 함수 책임과 이름이 명확한지, 중복과 전역 상태가 과도하지 않은지 확인해야 합니다.

</details>
