# 프로젝트 설정과 lockfile로 환경 재현하기

> 의존성을 선언하는 문서와 정확한 설치 결과를 잠그는 문서를 나누면, 프로젝트의 의도와 실행 환경을 함께 관리할 수 있다.

`pyproject.toml` · `uv.lock` · `uv init` · `uv add` · `uv sync`

## 핵심요약

- `pyproject.toml`은 프로젝트 정보와 직접 의존성처럼 사람이 관리하는 선언을 담는다.
- `uv.lock`은 선언을 해석해 선택된 직접·전이 의존성의 정확한 버전 조합을 기록한다.
- `uv init`은 프로젝트 기본 구조를 만들고, `uv add`는 직접 의존성을 선언과 잠금 흐름에 추가한다.
- `uv tree`는 의존성 관계를 보여 주고, `uv lock`은 잠금 정보를 갱신하며, `uv sync`는 환경을 잠금 상태와 맞춘다.
- 재현 가능성은 파일 두 개만 보유하는 것이 아니라 같은 파이썬 조건에서 동기화하고 테스트하는 과정까지 포함한다.

## 1. pyproject.toml은 프로젝트의 의도를 선언한다

### 1) 정의

`pyproject.toml`은 파이썬 프로젝트의 메타데이터, 지원 파이썬 버전, 직접 의존성과 도구 설정을 한곳에 표현할 수 있는 표준 설정 파일이다.

프로젝트가 **무엇을 필요로 하는가**를 사람이 읽고 수정할 수 있는 형태로 선언한다는 점이 핵심이다.

### 2) 왜 필요한가

패키지 설치 명령만 터미널 기록에 남으면 다른 사람은 프로젝트가 의도적으로 선택한 의존성을 알기 어렵다. 설정 파일에 직접 의존성을 선언하면 코드와 함께 변경 이력을 검토할 수 있다.

또한 지원 파이썬 범위와 여러 개발 도구의 설정을 프로젝트 단위로 관리하면 팀원마다 다른 설정을 사용하는 문제를 줄일 수 있다.

### 3) 핵심 흐름 재구성

```toml
[project]
name = "sample-service"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "requests>=2.31,<3",
]
```

여기에서 `requests`는 프로젝트가 직접 선택한 의존성이다. `requests`가 필요로 하는 하위 패키지를 모두 직접 나열하지는 않는다. 하위 패키지는 의존성 해결 과정에서 계산되고 잠금 파일에 반영된다.

### 4) 쉬운 예시

건축 설계서에는 “주방에는 싱크대가 필요하다”처럼 필요한 기능을 적는다. 나사 하나하나의 제조 번호까지 설계서에 모두 적지는 않는다. 직접 의존성 선언은 프로젝트가 선택한 큰 부품을 기록하는 설계서와 비슷하다.

### 5) 코드 예시

```bash
# 새 프로젝트의 기본 파일을 만든다.
uv init sample-service

# 프로젝트가 직접 사용하는 패키지를 추가한다.
uv add "requests>=2.31,<3"
```

`uv add`는 단순히 현재 환경에 패키지를 넣는 것에서 끝나지 않고, 프로젝트의 의존성 선언과 잠금 상태를 함께 갱신하는 흐름에 사용된다.

### 6) 헷갈리는 점

`pyproject.toml`의 `dependencies`에 모든 전이 의존성을 수동으로 복사할 필요는 없다. 직접 의존성과 전이 의존성을 섞으면 어떤 패키지를 프로젝트가 실제로 선택했는지 파악하기 어려워진다.

다만 코드에서 전이 의존성을 직접 import해 사용하기 시작했다면, 그것은 더 이상 우연한 하위 의존성에 기대는 것이므로 직접 의존성으로 선언하는 편이 명확하다.

### 7) 한 줄 정리

> `pyproject.toml`은 프로젝트가 직접 선택한 의존성과 실행 조건을 사람이 관리하는 선언 파일이다.

## 2. uv.lock은 해석된 정확한 조합을 기록한다

### 1) 정의

`uv.lock`은 프로젝트의 의존성 조건을 해석한 결과를 기록하는 잠금 파일이다. 직접 의존성뿐 아니라 설치에 필요한 전이 의존성의 정확한 버전과 관계를 담아 같은 조합을 다시 선택할 수 있게 한다.

### 2) 왜 필요한가

`requests>=2.31,<3`처럼 범위를 선언하면 오늘과 다음 달에 조건을 만족하는 최신 후보가 달라질 수 있다. 선언만으로는 두 시점에 같은 버전 조합이 선택된다고 보장하기 어렵다.

잠금 파일은 검증한 해석 결과를 저장해 개발자와 자동 테스트 환경이 같은 조합을 사용할 수 있도록 돕는다.

### 3) 핵심 흐름 재구성

의존성 관리에는 두 층이 있다.

| 층 | 질문 | 대표 파일 |
|---|---|---|
| 선언 | 프로젝트가 어떤 기능과 버전 범위를 요구하는가? | `pyproject.toml` |
| 해석 결과 | 그 조건을 만족하도록 정확히 어떤 버전들이 선택되었는가? | `uv.lock` |

예를 들어 직접 의존성 A가 B를 요구하면 `pyproject.toml`에는 A가 중심적으로 보이고, 잠금 파일에는 선택된 A와 B의 구체적인 버전과 관계가 기록된다.

### 4) 쉬운 예시

레시피에는 “중간 크기 달걀 2개”라고 적을 수 있다. 실제 납품 기록에는 어느 생산 단위의 어떤 제품을 사용했는지 더 정확히 남긴다. 선언 파일은 레시피이고 잠금 파일은 검증된 재료 조합의 납품 기록에 가깝다.

### 5) 코드 예시

```bash
# 현재 프로젝트 선언을 바탕으로 잠금 정보를 생성·갱신한다.
uv lock

# 잠금된 의존성 관계를 사람이 읽기 쉽게 확인한다.
uv tree
```

`uv tree`는 어떤 직접 의존성이 어떤 전이 의존성을 끌어오는지 추적할 때 유용하다. 같은 패키지가 여러 경로에서 요구되거나 충돌이 발생할 때 관계를 먼저 살펴볼 수 있다.

### 6) 헷갈리는 점

잠금 파일은 사람이 직접 버전을 골라 적는 목록이 아니다. 프로젝트 선언과 해결 규칙을 바탕으로 도구가 생성·갱신하는 결과물로 다루는 편이 안전하다.

또한 `uv.lock`과 가상환경은 다르다. 잠금 파일은 재현할 상태를 기록하고, `.venv`는 그 상태를 실제로 설치한 로컬 실행 공간이다.

### 7) 한 줄 정리

> `uv.lock`은 허용 범위를 실제 설치 가능한 정확한 의존성 조합으로 해석한 결과를 보존한다.

## 3. uv 명령으로 프로젝트 생명주기 연결하기

### 1) 정의

uv의 프로젝트 명령은 초기화, 의존성 추가, 관계 확인, 잠금, 환경 동기화를 하나의 흐름으로 연결한다.

| 명령 | 핵심 역할 | 확인할 결과 |
|---|---|---|
| `uv init` | 프로젝트 기본 구조 생성 | 설정 파일과 기본 항목 |
| `uv add` | 직접 의존성 추가 | 선언과 잠금 상태의 변경 |
| `uv tree` | 의존성 트리 표시 | 직접·전이 관계 |
| `uv lock` | 잠금 정보 생성·갱신 | 해석된 버전 조합 |
| `uv sync` | 환경을 프로젝트 상태와 동기화 | `.venv`의 설치 상태 |

### 2) 왜 필요한가

설정 파일을 수정하고 환경을 수동으로 맞추다 보면 선언과 실제 설치 상태가 어긋날 수 있다. 명령의 역할을 구분해 사용하면 어떤 단계에서 변경이 발생했는지 추적하기 쉽다.

### 3) 핵심 흐름 재구성

```bash
# 1. 새 프로젝트 시작
uv init sample-service

# 2. 프로젝트 디렉터리로 이동한 뒤 직접 의존성 추가
uv add "requests>=2.31,<3"

# 3. 의존성 관계 확인
uv tree

# 4. 잠금 정보 확인·갱신
uv lock

# 5. 환경을 선언과 잠금 상태에 맞춤
uv sync
```

일반적인 변경에서는 `uv add`가 필요한 파일 갱신을 함께 처리할 수 있다. `uv lock`은 환경 설치 없이 잠금 상태를 명시적으로 갱신하거나 확인하려는 흐름에서 구분해 이해하면 좋다.

### 4) 쉬운 예시

프로젝트를 여행 준비에 비유하면 `init`은 여행 계획표 만들기, `add`는 준비물 추가, `tree`는 준비물의 구성 관계 확인, `lock`은 최종 준비 목록 확정, `sync`는 실제 가방을 그 목록과 똑같이 맞추는 일이다.

### 5) 코드 예시

```bash
# 다른 개발자가 저장소를 받은 뒤 실행하는 기본 흐름
uv sync
uv run python -m pytest
```

첫 명령은 로컬 환경을 프로젝트 상태와 맞추고, 두 번째 명령은 그 환경에서 테스트를 실행한다.

### 6) 헷갈리는 점

`uv lock`과 `uv sync`는 같은 명령이 아니다. 전자는 설치할 정확한 의존성 해석 결과를 잠금 파일에 반영하는 데 초점이 있고, 후자는 로컬 환경을 그 프로젝트 상태와 맞추는 데 초점이 있다.

`uv tree` 역시 설치나 동기화를 대신하지 않는다. 관계를 읽기 쉽게 보여 주는 진단 도구다.

### 7) 한 줄 정리

> `init → add → tree → lock → sync` 흐름은 프로젝트 선언, 해석 결과, 로컬 환경을 단계별로 연결한다.

## 4. 재현 가능성의 범위와 검증

### 1) 정의

재현 가능성은 다른 개발자나 자동화 환경이 같은 프로젝트 조건에서 같은 의존성 조합을 구성하고, 동일한 검증 절차를 수행할 수 있는 성질이다.

### 2) 왜 필요한가

“내 컴퓨터에서는 된다”는 문제는 코드 차이뿐 아니라 파이썬 버전, 패키지 조합, 운영체제와 환경 설정 차이에서 발생한다. 선언과 잠금 파일은 이 차이 중 의존성 영역을 크게 줄인다.

### 3) 핵심 흐름 재구성

재현 가능한 작업 흐름은 다음 요소를 함께 확인한다.

1. 지원 파이썬 버전이 선언되어 있다.
2. 직접 의존성이 프로젝트 설정에 기록되어 있다.
3. 해석된 정확한 조합이 잠금 파일에 기록되어 있다.
4. 새 환경에서 `uv sync`를 실행한다.
5. 테스트와 최소 실행 확인으로 기능을 검증한다.

이 과정은 같은 입력으로 같은 패키지 상태를 만들 가능성을 높인다. 하지만 데이터베이스, 외부 API, 운영체제 설정과 비밀값 같은 애플리케이션 외부 조건까지 자동으로 재현하는 것은 아니다.

### 4) 쉬운 예시

같은 악보를 가진 연주자도 악기 조율이 다르면 소리가 달라진다. 선언과 잠금 파일은 악보와 조율 기준을 맞추지만, 공연장과 악기의 모든 조건까지 같게 만들지는 않는다. 그래서 최종 리허설에 해당하는 테스트가 필요하다.

### 5) 코드 예시

```bash
# 깨끗한 환경에서 프로젝트 상태 재현
uv sync

# 실제 선택된 의존성 관계 확인
uv tree

# 같은 환경에서 검증
uv run python -m pytest
```

### 6) 헷갈리는 점

잠금 파일이 있으면 테스트가 필요 없다는 생각은 위험하다. 잠금 파일은 패키지 조합을 재현하는 데 도움을 주지만, 코드 로직과 외부 서비스의 동작까지 검증하지는 않는다.

또한 직접 의존성 범위를 바꿨다면 잠금 파일의 변경도 함께 검토해야 한다. 선언과 해석 결과가 왜 바뀌었는지 코드 리뷰에서 확인하는 습관이 중요하다.

### 7) 한 줄 정리

> 재현 가능성은 의존성 상태를 되살리는 것과 그 상태에서 기능을 다시 검증하는 일을 함께 포함한다.

## 코드로 보기 — 새 컴퓨터에서 동일한 프로젝트 환경 만들기

```bash
# 1. 저장소를 받은 뒤 프로젝트 디렉터리에서 환경 동기화
uv sync

# 2. 의존성 관계 확인
uv tree

# 3. 프로젝트 환경과 파이썬 버전 확인
uv run python --version

# 4. 프로젝트 테스트 실행
uv run python -m pytest
```

### 코드 목적

프로젝트 선언과 잠금 정보를 이용해 로컬 환경을 구성하고, 실제 코드가 그 환경에서 동작하는지 확인한다.

### 코드 흐름

1. `uv sync`가 프로젝트 상태에 맞는 로컬 환경을 구성한다.
2. `uv tree`로 직접·전이 의존성 관계를 점검한다.
3. 프로젝트 환경의 파이썬 버전이 선언 범위와 맞는지 확인한다.
4. 테스트를 실행해 의존성 재현이 기능 재현으로 이어지는지 검증한다.

### 실행 결과 해석

동기화가 성공했다면 잠금 상태에 맞는 패키지 설치가 끝난 것이다. 트리에서 예상하지 못한 패키지가 보이면 어떤 직접 의존성이 가져왔는지 위쪽 관계를 확인한다.

파이썬 버전이 선언 범위를 벗어나거나 테스트가 실패하면 환경 구성 성공만으로 완료라고 판단하지 않는다. 실행 조건 또는 코드 호환성을 추가로 점검해야 한다.

### 실무 연결

신규 개발자 온보딩과 자동 테스트에서 동일한 `uv sync`·`uv run` 흐름을 사용하면 수동 설치 순서의 차이를 줄일 수 있다. 의존성을 추가하는 변경에서는 `pyproject.toml`과 `uv.lock`을 함께 리뷰해 의도와 실제 해석 결과를 확인한다.

1. `pyproject.toml`은 프로젝트가 직접 요구하는 의존성과 조건을 선언하고, `uv.lock`은 그 조건을 만족하도록 해석된 직접·전이 의존성의 정확한 버전 조합을 기록한다.
2. `uv lock`은 의존성 선언을 해석해 잠금 상태를 생성·갱신하는 데 초점이 있고, `uv sync`는 로컬 가상환경의 설치 상태를 프로젝트 선언과 잠금 상태에 맞춘다.
3. 프로젝트 환경의 파이썬 버전, 테스트가 요구하는 환경 변수·외부 서비스, 실패한 패키지 API와 코드의 호환성을 확인할 수 있다. 잠금 파일은 의존성 조합을 다루지만 모든 실행 조건을 대신하지 않는다.

</details>

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| 직접 의존성 vs 전이 의존성 | 프로젝트가 명시적으로 선택한 패키지와 그 패키지가 다시 요구하는 하위 패키지의 차이다. |
| `pyproject.toml` vs `uv.lock` | 전자는 사람이 관리하는 요구사항 선언이고, 후자는 도구가 해석한 정확한 버전 조합이다. |
| `uv add` vs `uv pip install` | 전자는 프로젝트 의존성 선언·잠금 흐름을 갱신하고, 후자는 pip 호환 방식으로 현재 환경에 설치한다. |
| `uv lock` vs `uv sync` | 전자는 잠금 정보를 계산·갱신하고, 후자는 로컬 환경을 프로젝트 상태와 맞춘다. |
| `uv tree` vs 잠금 파일 | 트리는 의존성 관계를 사람이 보기 좋게 표시하고, 잠금 파일은 재현할 정확한 해석 결과를 기록한다. |
| 버전 재현 vs 기능 재현 | 같은 패키지 조합을 만드는 것과 실제 서비스가 정상 동작하는지 테스트하는 것은 별도 검증이다. |

### 복습 질문 및 답변

**Q1. 직접 의존성만 선언해도 전이 의존성을 설치할 수 있는 이유는 무엇인가?**

<details>
<summary>답</summary>

의존성 해결 도구가 직접 의존성의 메타데이터를 읽고 필요한 하위 패키지와 버전 조건을 따라가며 전체 설치 조합을 계산하기 때문이다.

</details>

**Q2. 잠금 파일을 직접 편집하기보다 명령으로 갱신하는 편이 좋은 이유는 무엇인가?**

<details>
<summary>답</summary>

잠금 파일은 여러 패키지의 버전 조건과 관계를 도구가 일관되게 계산한 결과다. 사람이 일부만 수정하면 선언과 해석 결과가 어긋나거나 유효하지 않은 조합이 될 수 있다.

</details>

**Q3. 의존성 업그레이드 변경을 리뷰할 때 두 파일을 함께 봐야 하는 이유는 무엇인가?**

<details>
<summary>답</summary>

`pyproject.toml`에서는 개발자가 바꾼 의도와 허용 범위를 확인하고, `uv.lock`에서는 그 변경으로 실제 선택된 직접·전이 패키지 버전을 확인할 수 있기 때문이다. 둘을 함께 봐야 변경 범위와 위험을 판단할 수 있다.

</details>

## 한 줄 정리

> `pyproject.toml`이 프로젝트의 의존성 의도를 선언하고 `uv.lock`이 정확한 해석 결과를 보존하며, `uv sync`와 테스트가 그 상태를 실제 실행 환경으로 검증한다.
