# 코드 컨벤션과 읽기 쉬운 파이썬

> 코드는 컴퓨터가 실행하지만, 코드를 고치고 이어서 만드는 주체는 사람입니다. 같은 동작이라도 읽는 사람이 빠르게 의도를 파악할 수 있게 쓰는 것이 코드 컨벤션의 출발점입니다.

`코드 컨벤션` · `PEP 8` · `가독성` · `일관성` · `유지보수`

## 핵심요약

- 코드 컨벤션은 들여쓰기, 공백, 줄 길이, 이름, import 배치처럼 코드를 표현하는 공통 규칙이다.
- PEP 8은 파이썬 코드를 일관되고 읽기 쉽게 작성할 때 참고할 수 있는 대표적인 스타일 기준이다.
- 좋은 스타일은 실행 결과를 바꾸기보다 코드의 의도와 구조를 더 빠르게 드러낸다.
- 프로젝트 전체에서 같은 규칙을 사용하면 리뷰와 수정에 필요한 해석 비용이 줄어든다.
- 규칙을 기계적으로 지키는 데서 끝나지 않고, 이름과 함수 구조까지 읽기 쉽게 설계해야 한다.

## 1. 코드 컨벤션 — 함께 읽기 위한 공통 문법

### 1) 정의

코드 컨벤션은 한 프로젝트에서 코드를 어떤 모습으로 작성할지 합의한 규칙입니다. 파이썬에서는 다음과 같은 요소가 대표적입니다.

- 들여쓰기에 사용할 공백 수
- 연산자와 쉼표 주변의 공백
- 한 줄에 담을 코드의 길이
- 변수, 함수, 클래스, 상수의 이름 형태
- import 문을 묶고 배열하는 순서
- 함수와 클래스 사이에 둘 빈 줄

문법 오류를 막는 규칙과 코드 컨벤션은 목적이 다릅니다. 문법은 실행 가능 여부를 결정하지만, 컨벤션은 사람이 코드를 얼마나 쉽게 읽고 유지할 수 있는지에 영향을 줍니다.

### 2) 왜 필요한가

혼자 작성한 짧은 스크립트는 작성 직후에는 익숙합니다. 그러나 시간이 지나거나 다른 사람이 코드를 읽으면, 제각각인 스타일이 작은 장애물로 쌓입니다.

코드 컨벤션은 다음 네 가지 효과를 만듭니다.

| 효과 | 의미 |
|---|---|
| 가독성 | 구조와 의도를 빠르게 파악할 수 있다. |
| 유지보수성 | 수정할 위치를 찾기 쉬워지고 실수를 줄일 수 있다. |
| 협업 생산성 | 팀원이 스타일 논쟁보다 로직 검토에 집중할 수 있다. |
| 일관성 | 여러 사람이 작성해도 하나의 코드베이스처럼 읽힌다. |

### 3) 핵심 흐름 재구성

읽기 쉬운 코드는 보통 다음 순서로 점검할 수 있습니다.

1. 들여쓰기로 코드 블록의 경계를 분명히 한다.
2. 공백으로 연산자와 값의 관계를 구분한다.
3. 너무 긴 줄을 나누어 한눈에 읽을 수 있게 한다.
4. import를 성격별로 묶어 의존 관계를 찾기 쉽게 한다.
5. 빈 줄로 서로 다른 역할의 코드 덩어리를 분리한다.
6. 프로젝트 전체에서 같은 기준을 반복 적용한다.

### 4) 쉬운 예시

문장에 띄어쓰기와 문단 구분이 없다면 내용이 맞아도 읽기 어렵습니다. 코드의 공백과 빈 줄도 비슷한 역할을 합니다.

```python
# 의미는 추측할 수 있지만 구조가 잘 보이지 않는 형태
numbers=[82,91,77]
total=sum(numbers)
average=total/len(numbers)

# 관계와 흐름이 눈에 들어오는 형태
numbers = [82, 91, 77]
total = sum(numbers)
average = total / len(numbers)
```

두 코드는 같은 값을 계산합니다. 차이는 컴퓨터의 결과가 아니라 사람이 읽을 때의 속도와 확신입니다.

### 5) 코드 예시

역할이 드러나는 변수와 적절한 공백을 사용해 평균을 계산해 봅니다.

```python
scores = [82, 91, 77]

score_total = sum(scores)
score_count = len(scores)
average_score = score_total / score_count

print(f"평균 점수: {average_score:.2f}")
```

```text
평균 점수: 83.33
```

`score_total`, `score_count`, `average_score`를 차례로 읽으면 계산 의도를 별도 설명 없이 따라갈 수 있습니다.

### 6) 헷갈리는 점

코드 컨벤션을 지켰다고 코드의 로직까지 올바른 것은 아닙니다. 잘 정돈된 코드에도 계산 오류와 잘못된 조건이 있을 수 있습니다.

반대로 한 줄이 권장 길이를 조금 넘었다고 즉시 잘못된 프로그램이 되는 것도 아닙니다. 기준의 목적은 숫자를 맞추는 것이 아니라 읽기 좋은 구조를 만드는 데 있습니다.

### 7) 한 줄 정리

> 코드 컨벤션은 같은 로직을 더 예측 가능한 모습으로 표현해 읽기와 협업의 비용을 줄이는 약속이다.

## 2. PEP 8 핵심 규칙 — 코드의 모양에 기준 세우기

### 1) 정의

PEP 8은 파이썬 코드 스타일을 정리한 대표적인 기준입니다. 프로젝트가 별도 규칙을 두지 않았다면 일관된 스타일을 시작하는 공통 기준으로 활용할 수 있습니다.

### 2) 왜 필요한가

사람마다 선호하는 코드 모양이 다르면 같은 파일 안에서도 스타일이 흔들립니다. 공통 기준이 있으면 “어떤 모양이 더 예쁜가”보다 “이 로직이 정확하고 이해하기 쉬운가”를 검토하는 데 집중할 수 있습니다.

### 3) 핵심 흐름 재구성

#### 들여쓰기: 공백 4칸

파이썬에서 들여쓰기는 스타일인 동시에 코드 블록을 결정하는 문법입니다.

```python
temperature = 27

if temperature >= 25:
    message = "더운 날씨"
else:
    message = "선선한 날씨"

print(message)
```

같은 블록에 속한 문장은 같은 깊이로 맞춥니다. 깊이가 달라지면 실행 흐름도 달라질 수 있습니다.

#### 줄 길이: 79자 이내 권장

한 줄이 지나치게 길면 화면을 좌우로 이동해야 하고, 여러 파일을 나란히 비교하기도 어렵습니다. 긴 호출은 괄호 안에서 의미 단위로 나눌 수 있습니다.

```python
summary = (
    "일관된 스타일은 코드의 동작보다 "
    "사람이 코드를 이해하는 과정에 도움을 줍니다."
)
```

79자는 가독성을 위한 권장 기준입니다. 문자열이나 구조상 나누는 편이 더 어색한 경우까지 무조건 잘라야 한다는 뜻은 아닙니다.

#### 공백: 관계를 보여주는 시각적 구분

연산자 주변과 쉼표 뒤에 공백을 두면 값의 경계가 분명해집니다.

```python
width = 12
height = 5
area = width * height

dimensions = [width, height, area]
print(dimensions)
```

```text
[12, 5, 60]
```

#### import: 성격별로 묶기

import는 일반적으로 표준 라이브러리, 외부 패키지, 프로젝트 내부 모듈 순서로 나누어 읽습니다. 각 그룹 사이에 빈 줄을 두면 코드가 무엇에 의존하는지 더 빨리 찾을 수 있습니다.

```python
# 표준 라이브러리
import json
from pathlib import Path

# 외부 패키지
# import third_party_package

# 프로젝트 내부 모듈
# from project_module import helper
```

주석 처리된 두 줄은 그룹의 위치를 보여주기 위한 예시입니다. 실제 코드에서는 사용하는 모듈만 import합니다.

#### 빈 줄: 역할이 달라지는 지점 표시

함수 정의와 실행 흐름을 분리하면 문서의 문단처럼 구조가 보입니다.

```python
def calculate_average(values: list[int]) -> float:
    return sum(values) / len(values)


scores = [82, 91, 77]
result = calculate_average(scores)
print(f"{result:.2f}")
```

### 4) 쉬운 예시

서랍마다 라벨을 붙이고 같은 종류의 물건을 같은 위치에 보관하면 필요한 물건을 빨리 찾을 수 있습니다. 들여쓰기, import 그룹, 빈 줄은 코드에서 비슷한 길잡이 역할을 합니다.

### 5) 코드 예시

여러 규칙을 한 번에 적용한 짧은 예제입니다.

```python
def calculate_discount(price: int, discount_rate: float) -> int:
    discount = price * discount_rate
    return int(price - discount)


product_price = 20_000
final_price = calculate_discount(product_price, 0.15)

print(f"할인 후 가격: {final_price:,}원")
```

```text
할인 후 가격: 17,000원
```

함수 블록은 공백 4칸으로 들여썼고, 연산자와 인자 사이의 공백을 일정하게 유지했습니다. 실행 부분은 함수 정의와 빈 줄로 분리되어 있습니다.

### 6) 헷갈리는 점

- 공백 4칸은 탭 문자 4개를 뜻하지 않습니다. 한 단계의 들여쓰기에 공백 네 칸을 사용한다는 의미입니다.
- 줄 길이 권장은 모든 문장을 억지로 짧게 쓰라는 뜻이 아닙니다. 이해하기 좋은 단위로 나누는 것이 우선입니다.
- import 순서를 정리해도 사용하지 않는 import가 자동으로 필요한 코드가 되는 것은 아닙니다.
- 공백이 많다고 항상 읽기 쉬운 것은 아닙니다. 관련된 코드는 가까이, 역할이 달라지는 부분은 빈 줄로 나눕니다.

### 7) 한 줄 정리

> PEP 8의 핵심 규칙은 들여쓰기·줄 길이·공백·import·빈 줄을 일정하게 만들어 코드 구조를 눈에 보이게 한다.

## 코드로 보기 — 스타일이 의도를 드러내는 평균 계산기

```python
def calculate_average(values: list[int]) -> float:
    value_total = sum(values)
    value_count = len(values)
    return value_total / value_count


team_scores = [88, 92, 79, 86]
team_average = calculate_average(team_scores)

print(f"인원: {len(team_scores)}명")
print(f"평균: {team_average:.2f}점")
```

### 코드 목적

간단한 평균 계산을 통해 일관된 들여쓰기, 공백, 빈 줄, 의미 있는 이름이 코드 이해에 어떤 도움을 주는지 확인합니다.

### 코드 흐름

1. 숫자 목록을 받는 `calculate_average` 함수를 정의한다.
2. 합계와 개수를 의미 있는 변수에 나누어 저장한다.
3. 합계를 개수로 나눈 값을 반환한다.
4. 네 사람의 점수를 함수에 전달한다.
5. 인원과 평균을 정해진 형식으로 출력한다.

### 실행 결과

```text
인원: 4명
평균: 86.25점
```

### 실행 결과 해석

점수 합계는 345이고 개수는 4이므로 평균은 86.25입니다. 계산은 한 줄로도 작성할 수 있지만, `value_total`과 `value_count`를 두면 계산의 구성 요소가 이름으로 드러납니다.

코드가 길어졌다는 사실만으로 가독성이 나빠지는 것은 아닙니다. 읽는 사람이 중간값의 의미를 확인하거나 디버깅해야 한다면 명시적인 단계가 도움이 됩니다.

### 실무 연결

팀 프로젝트에서는 새로운 기능을 추가하는 시간만큼 기존 코드를 읽는 시간도 중요합니다. 스타일이 일정하면 리뷰에서 공백과 줄바꿈을 일일이 논의하는 대신, 입력값과 반환값, 예외 상황, 계산 로직에 집중할 수 있습니다.

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| 문법 vs 컨벤션 | 문법은 실행 가능 여부를 결정하고, 컨벤션은 코드를 일관되고 읽기 쉽게 표현하는 기준이다. |
| 가독성 vs 짧은 코드 | 가독성은 의도를 쉽게 이해하는 정도이며, 줄 수가 적다고 항상 읽기 쉬운 것은 아니다. |
| 공백 4칸 vs 탭 | 권장 들여쓰기는 한 단계마다 공백 네 칸이며, 탭 문자와 혼용하면 깊이를 오해하기 쉽다. |
| 규칙 준수 vs 로직 정확성 | 스타일이 좋아도 로직 오류는 남을 수 있으므로 동작과 구조를 따로 검토해야 한다. |
| 일관성 vs 개인 취향 | 프로젝트에서는 개인이 선호하는 모양보다 팀이 합의한 한 가지 기준을 계속 적용하는 것이 중요하다. |

소프트웨어는 작성 이후에도 반복해서 읽고 수정합니다. 일관된 스타일은 구조와 의도를 빠르게 파악하게 해 유지보수와 코드 리뷰의 비용을 줄입니다. 다만 들여쓰기처럼 파이썬 문법에 직접 영향을 주는 항목도 있습니다.

</details>

**Q2. PEP 8의 79자 권장을 절대적인 오류 기준으로 보면 안 되는 이유는 무엇인가요?**

<details>
<summary>답</summary>

목적이 숫자 자체가 아니라 가독성이기 때문입니다. 긴 줄을 의미 단위로 나누면 읽기 쉬워지지만, 무리하게 나누어 오히려 흐름을 해친다면 프로젝트 기준과 문맥을 함께 고려해야 합니다.

</details>

**Q3. 스타일이 일정한 코드 리뷰에서는 무엇에 더 집중할 수 있나요?**

<details>
<summary>답</summary>

공백과 줄바꿈 같은 표면적 차이보다 함수의 책임, 입력과 반환, 예외 상황, 계산의 정확성처럼 실제 동작과 설계에 더 집중할 수 있습니다.

</details>

## 한 줄 정리
