# 가상환경과 uv로 프로젝트 격리하기

> 프로젝트마다 독립된 작업실을 만들면, 서로 다른 패키지 버전이 충돌하는 문제를 줄일 수 있다.

`가상환경` · `uv venv` · `uv pip` · `uv run` · `.venv`

## 핵심요약

- 가상환경은 프로젝트별로 파이썬 패키지 설치 공간을 분리한다.
- 분리는 프로젝트 A의 패키지 변경이 프로젝트 B에 영향을 주는 문제를 줄인다.
- `uv venv`는 가상환경을 만들고, `uv pip`는 익숙한 pip 방식으로 그 환경의 패키지를 관리한다.
- `uv run`은 프로젝트 환경에서 명령을 실행해 잘못된 인터프리터를 선택할 가능성을 낮춘다.
- 가상환경 폴더 자체를 공유하기보다 의존성 선언과 잠금 정보를 공유하고 각 컴퓨터에서 다시 만드는 편이 안전하다.

## 1. 가상환경이 필요한 이유

### 1) 정의

가상환경은 특정 프로젝트가 사용할 파이썬 실행 환경과 패키지 설치 위치를 분리한 디렉터리다. 시스템 전체의 파이썬을 복제하는 개념이라기보다, 어떤 인터프리터와 패키지 집합을 사용할지 프로젝트 단위로 경계를 만드는 방식에 가깝다.

일반적으로 프로젝트 루트의 `.venv` 디렉터리를 환경 위치로 사용한다.

### 2) 왜 필요한가

프로젝트 A는 라이브러리 1.x를 요구하고 프로젝트 B는 같은 라이브러리 2.x를 요구할 수 있다. 전역 환경 하나에 둘을 설치하면 한쪽을 업데이트할 때 다른 쪽이 깨질 수 있다.

가상환경을 사용하면 각 프로젝트가 자신의 패키지 조합을 유지할 수 있다. 실험용 설치가 운영 프로젝트에 섞이거나, 내 컴퓨터의 우연한 전역 패키지 덕분에 코드가 실행되는 문제도 줄어든다.

### 3) 핵심 흐름 재구성

가상환경을 사용하는 기본 흐름은 다음과 같다.

1. 프로젝트 디렉터리에서 환경을 만든다.
2. 해당 환경을 활성화하거나 환경을 명시하는 실행 도구를 사용한다.
3. 필요한 패키지를 그 환경에 설치한다.
4. 어떤 파이썬과 패키지가 선택되었는지 확인한다.
5. 코드를 실행하고 테스트한다.

분리의 기준은 “명령을 어디서 입력했는가”만이 아니다. 실제로 어떤 파이썬 실행 파일과 설치 경로가 선택되었는지 확인해야 한다.

### 4) 쉬운 예시

한 책상 위에서 요리와 목공을 동시에 하면 도구가 섞이고 작업물이 손상될 수 있다. 가상환경은 프로젝트별 작업 상자를 따로 준비하는 것과 같다. 상자 안의 도구는 다른 상자에 직접 영향을 주지 않는다.

### 5) 코드 예시

```bash
# 프로젝트 폴더에서 가상환경을 만든다.
uv venv

# 환경의 파이썬 정보를 확인한다.
uv run python -c "import sys; print(sys.executable)"
```

출력 경로에 프로젝트의 `.venv`가 포함되어 있다면 프로젝트 전용 인터프리터가 선택된 것이다. 실제 경로 문자열은 운영체제와 프로젝트 위치에 따라 달라진다.

### 6) 헷갈리는 점

가상환경을 만들었다고 자동으로 모든 명령이 그 환경을 쓰는 것은 아니다. 활성화하지 않은 터미널에서 일반 `python`이나 `pip`를 실행하면 다른 환경을 선택할 수 있다.

그래서 실행 전에 `sys.executable`을 확인하거나, 환경 선택을 명시하는 `uv run`을 사용하는 습관이 유용하다.

### 7) 한 줄 정리

> 가상환경은 프로젝트마다 독립된 패키지 경계를 만들어 버전 충돌과 전역 환경 오염을 줄인다.

## 2. uv venv와 활성화

### 1) 정의

`uv venv`는 프로젝트에서 사용할 가상환경을 생성하는 명령이다. 기본 위치를 사용하면 프로젝트 아래 `.venv`가 만들어진다.

환경을 활성화하면 현재 셸에서 `python`과 관련 명령이 가상환경의 실행 파일을 우선 사용하도록 경로가 조정된다.

### 2) 왜 필요한가

활성화는 반복해서 긴 경로를 입력하지 않고도 같은 환경에서 여러 명령을 실행하게 해 준다. 다만 활성화는 현재 터미널 세션에만 적용되는 편의 기능이므로, 새 터미널에서는 다시 활성화해야 한다.

### 3) 핵심 흐름 재구성

```bash
uv venv
```

운영체제와 셸에 따라 활성화 명령은 다르다.

| 환경 | 활성화 명령 예시 |
|---|---|
| Windows PowerShell | `.venv\Scripts\Activate.ps1` |
| Windows 명령 프롬프트 | `.venv\Scripts\activate.bat` |
| macOS·Linux 셸 | `source .venv/bin/activate` |

활성화 후에는 다음처럼 확인할 수 있다.

```bash
python -c "import sys; print(sys.executable)"
python -m pip --version
```

두 출력이 모두 같은 `.venv`를 가리키는지 확인한다.

### 4) 쉬운 예시

가상환경 생성은 작업실을 새로 마련하는 일이고, 활성화는 현재 들어갈 작업실을 선택하는 일이다. 방을 만들어 놓고 다른 방에서 작업하면 분리 효과를 얻을 수 없다.

### 5) 코드 예시

```powershell
# Windows PowerShell 예시
uv venv
.venv\Scripts\Activate.ps1
python -c "import sys; print(sys.prefix)"
```

실행 정책 때문에 활성화 스크립트를 실행할 수 없는 환경에서는 정책을 무리하게 바꾸기보다 `uv run`으로 명령을 실행할 수 있다.

### 6) 헷갈리는 점

활성화와 환경 생성은 다른 동작이다. `uv venv`는 환경을 만들고, 활성화 스크립트는 현재 터미널이 그 환경을 먼저 찾도록 한다.

또한 `.venv`는 운영체제별 실행 파일과 절대 경로 정보를 포함할 수 있으므로 다른 사람에게 그대로 전달하는 산출물로 보기 어렵다.

### 7) 한 줄 정리

> 환경 생성은 독립 공간을 만들고, 활성화는 현재 터미널이 그 공간을 사용하도록 선택한다.

## 3. uv pip로 패키지 관리하기

### 1) 정의

`uv pip`는 익숙한 pip 명령 형태로 패키지를 설치하고 확인할 수 있게 하는 인터페이스다. 가상환경을 준비한 뒤 패키지를 빠르게 설치하거나 요구사항 파일을 적용할 때 사용할 수 있다.

### 2) 왜 필요한가

기존 pip 중심 작업 흐름을 크게 바꾸지 않고도 uv의 환경 관리와 설치 기능을 사용할 수 있다. 다만 `uv pip install`로 현재 환경을 직접 변경하는 흐름과 프로젝트 의존성을 선언하는 `uv add` 흐름은 목적이 다르다.

### 3) 핵심 흐름 재구성

```bash
uv venv
uv pip install requests
uv pip list
uv pip check
```

- `install`: 패키지를 환경에 설치한다.
- `list`: 현재 환경에 설치된 패키지를 확인한다.
- `check`: 설치된 패키지의 의존성 조건이 맞는지 검사한다.

이 명령들은 환경을 조작한다. 프로젝트 설정 파일에 직접 의존성을 선언하고 잠금 정보를 갱신하는 작업은 [프로젝트 설정과 lockfile로 환경 재현하기](07-pyproject-lockfiles-and-reproducibility.md)의 `uv add` 흐름과 구분해야 한다.

### 4) 쉬운 예시

`uv pip install`은 작업실 선반에 도구를 바로 가져다 놓는 일과 같다. 반면 `uv add`는 필요한 도구를 프로젝트 설계 목록에 기록하고, 함께 사용할 정확한 부품 조합까지 관리하는 흐름에 가깝다.

### 5) 코드 예시

```bash
# 요구사항 파일이 있는 기존 프로젝트의 환경 구성
uv venv
uv pip install -r requirements.txt
uv pip check
```

설치가 끝난 뒤 `check`가 성공하면 선언된 의존성 조건은 만족한다. 하지만 코드의 실제 동작은 테스트로 별도 확인해야 한다.

### 6) 헷갈리는 점

`uv pip install`이 패키지를 설치했다고 해서 프로젝트의 직접 의존성 선언이 자동으로 원하는 형태로 관리된다고 가정하면 안 된다. 환경의 현재 상태와 프로젝트가 공유하는 선언은 구분해서 확인해야 한다.

### 7) 한 줄 정리

> `uv pip`는 pip와 유사한 방식으로 가상환경의 패키지를 설치·점검하는 도구다.

## 4. uv run으로 환경을 명시해 실행하기

### 1) 정의

`uv run`은 프로젝트 환경 안에서 명령을 실행한다. 가상환경 활성화 여부에만 의존하지 않고 실행할 환경을 일관되게 선택하는 데 도움이 된다.

### 2) 왜 필요한가

개발자는 여러 터미널과 여러 프로젝트를 오간다. 프롬프트 표시만 믿고 실행하면 다른 파이썬을 사용하는 실수가 생길 수 있다. `uv run`을 명령 앞에 붙이면 프로젝트 맥락에서 실행한다는 의도를 명확히 표현할 수 있다.

### 3) 핵심 흐름 재구성

```bash
uv run python app.py
uv run python -m pytest
```

첫 번째 명령은 프로젝트 환경에서 애플리케이션을 실행하고, 두 번째 명령은 같은 환경에서 테스트 모듈을 실행한다.

### 4) 쉬운 예시

택배 주소에 건물 이름만 적는 대신 동과 호수까지 적으면 잘못 배송될 가능성이 줄어든다. `uv run`은 실행할 환경을 더 분명하게 지정하는 주소 표기와 비슷하다.

### 5) 코드 예시

```bash
uv run python -c "import sys; print(sys.executable)"
uv run python -c "import requests; print(requests.__version__)"
```

첫 출력은 사용한 인터프리터를, 두 번째 출력은 해당 환경에서 실제로 가져온 패키지 버전을 보여 준다.

### 6) 헷갈리는 점

`uv run`은 코드 오류를 해결하는 명령이 아니다. 올바른 환경을 선택해 실행하도록 돕는 것이므로, 패키지 API 변경이나 애플리케이션 로직 오류는 여전히 테스트와 디버깅으로 해결해야 한다.

### 7) 한 줄 정리

> `uv run`은 프로젝트 환경을 명시해 명령을 실행함으로써 인터프리터 선택 실수를 줄인다.

## 코드로 보기 — 격리된 환경을 만들고 검증하기

```bash
# 1. 프로젝트 전용 환경 생성
uv venv

# 2. 패키지 설치
uv pip install "requests>=2.31,<3"

# 3. 선택된 인터프리터와 패키지 버전 확인
uv run python -c "import sys, requests; print(sys.executable); print(requests.__version__)"

# 4. 의존성 조건 확인
uv pip check
```

### 코드 목적

새 프로젝트에 독립 환경을 만들고, 패키지를 설치한 뒤 실제 실행이 그 환경을 사용하는지 확인한다.

### 코드 흐름

1. `.venv`에 프로젝트 전용 환경을 만든다.
2. 허용 범위 안의 패키지를 해당 환경에 설치한다.
3. 프로젝트 환경에서 파이썬을 실행해 인터프리터와 버전을 출력한다.
4. 설치된 패키지의 의존성 조건을 검사한다.

### 실행 결과 해석

인터프리터 경로에 `.venv`가 보이면 프로젝트 환경이 선택된 것이다. 패키지 버전은 지정한 범위 안에 있어야 한다. `uv pip check`가 오류를 출력하면 충돌한 패키지와 요구 버전을 먼저 확인한다.

명령이 모두 성공해도 실제 서비스 기능이 보장되는 것은 아니다. 마지막으로 프로젝트 테스트나 최소 실행 확인을 수행해야 한다.

### 실무 연결

개발자 로컬 환경, 자동 테스트, 배포 전 검증에서 같은 실행 명령을 사용하면 “어느 파이썬으로 실행했는가”라는 변수를 줄일 수 있다. `.venv`는 저장소에 올려 공유하기보다 각 환경에서 의존성 정보를 바탕으로 재생성한다.

## 직접 해보기

1. 전역 환경에 모든 패키지를 설치할 때 생길 수 있는 문제를 두 가지 적어 보자.
2. `uv venv`와 `uv run`의 역할을 각각 설명해 보자.
3. 터미널에서 실행한 프로그램이 예상과 다른 패키지 버전을 가져왔다. 어떤 명령과 출력부터 확인할지 순서를 정해 보자.

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| 가상환경 생성 vs 활성화 | 생성은 독립 패키지 공간을 만들고, 활성화는 현재 터미널이 그 공간을 먼저 사용하게 한다. |
| 전역 환경 vs 프로젝트 환경 | 전역 환경은 여러 작업이 공유하지만 프로젝트 환경은 특정 프로젝트에 필요한 패키지를 분리한다. |
| `uv pip install` vs `uv add` | 전자는 현재 환경에 패키지를 설치하는 pip 호환 흐름이고, 후자는 프로젝트 의존성 선언과 잠금 흐름까지 연결한다. |
| 활성화 후 실행 vs `uv run` | 활성화는 현재 셸의 경로를 바꾸고, `uv run`은 프로젝트 환경에서 실행할 의도를 명령에 직접 표현한다. |
| `.venv` 공유 vs 환경 재생성 | 가상환경 폴더를 복사하기보다 선언·잠금 정보를 공유하고 각 컴퓨터에서 다시 만드는 편이 이식성이 높다. |

### 복습 질문 및 답변

**Q1. 가상환경은 왜 프로젝트 폴더마다 따로 만드는가?**

<details>
<summary>답</summary>

프로젝트별 패키지와 버전 요구를 분리해 한 프로젝트의 설치·업데이트가 다른 프로젝트를 깨뜨리는 일을 줄이기 위해서다.

</details>

**Q2. 활성화하지 않고도 `uv run`을 사용할 수 있는 이유는 무엇인가?**

<details>
<summary>답</summary>

`uv run`이 프로젝트 맥락에서 사용할 환경을 선택해 명령을 실행하기 때문이다. 현재 셸의 경로 변경에만 의존하지 않는다.

</details>

**Q3. `.venv`를 저장소에 그대로 올리는 것보다 재생성하는 편이 나은 이유는 무엇인가?**

<details>
<summary>답</summary>

가상환경에는 운영체제별 실행 파일과 로컬 경로가 포함될 수 있어 다른 컴퓨터로 옮겼을 때 동작을 보장하기 어렵다. 의존성 선언과 잠금 정보를 공유하고 각 환경에서 다시 만들면 이식성과 검증 가능성이 높아진다.

</details>

## 한 줄 정리

> 가상환경은 프로젝트의 패키지 경계를 만들고, `uv venv`·`uv pip`·`uv run`은 그 환경의 생성·설치·실행을 일관된 흐름으로 연결한다.
