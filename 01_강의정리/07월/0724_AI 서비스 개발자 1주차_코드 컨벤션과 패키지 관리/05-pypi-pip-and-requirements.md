# PyPI, pip, requirements.txt로 의존성 관리하기

> 내 컴퓨터에서만 실행되는 코드를 팀의 실행 가능한 프로젝트로 바꾸려면, 어떤 패키지를 어떻게 설치했는지 기록해야 한다.

`PyPI` · `pip` · `의존성` · `requirements.txt` · `버전 제약`

## 핵심요약

- PyPI는 파이썬 패키지를 찾고 배포하는 저장소이고, pip는 저장소에서 패키지를 설치하는 도구다.
- 프로젝트가 직접 사용하는 패키지뿐 아니라 그 패키지가 다시 요구하는 전이 의존성도 함께 설치된다.
- `requirements.txt`는 필요한 패키지와 버전 제약을 텍스트로 기록해 설치 명령을 반복 가능하게 만든다.
- `==`는 버전을 고정하고, `>=`는 최소 버전을 허용하므로 안정성과 유연성의 균형이 달라진다.
- 패키지 목록만 같아도 운영체제와 파이썬 버전이 다르면 결과가 달라질 수 있으므로 실행 환경까지 함께 관리해야 한다.

## 1. PyPI와 pip의 역할

### 1) 정의

PyPI는 다른 개발자가 공개한 파이썬 패키지와 버전 정보를 모아 둔 저장소다. pip는 사용자가 요청한 패키지를 찾아 내려받고 현재 파이썬 환경에 설치하는 명령행 도구다.

둘은 같은 것이 아니다. 쇼핑몰 비유로 보면 PyPI는 상품 목록과 상품을 보관하는 매장이고, pip는 주문서를 읽어 필요한 상품을 가져오는 배송 담당자에 가깝다.

### 2) 왜 필요한가

서비스를 만들 때 HTTP 요청, 데이터 처리, 테스트 같은 기능을 매번 처음부터 구현하면 시간이 많이 들고 오류 위험도 커진다. 검증된 패키지를 활용하면 핵심 비즈니스 로직에 집중할 수 있다.

다만 외부 패키지를 추가하는 순간 프로젝트는 그 버전과 하위 의존성에 영향을 받는다. 따라서 설치 자체보다 **무엇을 왜 설치했는지 기록하는 일**이 중요하다.

### 3) 핵심 흐름 재구성

패키지 설치는 보통 다음 순서로 진행된다.

1. 개발자가 설치할 패키지와 필요하면 버전 범위를 지정한다.
2. pip가 패키지 메타데이터를 확인한다.
3. 요청한 패키지가 필요로 하는 다른 패키지까지 계산한다.
4. 현재 운영체제와 파이썬 버전에 맞는 배포 파일을 선택한다.
5. 계산된 패키지를 현재 환경에 설치한다.

이때 사용자가 직접 선택한 패키지를 **직접 의존성**, 그 패키지가 내부적으로 요구하는 패키지를 **전이 의존성**이라고 한다.

### 4) 쉬운 예시

웹 API를 호출하려고 패키지 A를 하나 설치했다고 하자. 패키지 A가 문자 인코딩 처리용 패키지 B와 인증서 처리용 패키지 C를 필요로 한다면, pip는 A뿐 아니라 B와 C도 함께 설치한다.

사용자는 하나를 주문했지만 실제 실행 환경에는 여러 패키지가 들어간다. 이 구조를 모르고 A만 기록하면 다른 컴퓨터에서 세부 버전이 달라질 수 있다.

### 5) 코드 예시

```bash
# 현재 선택된 파이썬 인터프리터의 pip를 사용한다.
python -m pip install "requests==2.32.3"

# 설치된 패키지의 정보와 의존성을 확인한다.
python -m pip show requests

# 현재 환경의 설치 목록을 확인한다.
python -m pip list
```

`python -m pip` 형식은 `pip` 명령이 가리키는 파이썬과 실제 실행할 파이썬이 달라지는 실수를 줄이는 데 도움이 된다.

### 6) 헷갈리는 점

PyPI에 패키지가 있다는 사실과 그 패키지가 현재 프로젝트에 적합하다는 사실은 다르다. 이름이 비슷한 패키지를 잘못 설치할 수도 있고, 최신 버전이 기존 코드와 호환되지 않을 수도 있다.

설치 전에는 패키지 이름, 유지보수 상태, 지원 파이썬 버전, 라이선스와 보안 공지를 확인하는 습관이 필요하다.

### 7) 한 줄 정리

> PyPI는 패키지를 제공하고, pip는 요청한 패키지와 필요한 의존성을 현재 파이썬 환경에 설치한다.

## 2. 의존성과 버전 제약

### 1) 정의

의존성은 내 프로그램이 실행되기 위해 필요한 외부 패키지다. 버전 제약은 사용할 수 있는 패키지 버전의 범위를 표현한다.

```text
requests==2.32.3   # 정확히 이 버전
requests>=2.31.0   # 이 버전 이상
requests<3.0       # 3.0 미만
requests>=2.31,<3  # 최소·최대 범위를 함께 지정
```

### 2) 왜 필요한가

버전을 전혀 지정하지 않으면 설치 시점의 최신 버전이 선택될 수 있다. 새 버전에서 함수 동작이나 지원 범위가 바뀌면 어제 실행되던 코드가 오늘 실패할 수 있다.

반대로 모든 버전을 영원히 고정하면 보안 수정과 기능 개선을 받기 어렵다. 개발 단계에서는 허용 범위를 설계하고, 배포 단계에서는 검증된 조합을 재현하는 식으로 목적을 나누어 생각해야 한다.

### 3) 핵심 흐름 재구성

버전 선택은 다음 질문으로 판단할 수 있다.

| 질문 | 판단 기준 |
|---|---|
| 정확히 같은 환경이 중요한가? | 검증한 버전을 고정한다. |
| 호환되는 수정 버전을 허용할 수 있는가? | 상한과 하한을 함께 둔다. |
| 새 버전을 도입해도 되는가? | 테스트를 통과한 뒤 범위를 조정한다. |
| 충돌이 발생했는가? | 직접·전이 의존성의 요구 범위를 함께 확인한다. |

예를 들어 패키지 A는 C의 1.x를 요구하고 패키지 B는 C의 2.x만 요구한다면, 두 조건을 동시에 만족하는 버전이 없어 설치가 실패할 수 있다. 이것이 의존성 충돌이다.

### 4) 쉬운 예시

휴대전화 충전 규격을 떠올려 보자. 장치 A는 규격 1만 지원하고 장치 B는 규격 2만 지원하는데, 충전기가 하나뿐이라면 두 장치를 동시에 만족시키기 어렵다. 패키지 버전 충돌도 서로 양립할 수 없는 요구 조건이 만난 상황이다.

### 5) 코드 예시

```bash
# 호환 가능한 범위를 지정한다.
python -m pip install "requests>=2.31,<3"

# 설치 과정이 바꾼 패키지까지 포함해 환경을 점검한다.
python -m pip check
```

`pip check`가 문제를 보고하지 않는다면 설치된 패키지들이 선언한 의존성 조건을 현재 환경이 만족한다는 뜻이다. 그렇다고 애플리케이션 기능까지 모두 정상이라는 의미는 아니므로 테스트는 별도로 필요하다.

### 6) 헷갈리는 점

`>=`는 최신 버전을 항상 설치한다는 뜻이 아니다. 다른 패키지의 조건과 현재 해석 가능한 후보를 함께 고려한 뒤 조건을 만족하는 버전이 선택된다.

또한 버전 번호가 높다고 내 코드와 반드시 호환되는 것은 아니다. 의존성 해결과 애플리케이션 호환성 검증은 서로 다른 단계다.

### 7) 한 줄 정리

> 버전 제약은 업데이트 가능 범위와 재현 가능성 사이의 경계를 정하는 규칙이다.

## 3. requirements.txt로 설치 목록 기록하기

### 1) 정의

`requirements.txt`는 pip가 읽을 수 있는 패키지 요구사항 목록이다. 한 줄에 하나씩 패키지와 버전 조건을 기록하고, `-r` 옵션으로 한 번에 설치한다.

```text
requests==2.32.3
pytest>=8.0,<9
```

### 2) 왜 필요한가

구두로 “필요한 패키지를 설치해 주세요”라고 전달하면 패키지가 빠지거나 버전이 달라지기 쉽다. 요구사항 파일을 저장소에 함께 두면 팀원과 배포 환경이 같은 설치 명령을 사용할 수 있다.

### 3) 핵심 흐름 재구성

```bash
# 기록된 요구사항을 현재 환경에 설치한다.
python -m pip install -r requirements.txt

# 현재 환경의 정확한 설치 목록을 표준 출력으로 확인한다.
python -m pip freeze
```

`pip freeze` 결과는 현재 환경의 스냅샷이다. 직접 추가한 패키지와 전이 의존성이 함께 나타날 수 있으므로, 그 결과 전체가 프로젝트 설계 의도를 설명해 주는 것은 아니다.

### 4) 쉬운 예시

레시피에는 “파스타 면”처럼 직접 고른 재료가 적힌다. 실제 조리대에는 면을 만드는 데 쓰인 세부 원료까지 놓일 수 있다. 요구사항 파일을 설계 문서로 관리할지, 검증된 환경의 전체 스냅샷으로 관리할지 팀에서 기준을 정해야 한다.

### 5) 코드 예시

```text
# requirements.txt
requests==2.32.3
pytest==8.3.3
```

```bash
python -m pip install -r requirements.txt
python -m pip check
python -m pytest
```

설치 성공은 첫 번째 확인이고, 의존성 조건 확인은 두 번째 확인이며, 프로젝트 테스트 통과는 세 번째 확인이다. 세 단계를 구분하면 “설치는 됐지만 서비스가 깨지는” 문제를 줄일 수 있다.

### 6) 헷갈리는 점

`requirements.txt`에 버전을 정확히 적었다고 해서 운영체제, CPU 종류, 파이썬 버전까지 자동으로 같아지는 것은 아니다. 패키지에 따라 환경별 배포 파일과 하위 의존성이 달라질 수 있다.

또한 요구사항 파일은 설치 목록 형식이지 프로젝트의 이름, 빌드 방식, 도구 설정을 모두 담는 통합 설정 파일은 아니다. 통합 프로젝트 설정과 잠금 파일의 역할은 [프로젝트 설정과 lockfile로 환경 재현하기](07-pyproject-lockfiles-and-reproducibility.md)에서 이어서 살펴본다.

### 7) 한 줄 정리

> `requirements.txt`는 pip 설치 요구사항을 공유하지만, 전체 실행 환경 재현에는 추가 정보와 검증이 필요하다.

## 코드로 보기 — 새 환경에서 요구사항 설치 검증하기

```bash
# 1. 프로젝트 전용 환경을 준비한 뒤 실행한다.
python -m pip install -r requirements.txt

# 2. 선언된 의존성 조건의 충돌 여부를 확인한다.
python -m pip check

# 3. 실제 프로그램 또는 테스트를 실행한다.
python -m pytest
```

### 코드 목적

패키지 설치를 성공 여부 하나로 판단하지 않고, 의존성 무결성과 애플리케이션 동작을 단계별로 확인한다.

### 코드 흐름

1. 요구사항 파일에 기록된 패키지를 설치한다.
2. 설치된 패키지의 의존성 조건이 맞는지 검사한다.
3. 프로젝트 테스트로 실제 기능 호환성을 확인한다.
4. 실패하면 설치 로그와 충돌 패키지, 테스트 오류를 구분해 원인을 좁힌다.

### 실행 결과 해석

설치 명령이 성공하고 `pip check`가 문제를 보고하지 않더라도 테스트가 실패할 수 있다. 이 경우 패키지 메타데이터상의 조건은 맞지만 코드가 기대하는 API와 실제 버전의 동작이 다를 가능성이 있다.

반대로 설치 단계에서 충돌이 발생하면 애플리케이션 코드를 보기 전에 버전 조건부터 정리해야 한다.

### 실무 연결

신규 개발자의 환경 구성, 자동 테스트 서버, 배포 이미지 생성 과정에서 같은 설치 절차를 사용하면 환경 차이를 조기에 발견할 수 있다. 중요한 것은 명령을 복사하는 것이 아니라 각 단계가 무엇을 검증하는지 아는 것이다.

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| PyPI vs pip | PyPI는 패키지 저장소이고, pip는 패키지 설치 도구다. |
| 직접 의존성 vs 전이 의존성 | 직접 의존성은 프로젝트가 명시적으로 선택한 패키지이고, 전이 의존성은 그 패키지가 다시 요구하는 패키지다. |
| `pip list` vs `pip freeze` | `pip list`는 사람이 보기 좋은 설치 목록이고, `pip freeze`는 요구사항 형식의 환경 스냅샷을 출력한다. |
| 설치 성공 vs 실행 성공 | 설치 성공은 패키지 배치가 끝났다는 뜻이고, 실행 성공은 실제 코드와 테스트까지 호환된다는 뜻이다. |
| 요구사항 목록 vs 실행 환경 | 패키지 목록은 환경의 일부일 뿐이며 파이썬·운영체제 등의 조건까지 자동으로 고정하지 않는다. |

### 복습 질문 및 답변

**Q1. 패키지 하나만 설치했는데 여러 패키지가 함께 설치되는 이유는 무엇인가?**

<details>
<summary>답</summary>

요청한 패키지가 실행을 위해 다른 패키지를 요구하기 때문이다. pip는 이 전이 의존성의 조건까지 계산해 함께 설치한다.

</details>

**Q2. `pip freeze` 결과를 그대로 프로젝트의 설계 의도라고 보기 어려운 이유는 무엇인가?**

<details>
<summary>답</summary>

현재 환경에 우연히 설치된 도구와 전이 의존성까지 모두 포함될 수 있기 때문이다. 환경 스냅샷으로는 유용하지만, 프로젝트가 직접 선택한 의존성을 별도로 이해해야 한다.

</details>

**Q3. 정확한 버전 고정만으로 완전한 재현이 보장되지 않는 이유는 무엇인가?**

<details>
<summary>답</summary>

같은 패키지 버전이어도 파이썬 버전, 운영체제, 하드웨어와 환경 변수에 따라 선택되는 배포 파일이나 실행 결과가 달라질 수 있기 때문이다. 버전 기록과 함께 실행 조건과 테스트가 필요하다.

</details>

## 한 줄 정리

> 패키지 관리는 설치 명령을 외우는 일이 아니라, 의존성의 출처와 버전 조건을 기록하고 다른 환경에서도 같은 검증 절차를 반복할 수 있게 만드는 일이다.
