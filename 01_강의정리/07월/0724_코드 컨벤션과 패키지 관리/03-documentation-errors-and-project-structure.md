# 주석·문서화·예외 처리와 프로젝트 구조

> 읽기 좋은 코드는 정상 동작만 설명하지 않습니다. 왜 이런 선택을 했는지, 실패하면 무엇을 해야 하는지, 기능이 어디에 놓여 있는지까지 다음 개발자가 찾을 수 있게 합니다.

`comment` · `docstring` · `exception handling` · `module` · `project structure`

## 핵심요약

- 주석은 코드가 이미 보여 주는 동작보다 **그 선택을 한 이유와 제약**을 설명할 때 가치가 크다.
- docstring은 함수나 모듈의 목적, 입력, 반환값, 발생 가능한 실패를 사용자의 관점에서 기록한다.
- 예외는 가능한 한 구체적인 타입으로 잡고, 복구할 수 있는 경우에만 처리하며, 맥락이 드러나는 메시지를 남긴다.
- 프로젝트는 역할별 파일, 공통 기능, 설정, 실행 코드, 테스트 코드를 분리해 변경 영향 범위를 줄인다.
- 문서와 구조는 코드를 대신하지 않으며, 이름과 함수가 먼저 이해하기 쉬워야 한다.

## 1. 주석과 docstring

### 1) 정의

주석(comment)은 특정 코드 옆에서 구현 의도나 제약을 설명하는 짧은 메모입니다. docstring은 함수·클래스·모듈 바로 아래에 적어, 그 구성 요소를 **어떻게 사용해야 하는지** 설명하는 문자열입니다.

둘의 역할은 비슷해 보이지만 독자가 다릅니다.

| 구분 | 주로 답하는 질문 | 적합한 내용 |
|---|---|---|
| 주석 | 왜 이렇게 구현했는가? | 선택 이유, 예외적인 규칙, 외부 제약 |
| docstring | 이 기능을 어떻게 사용하는가? | 목적, 매개변수, 반환값, 예외 |

### 2) 왜 필요한가

코드는 실행 방법은 보여 주지만 배경까지 모두 말해 주지는 않습니다. 예를 들어 특정 임계값을 사용한 이유, 빈 입력을 허용하지 않는 이유, 실패했을 때 호출자가 무엇을 해야 하는지는 문법만 보고 알기 어렵습니다.

다만 설명이 많다고 항상 좋은 것은 아닙니다. 다음처럼 코드와 똑같은 내용을 되풀이하는 주석은 변경될 때 쉽게 낡습니다.

```python
count += 1  # count를 1 증가시킨다
```

이 경우에는 주석을 지우는 편이 낫습니다. 반대로 선택의 이유를 남기면 유지보수에 도움이 됩니다.

```python
# 외부 시스템이 한 번에 100개까지만 받으므로 묶음을 제한한다.
batch_size = 100
```

### 3) 핵심 흐름 재구성

문서화는 다음 순서로 접근하면 과해지지 않습니다.

1. 변수와 함수 이름만으로 기본 동작이 읽히게 작성합니다.
2. 함수가 외부에서 사용된다면 docstring으로 사용 계약을 적습니다.
3. 코드만으로 알기 어려운 선택 이유와 제약만 주석으로 보완합니다.
4. 구현을 바꾸면 관련 설명도 함께 확인합니다.

여기서 **사용 계약**은 입력으로 무엇을 받고, 무엇을 돌려주며, 어떤 실패가 가능한지를 뜻합니다. docstring은 구현의 모든 줄을 번역하는 문서가 아니라 호출자가 안전하게 사용할 수 있도록 경계를 알려 주는 문서입니다.

### 4) 쉬운 예시

엘리베이터 버튼을 생각해 봅시다. 버튼에 층수가 적혀 있으면 눌렀을 때 어디로 가는지 알 수 있습니다. 이것이 좋은 이름의 역할입니다.

“화재 시 사용 금지” 같은 안내는 버튼의 동작만 보고는 알 수 없는 제약입니다. 이것이 주석에 가까운 역할입니다. 사용 가능 인원과 비상 동작을 정리한 안내문은 기능 전체의 사용법을 알려 주므로 docstring에 가깝습니다.

### 5) 코드 예시

```python
def normalize_tags(tags: list[str]) -> list[str]:
    """태그의 공백을 정리하고 중복을 제거한다.

    Args:
        tags: 정리할 태그 문자열 목록.

    Returns:
        처음 등장한 순서를 유지한 태그 목록.
    """
    cleaned: list[str] = []
    seen: set[str] = set()

    for tag in tags:
        normalized = tag.strip().lower()
        if normalized and normalized not in seen:
            seen.add(normalized)
            cleaned.append(normalized)

    return cleaned


print(normalize_tags([" Python ", "API", "python", " "]))
```

```text
['python', 'api']
```

함수 이름과 변수 이름이 동작을 대부분 설명하므로 줄마다 주석을 달지 않았습니다. 대신 docstring에는 입력과 반환값의 의미를 적었습니다. 결과를 보면 공백과 대소문자가 정리되고, 처음 등장한 순서를 유지하면서 중복이 사라졌습니다.

### 6) 헷갈리는 점

docstring이 있다고 해서 함수 이름이 모호해도 되는 것은 아닙니다. `do_it()` 같은 이름에 긴 설명을 붙이는 것보다 `normalize_tags()`처럼 목적을 드러내는 이름을 먼저 선택해야 합니다.

또한 타입 힌트는 값의 형태를 알려 주지만 의미까지 설명하지 않습니다. `list[str]`만으로는 빈 문자열을 허용하는지, 중복을 유지하는지 알 수 없으므로 필요한 사용 규칙은 docstring에 보완합니다.

### 7) 한 줄 정리

> 좋은 문서화는 코드를 번역하지 않고, 코드만으로 알기 어려운 이유와 사용 계약을 보완한다.

## 2. 예외를 구체적으로 다루기

### 1) 정의

예외(exception)는 프로그램이 정상 흐름을 계속할 수 없을 때 발생하는 신호입니다. 예외 처리는 실패를 무조건 숨기는 기술이 아니라, **예상 가능한 실패를 구분하고 복구하거나 호출자에게 명확하게 전달하는 과정**입니다.

### 2) 왜 필요한가

모든 예외를 한꺼번에 잡으면 프로그램이 멈추지 않는 것처럼 보일 수 있습니다. 하지만 실제 원인이 파일 부재인지, 권한 문제인지, 데이터 형식 오류인지 알 수 없게 됩니다.

따라서 다음 원칙이 중요합니다.

- 예상하는 예외 타입을 구체적으로 적습니다.
- 복구 방법이 있을 때만 그 자리에서 처리합니다.
- 처리하지 못하면 의미 있는 맥락을 붙여 다시 알립니다.
- 오류 메시지에는 작업 대상과 실패 이유를 이해할 단서를 남깁니다.
- 진단이 필요한 서비스에서는 로그를 통해 발생 위치와 원인을 추적합니다.

### 3) 핵심 흐름 재구성

예외 처리의 판단 흐름은 다음과 같습니다.

```text
실패 가능 작업
  ├─ 예상한 실패인가? ─ 아니오 → 상위 호출자에게 전달
  └─ 예
      ├─ 지금 복구 가능한가? ─ 예 → 대체 흐름 실행
      └─ 아니오 → 맥락 있는 메시지와 함께 전달
```

`except:`처럼 타입을 생략한 처리는 원인과 무관한 오류까지 삼킬 수 있습니다. 반면 `FileNotFoundError`, `ValueError`처럼 구체적인 예외를 사용하면 실패의 의미가 코드에 드러납니다.

### 4) 쉬운 예시

택배가 도착하지 않았을 때 “문제가 생겼습니다”라고만 말하면 무엇을 해야 할지 알기 어렵습니다. 주소 오류인지, 수령인이 부재중인지, 물류가 지연됐는지 알려 줘야 다음 행동을 정할 수 있습니다.

예외 타입은 실패의 분류이고, 예외 메시지는 그 상황의 구체적인 설명입니다. 둘이 함께 있어야 복구와 디버깅이 쉬워집니다.

### 5) 코드 예시

```python
from pathlib import Path


def load_keywords(path: Path) -> list[str]:
    """텍스트 파일에서 비어 있지 않은 키워드를 읽는다."""
    try:
        text = path.read_text(encoding="utf-8")
    except FileNotFoundError:
        print(f"키워드 파일을 찾지 못했습니다: {path.name}")
        return []
    except UnicodeDecodeError as error:
        raise ValueError("키워드 파일은 UTF-8 텍스트여야 합니다.") from error

    return [line.strip() for line in text.splitlines() if line.strip()]
```

파일이 없을 때는 빈 목록으로 복구할 수 있다고 판단해 처리합니다. 인코딩이 잘못된 경우에는 임의로 데이터를 해석하지 않고, 호출자가 입력을 고칠 수 있도록 의미 있는 오류로 전달합니다.

### 6) 헷갈리는 점

예외를 잡았다고 해서 항상 `return []` 같은 기본값을 돌려줘야 하는 것은 아닙니다. 빈 목록이 “데이터가 없음”을 뜻하는지 “읽기에 실패함”을 뜻하는지 구분되지 않으면 더 큰 오류를 만들 수 있습니다.

복구 가능한 경우에만 대체값을 사용하고, 그렇지 않다면 실패를 명확하게 드러내는 편이 안전합니다.

### 7) 한 줄 정리

> 예외 처리는 오류를 감추는 장치가 아니라, 실패 원인을 구분하고 다음 행동을 결정하는 경계다.

## 3. 역할이 드러나는 프로젝트 구조

### 1) 정의

프로젝트 구조는 기능별 코드, 설정, 실행 진입점, 테스트, 설명 문서를 역할에 맞게 배치하는 규칙입니다. 파일이 많아져도 “어디를 읽고 어디를 수정해야 하는가”를 예측할 수 있게 하는 것이 목적입니다.

### 2) 왜 필요한가

하나의 실행 파일에 데이터 읽기, 처리, 출력, 설정값, 테스트 코드가 모두 섞이면 작은 수정도 전체 파일에 영향을 줍니다. 역할을 분리하면 다음 이점이 있습니다.

- 반복 기능을 모듈로 재사용할 수 있습니다.
- 실행 흐름은 짧고 명확하게 유지할 수 있습니다.
- 설정값을 한곳에서 관리할 수 있습니다.
- 기능 코드와 검증 코드를 독립적으로 바꿀 수 있습니다.
- 새 팀원이 필요한 위치를 빠르게 찾을 수 있습니다.

### 3) 핵심 흐름 재구성

작은 프로젝트는 다음처럼 시작할 수 있습니다.

```text
sample_project/
├── src/
│   ├── text_service.py
│   └── file_utils.py
├── config/
│   └── settings.py
├── scripts/
│   └── run.py
├── tests/
│   └── test_text_service.py
└── README.md
```

- `src/`: 핵심 기능과 재사용 가능한 모듈
- `config/`: 경로·옵션·상수처럼 함께 관리할 설정
- `scripts/`: 여러 기능을 조합해 실제 작업을 시작하는 코드
- `tests/`: 기능의 기대 동작을 검증하는 코드
- `README.md`: 프로젝트 목적과 사용 흐름을 설명하는 문서

이 구조가 모든 프로젝트의 정답은 아닙니다. 규모가 작다면 폴더 수를 줄일 수 있고, 역할이 늘어날 때 필요한 경계를 추가하면 됩니다. 중요한 것은 폴더를 많이 만드는 것이 아니라 **변경 이유가 다른 코드를 분리하는 것**입니다.

### 4) 쉬운 예시

주방에서 식재료, 조리 도구, 주문서, 완성된 음식을 한 상자에 섞어 두면 필요한 것을 찾기 어렵습니다. 보관 목적에 따라 위치를 나누면 담당자가 달라도 같은 흐름으로 일할 수 있습니다.

프로젝트 구조도 마찬가지입니다. 핵심 로직과 설정, 실행 코드, 테스트를 분리하면 각 파일이 한 가지 역할에 집중합니다.

### 5) 코드 예시

```python
# src/text_service.py
def count_words(text: str) -> int:
    """공백으로 구분된 단어 수를 반환한다."""
    return len(text.split())


# scripts/run.py
from src.text_service import count_words

sample = "small modules are easier to test"
print(count_words(sample))
```

```text
6
```

핵심 계산은 `src`의 모듈이 담당하고, 실행 파일은 입력을 준비해 함수를 호출하고 결과를 보여 주는 역할만 합니다. 이렇게 나누면 `count_words()`를 별도 테스트에서 직접 검증하기 쉽습니다.

### 6) 헷갈리는 점

파일을 잘게 쪼개는 것 자체가 모듈화는 아닙니다. 서로 강하게 의존하는 두 줄짜리 파일이 수십 개 생기면 오히려 흐름을 찾기 어렵습니다.

함께 바뀌는 코드는 가까이 두고, 다른 이유로 바뀌는 코드는 분리하는 것이 기준입니다. 실행 파일을 짧게 만든다는 이유로 모든 로직을 의미 없는 보조 함수로 나누는 것도 피해야 합니다.

### 7) 한 줄 정리

> 좋은 프로젝트 구조는 파일 개수를 늘리는 규칙이 아니라, 변경 이유와 책임이 다른 코드를 찾기 쉽게 나누는 약속이다.

## 코드로 보기 — 문서화와 구체적 예외 처리를 함께 적용하기

```python
from pathlib import Path


def read_unique_names(path: Path) -> list[str]:
    """UTF-8 텍스트에서 중복되지 않은 이름을 읽는다.

    Args:
        path: 한 줄에 이름 하나가 저장된 파일 경로.

    Returns:
        공백과 빈 줄을 제거한 이름 목록.

    Raises:
        ValueError: 파일이 UTF-8 텍스트가 아닐 때.
    """
    try:
        raw_text = path.read_text(encoding="utf-8")
    except FileNotFoundError:
        return []
    except UnicodeDecodeError as error:
        raise ValueError("입력 파일의 문자 인코딩을 확인하세요.") from error

    names = (line.strip() for line in raw_text.splitlines())
    return list(dict.fromkeys(name for name in names if name))
```

### 코드 목적

함수 이름과 docstring으로 사용법을 드러내고, 예상 가능한 두 실패를 서로 다르게 처리하는 예제입니다.

### 코드 흐름

1. 경로를 받아 UTF-8 텍스트 읽기를 시도합니다.
2. 파일이 없으면 복구 가능한 상황으로 보고 빈 목록을 반환합니다.
3. 문자 해석에 실패하면 입력 수정이 필요하므로 의미 있는 예외를 전달합니다.
4. 정상 입력에서는 빈 줄과 중복을 제거한 목록을 반환합니다.

### 실행 결과 해석

정상 파일에 `mina`, 빈 줄, `mina`, `jun`이 차례로 있다면 결과는 `['mina', 'jun']`입니다. 같은 이름은 처음 등장한 위치만 남습니다.

파일이 없으면 `[]`가 반환되고, UTF-8이 아닌 파일이면 호출자가 원인을 구분할 수 있는 `ValueError`가 발생합니다. 실제 서비스에서는 빈 목록이 적절한 복구값인지 업무 규칙에 따라 다시 판단해야 합니다.

### 실무 연결

파일 업로드, 환경 설정 로딩, 외부 응답 파싱처럼 실패 가능성이 있는 경계에서 같은 구조를 사용할 수 있습니다. 핵심 로직과 입출력 처리를 분리하면 테스트에서는 파일 시스템 대신 작은 입력만으로 기능을 검증하기 쉬워집니다.

## 직접 해보기

1. `price = price * 0.9  # 가격에 0.9를 곱한다`라는 주석을 더 유용하게 바꿔 보세요.
2. 파일 읽기 함수가 모든 오류를 `except:`로 처리하고 빈 문자열을 반환합니다. 어떤 문제를 만들 수 있으며 어떻게 고치면 좋을까요?
3. 한 파일에 설정값, 데이터 읽기, 핵심 계산, 화면 출력, 테스트 코드가 모두 있습니다. 어떤 기준으로 분리할지 제안해 보세요.

<details>
<summary>정답 보기</summary>

1. 코드가 이미 보여 주는 계산 대신 이유를 적습니다. 예를 들어 `# 첫 구매 고객에게 적용하는 10% 할인 규칙`처럼 업무 규칙을 설명할 수 있습니다.
2. 존재하지 않는 파일, 권한 오류, 인코딩 오류, 코드 버그가 모두 같은 결과로 숨겨집니다. 예상 가능한 예외를 구체적으로 잡고, 복구 가능한 경우만 대체값을 반환하며, 나머지는 맥락 있는 오류로 전달해야 합니다.
3. 설정은 `config`, 재사용할 읽기·계산 기능은 `src`, 실제 실행 흐름은 `scripts`, 검증 코드는 `tests`처럼 변경 이유와 역할을 기준으로 나눌 수 있습니다. 규모가 작다면 필요한 경계만 먼저 적용합니다.

</details>

## 헷갈리기 쉬운 포인트

| 헷갈리는 개념 | 차이 |
|---|---|
| 주석 vs docstring | 주석은 구현 이유·제약, docstring은 함수나 모듈의 사용 계약을 설명 |
| 타입 힌트 vs docstring | 타입 힌트는 값의 형태, docstring은 의미·규칙·예외를 보완 |
| 구체적 예외 처리 vs `except:` | 예상한 실패만 분기해 원인을 보존 vs 모든 실패를 한꺼번에 가릴 위험 |
| 복구 vs 오류 숨기기 | 의미 있는 대체 흐름으로 계속 진행 vs 실패를 알리지 않아 잘못된 결과 생성 |
| 파일 분리 vs 모듈화 | 파일 개수를 늘리는 일 vs 책임과 변경 이유를 기준으로 경계를 나누는 일 |
