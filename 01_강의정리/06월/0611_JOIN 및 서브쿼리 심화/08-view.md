# 뷰(VIEW) — 복잡한 쿼리를 표처럼 재사용하기

> 매번 표 네 개를 조인하는 긴 쿼리를 복붙하기 지쳤다면, 그 쿼리에 이름을 붙여 "표처럼" 부를 수 있습니다. 데이터를 따로 저장하지 않으면서요. 그게 뷰입니다.

`VIEW` `뷰` `가상테이블` `독립성` `편리성` `보안성`

## 핵심요약

- **뷰(VIEW)**는 다른 테이블(또는 조인 결과)에서 파생된 **가상의 테이블**이다.
- 데이터를 **물리적으로 저장하지 않고 논리적으로만 존재**한다 — 뷰를 조회하면 DBMS가 뷰 정의대로 쿼리를 다시 실행한다.
- 장점은 **편리성**(복잡한 쿼리를 짧게), **독립성**(원본 구조 변경에도 응용 영향 최소화), **보안성**(필요한 컬럼만 노출).
- 생성: `CREATE VIEW 이름 AS SELECT ...`. 조회는 일반 테이블처럼 `SELECT * FROM 뷰`.
- **뷰 위에 또 뷰**를 만들 수 있다. 원본 테이블/뷰가 삭제되면 그에 의존한 뷰도 함께 사라진다.
- SQLite는 `CREATE OR REPLACE VIEW`를 지원하지 않아 **`DROP VIEW IF EXISTS` 후 다시 `CREATE`**한다.

## 개념별 정리

### 뷰란 무엇인가

**1. 정의**
하나 이상의 테이블에서 뽑은 결과에 이름을 붙여, 마치 테이블처럼 다룰 수 있게 한 **논리적 가상 테이블**이다. 실제 데이터를 복제해 저장하는 게 아니라 "쿼리 정의"만 저장한다.

**2. 왜 필요한가?**
복잡한 조인·집계를 매번 새로 쓰는 건 번거롭고 실수도 잦다. 한 번 뷰로 정의해 두면, 이후엔 `FROM 뷰이름`만으로 짧게 재사용할 수 있다.

**3. 예시 (트랙 통합 정보 뷰)**
```sql
DROP VIEW IF EXISTS view_track_full;
CREATE VIEW view_track_full AS
SELECT t.TrackId,
       t.Name        AS TrackName,
       t.Milliseconds,
       t.UnitPrice,
       al.Title      AS AlbumTitle,
       ar.Name       AS ArtistName,
       g.Name        AS GenreName
FROM tracks t
INNER JOIN albums   al ON t.AlbumId   = al.AlbumId
INNER JOIN artists  ar ON al.ArtistId = ar.ArtistId
INNER JOIN genres   g  ON t.GenreId   = g.GenreId;

-- 이후엔 이렇게 짧게 조회
SELECT * FROM view_track_full
ORDER BY ArtistName, AlbumTitle
LIMIT 10;
```

**4. 헷갈리기 쉬운 점**
뷰는 데이터를 저장하지 않는다. 그래서 원본 테이블의 데이터가 바뀌면 뷰 조회 결과도 자동으로 최신이 된다(매번 다시 실행되니까). "뷰를 만들면 그 시점 데이터가 박제된다"는 오해를 주의하자.

**5. 한 줄 정리**
뷰는 데이터를 저장하지 않고 쿼리에 이름을 붙여 표처럼 부르는 가상 테이블이다.

> 비유: 복잡한 레시피를 매번 줄줄 읊는 대신 "오늘의 특선"이라는 이름표를 붙여 두고 그 이름만 부르는 것. 재료(원본 데이터)는 주방에 그대로 있다.

### 뷰의 장점 — 편리성·독립성·보안성

**1. 정의**
뷰가 주는 세 가지 이점이다. **편리성**(복잡한 쿼리 간소화), **독립성**(원본 구조 변경의 충격 흡수), **보안성**(노출 컬럼 통제).

**2. 왜 필요한가?**
- 편리성: 자주 쓰는 복잡한 조인을 뷰로 만들면 이후 쿼리가 짧아진다.
- 독립성: 원본 테이블 구조가 바뀌어도 뷰가 중간에서 형태를 맞춰 주면, 그 뷰를 쓰는 코드는 덜 바꿔도 된다.
- 보안성: 민감 컬럼(전화·주소 등)을 뺀 뷰만 특정 사용자에게 열어 주면, 원본 테이블을 직접 노출하지 않고 접근을 제어할 수 있다.

**3. 예시 (민감 정보 뺀 고객 공개 뷰)**
```sql
DROP VIEW IF EXISTS view_customer_public;
CREATE VIEW view_customer_public AS
SELECT CustomerId,
       FirstName || ' ' || LastName AS CustomerName,
       Company,
       City,
       Country,
       Email
FROM customers;          -- Phone, Fax, Address 등은 제외
```

**4. 헷갈리기 쉬운 점**
보안성은 "뷰에 포함하지 않은 컬럼은 그 뷰로는 볼 수 없다"는 원리다. 다만 원본 테이블 자체에 대한 접근 권한이 따로 있다면 그쪽으로 볼 수 있으니, 권한 설정과 함께 써야 의미가 있다.

**5. 한 줄 정리**
뷰는 쿼리를 간단히(편리성), 구조 변화를 흡수(독립성), 노출을 통제(보안성)한다.

### 뷰의 특징과 제약

**1. 정의**
뷰를 다룰 때 알아야 할 규칙들이다.

**2. 왜 필요한가?**
뷰를 안전하게 쓰려면 갱신·삭제·재정의 규칙을 알아야 한다.

**3. 핵심 규칙**
- 생성된 뷰는 **또 다른 뷰를 만드는 재료**로 쓸 수 있다.
- 뷰 정의는 직접 수정할 수 없고, **삭제 후 재생성**해야 한다.
- 뷰를 통한 데이터 갱신(INSERT/UPDATE)에는 제약이 있다. 특히 **조인을 포함한 뷰**는 갱신이 까다롭다(어느 원본 테이블을 바꿔야 할지 모호해지기 때문).
- 원본이 되는 테이블이나 뷰가 삭제되면, 그에 의존하는 뷰도 함께 영향을 받는다.

**4. 헷갈리기 쉬운 점**
"뷰니까 자유롭게 수정·삽입할 수 있겠지"가 가장 흔한 오해다. 조회(SELECT)는 자유롭지만, 갱신은 단순 단일 테이블 뷰가 아니면 제약이 크다. 대부분의 실무에서 뷰는 **읽기용(조회 간소화)**으로 쓴다.

**5. 한 줄 정리**
뷰는 조회 재사용에 강하고, 갱신에는 제약이 있으며, 정의 변경은 삭제 후 재생성이다.

## 코드로 보기 — 뷰 위에 뷰 만들기

```sql
DROP VIEW IF EXISTS view_customer_by_country;
CREATE VIEW view_customer_by_country AS
SELECT Country,
       COUNT(*) AS CustomerCount
FROM view_customer_public          -- 앞서 만든 뷰를 다시 재료로
GROUP BY Country;

-- 조회
SELECT * FROM view_customer_by_country
ORDER BY CustomerCount DESC;
```

**코드목적**
앞서 만든 `view_customer_public`(공개용 고객 뷰)을 재료로, 국가별 고객 수를 집계한 **2차 뷰**를 만든다.

**해석**
`view_customer_by_country`의 `FROM`에 일반 테이블이 아니라 **뷰**가 들어가 있다. 뷰는 테이블처럼 다룰 수 있으므로, 뷰를 기반으로 또 다른 뷰를 쌓을 수 있다. 이렇게 단계별로 가공하면 복잡한 분석도 작은 뷰의 조합으로 깔끔히 정리된다. 단, 바탕이 된 `view_customer_public`을 삭제하면 이 뷰도 동작하지 않게 된다.

**실무 연결**
"원본 → 정제 뷰 → 집계 뷰 → 리포트 뷰"처럼 단계별 뷰를 쌓는 방식은, 데이터 파이프라인을 읽기 쉽게 모듈화하는 흔한 전략이다.

## 헷갈리기 쉬운 포인트

- **뷰 vs 테이블**: 테이블은 데이터를 실제로 저장, 뷰는 정의만 저장(조회 시 재실행). 뷰 결과는 항상 최신.
- **조회 vs 갱신**: 뷰는 조회 재사용에 강하지만, 조인 포함 뷰의 갱신은 제약이 크다(주로 읽기용).
- **`CREATE OR REPLACE` vs `DROP + CREATE`**: SQLite는 전자를 미지원 → `DROP VIEW IF EXISTS` 후 `CREATE`.
- **서브쿼리(FROM절) vs 뷰**: 둘 다 "쿼리를 표처럼" 쓰지만, 서브쿼리는 그 쿼리 안에서만 일회성, 뷰는 이름 붙여 여러 곳에서 재사용.

## 셀프 체크

- [ ] 뷰가 데이터를 저장하지 않는 가상 테이블임을 안다.
- [ ] 뷰 조회 결과가 항상 최신임을 설명할 수 있다.
- [ ] 편리성·독립성·보안성 세 장점을 든다.
- [ ] 뷰 위에 뷰를 만들 수 있음을 안다.
- [ ] SQLite에서 뷰를 다시 정의하려면 `DROP` 후 `CREATE`임을 안다.

**복습 질문 및 답변**

- (기본) 뷰는 데이터를 물리적으로 저장하나요?
  → 아닙니다. 정의(쿼리)만 저장하고, 조회할 때마다 그 정의대로 다시 실행합니다.
- (이해 확인) 뷰의 "보안성" 장점은 어떻게 구현되나요?
  → 민감 컬럼을 제외한 뷰만 노출해, 원본 테이블을 직접 보여 주지 않고 접근을 제어합니다.
- (응용) SQLite에서 같은 이름의 뷰를 새 정의로 바꾸려면 어떻게 하나요?
  → `DROP VIEW IF EXISTS 뷰이름;` 후 `CREATE VIEW 뷰이름 AS ...`로 다시 만듭니다.

## 한 줄 정리

> 뷰는 데이터를 저장하지 않고 쿼리에 이름을 붙여 표처럼 재사용하는 가상 테이블로, 편리성·독립성·보안성을 제공한다.
