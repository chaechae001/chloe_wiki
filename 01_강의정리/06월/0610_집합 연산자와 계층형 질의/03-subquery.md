# 서브쿼리 — 쿼리 속의 쿼리로 문제를 쪼개기

> 복잡한 질문은 "한 방에" 풀려고 하면 막힙니다. "필요한 값을 먼저 구하고, 그걸 본 쿼리에 합치는" 두 단계로 나누면 길이 보입니다.

`서브쿼리` `중첩 쿼리` `인라인 뷰` `스칼라 서브쿼리` `연관 서브쿼리` `IN` `EXISTS` `별칭` `분할과 결합`

## 핵심요약

- **서브쿼리**는 다른 SQL 문 안에 들어 있는 `SELECT`다. "쿼리 속의 쿼리"라고 보면 된다.
- 들어가는 **위치**에 따라 세 가지: `WHERE` 절(조건 비교), `FROM` 절(인라인 뷰), `SELECT` 절(스칼라).
- 바깥 쿼리 값을 참조하면 **연관(correlated)**, 독립적으로 실행되면 **비연관(non-correlated)** 서브쿼리다.
- `IN` / `NOT IN`, `EXISTS` / `NOT EXISTS`로 "있는지/없는지"를 조건으로 걸 수 있다.
- 풀이 전략은 **분할하고 합치기**: 필요한 값(최댓값·평균 등)을 먼저 따로 구한 뒤, 본 쿼리에 끼워 넣는다.
- 테이블 **별칭(alias)** 은 필수는 아니지만, 서브쿼리·조인이 겹칠수록 가독성에 사실상 필수다.

## 개념별 정리

### 서브쿼리란?

**1. 정의**
하나의 SQL 문 안에 또 다른 `SELECT` 문이 괄호로 묶여 들어간 형태입니다.

**2. 왜 필요한가?**
"평균보다 비싼 트랙", "가장 긴 트랙"처럼, *기준값을 먼저 알아야* 본 질문에 답할 수 있는 경우가 많습니다. 그 기준값을 만드는 것이 서브쿼리의 역할입니다.

**3. 예시**

```sql
-- 가장 긴 트랙의 정보 (기준값: 최대 재생시간)
SELECT TrackId, Name, Milliseconds
FROM tracks
WHERE Milliseconds = (
    SELECT MAX(Milliseconds)   -- 먼저 '최댓값'을 구함
    FROM tracks
);
```

**4. 헷갈리기 쉬운 점**
서브쿼리가 *하나의 값*을 돌려주는지(`= (...)`), *여러 값(목록)*을 돌려주는지(`IN (...)`)에 따라 바깥에서 쓰는 연산자가 달라집니다. 단일 값을 `IN`으로, 목록을 `=`로 받으면 오류가 납니다.

**5. 한 줄 정리**
서브쿼리는 "본 질문에 필요한 재료를 미리 만드는 안쪽 쿼리"다.

> 비유: 요리(본 쿼리) 전에 육수(서브쿼리)를 따로 우려내는 것과 같습니다. 육수가 준비돼야 본 요리를 완성할 수 있습니다.

### 위치별 서브쿼리 — WHERE · FROM · SELECT

**1. 정의**
서브쿼리가 문장의 어느 자리에 들어가느냐에 따라 역할이 갈립니다.

| 위치 | 이름 | 역할 |
| --- | --- | --- |
| `WHERE` 절 | (조건 서브쿼리) | 비교·필터 기준 만들기 (가장 흔함) |
| `FROM` 절 | 인라인 뷰 / 파생 테이블 | 서브쿼리 결과를 *임시 테이블*처럼 사용 |
| `SELECT` 절 | 스칼라 서브쿼리 | 행마다 *단일 값 하나*를 컬럼처럼 출력 |

**2. 왜 필요한가?**
"집계한 결과를 다시 조인하거나 정렬하고 싶을 때"는 `FROM` 절 인라인 뷰가, "각 행 옆에 관련 값 하나를 붙이고 싶을 때"는 `SELECT` 절 스칼라 서브쿼리가 깔끔합니다.

**3. 예시**

```sql
-- FROM 절 인라인 뷰: 고객별 총매출을 임시 테이블로 만든 뒤 고객명과 결합
SELECT sub.CustomerId,
       c.FirstName || ' ' || c.LastName AS 고객명,
       sub.총매출
FROM (
    SELECT CustomerId,
           ROUND(SUM(Total), 2) AS 총매출
    FROM invoices
    GROUP BY CustomerId
) AS sub
JOIN customers c ON sub.CustomerId = c.CustomerId
ORDER BY sub.총매출 DESC
LIMIT 5;
```

```sql
-- SELECT 절 스칼라 서브쿼리: 앨범 옆에 '트랙 수'를 붙여 출력
SELECT AlbumId,
       Title,
       (
           SELECT COUNT(TrackId)
           FROM tracks
           WHERE tracks.AlbumId = albums.AlbumId
       ) AS 트랙수
FROM albums
ORDER BY 트랙수 DESC;
```

**4. 헷갈리기 쉬운 점**
`FROM` 절 서브쿼리에는 거의 항상 별칭(`AS sub`)이 필요합니다. 이름이 없으면 바깥에서 그 결과를 가리킬 수 없습니다.

**5. 한 줄 정리**
같은 서브쿼리도 *어느 자리*에 두느냐에 따라 역할이 달라진다.

> 비유: 같은 재료라도 "양념(WHERE)", "밑반찬 한 접시(FROM)", "고명(SELECT)"으로 쓰임이 달라지는 것과 같습니다.

### 연관 vs 비연관 서브쿼리

**1. 정의**
- **비연관**: 바깥 쿼리와 상관없이 서브쿼리 혼자 한 번 실행되어 값이 정해집니다.
- **연관**: 서브쿼리가 바깥 쿼리의 컬럼을 참조해, *바깥의 행마다 다시* 실행됩니다.

**2. 왜 필요한가?**
"각 트랙을, 자신이 속한 장르의 평균 단가와 비교"하려면 트랙마다 기준(그 장르의 평균)이 달라져야 합니다. 이럴 때 연관 서브쿼리가 필요합니다.

**3. 예시**

```sql
-- 연관 서브쿼리: 자신이 속한 장르의 평균 단가보다 비싼 트랙
SELECT t.TrackId, t.Name, t.UnitPrice, g.Name AS 장르
FROM tracks t
JOIN genres g ON t.GenreId = g.GenreId
WHERE t.UnitPrice > (
    SELECT AVG(t2.UnitPrice)
    FROM tracks t2
    WHERE t2.GenreId = t.GenreId   -- 바깥 행의 GenreId를 참조
);
```

**4. 헷갈리기 쉬운 점**
연관 서브쿼리는 바깥 행마다 다시 도는 구조라 데이터가 크면 느려질 수 있습니다. 같은 결과를 조인이나 인라인 뷰로 바꿀 수 있다면 성능 면에서 유리한 경우가 많습니다.

**5. 한 줄 정리**
비연관은 "한 번 구한 고정 기준", 연관은 "행마다 달라지는 기준"이다.

> 비유: 비연관은 "반 전체 평균(한 번 계산)"과 비교하는 것, 연관은 "각 학생을 자기 조 평균과 비교(조마다 따로 계산)"하는 것입니다.

### IN / EXISTS — 있는지 없는지로 거르기

**1. 정의**
- `IN (서브쿼리)`: 값이 서브쿼리 결과 목록 안에 있으면 참.
- `EXISTS (서브쿼리)`: 서브쿼리가 행을 하나라도 돌려주면 참.

**2. 왜 필요한가?**
"청구서가 있는 고객", "한 번도 판매되지 않은 트랙"처럼 *다른 테이블에 존재하는지/안 하는지*를 조건으로 걸 때 씁니다.

**3. 예시**

```sql
-- EXISTS: 청구서가 하나라도 있는 고객
SELECT c.CustomerId,
       c.FirstName || ' ' || c.LastName AS 고객명
FROM customers c
WHERE EXISTS (
    SELECT 1
    FROM invoices i
    WHERE i.CustomerId = c.CustomerId
);
```

```sql
-- NOT EXISTS: 한 번도 판매된 적 없는 트랙
SELECT t.TrackId, t.Name
FROM tracks t
WHERE NOT EXISTS (
    SELECT 1
    FROM invoice_items ii
    WHERE ii.TrackId = t.TrackId
);
```

**4. 헷갈리기 쉬운 점**
`NOT IN`은 서브쿼리 결과에 NULL이 섞이면 예상과 다르게 *아무 행도 안 나오는* 함정이 있습니다. "없는 것 찾기"는 `NOT EXISTS`가 더 안전한 경우가 많습니다. 또 결과 집합이 클 때는 `EXISTS`가 `IN`보다 빠른 경향이 있습니다.

**5. 한 줄 정리**
IN은 "목록 안에 있나?", EXISTS는 "그런 행이 있긴 하나?"를 묻는다.

> 비유: `IN`은 "초대 명단에 이 이름이 있나" 확인하는 것, `EXISTS`는 "이 사람 앞으로 온 우편물이 한 통이라도 있나" 확인하는 것입니다.

## 코드로 보기 — 분할하고 합치기 전략

```sql
-- 목표: 자신의 총 구매액이 '전체 고객 평균' 이상인 VIP 고객
SELECT c.CustomerId,
       c.FirstName || ' ' || c.LastName AS 고객명,
       ROUND(SUM(i.Total), 2)           AS 총구매액
FROM customers c
JOIN invoices i ON c.CustomerId = i.CustomerId
GROUP BY c.CustomerId
HAVING 총구매액 >= (
    SELECT AVG(고객별합계)            -- ② 고객별 합계의 '평균'
    FROM (
        SELECT SUM(Total) AS 고객별합계 -- ① 먼저 고객별 합계를 구함
        FROM invoices
        GROUP BY CustomerId
    )
)
ORDER BY 총구매액 DESC;
```

**코드목적**
"전체 고객 평균보다 많이 산 고객"을 뽑습니다. 기준값(평균)이 복잡해, 한 번에 풀기 어려운 문제입니다.

**해석**
① 안쪽 서브쿼리에서 *고객별 합계*를 먼저 구합니다. ② 그 합계들의 *평균*을 구해 "VIP 기준선"을 만듭니다. 바깥 쿼리는 고객별 총구매액을 구해, 이 기준선 이상인 고객만 `HAVING`으로 남깁니다. 즉 "기준을 먼저 만들고(분할), 본 쿼리에 합친다(결합)"는 전략 그대로입니다.

**실무 연결**
"평균 이상 구매 고객", "상위 N% 사용자", "특정 기준을 넘는 항목"을 뽑는 일은 마케팅·운영에서 끝없이 반복됩니다. 한 번에 안 풀린다면 *기준값부터 따로 구하는 습관*이 핵심입니다.

## 헷갈리기 쉬운 포인트

- **= 서브쿼리 vs IN 서브쿼리**: 단일 값이면 `=`, 여러 값(목록)이면 `IN`.
- **IN vs EXISTS**: `IN`은 값 목록과 비교, `EXISTS`는 "행이 존재하는지"만 확인. "없는 것 찾기"는 `NOT EXISTS`가 안전.
- **연관 vs 비연관**: 바깥 컬럼을 참조하면 연관(행마다 재실행), 아니면 비연관(한 번 실행).
- **별칭 생략 vs 사용**: `FROM` 절 서브쿼리는 별칭이 사실상 필수, 쿼리가 길어질수록 별칭이 가독성을 살린다.

## 셀프 체크

- [ ] 서브쿼리가 들어가는 세 위치(WHERE·FROM·SELECT)와 각 역할을 말할 수 있다.
- [ ] 연관 서브쿼리와 비연관 서브쿼리를 구분할 수 있다.
- [ ] `IN`과 `EXISTS`의 차이를 설명할 수 있다.
- [ ] `FROM` 절 서브쿼리에 별칭이 필요한 이유를 안다.
- [ ] "분할하고 합치기" 전략으로 복잡한 문제를 두 단계로 나눌 수 있다.

**복습 질문 및 답변**

- (기본) 서브쿼리란 무엇인가요?
  → 다른 SQL 문 안에 들어 있는 `SELECT`로, 본 쿼리에 필요한 값이나 집합을 만들어 줍니다.
- (이해 확인) `SELECT` 절에 들어가 행마다 단일 값을 돌려주는 서브쿼리를 무엇이라 하나요?
  → 스칼라 서브쿼리입니다.
- (응용) "한 번도 판매되지 않은 트랙"을 안전하게 뽑으려면 `NOT IN`과 `NOT EXISTS` 중 무엇이 더 권장되나요?
  → `NOT EXISTS`입니다. (`NOT IN`은 NULL이 섞이면 결과가 비는 함정이 있습니다.)

## 한 줄 정리

> 서브쿼리는 복잡한 질문을 "기준값 만들기"와 "본 질문 풀기"로 나누는 도구이며, 위치(WHERE·FROM·SELECT)와 연관 여부에 따라 쓰임이 갈린다.
