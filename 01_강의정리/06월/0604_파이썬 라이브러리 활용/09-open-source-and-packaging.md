# 내 코드를 세상과 공유하기 — 오픈소스와 패키지 배포

> 지금까지는 남의 라이브러리를 가져다 썼습니다. 그런데 PyPI에 등록된 50만 개의 패키지는 모두 누군가가 올린 것입니다. 왜 사람들은 자기 코드를 무료로 공개할까요? 그리고 나도 그 "누군가"가 되려면 어떻게 할까요?

`오픈소스` `패키징` `pyproject.toml` `빌드 백엔드` `라이선스` `PyPI` `twine`

## 핵심요약

- 오픈소스는 소스 코드를 공개해 누구나 자유롭게 사용·수정·배포하도록 허용하는 방식이다.
- 코드를 공개하는 이유는 커뮤니티 기여와 명성, 개인의 성장과 협업, 지식 공유의 가치 때문이다.
- 패키지 배포는 "코드 작성 → 배포 파일 준비 → 빌드 백엔드 선정 → 메타데이터 추가 → 배포 패키지 생성 → 업로드"의 흐름을 따른다.
- 배포 파일에는 코드, `pyproject.toml`, `README.md`, `LICENSE`가 필요하다.
- `pyproject.toml`에 빌드 시스템과 패키지 메타데이터를 적는다.
- 실제 업로드는 연습용 TestPyPI에서 `twine`으로 해 보고, API 토큰·2FA로 계정을 보호한다.

## 개념별 정리

### 왜 코드를 공개하는가 — 오픈소스

**1. 정의**
오픈소스는 소스 코드를 공개해 누구나 자유롭게 사용·연구·수정·배포할 수 있도록 허용하는 소프트웨어 개발·배포 방식입니다. 리눅스, 파이썬, 깃 등이 대표적입니다.

**2. 왜 필요한가? (공개하는 이유)**
- **간접적 이익:** 커뮤니티 기여로 쌓이는 명성, 포트폴리오 구축(취업 경쟁력)
- **성장:** 개인의 성장, 피드백과 협업
- **지식 공유의 가치:** 기술 발전에 기여, 개방적인 소프트웨어 문화 지지

오픈소스는 혁신을 가속하고 기술의 대중화를 촉진해, 소프트웨어 개발 방식을 근본적으로 바꿔 왔습니다.

**3. 예시**
GitHub Issue로 기능 제안·버그 제보를 하면 개발자가 대응하고, 그렇게 라이브러리가 발전합니다. 직접 코드를 고쳐 기여(PR)하는 것은 실력을 보여 주는 확실한 근거가 됩니다.

**4. 헷갈리기 쉬운 점**
"공개 = 아무 제약 없음"이 아닙니다. 오픈소스도 라이선스에 따라 사용 조건(상업적 사용 가능 여부 등)이 정해져 있습니다(아래에서 다룹니다).

**5. 한 줄 정리**
오픈소스는 코드를 나눠 함께 키우는 문화이며, 동시에 나를 증명하는 가장 좋은 포트폴리오입니다.

### 패키지 등록 과정 한눈에

**1. 정의**
내 코드를 PyPI에 올려 누구나 `pip install`할 수 있게 만드는 전체 절차입니다.

**2. 왜 필요한가?**
흐름을 알면 각 단계가 왜 필요한지 이해하고, 막혔을 때 어디를 봐야 할지 알 수 있습니다.

**3. 예시 (순서)**

```
코드 작성 → 배포 파일 준비 → 빌드 백엔드 선정 → 메타데이터 추가
       → 배포 패키지 생성 → PyPI에 업로드 → 완료!
```

**4. 헷갈리기 쉬운 점**
"코드만 잘 짜면 끝"이 아닙니다. 포장(메타데이터·라이선스·빌드)이 절차의 절반입니다. 이 포장 덕분에 남이 안전하게 설치하고 쓸 수 있습니다.

**5. 한 줄 정리**
배포는 "코드 작성 → 포장 → 업로드"의 정해진 흐름입니다.

### 배포 파일 준비 — 폴더 구조

**1. 정의**
패키지로 배포하기 위해 갖춰야 할 파일과 폴더 구성입니다.

**2. 왜 필요한가?**
정해진 구조를 따라야 빌드 도구가 패키지를 올바르게 인식하고, 사용자가 설치 조건과 사용법을 알 수 있습니다.

**3. 예시**

```
packaging_tutorial/
├── LICENSE
├── pyproject.toml
├── README.md
├── src/
│   └── example_package/
│       ├── __init__.py
│       └── example.py
└── tests/
```

- **`__init__.py`:** 디렉터리를 단순 폴더가 아닌 '패키지'로 인식하게 함(권장). 비어 있어도, 초기화 코드를 담아도 됩니다.
- **`example.py`:** 패키지의 주요 로직(함수·클래스·상수)을 담는 모듈
- **`LICENSE`:** 패키지를 설치하는 사용자가 어떤 조건으로 쓸 수 있는지 명시
- **`pyproject.toml`:** 빌드 시스템을 정의하고 메타데이터를 관리
- **`README.md`:** 프로젝트 개요·설치·사용법을 담는 마크다운 문서
- **`tests/`:** 테스트 파일을 위한 자리(플레이스홀더)

**4. 헷갈리기 쉬운 점**
`tests/`는 비어 있어도 자리를 잡아 두는 플레이스홀더입니다. 실제 배포 패키지에 테스트가 꼭 포함돼야 하는 건 아니지만, 보통은 기능이 정상 동작하는지 확인하는 테스트 코드를 함께 작성합니다(단위 테스트·통합 테스트).

**5. 한 줄 정리**
코드(`src/`) + 설명(`README.md`) + 조건(`LICENSE`) + 설정(`pyproject.toml`)이 배포의 기본 한 세트입니다.

### 빌드 백엔드와 메타데이터 — pyproject.toml

**1. 정의**
- **빌드 백엔드:** 소스 코드를 설치·배포 가능한 형태(패키지)로 변환하는 역할
- **메타데이터:** 패키지의 이름·버전·작성자·설명 등 부가 정보

둘 다 `pyproject.toml` 파일에 적습니다.

**2. 왜 필요한가?**
사람이 읽는 코드를 컴퓨터가 설치할 수 있는 패키지로 바꾸려면 빌드가 필요하고, 사용자가 패키지를 식별·검색하려면 메타데이터가 필요합니다.

**3. 예시**

```toml
[build-system]
requires = ["setuptools>=61.0"]
build-backend = "setuptools.build_meta"

[project]
name = "example-package"
version = "0.0.1"
authors = [
  { name="Example Author", email="author@example.com" },
]
description = "A small example package"
readme = "README.md"
requires-python = ">=3.8"
classifiers = [
    "Programming Language :: Python :: 3",
    "License :: OSI Approved :: MIT License",
    "Operating System :: OS Independent",
]

[project.urls]
Homepage = "https://github.com/example/example-package"
Issues = "https://github.com/example/example-package/issues"
```

빌드 백엔드 후보:
- **setuptools:** 가장 오래되고 널리 쓰임. 복잡한 프로젝트 지원, 자료·커뮤니티 많음.
- **flit:** 순수 파이썬 코드 패키지를 쉽게 배포. 설정이 간단함.
- **poetry:** 의존성 관리와 패키지 빌드·배포를 하나로 처리. 비교적 최근.

**4. 헷갈리기 쉬운 점**
`name`은 PyPI에서 이미 쓰이는 이름이면 사용할 수 없습니다. `version`은 `0.0.1 → 0.0.2`처럼 올려 가며 점진적으로 발전시킵니다. `classifiers`는 검색·분류를 위한 부가 정보로, PyPI에서 필터링에 쓰입니다.

**5. 한 줄 정리**
`pyproject.toml`은 "어떻게 빌드하고, 이 패키지가 무엇인지"를 한곳에 적는 설정 파일입니다.

### 라이선스

**1. 정의**
패키지를 설치하는 사용자가 어떤 조건으로 코드를 쓸 수 있는지 정하는 법적 약속입니다.

**2. 왜 필요한가?**
라이선스가 없으면 남이 함부로 쓰기 어렵고, 상업적 사용 가능 여부도 불분명합니다. 명시해야 안심하고 쓸 수 있습니다.

**3. 예시**
대표적인 라이선스로 MIT, GNU GPL, Apache License 2.0, BSD 등이 있습니다. 어떤 라이선스를 고를지 모르겠다면 choosealicense.com 같은 가이드를 참고할 수 있습니다.

**4. 헷갈리기 쉬운 점**
라이선스마다 조건이 다릅니다. 예를 들어 MIT는 비교적 자유롭지만, GPL은 파생 저작물도 공개하도록 요구하는 경향이 있습니다. 상업적 사용을 원하면 반드시 조건을 확인하세요.

**5. 한 줄 정리**
라이선스는 "이 코드를 어떻게 써도 되는지" 정하는 사용 약관입니다.

## 코드로 보기 — 배포 패키지 생성과 업로드

```bash
# 1) 배포 패키지(whl, tar.gz) 생성 — build 라이브러리 필요
# Windows
py -m build
# MacOS / Unix
python3 -m build
```

```
# 실행 결과: dist 폴더에 두 개의 배포 파일이 생성됨
dist/
├── example_package-0.0.1-py3-none-any.whl
└── example_package-0.0.1.tar.gz
```

```bash
# 2) 업로드 (연습용 TestPyPI) — twine 사용
pip install twine
python3 -m twine upload --repository testpypi dist/*
```

```bash
# 3) 업로드한 패키지 설치해 보기
python3 -m pip install --index-url https://test.pypi.org/simple/ --no-deps example-package-yourname
```

```python
# 4) 설치 후 사용 확인
from example_package import example
print(example.add_one(2))   # 3
```

**코드목적**
포장이 끝난 코드를 실제 배포 파일로 만들고, 연습 저장소에 올린 뒤, 다시 설치해 동작을 확인하는 전체 한 바퀴를 도는 것이 목적입니다.

**해석**
`build`가 자동으로 `.whl`과 `.tar.gz` 두 개를 만들어 줍니다(앞서 본 두 배포 형식 그대로입니다). `twine`으로 TestPyPI에 올리는데, TestPyPI는 실제 PyPI에 올리지 않고 연습하는 용도입니다. 마지막에 그 패키지를 설치해 `add_one(2)`가 `3`을 반환하면, 남이 내 코드를 가져다 쓰는 경험을 처음부터 끝까지 완성한 것입니다.

**실무 연결**
계정 보호를 위해 비밀번호 대신 **API 토큰**을 쓰고, **2FA**(2단계 인증)를 켜는 것이 권장됩니다. 토큰을 매번 입력하기 번거로우면 `.pypirc` 파일에 저장해 둘 수 있습니다. 작은 라이브러리 하나를 만들어 버전을 `0.0.1 → 0.0.2`로 올려 가며 배포해 보는 것은 훌륭한 포트폴리오가 됩니다.

## 직접 해보기

1. 내가 만들고 싶은 작은 라이브러리의 이름·한 줄 설명·라이선스를 정해 `pyproject.toml`의 `[project]` 부분을 채워 보세요.
2. `README.md`에 제목(`#`), 설치법, 간단한 사용 예제를 마크다운으로 작성해 보세요.
3. 빌드 백엔드 setuptools·flit·poetry 중 내 프로젝트에 맞는 것을 고르고 이유를 적어 보세요.

## 헷갈리기 쉬운 포인트

- **공개 vs 무조건 자유:** 오픈소스도 라이선스 조건을 따릅니다.
- **코드 작성 vs 포장:** 배포는 코드만이 아니라 메타데이터·라이선스·빌드까지 포함합니다.
- **PyPI vs TestPyPI:** 실제 저장소 vs 연습용 저장소.
- **비밀번호 vs API 토큰:** 토큰이 더 안전하고 관리하기 쉽습니다.

## 셀프 체크

- [ ] 오픈소스의 정의와 공개 이유를 말할 수 있다.
- [ ] 패키지 등록 과정의 큰 흐름을 안다.
- [ ] 배포에 필요한 파일(`pyproject.toml`, `README.md`, `LICENSE` 등)을 안다.
- [ ] `pyproject.toml`에 빌드 시스템과 메타데이터가 들어간다는 걸 안다.
- [ ] 라이선스를 확인해야 하는 이유를 안다.
- [ ] TestPyPI와 API 토큰·2FA의 역할을 안다.

**복습 질문 및 답변**

- (기본) 오픈소스란 무엇인가요? → 소스 코드를 공개해 누구나 자유롭게 사용·수정·배포하도록 허용하는 방식입니다.
- (이해 확인) `pyproject.toml`에는 무엇을 적나요? → 빌드 시스템(빌드 백엔드)과 패키지 메타데이터를 적습니다.
- (응용) 실제 PyPI에 올리기 전에 연습하려면 어디에 올리나요? → TestPyPI에 `twine`으로 업로드해 봅니다.

## 한 줄 정리

> 코드를 공개하는 건 함께 성장하고 나를 증명하는 길이며, 작성한 코드를 `pyproject.toml`로 포장해 빌드하고 PyPI(연습은 TestPyPI)에 올리면 누구나 `pip install`로 내 라이브러리를 쓸 수 있습니다.
