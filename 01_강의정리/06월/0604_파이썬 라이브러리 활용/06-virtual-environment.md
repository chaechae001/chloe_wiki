# 가상환경 — 프로젝트별 작업실 만들기

> A 프로젝트는 옛 버전 pandas가 필요하고, B 프로젝트는 최신 버전이 필요합니다. 컴퓨터에는 한 번에 하나의 버전만 깔 수 있는데, 어떻게 둘 다 돌릴까요? 정답은 프로젝트마다 따로 작업실을 만드는 것 — 가상환경입니다.

`가상환경` `venv` `conda` `의존성` `버전 충돌` `격리` `activate`

## 핵심요약

- 가상환경은 프로젝트별로 격리된 독립적인 파이썬 실행 환경이다.
- 같은 컴퓨터 안에서 프로젝트마다 다른 라이브러리·버전을 충돌 없이 관리하게 해 준다.
- 가상환경이 필요한 이유는 버전 문제, 의존성 문제, 무거운 환경 세 가지로 정리된다.
- 대표 도구는 표준 라이브러리 `venv`와 데이터 과학에서 인기 있는 `conda`다.
- `python -m venv <환경명>`으로 만들고, OS별 명령어로 활성화(activate)한다.
- 활성화된 환경에 설치한 라이브러리는 그 환경의 `site-packages`에만 들어간다.

## 개념별 정리

### 가상환경이란

**1. 정의**
독립적인 파이썬 실행 환경입니다. 프로젝트가 필요로 하는 라이브러리와 패키지를 다른 프로젝트와 분리된 공간에서 관리합니다.

**2. 왜 필요한가?**
한 컴퓨터에서 여러 프로젝트를 하면, 프로젝트마다 요구하는 라이브러리 버전이 다를 수 있습니다. 가상환경은 프로젝트 간 충돌을 막고 환경을 깔끔하게 관리하도록 돕습니다.

**3. 예시 (개념도)**

```
내 컴퓨터
 ├─ 가상환경 A  →  프로그램 A (옛 버전 라이브러리)
 └─ 가상환경 B  →  프로그램 B (최신 버전 라이브러리)
```

**4. 헷갈리기 쉬운 점**
가상환경은 "가상 컴퓨터"가 아닙니다. 새 PC를 만드는 게 아니라, 라이브러리 설치 공간만 프로젝트별로 나누는 것입니다. 가벼운 칸막이라고 생각하면 됩니다.

**5. 한 줄 정리**
가상환경은 프로젝트마다 따로 쓰는 "전용 작업실"입니다.

> 비유: 공유 주방이 아니라 집집마다 따로 있는 부엌이에요. 옆집이 무슨 재료를 쓰든 우리 집 요리에 영향을 주지 않습니다.

### 왜 필요한가 — 세 가지 문제

**1. 정의**
가상환경 없이 모든 라이브러리를 한 곳에 깔면 생기는 문제들입니다.

**2. 왜 필요한가? (문제 상황)**
- **버전 문제:** 프로그램 A는 `pandas 1.5.3`에서 잘 돌지만, 프로그램 B는 `pandas >= 2.2.0`을 요구합니다. 한 공간(`site-packages`)에는 한 버전만 깔리므로, B를 위해 올리면 A가 깨질 수 있습니다.
- **의존성 문제:** 라이브러리는 다른 라이브러리에 기대어 동작합니다. 예를 들어 `matplotlib 3.9`는 `numpy >= 1.23.0`을 요구합니다. A가 의존하는 버전과 B가 의존하는 버전이 충돌할 수 있습니다.
- **무거운 환경:** 모든 프로젝트의 라이브러리를 한곳에 다 깔면, 한 프로젝트엔 필요 없는 패키지까지 잔뜩 쌓여 환경이 무겁고 지저분해집니다.

**3. 예시 (버전 변경의 위험 — deprecate와 remove)**
라이브러리는 계속 유지·보수되면서 기존 기능이 사라지거나 새로 생깁니다. 사라지기 전에 "곧 제거 예정"임을 알리는 것이 **deprecate(삭제 예고)**로, 보통 `FutureWarning`을 띄웁니다. 이후 실제로 빠지는 것이 **remove(삭제)**입니다. 이런 변경은 공식 홈페이지나 PyPI의 release note로 공유됩니다.

**4. 헷갈리기 쉬운 점**
"의존성"은 눈에 안 보여서 놓치기 쉽습니다. 내가 직접 설치한 적 없는 패키지가 같이 깔리는 이유가 바로 의존성 때문입니다(다음 글의 pip가 자동으로 챙겨 줍니다).

**5. 한 줄 정리**
버전·의존성·무거운 환경 — 이 세 가지가 가상환경을 쓰는 이유입니다.

### venv vs conda

**1. 정의**
- **venv:** 파이썬 3.3 이상에 포함된 표준 라이브러리. 가상환경 생성·활성화 기능 제공.
- **conda:** Anaconda 배포판의 일부로 제공되는 환경·패키지 관리 시스템.

**2. 왜 필요한가?**
도구마다 강점이 다릅니다. 간단한 프로젝트나 표준 기능만 쓸 때는 venv가 가볍고 충분하며, 데이터 과학·머신러닝처럼 복잡한 환경에서는 conda가 인기 있습니다.

**3. 예시**
- venv: 순수 파이썬 프로젝트, 표준 기능 중심일 때
- conda: NumPy·pandas·scikit-learn·TensorFlow 등 데이터 과학 패키지를 묶어 다룰 때 (Anaconda는 Jupyter Notebook 등 도구도 함께 제공)

**4. 헷갈리기 쉬운 점**
둘 중 무엇이든 "프로젝트별 격리"라는 목적은 같습니다. 입문 단계에서는 표준 도구인 venv로 개념을 익히고, 필요해지면 conda를 더하는 식으로 접근하면 부담이 적습니다.

**5. 한 줄 정리**
가벼우면 venv, 데이터 과학 환경이면 conda — 목적은 똑같이 "격리"입니다.

### 만들고, 켜고, 끄고, 지우기

**1. 정의**
가상환경의 생성·활성화·비활성화·삭제 명령어입니다.

**2. 왜 필요한가?**
환경은 만들고 끝이 아니라, 작업할 때 켜고(activate) 끝나면 끄며(deactivate), 필요 없으면 지우는 전체 수명 주기를 갖습니다.

**3. 예시**

```bash
# 생성: 뒤의 venv 모듈을 실행해 <환경명> 디렉터리 만들기
python -m venv myenv

# 활성화 (Windows)
myenv\Scripts\activate
# 활성화 (MacOS / Linux)
source myenv/bin/activate

# 비활성화 (공통)
deactivate

# 삭제 (Windows)
rmdir /s myenv
# 삭제 (MacOS / Linux)
rm -rf myenv
```

**4. 헷갈리기 쉬운 점**
활성화되면 터미널 프롬프트 앞에 `(myenv)`처럼 환경 이름이 표시됩니다. 이게 안 보이면 아직 켜지지 않은 것입니다. "설치했는데 import가 안 된다"의 단골 원인이 바로 "활성화 안 한 채 설치/실행"입니다.

**5. 한 줄 정리**
`python -m venv`로 만들고, OS별 명령으로 켜고 끄며, 폴더를 지우면 환경도 사라집니다.

## 코드로 보기 — "설치했는데 왜 import가 안 되지?"

```bash
# 1) 환경 밖에서 파이썬 위치 확인
which python        # 예: /usr/bin/python

# 2) 가상환경 활성화 후 다시 확인
source myenv/bin/activate
(myenv) which python   # 예: /.../myenv/bin/python  ← 경로가 달라짐
```

**코드목적**
가상환경을 켜면 사용하는 파이썬과 라이브러리 설치 위치가 바뀐다는 것을 직접 확인하는 것이 목적입니다.

**해석**
`which python`의 결과 경로가 환경 안/밖에서 다릅니다. 활성화 후 설치한 라이브러리는 그 환경의 `site-packages`에만 들어갑니다. 그래서 환경을 끈 채 실행하면 "분명 설치했는데 못 찾는" 일이 생깁니다. 즉, **import 오류의 상당수는 코드가 아니라 환경 문제**입니다.

**실무 연결**
협업이나 배포에서 "내 컴퓨터에선 되는데 다른 데선 안 돼요" 문제의 핵심이 환경 차이입니다. 가상환경을 쓰고 설치 목록을 공유하면(다음 글의 `requirements.txt`) 이 문제를 크게 줄일 수 있습니다.

3. `deactivate`로 환경을 끄고, 프롬프트의 환경 표시가 사라지는지 확인하세요.

## 헷갈리기 쉬운 포인트

- **가상환경 vs 가상 컴퓨터:** 가상환경은 라이브러리 칸막이일 뿐, 새 OS를 만드는 게 아닙니다.
- **활성화 됨 vs 안 됨:** 프롬프트의 `(환경명)` 표시 유무로 구분합니다.
- **venv vs conda:** 목적은 같고, 가벼움(venv)과 데이터 과학 편의(conda)의 차이입니다.

## 한 줄 정리

> 가상환경은 프로젝트별 전용 작업실을 만들어 버전·의존성 충돌을 막는 도구이며, 만들고(`venv`) 켜고(`activate`) 그 안에 라이브러리를 설치하는 흐름으로 사용합니다.
