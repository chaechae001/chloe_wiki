# 데이터로 문제를 푸는 법 — 목적 사고력과 분석 프로세스

> 분석을 잘하는 사람은 코드를 빨리 짜는 사람이 아니라, "무엇을 풀지"를 정확히 아는 사람입니다. 데이터는 답이 아니라 도구이기 때문입니다.

`목적 사고력` · `문제 정의` · `SCQA` · `분석 프로세스` · `데이터는 수단` · `포트폴리오`

## 핵심요약

- 데이터 자체는 목적이나 결론이 아니라, **의사결정을 위한 수단**이다.
- 같은 데이터라도 "단순 평균 확인"과 "고급 알고리즘 기반 패턴 탐지"는 분석의 깊이가 다르다.
- 프로젝트의 성패는 **문제 정의**에서 크게 갈린다 — 관찰·관심·자료조사로 문제를 발굴해야 한다.
- 문제 정의 프레임으로 **SCQA**(상황-전개-질문-답)가 널리 쓰인다.
- 데이터 분석 업무는 보통 **문제 정의 → 필요 데이터 정의 → 수집 → 전처리 → 분석 → 결과 확인 → 결과 검증 → 의사결정** 8단계로 흐른다.
- 좋은 포트폴리오의 핵심은 "성능 수치"가 아니라 **"어떤 문제를 어떻게 해결했는가"** 다.

## 개념별 정리

### 데이터는 목적이 아니라 수단

**1. 정의**
데이터 자체(≠) 목적·결론입니다. 데이터는 **의사결정을 위한 수단으로써 활용**되는 것입니다.

**2. 왜 필요한가?**
이 관점을 놓치면 "데이터를 모았으니 뭔가 나오겠지", "정확도를 0.1% 올렸으니 성공"처럼 수단과 목적이 뒤바뀝니다. 분석의 기준은 언제나 **"데이터로 원하는 문제에 도움을 주었느냐"** 입니다.

**3. 예시**
- 간단히 데이터 평균을 살펴본 분석 **vs** 고급 알고리즘을 적용한 데이터 분석
  - 둘 중 무엇이 옳다기보다, **문제에 부합하는가**가 기준입니다.
- 복잡한 분석 기법을 적용한 것보다, 기술적으로 단순해도 분석 목적에 부합하는 데이터 처리가 더 나을 수 있습니다.

**4. 헷갈리기 쉬운 점**
"더 어려운 기법 = 더 좋은 분석"이라는 착각입니다. 기술 난이도가 아니라 **목적 부합도**가 분석의 품질을 결정합니다.

**5. 한 줄 정리**
데이터는 답이 아니라, 답을 찾기 위한 도구입니다.

> 비유: 데이터 분석은 **망치질**이 아니라 **집을 짓는 일**입니다. 망치(기법)가 좋아도 설계(목적)가 없으면 집은 못 짓습니다.

### 목적 사고력의 현실

**1. 정의**
목적 사고력은 "이 데이터로 무엇을 밝히고 싶은가"를 먼저 정의하는 능력입니다.

**2. 왜 필요한가?**
예를 들어 "웹 페이지 중 고객 이탈률이 높은 구간을 데이터로 찾아내자"라는 문제는, 경험이 없으면 곧바로 떠올리기 어렵습니다. 이런 문제를 정의하려면 도메인 감각과 분석 목적 사고가 필요합니다.

**3. 예시 (고객 이탈 구간 찾기)**
"고객 이탈률이 높은 구간"을 데이터로 찾으려면 다음과 같은 접근이 나올 수 있습니다.
- 페이지를 종료하는 가장 많은 순간은 언제인가
- 페이지 간 선후 관계 분석
- Node(노드)의 개념으로 페이지 간 연결성 혹은 군집성 파악

**4. 헷갈리기 쉬운 점**
"분석 목적 사고력"은 타고나는 게 아니라 훈련되는 능력입니다. 처음에는 용어 정의, 접근 방법, 샘플 코드부터 빠르게 확보해 문제의 모양을 잡아 가면 진입장벽이 낮아집니다.

**5. 한 줄 정리**
좋은 분석은 좋은 질문에서 시작합니다.

### 목적 사고력 — 3단계 역방향 프레임

**1. 정의**
데이터를 먼저 모으는 것이 아니라, **목적 → 활용 방안 → 필요 데이터** 순으로 거꾸로 생각하는 사고법입니다.

```
[1단계] 알고 싶은 내용이 무엇인가?
        ↓
[2단계] 알게 되면 어떻게 활용할 것인가?
        ↓
[3단계] 이를 위해 필요한 데이터가 무엇인가?
```

**2. 왜 필요한가?**
데이터부터 모으면 "이 데이터로 뭘 하지?"에서 막힙니다. 목적과 활용 방안을 먼저 정하면, 정작 어떤 데이터가 필요한지가 자연스럽게 따라 나옵니다.

**3. 예시**
- (1단계) 어느 페이지에서 고객이 가장 많이 이탈하는지 알고 싶다.
- (2단계) 알게 되면 그 페이지의 UI를 개선해 이탈을 줄이겠다.
- (3단계) 그러려면 페이지별 체류·종료 로그 데이터가 필요하다.

**4. 헷갈리기 쉬운 점**
"데이터가 많으니 일단 분석해 보자"는 정방향 접근은 길을 잃기 쉽습니다. 목적 사고력은 **역방향**이 핵심입니다.

**5. 한 줄 정리**
무엇을·왜·무슨 데이터로 — 이 순서를 거꾸로 밟는 것이 목적 사고력입니다.

### 문제 정의와 SCQA

**1. 정의**
**문제 정의**는 데이터로 해야 하는 문제를 정확히 진단하고 정의하는 단계입니다. **SCQA**는 문제를 논리적으로 정의·전달하는 프레임으로, 다음 네 요소로 구성됩니다.

- **S(Situation, 상황)**: 모두가 동의하는 배경
- **C(Complication, 전개/문제)**: 그 상황에서 발생한 변화나 갈등
- **Q(Question, 질문)**: 그래서 무엇을 풀어야 하는가
- **A(Answer, 답)**: 그에 대한 해법(가설)

**2. 왜 필요한가?**
프로젝트의 성패는 문제 정의에서 크게 갈립니다. 관찰·관심·자료조사를 통해 문제를 발굴하고, SCQA로 정리하면 "무엇을, 왜 푸는지"가 명확해져 팀과 의사결정자를 설득하기 쉬워집니다.

**3. 예시**
- (S) 우리 쇼핑몰은 꾸준히 신규 가입자가 늘고 있다.
- (C) 그런데 최근 특정 페이지에서 이탈이 급증했다.
- (Q) 어느 구간에서, 왜 고객이 떠나는가?
- (A) 결제 단계의 추가 입력 항목이 원인일 수 있으니, 해당 구간 데이터를 분석하자.

**4. 헷갈리기 쉬운 점**
SCQA는 화려한 보고용 틀이 아니라, **분석가 스스로 문제를 명확히 하기 위한 사고 도구**입니다. 답(A)을 먼저 정해 놓고 끼워 맞추면 안 됩니다.

**5. 한 줄 정리**
SCQA는 "무엇을 왜 푸는가"를 한 장으로 정리해 주는 문제 정의 프레임입니다.

### 데이터 분석 업무 프로세스 (8단계)

**1. 정의**
데이터 분석은 보통 다음 흐름으로 진행됩니다.

```
문제 정의 → 필요 데이터 정의 → 데이터 수집 → 데이터 전처리
   → 데이터 분석 → 결과 확인 → 결과 검증 → 의사결정
```

**2. 단계별 핵심**

| 단계 | 무엇을 하는가 | 예시 |
| --- | --- | --- |
| 문제 정의 | 데이터로 풀 문제를 진단·정의 | "A 상품 판매량이 급감 → 원인과 해결 방안 필요" |
| 필요 데이터 정의 | 문제 해결에 필요한 데이터를 정의(기보유/미보유 구분) | A 상품 판매실적, SNS 트래픽, 마케팅 활동 데이터 |
| 데이터 수집 | 필요한 데이터를 실제로 수집(사내 시스템·크롤링 등) | 문제 기간의 데이터 확보 |
| 데이터 전처리 | 결측·이상치 정리 등 분석 가능한 형태로 가공 | 표준화·결측 처리 |
| 데이터 분석 | 목적에 맞는 정보를 도출(통계·AI 기법 활용) | "문자 발송 고객의 A 상품 판매비율 급감" 파악 |
| 결과 확인 | 분석 결과를 수치로 검증 | "문자 미발송 대비 약 23% 판매량 감소 확인" |
| 결과 검증 | 새로운 실험으로 결과를 2차 확인(같은 조건인지 점검) | 소규모 2차 문자 발송으로 재현 확인 |
| 의사결정 | 문제 원인과 결과를 종합해 해결 방안 결정 | 문자 발송 혜택 증가 결정 |

**3. 왜 필요한가?**
프로세스를 알면 "지금 내가 어느 단계에 있는지"를 알 수 있고, 막혔을 때 **언제든 문제 정의 단계로 되돌아갈 수 있다**는 안전장치가 됩니다. 특히 결과 확인과 결과 검증을 분리하는 이유는, 한 번의 분석 결과가 **우연이 아니라 반복 가능한 현상인지** 확인하기 위해서입니다.

**4. 헷갈리기 쉬운 점**
- **결과 확인 vs 결과 검증**: 확인은 "분석 결과를 수치로 정리"하는 단계, 검증은 "새로운 실험으로 동일하게 재현되는지 2차로 점검"하는 단계입니다.
- 프로세스는 일직선이 아니라, 필요하면 이전 단계로 **되돌아가는 순환**입니다.

**5. 한 줄 정리**
문제 정의에서 시작해 의사결정으로 끝나는 8단계가 분석의 큰 지도입니다.

## 코드로 보기 — "데이터가 없다" 딜레마

이 글은 사고력 중심이라, 실무에서 자주 부딪히는 상황 하나를 정리합니다.

**상황**: 문제를 잘 정의했는데, 정작 필요한 데이터가 존재하지 않는 경우가 많습니다. 이때 선택지는 둘입니다.

1. **데이터에 맞춰 문제 정의를 수정한다** — 가진 데이터로 답할 수 있는 문제로 좁힌다.
2. **데이터를 새로 생성·수집한다** — 설문, 테스트 마케팅 등으로 데이터를 만들어 문제 정의를 유지한다.

**해석**
정답은 없습니다(케이스 바이 케이스). 판단 기준은 문제의 **중요도와 시급도**입니다.
- 중요하고 급한데 데이터가 없다면 → 현실적으로 문제 정의를 조정
- 중요하지만 시간이 있다면 → 필요한 데이터를 새로 생성·확보
  - 데이터 생성 방법: 실험, 마케팅 테스트, 설문조사, 소비자 반응 조사, 데모·샘플 테스트 등

**실무 연결**
포트폴리오·미니 프로젝트에서 "데이터가 없어서 못 했다"가 아니라, "데이터가 없을 때 어떻게 판단했는가"를 보여 주면 문제 해결력이 드러납니다. 과거에는 성능 중심(예: 경진대회 순위) 포트폴리오가 강력했지만, 점점 **문제 정의와 실사례 기반 임팩트**를 더 중시하는 방향으로 바뀌고 있습니다. 좋은 포트폴리오는 "어떤 문제를 정의했는지, 왜 중요한지, 어떤 데이터를 썼는지, 결과가 문제 해결에 어떻게 기여했는지"를 함께 보여 줍니다.

## 데이터 분석가에게 필요한 역량

분석가는 코드만 잘 짜는 사람이 아니라 **기술자이면서 커뮤니케이터**입니다. 분석 결과가 아무리 좋아도 조직이 이해하지 못하거나 의사결정으로 이어지지 않으면 가치가 떨어집니다. 그래서 다음 역량을 고루 길러야 합니다.

- 코딩 능력, 통계·분석 방법 이해, 데이터 전처리 능력, SQL 활용 능력
- 리포트 작성, 발표·장표 제작, 커뮤니케이션과 설득 능력
- 비즈니스 문제를 이해하는 능력

> 참고: AI 서비스를 기획할 때는 "이 문제에 **안정적으로 발견 가능한 패턴**이 있는가?"를 먼저 점검해야 합니다. 머신러닝·딥러닝은 결국 데이터에서 패턴을 찾는 기술이라, 주식 예측처럼 정치·전쟁·감염병 등 외부 변수로 패턴이 쉽게 깨지는 문제는 과거 데이터만으로 안정적으로 예측하기 어렵습니다.

## 직접 해보기

1. 관심 있는 주제(예: 카페 매출, 헬스장 출석)로 **SCQA 네 줄**을 직접 작성해 보세요.
2. 그 문제를 풀기 위해 필요한 데이터를 적고, **기보유 / 미보유**로 나눠 보세요.
3. 미보유 데이터를 "문제 정의 수정"과 "데이터 새로 수집" 중 어느 쪽으로 해결할지, 이유와 함께 정해 보세요.

## 헷갈리기 쉬운 포인트

- **데이터 vs 목적**: 데이터는 수단, 목적은 의사결정. 둘을 바꾸면 분석이 길을 잃습니다.
- **결과 확인 vs 결과 검증**: 수치로 "정리"하는 것과 실험으로 "재현"하는 것은 다른 단계입니다.
- **복잡한 기법 vs 목적 부합**: 어려운 기법이 항상 더 좋은 분석은 아닙니다.

  - 결과 확인은 분석 결과를 수치로 정리하는 단계이고, 결과 검증은 새로운 실험으로 같은 현상이 재현되는지 2차로 점검하는 단계입니다.
- (응용) 필요한 데이터가 없을 때, 시급한 문제와 장기적 문제의 대응은 어떻게 달라지나요?
  - 시급하면 가진 데이터에 맞게 문제 정의를 조정하고, 장기적으로 중요하면 비용을 감수하고 데이터를 새로 수집·생성합니다.

## 한 줄 정리

> 데이터 분석은 좋은 문제 정의에서 시작해 의사결정으로 끝나며, 데이터는 그 과정을 돕는 수단일 뿐입니다.
