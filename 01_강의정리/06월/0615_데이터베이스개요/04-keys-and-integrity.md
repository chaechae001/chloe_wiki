# 키와 무결성 — 행을 구별하고 테이블을 연결하는 기준

> "이 줄이 누구의 기록인가"를 단 하나의 값으로 가려내고, 흩어진 테이블을 하나로 잇는 일. 관계형 데이터베이스가 "관계형"인 이유가 바로 이 키(Key)에 있습니다.

`기본키` `외래키` `후보키` `대체키` `슈퍼키` `복합키` `참조 무결성` `개체 무결성`

## 핵심요약

- 키(Key)는 조건에 맞는 튜플을 찾거나 정렬할 때 기준이 되는 속성이다.
- **기본키(Primary Key)** 는 서로 다른 튜플을 유일하게 식별하는 속성으로, 중복·NULL이 불가하며 테이블당 보통 1개다.
- **외래키(Foreign Key)** 는 다른 테이블의 기본키를 참조해 테이블 사이의 관계를 정의한다.
- 외래키가 가리키는 값은 반드시 부모 테이블의 기본키에 존재해야 한다(참조 무결성).
- 후보키·대체키·슈퍼키는 "유일성"과 "최소성"이라는 두 잣대로 구분된다.
- 두 개 이상의 컬럼을 묶어 기본키로 삼는 **복합 기본키** 는 주로 연결(중간) 테이블에서 쓴다.
- 키는 곧 무결성 규칙과 직결된다: 개체 무결성(기본키)과 참조 무결성(외래키).

## 개념별 정리

### 기본키 (Primary Key)

**1. 정의**
기본키는 서로 다른 튜플을 유일하게 식별할 수 있는 기준이 되는 속성입니다. 세 가지 성질을 가집니다: 중복되는 값을 가질 수 없고, 널 값을 가질 수 없으며, 테이블당 1개만 설정합니다.

**2. 왜 필요한가?**
"이 행이 정확히 어떤 대상의 기록인지"를 한 값으로 콕 집어낼 수 있어야 데이터를 안전하게 다룰 수 있습니다. 동명이인이 있어도 회원번호 하나면 헷갈릴 일이 없습니다.

**3. 예시**
고객 테이블에서 `ID` 를 기본키로 삼으면, `kmax6`·`flykite`·`freeman123` 처럼 서로 겹치지 않는 값으로 각 고객을 식별할 수 있습니다.

```sql
CREATE TABLE customer(
    id      VARCHAR(10) PRIMARY KEY,
    name    VARCHAR(10),
    address VARCHAR(30)
);
```

**4. 헷갈리기 쉬운 점**
이름은 동명이인 때문에 기본키로 부적합합니다. 기본키는 "절대 겹치지 않고, 절대 비지 않는" 속성이어야 합니다.

**5. 한 줄 정리**
기본키는 테이블 속 모든 행의 "주민등록번호"다.

### 외래키 (Foreign Key)

**1. 정의**
외래키는 다른 테이블의 기본키를 참조하는 속성으로, 이를 통해 두 테이블의 관계를 정의합니다.

**2. 왜 필요한가?**
관계가 없다면 주문번호를 저장하기 위해 이름·주소까지 매번 중복 저장해야 합니다. 외래키로 테이블을 연결하면 하나의 속성만으로 두 테이블을 이어, 데이터를 효율적으로 관리할 수 있습니다.

**3. 예시**
고객 테이블(`customer`)과 주문 이력 테이블(`order_history`)을 고객 ID로 연결합니다.

```sql
CREATE TABLE order_history(
    customer_id VARCHAR(10),
    order_id    VARCHAR(14),
    FOREIGN KEY (customer_id) REFERENCES customer(id),
    CONSTRAINT order_history_pk PRIMARY KEY (customer_id, order_id)
);
```

외래키 설정 형태는 `FOREIGN KEY (참조할 속성) REFERENCES 참조되는 테이블(참조되는 속성)` 입니다.

**4. 헷갈리기 쉬운 점**
참조되는 테이블의 기본키에 없는 값은 외래키로 지정할 수 없습니다. 즉 존재하지 않는 고객 ID로 주문을 만들 수 없습니다 — 이것이 **참조 무결성** 입니다.

**5. 한 줄 정리**
외래키는 "다른 테이블의 주민등록번호를 가리키는 손가락"이다.

### 후보키 · 대체키 · 슈퍼키

**1. 정의**
세 키는 "유일성(튜플을 구별할 수 있음)"과 "최소성(더 줄일 수 없는 최소한의 속성 조합)"이라는 두 잣대로 갈립니다.

- **후보키**: 기본키가 될 수 있는 키로, 유일성과 최소성을 모두 만족 (기본키 ⊂ 후보키)
- **대체키**: 후보키 중에서 기본키가 아닌 키 (대체키 ⊂ 후보키)
- **슈퍼키**: 튜플을 식별할 수 있는 유일성은 만족하지만 최소성은 만족하지 않는 키

**2. 왜 필요한가?**
기본키 하나만 알면 될 것 같지만, "어떤 속성이 기본키가 될 자격이 있는가"를 따지려면 후보키·슈퍼키 개념이 필요합니다. 면접·코딩테스트에서도 단골로 나옵니다.

**3. 예시**
회원 테이블에 `회원번호`, `이메일`, `(이메일+이름)` 조합이 있다고 합시다.

| 키 | 유일성 | 최소성 | 분류 |
| --- | --- | --- | --- |
| 회원번호 | O | O | 후보키 (→ 기본키로 선택) |
| 이메일 | O | O | 후보키 (기본키가 아니면 대체키) |
| 이메일 + 이름 | O | X (이메일만으로 충분) | 슈퍼키 |

**4. 헷갈리기 쉬운 점**
슈퍼키는 "불필요한 속성이 끼어 있어도 식별만 되면 슈퍼키"입니다. 거기서 군더더기를 걷어내 최소한으로 줄이면 후보키가 됩니다. 포함 관계는 **슈퍼키 ⊃ 후보키 ⊃ 기본키** 로 기억하세요.

**5. 한 줄 정리**
슈퍼키는 "식별만 되면 OK", 후보키는 "군더더기 없이 식별", 기본키는 "후보키 중 대표 선수"다.

### 복합 기본키

**1. 정의**
한 컬럼만으로 튜플을 식별할 수 없을 때, 두 개 이상의 컬럼을 묶어 기본키로 삼는 것을 복합 기본키라고 합니다.

**2. 왜 필요한가?**
"누가 무엇을 했다"를 기록하는 연결 테이블에서는 한 컬럼만으로는 행이 구별되지 않습니다. 예컨대 한 학생이 여러 강의를 듣고, 한 강의를 여러 학생이 듣는다면, `학생ID` 하나로도 `강의ID` 하나로도 행을 특정할 수 없습니다.

**3. 예시**
학생–강의의 수강 관계를 담는 연결 테이블 `Enrollment` 는 `student_id + course_id` 를 복합 기본키로 두고, 각각을 학생·강의 테이블의 외래키로 가집니다. 위 `order_history` 예시의 `PRIMARY KEY (customer_id, order_id)` 도 같은 원리입니다.

**4. 헷갈리기 쉬운 점**
복합 기본키는 "두 컬럼 값의 *조합* 이 유일하면 된다"는 뜻입니다. `customer_id` 가 같아도 `order_id` 가 다르면 다른 행으로 인정됩니다.

**5. 한 줄 정리**
복합 기본키는 "두 이름표를 합쳐야 비로소 한 사람을 가리키는" 경우다.

### 무결성 제약 조건

**1. 정의**
키와 직결된 무결성 규칙은 데이터가 정확하고 일관되게 유지되도록 보장합니다.

**2. 왜 필요한가?**
키를 잘 잡아도 규칙으로 강제되지 않으면 의미가 없습니다. 무결성 규칙은 키의 약속을 DB가 지키게 만듭니다.

**3. 예시**

- **개체 무결성**: 기본키는 널 값과 중복된 값을 가질 수 없음
- **참조 무결성**: 외래키는 널이거나, 참조되는 릴레이션의 기본키 값과 동일해야 함

이 외에도 도메인 무결성(속성값은 정의된 도메인에 속해야 함), NULL 무결성(특정 속성은 널 불가), 고유 무결성(각 튜플의 속성값은 서로 달라야 함), 키 무결성(테이블에 최소 한 개 이상의 키 존재) 등이 있습니다.

**4. 헷갈리기 쉬운 점**
개체 무결성은 *기본키* 에 대한 규칙, 참조 무결성은 *외래키* 에 대한 규칙입니다. 둘을 짝지어 기억하세요.

**5. 한 줄 정리**
무결성 제약 조건은 "키가 한 약속을 DB가 끝까지 지켜 주는" 장치다.

## 코드로 보기 — 두 테이블을 키로 잇기

```sql
-- 부모 테이블: 고객을 id로 식별
CREATE TABLE customer(
    id      VARCHAR(10) PRIMARY KEY,
    name    VARCHAR(10),
    address VARCHAR(30)
);

-- 자식 테이블: 고객의 주문 이력을 customer_id로 연결
CREATE TABLE order_history(
    customer_id VARCHAR(10),
    order_id    VARCHAR(14),
    FOREIGN KEY (customer_id) REFERENCES customer(id),
    CONSTRAINT order_history_pk PRIMARY KEY (customer_id, order_id)
);
```

**코드목적**
기본키(개체 식별), 외래키(테이블 연결), 복합 기본키(연결 테이블의 식별)가 한 화면에서 어떻게 맞물리는지 보여 줍니다.

**해석**
`customer` 의 `id` 는 고객을 유일하게 구별합니다. `order_history` 의 `customer_id` 는 그 `id` 를 참조하므로, 존재하지 않는 고객의 주문은 만들 수 없습니다(참조 무결성). 그리고 한 고객이 여러 번 주문할 수 있으니, `customer_id` 하나로는 행을 구별할 수 없어 `order_id` 와 묶어 복합 기본키로 삼았습니다.

**실무 연결**
회원–주문, 상품–카테고리, 사용자–게시글처럼 거의 모든 서비스 데이터는 이렇게 부모–자식 테이블로 연결됩니다. 분석할 때 `JOIN` 으로 두 테이블을 합치는 작업도, 결국 이 키 연결이 있어야 가능합니다.

## 헷갈리기 쉬운 포인트

- **기본키 vs 외래키**: 기본키는 *자기 테이블* 의 행을 식별, 외래키는 *다른 테이블* 의 기본키를 참조.
- **후보키 vs 슈퍼키**: 둘 다 식별은 되지만, 최소성을 만족하면 후보키, 군더더기가 있으면 슈퍼키.
- **후보키 vs 대체키**: 후보키 중 대표로 뽑힌 게 기본키, 나머지가 대체키.
- **개체 무결성 vs 참조 무결성**: 전자는 기본키 규칙(NULL·중복 불가), 후자는 외래키 규칙(부모 기본키에 존재).

## 셀프 체크

- [ ] 기본키의 세 가지 성질(중복·NULL 불가, 테이블당 1개)을 말할 수 있다.
- [ ] 외래키가 참조 무결성을 어떻게 보장하는지 설명할 수 있다.
- [ ] 후보키·대체키·슈퍼키를 유일성·최소성으로 구분할 수 있다.
- [ ] 복합 기본키가 필요한 상황(연결 테이블)을 예로 들 수 있다.
- [ ] 개체 무결성과 참조 무결성을 키와 짝지어 설명할 수 있다.

**복습 질문 및 답변**

- (기본) 기본키가 가질 수 없는 두 가지 값은?
  → 중복된 값과 널(NULL) 값.
- (이해확인) 슈퍼키와 후보키의 결정적 차이는?
  → 후보키는 유일성과 최소성을 모두 만족하지만, 슈퍼키는 최소성을 만족하지 않아도 된다.
- (응용) 학생과 강의가 다대다(N:M) 관계일 때, 수강 정보를 담는 연결 테이블의 기본키를 어떻게 설계하면 좋을까?
  → `학생ID`와 `강의ID`를 묶은 복합 기본키로 설계하고, 두 컬럼을 각각 학생·강의 테이블의 외래키로 둔다.

## 한 줄 정리

> 기본키는 행을 유일하게 식별하고 외래키는 테이블을 연결하며, 후보키·대체키·슈퍼키는 유일성과 최소성으로 구분된다 — 이 키들이 곧 개체 무결성·참조 무결성을 지탱한다.
