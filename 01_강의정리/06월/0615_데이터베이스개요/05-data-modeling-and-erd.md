# 데이터 모델링과 ERD — 현실을 데이터로 옮기는 설계도

> "공유 킥보드 서비스를 만들자"는 한 문장에서 시작해, 회원·킥보드·대여라는 표 구조까지 도달하는 과정. 그 다리를 놓아 주는 것이 데이터 모델링이고, 그 결과를 그림으로 그린 것이 ERD입니다.

`데이터 모델링` `개체` `속성` `관계` `ERD` `Peter Chen` `IE` `까마귀발` `카디널리티`

## 핵심요약

- 데이터 모델링은 **현실 세계에 존재하는 데이터를 데이터베이스화하는 과정** 이다.
- 데이터 모델은 현실 세계의 데이터를 단순화·추상화해 표현한 것으로, **개체(Entity)·속성(Attribute)·관계(Relationship)** 로 구성된다.
- 설계는 **개념적 → 논리적 → 물리적** 의 3단계를 거친다.
- **ERD(개체-관계 다이어그램)** 는 현실 데이터를 개체와 관계 형태의 그림으로 나타낸 것이다.
- 대표 표기법은 **Peter Chen** 과 **IE** 두 가지다.
- 관계의 카디널리티는 **1:1, 1:N, N:M** 으로 나뉘며, N:M은 중간 테이블로 분해해 1:N 구조로 구현한다.
- IE의 **까마귀발(crow's foot)** 표기법은 "0 또는 1 / 정확히 1 / 0 이상 / 1 이상"으로 관계의 참여 수를 세밀하게 나타낸다.

## 개념별 정리

### 데이터 모델링이란

**1. 정의**
데이터 모델링은 현실 세계에 존재하는 데이터를 데이터베이스 구조로 옮기는 과정입니다. 데이터 모델은 그 현실을 단순화·추상화하여 표현한 결과물입니다.

**2. 왜 필요한가?**
현실은 복잡합니다. "공유 킥보드를 모아서 관리하는 서비스"를 만들려면, 무엇을 데이터로 저장할지부터 정해야 합니다. 모델링은 막연한 아이디어를 "어떤 테이블에 어떤 컬럼을 둘 것인가"라는 구체적 설계로 바꾸는 첫 단계입니다.

**3. 예시**
"여러 브랜드의 공유 킥보드를 한 곳에서 관리하자"는 요구는, 모델링을 거치며 다음과 같이 정리됩니다.

- 저장할 대상: 회원, 킥보드, 대여 기록
- 각 대상의 정보: 회원의 이름·ID, 킥보드의 브랜드·기본료 등
- 대상 사이의 연관: "회원이 킥보드를 대여한다"

**4. 헷갈리기 쉬운 점**
모델링은 "코딩"이 아니라 "설계"입니다. SQL을 한 줄도 쓰기 전에, 종이 위에서 먼저 끝내야 하는 사고 과정입니다.

**5. 한 줄 정리**
데이터 모델링은 현실이라는 풍경을 데이터라는 지도로 옮겨 그리는 일이다.

### 데이터 모델의 구성 요소 (개체·속성·관계)

**1. 정의**
데이터 모델은 세 요소로 이루어집니다.

- **개체(Entity)**: 데이터로 표현하고자 하는 현실 세계의 개념·정보 단위 (예: 킥보드, 회원)
- **속성(Attribute)**: 개체에 대한 정보 (예: 킥보드의 브랜드·이용 가격, 회원의 아이디·이름)
- **관계(Relationship)**: 개체 간의 연관성 (예: 고객은 킥보드를 대여한다)

**2. 왜 필요한가?**
이 세 가지는 모든 ERD의 부품입니다. 개체는 네모(테이블), 속성은 그 안의 항목(컬럼), 관계는 개체를 잇는 선이 됩니다.

**3. 예시**
공유 킥보드 서비스에서 `회원` 과 `킥보드` 는 개체, 회원의 `이름·ID` 와 킥보드의 `브랜드·기본료` 는 속성, "회원이 킥보드를 대여한다"는 관계입니다.

**4. 헷갈리기 쉬운 점**
개체와 속성을 혼동하기 쉽습니다. "킥보드"는 독립적으로 존재하는 대상이라 개체이고, "브랜드"는 킥보드를 설명하는 정보라 속성입니다. 혼자 설 수 있으면 개체, 무언가를 꾸며 주면 속성입니다.

**5. 한 줄 정리**
개체는 명사(킥보드), 속성은 그 명사의 형용사(빨간, 비싼), 관계는 동사(대여한다)다.

### 설계의 3단계 (개념적·논리적·물리적)

**1. 정의**
데이터 모델링은 세 단계로 점점 구체화됩니다.

1. **개념적 설계**: 현실 세계를 추상적 개념으로 표현하는 과정
2. **논리적 설계**: DBMS가 처리할 수 있는 데이터 구조(스키마)를 설계
3. **물리적 설계**: DBMS에 테이블을 저장할 구조를 설계

**2. 왜 필요한가?**
처음부터 "VARCHAR(10)"을 정하려 들면 큰 그림을 놓칩니다. 먼저 개념(무엇을 저장할까) → 다음 논리(어떤 테이블·관계로) → 마지막 물리(어떤 타입·인덱스로) 순으로 좁혀 가야 흔들림 없는 설계가 나옵니다.

**3. 예시**
개념적 설계에서 그린 ERD가, 논리적 설계에서 테이블 스키마(컬럼·키)로 바뀌고, 물리적 설계에서 실제 `CREATE TABLE` 구문과 데이터 타입으로 구체화됩니다.

**4. 헷갈리기 쉬운 점**
세 단계는 칼로 자르듯 분리되지 않고 점진적으로 이어집니다. ERD(개념·논리)와 `CREATE TABLE`(물리)이 사실상 같은 설계의 다른 표현인 이유입니다.

**5. 한 줄 정리**
개념적 설계는 스케치, 논리적 설계는 도면, 물리적 설계는 시공 계획이다.

### ERD와 두 가지 표기법 (Peter Chen · IE)

**1. 정의**
ERD(Entity-Relationship Diagram, 개체-관계 다이어그램)는 현실 세계의 데이터를 개체와 관계 형태의 다이어그램으로 나타낸 것입니다. 대표 표기법으로 **Peter Chen** 과 **IE(Information Engineering)** 가 있습니다.

**2. 왜 필요한가?**
글로 적은 요구사항은 사람마다 다르게 해석합니다. 그림으로 그리면 개체·속성·관계가 한눈에 보여, 설계 의도를 팀 전체가 공유할 수 있습니다.

**3. 예시 — Peter Chen 표기법**
개념을 도형으로 표현하는 데 강합니다.

| 기호 | 의미 |
| --- | --- |
| 사각형 | 개체(Entity) |
| 타원 | 속성(Attribute) |
| 마름모 | 관계(Relationship) |
| 선 | 개체와 속성의 연결 |
| 밑줄 친 타원 | 기본키 |

**예시 — IE 표기법**
키(PK/FK)·데이터 타입·제약 조건까지 테이블 형태로 세밀하게 표현하며, 관계는 까마귀발 기호로 나타냅니다.

**4. 헷갈리기 쉬운 점**
Peter Chen은 "개념을 빠르게 스케치"하는 데, IE는 "실제 테이블에 가깝게 상세히" 표현하는 데 강합니다. 같은 설계를 다른 그림 언어로 적는 것일 뿐, 둘 중 하나가 옳은 게 아닙니다.

**5. 한 줄 정리**
Peter Chen은 개념 스케치, IE는 시공 도면에 가까운 ERD다.

### 관계의 카디널리티 (1:1, 1:N, N:M)

**1. 정의**
카디널리티는 하나의 데이터가 다른 테이블의 몇 개 데이터와 관계를 가지는지를 나타냅니다.

- **1:1**: 매우 예외적 (보안·민감정보 분리 등)
- **1:N**: 가장 기본이 되는 관계
- **N:M**: 최종적으로 중간(연결) 테이블로 분해하여 1:N 구조로 구현

**2. 왜 필요한가?**
"한 고객이 여러 주문을 한다(1:N)", "한 학생이 여러 강의를 듣고 한 강의에 여러 학생이 있다(N:M)"처럼, 관계의 모양에 따라 테이블 설계가 완전히 달라집니다.

**3. 예시**
N:M 관계는 그대로 둘 수 없어 중간 테이블로 풀어냅니다. 이때 중간 테이블은 양쪽 개체의 기본키를 외래키로 가지며, 이 둘을 묶어 복합 기본키로 삼습니다. ([키와 무결성](04-keys-and-integrity.md)의 복합 기본키와 이어집니다.)

**4. 헷갈리기 쉬운 점**
IE의 까마귀발 표기법은 카디널리티를 더 세밀하게 나눕니다.

| 기호 | 의미 |
| --- | --- |
| `+○─` | 0 또는 1 |
| `+│─` | 정확히 1 |
| `>○─` | 0 이상 |
| `>│─` | 1 이상 |

"필수인지(1 이상) 선택인지(0 이상)"를 구분하는 것이 핵심입니다. 예컨대 고객–계좌 관계에서 계좌가 반드시 있어야 하면 1 이상, 없어도 되면 0 이상으로 표기합니다.

**5. 한 줄 정리**
관계의 카디널리티는 "한 쪽이 다른 쪽 몇 개와 이어지는가"를 정하는 약속이다.

## 코드로 보기 — 공유 킥보드 ERD를 테이블로 옮기기

아래는 공유 킥보드 서비스의 요구사항을 IE 표기법 ERD로 설계하고, 이를 테이블 구조로 옮긴 결과입니다.

> 요구사항 요약: 고객은 회원 가입 시 이름·ID·PW·전화번호·생년월일을 입력한다. 각 킥보드는 고유 ID를 가지며, 브랜드와 연식에 따라 기본료가 달라진다. 고객이 킥보드를 대여하면 대여 상태·시간·위치를 기록한다. 한 명의 고객은 한 번에 하나의 킥보드만 대여할 수 있다.

```mermaid
erDiagram
    customer ||--o{ borrow : "대여한다"
    kickboard ||--o{ borrow : "대여된다"

    customer {
        VARCHAR customer_number PK
        VARCHAR name
        VARCHAR id "UNIQUE"
        VARCHAR pw
        VARCHAR phone_number
        DATE    birth_date
    }
    kickboard {
        VARCHAR id PK
        VARCHAR brand "UNIQUE"
        INT     model_year
        INT     price_per_minute
        INT     basic_price
        VARCHAR company "UNIQUE"
    }
    borrow {
        VARCHAR  customer_number PK_FK
        DATETIME rental_time PK
        ENUM     rental_status
        VARCHAR  rental_location
    }
```

테이블 정의로 옮기면 다음과 같습니다.

```sql
CREATE TABLE customer(
    customer_number VARCHAR(10) PRIMARY KEY,
    name            VARCHAR(10) NOT NULL,
    id              VARCHAR(15) NOT NULL UNIQUE,
    pw              VARCHAR(20) NOT NULL,
    phone_number    VARCHAR(11),
    birth_date      DATE
);

CREATE TABLE kickboard(
    id               VARCHAR(10) PRIMARY KEY,
    brand            VARCHAR(20) NOT NULL UNIQUE,
    model_year       INT NOT NULL,
    price_per_minute INT NOT NULL,
    basic_price      INT NOT NULL,
    company          VARCHAR(20) NOT NULL UNIQUE
);

CREATE TABLE borrow(
    customer_number VARCHAR(10),
    rental_time     DATETIME,
    rental_status   ENUM('대여', '반납') NOT NULL,
    rental_location VARCHAR(20) NOT NULL,
    FOREIGN KEY (customer_number) REFERENCES customer(customer_number),
    CONSTRAINT borrow_pk PRIMARY KEY (customer_number, rental_time)
);
```

**코드목적**
"요구사항(글) → ERD(그림) → 테이블(코드)"로 이어지는 설계의 전 과정을, 이번 학습의 모든 개념(제약 조건·키·관계)을 모아 보여 줍니다.

**해석**
`customer` 와 `kickboard` 는 각각 회원·킥보드 개체를 표현하고, `borrow` 는 둘 사이의 대여 관계를 담는 연결 테이블입니다. 회원은 `customer_number`(기본키)로, 킥보드는 `id`(기본키)로 식별됩니다. `borrow` 는 어떤 회원이 언제 대여했는지를 `customer_number + rental_time` 복합 기본키로 구별하고, `customer_number` 는 외래키로 회원 테이블을 참조합니다. 제약 조건(`NOT NULL`·`UNIQUE`)으로 데이터 품질까지 챙긴, 완성된 설계입니다.

**실무 연결**
서비스 기획자가 요구사항을 정의하고, 설계자가 ERD를 그리고, 개발자가 `CREATE TABLE` 로 구현하는 협업 흐름이 정확히 이 모습입니다. ERD는 기획·개발·분석을 잇는 공통 언어이며, 도구로는 draw.io(diagrams.net) 같은 무료 에디터를 흔히 씁니다.

## 헷갈리기 쉬운 포인트

- **개체 vs 속성**: 혼자 설 수 있으면 개체(킥보드), 무언가를 설명하면 속성(브랜드).
- **Peter Chen vs IE**: 전자는 개념 스케치(도형 중심), 후자는 상세 도면(테이블·키·타입 중심).
- **1:N vs N:M**: N:M은 그대로 두지 않고 중간 테이블로 분해해 1:N 두 개로 만든다.
- **0 이상 vs 1 이상(까마귀발)**: 선택적 참여(0 이상)인지 필수 참여(1 이상)인지의 차이.

- (이해확인) N:M 관계는 최종적으로 어떻게 구현하는가?
  → 중간(연결) 테이블로 분해해 1:N 관계 두 개로 만들고, 양쪽 기본키를 외래키로 가져와 복합 기본키로 삼는다.
- (응용) "한 명의 고객은 한 번에 하나의 킥보드만 대여할 수 있다"는 요구사항은 ERD 설계에 어떤 영향을 줄까?
  → 대여 시점 기준으로 고객–대여 관계의 참여 수를 제한하게 되며, 대여 테이블의 기본키 설계(예: 고객번호+대여시간)에 반영된다.

## 한 줄 정리

> 데이터 모델링은 현실을 개체·속성·관계로 추상화해 데이터베이스로 옮기는 과정이고, ERD는 그 설계를 Peter Chen(개념)·IE(상세) 표기법의 그림으로 나타낸 공통 언어다.
