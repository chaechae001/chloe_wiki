# 데이터베이스 개요 — 엑셀로도 충분한데 왜 DB일까?

> 혼자 가계부를 쓸 땐 엑셀이면 충분합니다. 그런데 회사 수십 명이 같은 데이터를 동시에 고치기 시작하면 무슨 일이 벌어질까요? 데이터베이스가 태어난 이유가 바로 여기 있습니다.

`데이터베이스` `DBMS` `무결성` `RDB` `NoSQL` `데이터 종속` `데이터 중복`

## 핵심요약

- **데이터(Data)** 는 수집된 단순한 사실과 값, **정보(Information)** 는 그 데이터를 목적에 맞게 가공·해석한 결과다.
- **데이터베이스** 는 한 조직에서 여러 사용자와 응용 프로그램이 *공동으로* 사용하기 위해 데이터를 통합·저장·운영하는 묶음이다.
- 파일 처리 방식은 **데이터 종속·데이터 중복·무결성 훼손** 이라는 세 가지 한계를 가지며, 데이터베이스는 이를 해결하기 위해 등장했다.
- DB의 핵심 특징은 **실시간 접근성, 지속적인 변화, 동시 공유, 내용 기반 참조** 다.
- 데이터베이스는 크게 **RDB(관계형)** 와 **NoSQL** 로 나뉜다.
- RDB는 구조가 일관되고 무결성이 중요한 경우, NoSQL은 구조가 자주 바뀌고 대용량을 빠르게 처리해야 하는 경우에 적합하다.
- "혼자 쓰는 데이터"가 아니라 **"함께 쓰는 데이터"** 라는 점이 DB를 쓰는 근본 이유다.

## 개념별 정리

### 데이터 vs 정보

**1. 정의**
데이터는 현실에서 수집한 가공되지 않은 사실과 값의 모음입니다. 정보는 그 데이터를 특정 목적에 맞게 해석하거나 가공한 형태입니다.

**2. 왜 필요한가?**
데이터 분석이라는 일은 결국 "쌓인 데이터(원재료)를 의미 있는 정보(요리)로 바꾸는 일"입니다. 둘을 구분하지 못하면 "숫자는 많은데 말할 수 있는 건 없는" 상황에 빠집니다.

**3. 예시**
`23, 25, 19, 31`이라는 숫자 나열은 그냥 데이터입니다. 여기에 "고객 평균 나이 24.5세"라는 해석을 붙이면 정보가 됩니다.

**4. 헷갈리기 쉬운 점**
데이터가 많다고 곧바로 정보가 되는 건 아닙니다. 가공·해석이라는 과정을 거쳐야 비로소 정보입니다.

**5. 한 줄 정리**
데이터는 재료, 정보는 요리다. (밀가루와 빵의 차이)

### 데이터베이스의 정의와 필요성

**1. 정의**
데이터베이스는 한 조직 안에서 여러 사용자와 응용 프로그램이 공동으로 사용하기 위해 데이터를 통합하여 저장하고 운영하는 데이터의 집합입니다.

**2. 왜 필요한가?**
개인 작업이라면 엑셀, CSV, 가벼운 파일 기반 DB로도 충분합니다. 하지만 조직 단위에서 **여러 사람이 동시에**, **권한을 나눠**, **데이터가 어긋나지 않게** 다뤄야 한다면 이야기가 달라집니다. 파일을 각자 복사해서 쓰면 누구 파일이 최신인지 알 수 없고, 같은 데이터가 여기저기 중복되며, 한쪽만 수정되면 데이터가 서로 모순됩니다.

**3. 예시**
파일 처리 시스템의 세 가지 한계를 정리하면 이렇습니다.

- 데이터의 구조가 바뀌면 그 데이터를 쓰는 응용 프로그램의 구조도 같이 바꿔야 한다 → **데이터 종속**의 문제
- 응용 프로그램마다 따로 데이터를 만들 수 있어 같은 데이터가 여러 곳에 중복된다 → **데이터 중복**의 문제
- 위 두 문제 때문에 데이터가 정확하고 일관되게 유지되지 못한다 → **무결성**을 지킬 수 없음

**4. 헷갈리기 쉬운 점**
"무결성"은 단순히 "데이터가 없어지지 않는다"가 아니라, **데이터가 정확하고 일관된 형태로 유지된다**는 뜻입니다. A 화면에는 주소가 바뀌었는데 B 화면에는 옛 주소가 남아 있으면 무결성이 깨진 것입니다.

**5. 한 줄 정리**
DB는 "함께 쓰는 데이터를 어긋나지 않게 모아두는 공용 창고"다.

### 데이터베이스의 특징

**1. 정의**
DB는 네 가지 특징으로 설명됩니다: 실시간 접근성, 지속적인 변화, 동시 공유, 내용에 대한 참조.

**2. 왜 필요한가?**
이 네 가지는 곧 "파일 한 덩어리"와 "데이터베이스"를 가르는 기준입니다.

**3. 예시**

- **실시간 접근성**: 사용자가 원할 때 언제든 접근할 수 있어야 함
- **지속적인 변화**: 삽입·삭제·갱신을 통해 늘 최신 상태를 유지해야 함
- **동시 공유**: 여러 사용자가 동시에 이용할 수 있어야 함
- **내용에 대한 참조**: 데이터가 저장된 물리적 위치가 아니라 *값* 으로 찾을 수 있어야 함

**4. 헷갈리기 쉬운 점**
"내용에 대한 참조"가 특히 중요합니다. "3번째 폴더 5번째 파일"처럼 위치로 찾는 게 아니라, "이름이 김민준인 고객"처럼 값으로 검색한다는 의미입니다.

**5. 한 줄 정리**
DB는 "위치가 아니라 내용으로 찾을 수 있는, 늘 살아 움직이는 공용 데이터 저장소"다.

### RDB vs NoSQL

**1. 정의**
RDB(Relational Database)는 관계형 모델을 기반으로 SQL을 이용해 데이터를 관리합니다. NoSQL(Not only SQL)은 데이터 간 관계를 엄격하게 정의하지 않고 RDB보다 유연한 모델을 사용합니다.

**2. 왜 필요한가?**
모든 데이터가 깔끔한 표로 정리되지는 않습니다. 이미지, 자연어 텍스트처럼 형태가 들쭉날쭉한 데이터, 구조가 자주 바뀌는 데이터를 다룰 땐 NoSQL이 유리합니다. 반대로 회계·주문처럼 한 치의 오차도 허용하면 안 되는 데이터는 RDB가 안전합니다.

**3. 예시**

| 구분 | RDB | NoSQL |
| --- | --- | --- |
| 데이터 표현 | 행과 열의 테이블(고정) | 고정적이지 않고 유연함 |
| 강점 | 무결성·안정성 | 대용량·빠른 처리, 유연성 |
| 적합한 상황 | 구조가 일관된 데이터 | 구조가 일관되지 않은 빅데이터 |
| 대표 제품 | MySQL, PostgreSQL, MariaDB | MongoDB, Redis, Apache Cassandra |

지도·공간 데이터처럼 특수한 데이터는 PostgreSQL 같은 특정 RDB가 더 잘 다루기도 합니다. 정답은 하나가 아니라 "데이터의 성격에 맞춰 고른다"입니다.

**4. 헷갈리기 쉬운 점**
NoSQL이 "더 최신이라 더 좋다"가 아닙니다. 유연한 만큼 학습 난이도가 있고, 무결성을 직접 챙겨야 하는 부담이 큽니다. **"언제 어떤 DB를 쓸 것인가"** 가 핵심 질문입니다.

**5. 한 줄 정리**
RDB는 잘 정리된 서랍장, NoSQL은 칸막이 없이 큰 보관함이다.

## 코드로 보기 — 데이터를 값으로 찾는다는 것

```sql
-- 위치가 아니라 "값"으로 데이터를 찾는다
SELECT name, address FROM customer WHERE name = '김민준';
```

**코드목적**
DB의 핵심 특징인 "내용에 대한 참조"가 실제로 어떤 모습인지 보여 줍니다.

**해석**
이 쿼리는 "customer 테이블에서 이름이 김민준인 행의 이름과 주소를 가져와라"는 뜻입니다. 파일을 몇 번째 줄인지 외울 필요 없이, 우리가 알고 있는 값(이름)만으로 데이터를 찾아낼 수 있습니다. (`SELECT` 문법은 [다음 글](02-relational-db-and-sql.md)에서 자세히 다룹니다.)

**실무 연결**
데이터 분석에서 "특정 조건을 만족하는 고객만 뽑아 보기"는 가장 기본적인 작업입니다. 마케팅 타겟 추출, 이상 거래 탐지, 리포트 집계 모두 이 "값으로 찾기"에서 출발합니다.

## 헷갈리기 쉬운 포인트

- **데이터 vs 정보**: 데이터는 가공 전(재료), 정보는 가공 후(결과).
- **데이터 종속 vs 데이터 중복**: 종속은 "구조가 바뀌면 프로그램도 바꿔야 하는" 문제, 중복은 "같은 데이터가 여러 곳에 따로 저장되는" 문제.
- **RDB vs NoSQL**: 무결성·일관성이 우선이면 RDB, 유연성·대용량 처리가 우선이면 NoSQL.

## 한 줄 정리

> 데이터베이스는 "여러 사람이 함께 쓰는 데이터를, 어긋나지 않게, 값으로 찾을 수 있도록 모아둔 공용 저장소"이며, 데이터의 성격에 따라 RDB와 NoSQL 중에서 고른다.
