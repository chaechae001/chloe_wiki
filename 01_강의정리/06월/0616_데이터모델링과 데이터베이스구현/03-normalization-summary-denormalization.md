# 정규화 한눈에 정리 — BCNF·4NF·5NF와 역정규화

> 1NF·2NF·3NF를 거쳤다면 이미 실무의 8할은 끝난 셈입니다. 이 글은 전체 단계를 한 장으로 묶고, 더 깊은 정규형(BCNF·4NF·5NF)과 일부러 거꾸로 가는 역정규화, 그리고 완성된 공유 킥보드 DB까지 정리합니다.

`정규화단계` `BCNF` `4NF` `5NF` `다치종속` `조인종속` `역정규화` `ERD`

## 핵심요약

- 정규화는 **비정규화 → 1NF → 2NF → 3NF → BCNF → 4NF → 5NF** 순으로 점점 엄격해진다.
- 단계마다 "무엇을 제거하는가"가 핵심: 1NF=다중값, 2NF=부분 종속, 3NF=이행 종속, BCNF=후보키 아닌 결정자, 4NF=다치 종속, 5NF=조인 종속.
- 실무는 보통 **3NF~BCNF까지**면 충분하다.
- **역정규화**는 성능을 위해 일부러 테이블을 다시 합치는 의도적 선택이다.
- 정규화는 무결성을, 역정규화는 조회 성능을 우선하며 둘은 **트레이드오프** 관계다.
- 완성된 공유 킥보드 DB는 고객·대여·킥보드·브랜드 네 테이블로 나뉜다.

## 개념별 정리

### 정규화 단계 정리

**1. 정의**
정규화는 한 단계가 다음 단계의 전제가 되는 계단식 과정입니다. 각 계단은 특정 종속 관계를 하나씩 제거합니다.

**2. 왜 필요한가?**
단계 이름을 외우는 게 목적이 아니라, "지금 이 테이블이 어떤 종속 때문에 위험한가"를 보고 어디까지 정규화할지 정하기 위함입니다.

**3. 예시**

```text
비정규화 DB
   │  (도메인을 원자값으로)
   ▼
1차 정규화
   │  (부분 함수 종속 제거)
   ▼
2차 정규화
   │  (이행 함수 종속 제거)
   ▼
3차 정규화
   │  (결정자이면서 후보키가 아닌 것 제거)
   ▼
BCNF
   │  (다치 종속 제거)
   ▼
4차 정규화
   │  (조인 종속 제거)
   ▼
5차 정규화
```

**4. 헷갈리기 쉬운 점**
정규형은 "위 단계를 만족하면 아래 단계도 자동으로 만족"하는 포함 관계입니다. 즉 2NF면 반드시 1NF이지만, 그 반대는 아닙니다.

**5. 한 줄 정리**
정규화는 종속을 하나씩 제거하며 올라가는 계단이고, 위로 갈수록 더 엄격합니다.

> 비유: 짐을 정리할 때 큰 박스부터 칸막이로 점점 잘게 나눠 담는 것과 같습니다.

### BCNF — 결정자이면서 후보키가 아닌 것

**1. 정의**
3NF를 만족하면서, **모든 결정자가 후보키**가 되도록 만드는 단계입니다. 결정자인데 후보키가 아닌 속성이 있으면 그것을 분리합니다.

**2. 왜 필요한가?**
3NF까지 했는데도 미묘한 중복이 남는 경우가 있습니다. "한 속성이 다른 속성을 결정하는데, 정작 그 속성은 행을 유일하게 식별하지는 못하는" 상황입니다.

**3. 예시**
`(학번, 과목)`이 키이고, 한 교수는 한 과목만 가르친다고 합시다. 그러면 `교수 → 과목`이 성립합니다.

```text
학번   과목      교수
100    C         P1
100    Python    P2
200    JAVA      P3
200    C         P1
```

`교수`는 `과목`을 결정하는 **결정자**이지만, 교수만으로는 행을 구분할 수 없어 **후보키가 아닙니다.** 이런 결정자를 분리하는 것이 BCNF입니다.

**4. 헷갈리기 쉬운 점**
"3NF와 BCNF가 뭐가 다르냐"는 질문이 많습니다. 대부분의 테이블은 3NF면 BCNF도 만족합니다. BCNF는 후보키가 여러 개이고 서로 겹칠 때만 추가로 문제가 되는, 더 엄격한 3NF라고 보면 됩니다.

**5. 한 줄 정리**
BCNF는 "결정자라면 반드시 후보키여야 한다"는 더 깐깐한 3NF입니다.

### 4NF(다치 종속)와 5NF(조인 종속)

**1. 정의**
- **4NF**: 하나의 키에 서로 독립적인 여러 값이 따라붙는 **다치 종속(multivalued dependency)** 을 제거합니다.
- **5NF**: 테이블을 쪼갰다가 다시 JOIN했을 때 원본에 없던 가짜 행이 생기는 **조인 종속(join dependency)** 을 제거합니다.

**2. 왜 필요한가?**
독립적인 두 종류의 다중값(예: 한 과목에 여러 교수 × 여러 교재)을 한 테이블에 두면 조합 수만큼 행이 불어납니다. 4NF·5NF는 이 조합 폭발을 막습니다.

**3. 예시**
다치 종속: 하나의 과목을 여러 교수가 가르치고, 동시에 여러 공통 교재가 쓰입니다.

```text
과목      교수    교재
Python    P1      T1
Python    P1      T2
Python    P2      T1
Python    P2      T2
```

교수를 새로 등록하려면 교재 수만큼 행을 만들어야 해 교수가 중복됩니다. `(과목, 교수)`와 `(과목, 교재)`로 나누면 해결됩니다.

조인 종속: 수업을 `(수업,교수)`와 `(수업,학생)`으로 나눴다가 다시 JOIN하면, 원래 없던 "P2가 S2를 가르친" 조합 같은 가짜 행이 생길 수 있습니다. 5NF는 이런 손실 없는 분해를 보장합니다.

**4. 헷갈리기 쉬운 점**
4NF·5NF는 실무에서 마주칠 일이 드뭅니다. "독립적인 다중값이 한 테이블에 섞였을 때" 정도로만 기억해도 충분합니다.

**5. 한 줄 정리**
4NF는 독립적인 다중값을, 5NF는 다시 합쳤을 때 생기는 가짜 행을 막는 단계입니다.

### 역정규화 (Denormalization)

**1. 정의**
정규화된 데이터베이스의 **성능을 개선하기 위해 일부러 테이블을 다시 통합**해 구조를 재구성하는 것입니다.

**2. 왜 필요한가?**
정규화로 테이블이 잘게 나뉘면, 화면 하나 그리는 데 JOIN을 여러 번 해야 해 조회가 느려질 수 있습니다. 자주 쓰는 쿼리라면 중복을 어느 정도 감수하고 합치는 편이 빠릅니다.

**3. 예시**
완성된 킥보드 DB에서도 "가격을 계산하는 쿼리가 많이 쓰인다"는 이유로 `분당 가격` 컬럼을 킥보드 테이블에 함께 넣어, 매번 브랜드 테이블과 JOIN하지 않도록 했습니다. 이것이 의도적인 역정규화입니다.

**4. 헷갈리기 쉬운 점**
역정규화는 "정규화를 안 한 것(비정규화)"과 다릅니다. **정규화를 충분히 이해한 뒤, 측정된 성능 문제를 근거로 선택적으로 되돌리는 것**입니다.

**5. 한 줄 정리**
역정규화는 무결성을 조금 양보하고 조회 속도를 얻는 의도적 트레이드오프입니다.

> 비유: 자주 보는 책을 서가에서 매번 찾기 번거로워, 책상 위에 사본 한 부를 둬서 빨리 보는 것.

## 코드로 보기 — 완성된 공유 킥보드 DB

정규화와 일부 역정규화를 거쳐, 최종 데이터베이스는 네 테이블로 정리됩니다.

```mermaid
erDiagram
    customer ||--o{ borrow : "대여한다"
    kickboard ||--o{ borrow : "대여된다"
    brand ||--o{ kickboard : "제조한다"

    customer {
        VARCHAR customer_number PK
        VARCHAR name
        VARCHAR id "UNIQUE"
        VARCHAR pw
        VARCHAR phone_number
        DATE birth_date
    }
    borrow {
        VARCHAR customer_number PK_FK
        DATETIME rental_time PK
        FLOAT lat_location
        FLOAT lon_location
        ENUM rental_status "대여/반납"
        VARCHAR kickboard_id FK
    }
    kickboard {
        VARCHAR id PK
        INT brand_number FK
        INT model_year
        INT price_per_minute
        INT basic_price
    }
    brand {
        INT brand_number PK
        VARCHAR name "UNIQUE"
        VARCHAR company
    }
```

**코드목적**
이상 현상을 제거하면서 회원가입 시 필요한 정보까지 반영한, 운영 가능한 형태의 스키마를 보여줍니다.

**해석**
설계에 담긴 실무적 판단들입니다. 회원의 기본키를 `id` 대신 변하지 않는 고유 번호(`customer_number`)로 둬 ID가 바뀌어도 안전하게 했고, 비밀번호는 그대로 저장하지 않고 해시 값으로 둬 보안을 높였습니다. 대여 위치는 주소 문자열 대신 위도·경도로 정확히 기록하고, 브랜드는 이름 대신 고유 번호를 외래키로 써서 브랜드명이 바뀌어도 연결이 끊기지 않게 했습니다. 한편 자주 쓰이는 가격 계산을 위해 `분당 가격`은 킥보드 테이블에도 둬 역정규화했습니다.

**실무 연결**
이 구조가 곧 백엔드 API가 다루는 테이블이 됩니다. 회원가입은 `customer`에, 대여/반납은 `borrow`에, 요금 조회는 `kickboard`·`brand`에 매핑됩니다.

## 헷갈리기 쉬운 포인트

- **비정규화 vs 역정규화**: 비정규화는 *정규화를 안 한 상태*, 역정규화는 *정규화 후 의도적으로 되돌린 상태*.
- **3NF vs BCNF**: 둘 다 "키가 아닌 결정자" 문제를 다루지만, BCNF가 더 엄격(모든 결정자가 후보키여야 함).

- (기본) 역정규화란? → 성능 개선을 위해 정규화된 테이블을 의도적으로 다시 통합하는 것.

## 한 줄 정리

> 정규화는 종속을 단계적으로 제거해 무결성을 지키는 과정이고, 역정규화는 성능을 위해 그 일부를 의도적으로 되돌리는 균형 잡기입니다.
