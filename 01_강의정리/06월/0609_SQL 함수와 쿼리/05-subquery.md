# 서브쿼리 — 쿼리 안에 또 다른 쿼리 넣기

> "Alice보다 급여가 많은 사원"을 찾고 싶은데, 정작 Alice의 급여가 얼마인지 모른다면? 그 값을 먼저 구하는 쿼리를 조건 안에 끼워 넣으면 된다.

`서브쿼리` `단일행서브쿼리` `다중행서브쿼리` `IN` `ANY` `ALL` `스칼라서브쿼리`

## 핵심요약

- 서브쿼리는 **하나의 쿼리 안에 포함된 또 하나의 쿼리**다(메인 쿼리가 서브쿼리를 품는 종속 관계).
- 모르는 기준값을 "먼저 구해서" 조건에 쓸 수 있어, 알려지지 않은 기준의 검색에 유용하다.
- 서브쿼리는 메인 쿼리보다 **먼저 한 번 실행**되어 그 결과를 메인 쿼리에 넘긴다.
- **반환 결과 수**로 단일 행(한 값)과 다중 행(여러 값)으로 나뉜다.
- 단일 행은 비교 연산자(`=`, `>`, …), 다중 행은 `IN`·`ANY`·`ALL`을 쓴다.
- **위치**로도 나뉜다: `WHERE` 절 서브쿼리(가장 흔함), `SELECT` 절의 스칼라 서브쿼리 등.
- 풀이 전략: **분할 → 각각 실행 → 합치기**. 메인/서브를 먼저 글로 구분한 뒤 코딩한다.

## 개념별 정리

### 서브쿼리란

**1. 정의**
쿼리(SELECT문) 안에 괄호로 감싸 넣은 또 다른 쿼리다. 안쪽이 서브쿼리, 바깥쪽이 메인 쿼리다.

**2. 왜 필요한가?**
"평균보다 점수가 높은 학생", "최고가와 같은 가격의 상품"처럼 **기준값을 미리 모르는 검색**에 쓴다. 기준값(평균·최고가 등)을 사람이 먼저 조회해 외워 두고 다시 검색하는 대신, 그 계산을 조건 안에 통째로 넣어 한 번에 처리한다.

**3. 예시**

```sql
-- 기존 방식: Alice의 급여(예: 2500)를 이미 알고 있어야 한다
SELECT * FROM employee
WHERE 급여 > 2500;

-- 서브쿼리: Alice의 급여를 몰라도 된다
SELECT * FROM employee
WHERE 급여 >
(SELECT 급여 FROM employee WHERE 이름 = 'Alice');
```

안쪽 `(SELECT 급여 ... 이름='Alice')`가 먼저 실행되어 Alice의 급여를 구하고, 바깥 쿼리는 그 값보다 급여가 많은 사원을 찾는다.

**4. 헷갈리기 쉬운 점**
서브쿼리에는 지켜야 할 규칙이 있다. ① 반드시 **괄호**로 감싼다. ② 서브쿼리 안에서는 `ORDER BY`를 쓸 수 없다. ③ 보통 연산자의 **오른쪽**에 둔다(`WHERE 급여 > (서브쿼리)`). ④ 서브쿼리는 `SELECT`문으로만 작성한다.

**5. 한 줄 정리**
서브쿼리는 "기준값을 먼저 구하는 작은 쿼리를 조건 안에 끼워 넣는" 방법이다.

> 비유: "반 평균보다 높은 사람 손 들어" 하려면 먼저 평균을 계산해야 한다. 그 "평균 계산"을 머릿속이 아니라 조건문 안에 직접 적어 넣는 것이 서브쿼리다.

### 단일 행 서브쿼리 — 결과가 한 값

**1. 정의**
서브쿼리의 결과가 단 하나의 값(한 행)으로 나오는 경우다.

**2. 왜 필요한가?**
"평균 재생시간보다 긴 트랙", "최고 단가와 같은 단가의 트랙"처럼, 비교 기준이 하나의 값일 때 쓴다.

**3. 예시**

```sql
-- 평균 재생시간보다 긴 트랙
SELECT * FROM track
WHERE milliseconds > (SELECT AVG(milliseconds) FROM track);

-- 최고 단가와 같은 단가의 트랙
SELECT * FROM track
WHERE unit_price = (SELECT MAX(unit_price) FROM track);
```

`AVG(...)`, `MAX(...)`는 값을 하나만 돌려주므로 `>`, `=` 같은 비교 연산자로 바로 비교할 수 있다.

**4. 헷갈리기 쉬운 점**
단일 행 서브쿼리에 비교 연산자(`=`, `>` 등)를 썼는데 서브쿼리가 실제로 여러 값을 돌려주면 오류가 난다. "이 서브쿼리가 값을 하나만 주는가, 여럿 주는가"를 먼저 따져 연산자를 골라야 한다.

**5. 한 줄 정리**
결과가 한 값이면 `=`, `>`, `<` 같은 비교 연산자로 메인 쿼리와 비교한다.

단일 행 연산자는 다음과 같다.

| 기호 | 뜻 |
| --- | --- |
| `=` | 같다 |
| `<>` | 같지 않다 |
| `>` | 크다 |
| `>=` | 크거나 같다 |
| `<` | 작다 |
| `<=` | 작거나 같다 |

### 다중 행 서브쿼리 — 결과가 여러 값

**1. 정의**
서브쿼리의 결과가 두 개 이상의 값(여러 행)으로 나오는 경우다.

**2. 왜 필요한가?**
"각 부서의 최고 급여자"처럼 서브쿼리가 부서 수만큼 여러 값을 돌려줄 때, 비교 연산자 하나로는 처리할 수 없다. 이때 다중 행 연산자를 쓴다.

**3. 예시**

```sql
SELECT * FROM employee
WHERE 급여 IN (
  SELECT MAX(급여) FROM employee GROUP BY 부서번호
);
```

안쪽 서브쿼리는 부서별 최고 급여를 여러 개 돌려준다. `IN`은 그중 **하나라도 일치하면** 그 사원을 결과에 포함한다.

**4. 헷갈리기 쉬운 점**
여러 값이 나오는 서브쿼리에 `=`를 쓰면 오류가 난다. `IN`(목록 중 하나라도 일치), `ANY`(하나라도 만족), `ALL`(모두 만족)을 상황에 맞게 골라야 한다.

**5. 한 줄 정리**
결과가 여러 값이면 `IN`·`ANY`·`ALL`로 "목록과의 관계"를 따진다.

다중 행 연산자와 동작 예시는 다음과 같다.

| 기호 | 뜻 |
| --- | --- |
| `IN` | 목록 중 하나라도 같으면 만족 |
| `ANY` | 하나라도 만족하면 참 (비교 연산과 함께) |
| `ALL` | 모두 만족해야 참 (비교 연산과 함께) |

```sql
1  IN  (1, 2, 3, 4)      -- 참: 1이 목록 안에 있음
10 <ANY (1, 2, 3, 4)     -- 참: 목록 중 하나(예: 1)보다 10이 크기만 하면 됨 → 사실 ANY는 "하나라도 조건 성립"
99 >=ALL (99, 100, 101)  -- 거짓: 99는 100, 101보다 크거나 같지 않음 (ALL은 전부 성립해야 함)
```

> `ANY`는 "목록 중 하나라도 비교가 성립하면 참", `ALL`은 "목록 전부에 대해 성립해야 참"이라고 기억하면 된다.

### 위치에 따른 분류 — WHERE 서브쿼리와 스칼라 서브쿼리

**1. 정의**
서브쿼리는 들어가는 위치에 따라서도 나뉜다. 가장 흔한 것은 `WHERE` 절 서브쿼리이고, `SELECT` 절에 들어가 한 값을 돌려주는 것을 스칼라 서브쿼리라 한다.

**2. 왜 필요한가?**
조건을 거는 데는 `WHERE` 서브쿼리를, 결과 표에 "계산된 한 칸"을 덧붙이는 데는 스칼라 서브쿼리를 쓴다. 스칼라 서브쿼리는 JOIN과 비슷한 결과를 내기도 한다.

**3. 예시**

```sql
-- WHERE 절 서브쿼리 (가장 일반적)
SELECT * FROM employee
WHERE 급여 > (SELECT 급여 FROM employee WHERE 이름 = 'Alice');

-- 스칼라 서브쿼리 (SELECT 절에서 한 값을 가져옴)
SELECT students.name, (
  SELECT math
  FROM middle_test AS m
  WHERE m.student_id = students.student_id
) AS middle_math
FROM students;
```

스칼라 서브쿼리는 학생마다 그 학생의 시험 점수를 한 칸씩 채워 넣는다. 결과적으로 두 테이블을 이어 붙인 JOIN과 비슷해 보인다.

**4. 헷갈리기 쉬운 점**
스칼라 서브쿼리는 행마다 단 하나의 값만 돌려줘야 한다. 만약 한 학생에 점수가 여러 개 나오면 오류가 난다. "한 행당 한 값"이 스칼라 서브쿼리의 전제다.

**5. 한 줄 정리**
조건엔 WHERE 서브쿼리, 결과 표에 계산 칸을 더할 땐 스칼라 서브쿼리.

## 코드로 보기 — 서브쿼리 풀이 전략: 분할 → 실행 → 합치기

서브쿼리가 어려운 이유는 위치가 다양하고, 단일/다중 행이 섞이며, 중첩이 깊어질수록 한눈에 안 들어오기 때문이다. 그래서 **바로 코딩하지 말고 메인/서브를 먼저 글로 구분**하는 습관이 중요하다.

문제: "평균 재생시간보다 긴 트랙의 이름을 보고 싶다."

```sql
-- 1단계(분할): 메인 / 서브를 말로 나눈다
--   서브: 평균 재생시간을 구한다
--   메인: 그 평균보다 긴 트랙을 조회한다

-- 2단계(각각 실행): 서브쿼리 먼저 단독 실행해 값을 확인
SELECT AVG(milliseconds) FROM track;   -- 예: 어떤 평균값이 나옴

-- 3단계(합치기): 확인한 서브쿼리를 조건 안에 끼워 넣는다
SELECT name FROM track
WHERE milliseconds > (SELECT AVG(milliseconds) FROM track);
```

**코드목적**
"평균보다 긴 트랙"이라는, 기준값(평균)을 미리 모르는 검색을 한 번의 쿼리로 처리하는 것이 목적이다.

**해석**
서브쿼리를 따로 실행해 보면 평균값이 제대로 나오는지 먼저 확인할 수 있다. 그 검증이 끝난 뒤 조건에 끼워 넣으면, 메인 쿼리는 매번 평균을 다시 계산하지 않고 그 한 값을 기준으로 비교한다(서브쿼리는 한 번만 실행되어 결과를 넘긴다).

**실무 연결**
"평균 객단가 이상 구매 고객", "최고 매출 지점과 같은 매출의 지점", "특정 조건을 만족하는 고객의 주문만"처럼, 기준값을 동적으로 계산해 걸러야 하는 분석에서 서브쿼리는 필수다. 복잡한 문제일수록 "메인/서브를 먼저 나누고 각각 검증한 뒤 합친다"는 절차가 실수를 크게 줄여 준다.

### 조인 vs 서브쿼리

같은 결과를 JOIN으로도, 서브쿼리로도 풀 수 있는 경우가 많다. 이 단계에서는 **"정답이 하나가 아니다"** 라는 점을 받아들이고, 결과가 맞는지를 기준으로 이해하면 된다. 복잡한 요구에서는 조인과 서브쿼리가 각각 장단점이 있어, 숙련될수록 상황에 맞게 고르게 된다. 예를 들어 "짝이 없는 데이터 찾기"는 [LEFT JOIN + IS NULL](04-outer-join-and-null.md)로도, `NOT IN` 서브쿼리로도 풀 수 있다.

## 직접 해보기

1. 트랙 중 "최고 단가(`unit_price`)와 같은 단가"인 트랙을 서브쿼리로 조회해 보자. (단일 행? 다중 행?)
2. 부서별 최고 급여를 받는 사원을 `IN` 서브쿼리로 조회해 보자.
3. "평균 재생시간보다 긴 트랙"을, 먼저 서브쿼리만 단독 실행해 평균을 확인한 뒤 전체 쿼리로 합쳐 보자.

## 헷갈리기 쉬운 포인트

- **단일 행 vs 다중 행**: 서브쿼리가 값 하나면 `=`·`>` 등 비교 연산자, 여러 값이면 `IN`·`ANY`·`ALL`. 여러 값에 `=`를 쓰면 오류.
- **ANY vs ALL**: `ANY`는 "하나라도 성립하면 참", `ALL`은 "전부 성립해야 참".
- **JOIN vs 서브쿼리**: 같은 결과를 둘 다로 풀 수 있을 때가 많다. 정답은 하나가 아니며, 결과의 정확성으로 판단한다.

## 연결되는 개념

- 이전 글: [LEFT / RIGHT JOIN과 NULL](04-outer-join-and-null.md) — "짝 없는 데이터 찾기"를 서브쿼리(`NOT IN`)로도 풀 수 있어 비교에 좋다.
- 함께 보면 좋은 글: [집계 함수와 LIMIT](01-aggregate-functions.md) — 서브쿼리는 `AVG`·`MAX` 같은 집계 결과를 기준값으로 자주 활용한다.
- 더 찾아볼 키워드: `NOT IN`, `EXISTS`, 상관 서브쿼리(correlated subquery), `FROM` 절 서브쿼리(인라인 뷰)

## 셀프 체크

- [ ] 서브쿼리가 "쿼리 안의 쿼리"이며 먼저 실행됨을 설명할 수 있다.
- [ ] 서브쿼리 사용 규칙(괄호·ORDER BY 불가·연산자 오른쪽·SELECT문)을 안다.
- [ ] 단일 행과 다중 행 서브쿼리에 쓰는 연산자를 구분할 수 있다.
- [ ] `IN`·`ANY`·`ALL`의 차이를 예로 들 수 있다.
- [ ] WHERE 서브쿼리와 스칼라 서브쿼리의 위치 차이를 안다.
- [ ] "분할 → 실행 → 합치기" 순서로 서브쿼리 문제를 접근할 수 있다.

**복습 질문 및 답변**

*기본* — 서브쿼리는 메인 쿼리와 언제 실행되나?
> 메인 쿼리가 실행되기 전에 먼저 한 번 실행되어, 그 결과를 메인 쿼리에 넘긴다.

*이해 확인* — 부서별 최고 급여처럼 서브쿼리가 여러 값을 돌려줄 때 `=`를 쓰면?
> 오류가 난다. 여러 값에는 `IN`(또는 `ANY`/`ALL`)을 써야 한다.

*응용* — "평균보다 긴 트랙"을 풀 때 가장 먼저 해야 할 일은?
> 메인/서브를 글로 구분하고, 서브쿼리(평균 계산)를 단독 실행해 값이 맞는지 확인하는 것. 그다음 조건에 합친다.

## 한 줄 정리

> 서브쿼리는 모르는 기준값을 먼저 구해 조건에 끼워 넣는 "쿼리 속 쿼리"다. 반환 수(단일/다중)에 맞춰 연산자를 고르고, 복잡할수록 "분할 → 실행 → 합치기" 순서로 접근하면 길을 잃지 않는다.
