# 웹서버와 VM 배포 운영

> 인터넷에 앱을 공개한다는 것은 파일 복사보다 네트워크 경계, 웹서버, 보안 업데이트와 장애 복구를 운영하는 일에 가깝습니다.

`VM` · `Web Server` · `Public IP` · `SSH` · `Firewall`

## 핵심요약

- VM은 네트워크 주소를 가진 실행 환경이고 웹서버가 앱 산출물을 제공합니다.
- HTTP·HTTPS와 관리용 SSH는 역할과 공개 범위를 분리합니다.
- 개인 키와 비밀값은 저장소나 빌드 산출물에 포함하지 않습니다.
- 실제 운영에서는 프로세스 재시작, 로그, TLS, 모니터링이 필요합니다.
- 배포 후 기능뿐 아니라 CORS, 성능, 접근성, 보안과 롤백을 확인합니다.

## 1. 배포 요청 흐름

```text
사용자 → DNS/Public IP → 방화벽 → 웹서버 → 정적 앱
                                      └→ API 서버 → 데이터 저장소
```

브라우저는 웹서버에서 앱 파일을 받고, 실행된 앱은 별도 API 서버에 데이터를 요청할 수 있습니다. 두 서버의 Origin이 다르면 API의 CORS 정책도 점검합니다.

## 2. 최소 권한으로 서버 준비하기

- 관리 접속은 비밀번호보다 SSH 키를 사용하고 개인 키 권한을 제한합니다.
- SSH 포트는 가능한 신뢰할 네트워크로 범위를 제한합니다.
- 사용자 트래픽은 HTTP보다 TLS가 적용된 HTTPS를 기본으로 합니다.
- 앱은 일반 사용자 권한으로 실행하고 필요한 포트만 엽니다.
- 운영체제와 런타임 보안 업데이트를 적용합니다.

실습에서 편의를 위해 모든 IP나 포트를 허용하는 설정은 운영에 그대로 사용하지 않습니다.

## 3. 웹서버 배포 예시

```nginx
server {
  listen 80;
  server_name example.com;
  root /srv/app/dist;

  location /assets/ {
    try_files $uri =404;
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  location / {
    try_files $uri /index.html;
  }
}
```

### 코드 목적

빌드된 정적 파일을 제공하고 SPA 내부 경로는 `index.html`로 연결합니다.

### 코드 흐름과 결과 해석

정적 asset이 있으면 해당 파일을 반환하고 없으면 404를 냅니다. 앱 경로는 진입 HTML을 반환해 클라이언트 라우터가 화면을 선택합니다. 배포 뒤 `/`, 중첩 URL 새로고침, asset 캐시를 각각 확인합니다.

### 실무 연결

웹서버 앞에 CDN과 TLS 종료 지점을 두거나, 관리형 정적 호스팅을 사용해 VM 운영 부담을 줄일 수 있습니다. 직접 VM을 쓸 때는 프로세스 관리자, 로그 수집, 상태 확인과 백업 배포본을 준비합니다.

## 4. 배포 체크리스트

빌드 커밋, 환경 설정, 헬스 체크, 주요 사용자 흐름, 브라우저 호환성, API CORS, 로딩 성능, 로그와 알림을 확인합니다. 실패 시 이전 버전으로 되돌리는 롤백 절차도 배포 전에 정합니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| Public IP vs Domain | 네트워크 주소 vs 사람이 읽는 이름과 주소 매핑 |
| SSH key vs 앱 secret | 서버 접속 자격 증명 vs 앱 실행 시 필요한 비밀 설정 |
| Build vs Serve | 배포 파일 생성 vs 네트워크 요청에 파일 응답 |
