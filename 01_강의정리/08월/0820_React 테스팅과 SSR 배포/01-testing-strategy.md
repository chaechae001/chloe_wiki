# React 테스트 전략

> 좋은 테스트는 구현 방법보다 사용자가 믿고 사용할 수 있는 동작을 검증합니다.

`Unit Test` · `Integration Test` · `E2E` · `Mocking` · `TDD`

## 핵심요약

- 테스트는 변경 후에도 기존 동작이 유지되는지 빠르게 확인합니다.
- 테스트 범위가 작을수록 원인 파악이 쉽고, 클수록 실제 사용 흐름에 가깝습니다.
- Setup, Exercise, Assertion의 순서로 테스트 의도를 분명하게 만듭니다.
- Mock은 외부 의존성의 동작을 대신하고 Stub은 필요한 자리를 단순한 값으로 채웁니다.
- 사이드 이펙트가 작고 책임이 분리된 코드는 테스트하기 쉽습니다.

## 1. 테스트가 필요한 이유

컴포넌트가 많아지면 한 부분의 수정이 다른 화면에 영향을 줄 수 있습니다. 자동화된 테스트는 버그 상황을 재현하고 리팩터링 전후의 계약을 지켜 줍니다. 테스트 이름과 예시는 기능의 사용법을 설명하는 실행 가능한 문서가 되기도 합니다.

## 2. 범위에 따른 테스트

| 범위 | 검증 대상 | 장점 | 주의점 |
|---|---|---|---|
| Unit | 함수·컴포넌트 하나 | 빠르고 실패 원인이 명확 | 통합 문제를 놓칠 수 있음 |
| Integration | 여러 컴포넌트·라우터·상태 연결 | 기능 단위 신뢰도가 높음 | 환경 준비가 더 필요 |
| E2E | 사용자 시나리오 전체 | 실제 서비스 흐름과 가까움 | 느리고 원인 추적이 어려움 |

테스트 포트폴리오는 작은 테스트만 많이 만들기보다 핵심 계산, 주요 기능 통합, 중요한 사용자 여정을 균형 있게 배치합니다.

## 3. 테스트 가능한 코드

```javascript
export function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
```

```javascript
test('수량을 반영한 주문 합계를 계산한다', () => {
  const items = [{ price: 3000, quantity: 2 }, { price: 1500, quantity: 1 }];
  const result = calculateTotal(items);
  expect(result).toBe(7500);
});
```

### 코드 목적

UI와 분리된 계산 규칙이 주어진 입력에서 올바른 결과를 만드는지 확인합니다.

### 코드 흐름과 결과 해석

Setup에서 입력을 준비하고, 함수를 실행한 뒤, Assertion에서 기대값을 비교합니다. 실패하면 계산 규칙 또는 기대 계약 중 무엇이 달라졌는지 검토합니다.

### 실무 연결

가격, 권한, 데이터 변환처럼 오류 비용이 큰 순수 로직을 먼저 분리하면 빠르고 안정적인 회귀 테스트를 만들 수 있습니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| Unit vs Integration | 분리된 작은 단위 vs 여러 단위의 연결 |
| Mock vs Stub | 동작과 호출을 관찰하는 대역 vs 필요한 값을 채우는 단순 대역 |
| White-box vs Black-box | 내부 구조 기준 vs 외부 동작 기준 |
