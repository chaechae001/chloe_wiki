# CSR과 SSR 성능

> 렌더링 전략은 HTML을 어디서 만드느냐뿐 아니라 사용자가 언제 내용을 보고 조작할 수 있는지를 결정합니다.

`CSR` · `SSR` · `TTFB` · `FCP` · `TTI`

## 핵심요약

- CSR은 브라우저가 JavaScript와 데이터를 받아 화면을 만듭니다.
- SSR은 서버가 요청마다 초기 HTML을 만들어 보냅니다.
- TTFB, FCP, TTI는 서로 다른 사용자 대기 구간을 측정합니다.
- SSR은 초기 콘텐츠와 검색 노출에 유리하지만 서버 비용과 TTFB가 늘 수 있습니다.
- 렌더링 전략은 페이지 특성과 캐시 가능성에 따라 선택합니다.

## 1. 렌더링 위치 비교

CSR에서는 작은 HTML 뒤 JavaScript와 데이터를 받아야 첫 화면이 완성될 수 있습니다. SSR에서는 서버가 데이터와 라우팅을 반영한 HTML을 먼저 보내 콘텐츠를 일찍 보여 줄 수 있고, 이후 JavaScript가 상호작용을 연결합니다.

| CSR | SSR |
|---|---|
| 브라우저에서 초기 화면 생성 | 서버에서 초기 HTML 생성 |
| 앱 내부 이동과 상호작용에 강점 | 첫 콘텐츠와 크롤러 정보에 강점 |
| 큰 JS 번들이 초기 표시를 늦출 수 있음 | 요청마다 서버 렌더링 비용 발생 |
| 정적 파일 CDN 배포가 단순 | 서버 운영과 캐시 전략 필요 |

## 2. 성능 지표 읽기

- **TTFB**: 요청부터 첫 응답 바이트까지. 네트워크 왕복과 서버 처리 시간이 포함됩니다.
- **FCP**: 첫 텍스트·이미지 같은 콘텐츠가 화면에 그려질 때까지입니다.
- **TTI**: 주요 UI가 입력에 안정적으로 반응할 준비가 될 때까지입니다.

SSR은 HTML 생성 때문에 TTFB가 늘 수 있지만 콘텐츠가 포함된 응답으로 FCP를 앞당길 수 있습니다. 그러나 JavaScript가 늦게 준비되면 화면은 보여도 버튼이 바로 반응하지 않는 간격이 생깁니다.

## 3. 측정 기반 선택

```javascript
const navigation = performance.getEntriesByType('navigation')[0];
console.log('TTFB(ms):', navigation.responseStart - navigation.requestStart);
```

### 코드 목적

브라우저 Navigation Timing 정보에서 서버 응답 대기의 한 부분을 관찰합니다.

### 코드 흐름과 결과 해석

요청 시작과 첫 응답 시점의 차이를 계산합니다. 값이 크면 네트워크, 서버 처리, 캐시 여부를 나눠 조사해야 하며 SSR 자체만 원인으로 단정하지 않습니다.

### 실무 연결

콘텐츠 페이지, 검색 유입 페이지, 로그인 후 대시보드는 목표가 다릅니다. 페이지별 실제 지표와 사용자 환경을 측정해 CSR, SSR, 정적 생성을 조합합니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| SSR vs 전통 서버 렌더링 | 초기 HTML 뒤 같은 앱이 Hydration됨 vs 페이지 이동마다 서버 문서 중심 |
| TTFB vs FCP | 첫 바이트 도착 vs 첫 콘텐츠 표시 |
| 빠른 표시 vs 빠른 상호작용 | 화면이 보이는 시점 vs 이벤트에 반응하는 시점 |

</details>

## 한 줄 정리

> CSR과 SSR의 선택은 초기 표시, 상호작용, 검색 노출, 서버 비용을 실제 지표로 비교하는 과정입니다.
