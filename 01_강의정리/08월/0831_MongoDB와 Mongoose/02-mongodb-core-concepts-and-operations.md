# MongoDB 핵심 구조와 운영 방식

MongoDB를 안전하게 사용하려면 데이터베이스·컬렉션·문서·ObjectId의 계층과 연결 환경을 함께 이해해야 합니다.

**핵심 키워드:** Database, Collection, Document, ObjectId, Compass

## 핵심 내용

- Database는 관련 컬렉션을 묶는 논리적 공간입니다.
- Collection은 비슷한 목적의 문서를 저장하며 관계형 테이블에 대응되는 개념입니다.
- Document는 필드와 값으로 구성된 기본 저장 단위입니다.
- `_id`는 문서를 고유하게 식별하며 기본적으로 ObjectId가 생성될 수 있습니다.
- 로컬 설치, 관리형 클라우드와 GUI 도구는 운영 책임과 접근 제어 방식이 다릅니다.

## 계층 구조

```text
MongoDB Server / Cluster
└─ Database
   └─ Collection
      └─ Document
```

하나의 애플리케이션이 여러 데이터베이스를 사용할 수 있지만 권한과 백업, 운영 경계를 불필요하게 복잡하게 만들지 않도록 설계합니다.

## ObjectId 이해

ObjectId는 고유 식별자로 편리하지만 비즈니스 순번이나 보안 토큰으로 사용하지 않습니다. 문자열로 받은 ID가 유효한 형식인지 확인하고, 존재 여부와 접근 권한은 별도로 검사합니다.

```javascript
import mongoose from "mongoose";

function isValidId(value) {
  return mongoose.isValidObjectId(value);
}
```

- **목적:** 쿼리 전에 식별자 형식을 검증합니다.
- **흐름:** 경로 입력 수신 → ObjectId 형식 확인 → 조회 또는 400 응답입니다.
- **결과:** 잘못된 캐스팅 오류를 예측 가능한 클라이언트 오류로 바꿀 수 있습니다.
- **실무 포인트:** 형식이 유효해도 해당 문서가 존재하거나 사용자가 접근할 수 있다는 뜻은 아닙니다.

## 실행 환경 선택

| 방식 | 장점 | 책임 |
|---|---|---|
| 로컬 설치 | 학습과 독립 개발에 편리 | 설치, 업데이트, 백업 |
| 관리형 클라우드 | 운영 기능과 확장이 편리 | 네트워크·계정·비용 설정 |
| Compass | 문서 탐색과 쿼리 확인에 유용 | 운영 변경 시 주의 |

클라우드 연결에서는 허용 IP, 최소 권한 계정, TLS와 비밀정보 보관을 확인합니다. 연결 문자열은 코드나 공개 저장소에 커밋하지 않고 환경변수 또는 비밀 관리 시스템에서 주입합니다.

## 운영 기본 원칙

- 개발·테스트·운영 데이터베이스와 계정을 분리합니다.
- 백업만 생성하지 말고 복원 절차를 검증합니다.
- 쿼리 패턴에 맞는 인덱스를 설계하고 사용량을 관찰합니다.
- GUI에서 직접 수정한 운영 데이터도 감사와 변경 절차를 따릅니다.

## 복습 질문 및 답변

### Q1. Collection의 모든 문서는 필드가 완전히 같아야 하나요?

<details>
<summary>답</summary>

MongoDB 자체는 유연한 구조를 허용하지만 애플리케이션 안정성을 위해 스키마 검증과 마이그레이션 규칙을 두는 것이 좋습니다.

</details>

### Q2. ObjectId가 유효하면 문서가 반드시 존재하나요?

<details>
<summary>답</summary>

아닙니다. 형식 검증은 조회 가능한 모양인지 확인할 뿐 실제 존재 여부는 데이터베이스 조회 결과로 판단합니다.

</details>

### Q3. Compass는 데이터베이스 서버인가요?

<details>
<summary>답</summary>

아닙니다. MongoDB 서버나 클러스터에 연결해 데이터를 탐색하고 쿼리를 수행하는 GUI 클라이언트입니다.

</details>

## 요약

MongoDB는 데이터베이스, 컬렉션과 문서 계층으로 구성되고 ObjectId로 문서를 식별합니다. 도구 사용보다 계정·네트워크·비밀정보·백업 같은 운영 경계를 먼저 안전하게 설계해야 합니다.
