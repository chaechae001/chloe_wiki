# Git과 GitHub 기초

코드를 안전하게 되돌리고 함께 발전시키려면 변경의 이력을 남기는 방식부터 이해해야 합니다.

**핵심 키워드:** 버전 관리, Git, GitHub, 커밋, 브랜치

## 핵심 내용

- Git은 파일의 변경 이력을 로컬 저장소에 기록하는 분산 버전 관리 시스템입니다.
- GitHub는 Git 저장소를 온라인에서 공유하고 리뷰·이슈·자동화를 연결하는 협업 플랫폼입니다.
- 커밋은 의미 있는 변경 묶음이며, 메시지는 변경의 목적을 설명해야 합니다.
- 브랜치는 기존 이력을 보존한 채 독립적으로 작업하는 포인터입니다.
- 분산 구조에서는 네트워크가 없어도 조회·커밋·브랜치 작업을 계속할 수 있습니다.

## Git이 해결하는 문제

파일을 `final`, `final2`, `really-final`처럼 복사하면 어떤 버전이 기준인지 알기 어렵습니다. Git은 각 변경에 작성자, 시점, 메시지, 부모 커밋 정보를 붙여 하나의 이력으로 연결합니다. 필요한 시점의 상태를 비교하거나 복원할 수 있고, 여러 작업을 브랜치로 나누어 병렬로 진행할 수 있습니다.

## Git과 GitHub의 역할

| 구분 | Git | GitHub |
|---|---|---|
| 실행 위치 | 로컬 컴퓨터 | 원격 서비스 |
| 핵심 역할 | 변경 이력 관리 | 저장소 공유와 협업 |
| 대표 기능 | 커밋, 브랜치, 병합 | Pull Request, Issue, Wiki |
| 네트워크 | 기본 작업에 불필요 | 동기화와 협업에 필요 |

Git만으로도 버전 관리는 가능하지만, 팀에서는 GitHub 같은 원격 호스팅 서비스가 공동 기준점 역할을 합니다.

## 기본 흐름

```bash
git status
git add README.md
git commit -m "docs: 프로젝트 소개 추가"
git log --oneline
```

- **목적:** 변경을 확인하고 필요한 파일만 하나의 커밋으로 기록합니다.
- **흐름:** 작업 파일 확인 → 스테이징 → 커밋 → 이력 확인 순서입니다.
- **결과:** 현재 브랜치에 새 커밋이 생깁니다.
- **실무 포인트:** `git add .` 전에 `git status`와 `git diff`로 포함 범위를 확인하면 불필요한 파일이 섞이는 일을 줄일 수 있습니다.

## 커밋과 브랜치

커밋은 프로젝트의 스냅샷이 아니라 이전 커밋과 연결된 변경 이력의 한 지점입니다. 브랜치는 특정 커밋을 가리키는 이동 가능한 이름입니다. 새 브랜치를 만들면 기준 이력은 공유하지만 이후 커밋은 독립적으로 쌓입니다.

```bash
git switch -c feature/profile
git branch --show-current
```

## 복습 질문 및 답변

### Q1. GitHub 없이도 Git을 사용할 수 있나요?

<details>
<summary>답</summary>

가능합니다. Git의 커밋, 브랜치, 병합은 로컬에서 동작합니다. GitHub는 원격 공유와 협업 기능을 더합니다.

</details>

### Q2. 커밋은 파일 전체를 매번 복사하는 것인가요?

<details>
<summary>답</summary>

사용자 관점에서는 특정 시점의 프로젝트 상태를 가리키지만, Git은 객체와 참조를 효율적으로 저장하며 커밋을 부모 이력과 연결합니다.

</details>

### Q3. 브랜치를 사용하는 이유는 무엇인가요?

<details>
<summary>답</summary>

기준 브랜치를 안정적으로 유지하면서 기능, 수정, 실험을 독립적으로 진행하고 검토 후 병합하기 위해서입니다.

</details>

## 요약

Git은 변경 이력을 관리하고 GitHub는 그 이력을 중심으로 협업하게 합니다. 작은 목적 단위로 커밋하고 작업별 브랜치를 사용하는 습관이 안전한 협업의 출발점입니다.
