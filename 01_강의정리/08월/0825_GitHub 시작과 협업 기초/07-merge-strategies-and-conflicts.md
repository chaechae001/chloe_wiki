# 병합 전략과 충돌 해결

병합 방식은 결과 코드뿐 아니라 저장소 이력을 읽고 되돌리는 방식까지 결정합니다.

**핵심 키워드:** Merge Commit, Squash, Rebase, 충돌, 이력

## 핵심 내용

- Merge Commit은 브랜치의 개별 커밋과 병합 지점을 보존합니다.
- Squash and Merge는 PR의 여러 커밋을 하나로 합쳐 기준 브랜치에 반영합니다.
- Rebase and Merge는 커밋을 기준 브랜치 끝에 다시 배치해 선형 이력을 만듭니다.
- 충돌은 같은 부분에 양립할 수 없는 변경이 있을 때 사람이 최종 내용을 결정해야 하는 상태입니다.
- 팀은 저장소 설정과 기여 규칙에서 허용할 병합 방식을 합의해야 합니다.

## 병합 방식 비교

| 방식 | 장점 | 주의점 | 적합한 상황 |
|---|---|---|---|
| Merge Commit | 브랜치 구조와 커밋 보존 | 이력이 복잡해질 수 있음 | 작업 맥락 보존이 중요할 때 |
| Squash and Merge | PR당 한 커밋으로 간결 | 세부 커밋 경계가 사라짐 | 작은 기능 PR을 정돈할 때 |
| Rebase and Merge | 선형 이력 유지 | 커밋 기반이 바뀜 | 커밋 품질이 높고 정책이 명확할 때 |

## 로컬 병합과 충돌

```bash
git switch main
git pull --ff-only
git merge feature/search-filter
git status
```

- **목적:** 기능 브랜치의 변경을 현재 브랜치에 통합합니다.
- **흐름:** 대상 브랜치 이동 → 최신화 → 병합 → 상태 확인입니다.
- **결과:** 자동 병합되거나 충돌 파일이 표시됩니다.
- **실무 포인트:** 충돌 해결 전 양쪽 변경의 의도를 확인하고, 해결 후 테스트를 다시 실행합니다.

## 충돌 해결 순서

1. `git status`로 충돌 파일을 확인합니다.
2. 충돌 표시의 양쪽 내용을 읽고 최종 코드를 결정합니다.
3. 관련 테스트와 린트를 실행합니다.
4. 해결한 파일을 `git add`로 표시합니다.
5. merge 또는 rebase 절차를 완료합니다.

```bash
git add src/search.js
git commit
```

진행이 잘못되었다면 무리하게 파일을 덮지 말고 `git merge --abort`처럼 현재 작업을 중단할 수 있는지 먼저 확인합니다.

## rebase 주의사항

Rebase는 커밋을 새 부모 위에 다시 생성하므로 커밋 식별자가 바뀝니다. 혼자 사용하는 로컬 작업 브랜치를 최신화할 때는 유용하지만, 다른 사람이 이미 기반으로 삼은 공개 브랜치를 재작성하면 혼란이 생깁니다.

## 복습 질문 및 답변

### Q1. Squash and Merge의 핵심 효과는 무엇인가요?

<details>
<summary>답</summary>

PR 안의 여러 커밋을 하나의 커밋으로 합쳐 기준 브랜치 이력을 간결하게 만드는 것입니다.

</details>

### Q2. 충돌은 Git의 오류인가요?

<details>
<summary>답</summary>

오류라기보다 자동으로 어느 변경을 선택해야 할지 판단할 수 없어 사람의 결정을 요청하는 상태입니다.

</details>

### Q3. rebase는 언제 특히 조심해야 하나요?

<details>
<summary>답</summary>

이미 원격에 게시되어 다른 사람이 기반으로 사용 중인 커밋을 재작성할 때 특히 조심해야 합니다.

</details>

## 요약

Merge Commit, Squash, Rebase는 같은 코드를 만들 수 있어도 이력의 형태가 다릅니다. 팀의 추적·되돌리기 방식에 맞는 정책을 정하고, 충돌은 의도를 확인한 뒤 검증하며 해결해야 합니다.
