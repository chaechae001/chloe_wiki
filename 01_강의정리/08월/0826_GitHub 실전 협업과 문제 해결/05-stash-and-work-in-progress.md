# 작업 중 변경 임시 보관

긴급 작업 때문에 브랜치를 바꿔야 할 때 미완성 코드를 억지로 커밋하지 않고 잠시 보관할 수 있습니다.

**핵심 키워드:** stash, apply, pop, working tree, WIP

## 핵심 내용

- 브랜치 전환 전 `git status`로 작업 트리가 깨끗한지 확인합니다.
- 의미 있는 작업 단위가 완성되었다면 커밋이 가장 명확한 보관 방법입니다.
- 아직 커밋하기 어려운 변경은 stash에 임시 보관할 수 있습니다.
- `apply`는 적용 후 stash를 남기고 `pop`은 적용 성공 시 목록에서 제거합니다.
- stash 복원도 충돌할 수 있으므로 복원 후 상태와 테스트를 확인합니다.

## 왜 전환이 거부될까요?

다른 브랜치로 이동하면서 현재 변경이 덮어써질 가능성이 있으면 Git은 전환을 막습니다. 이때 변경을 버리거나 강제로 덮기보다 커밋 또는 stash를 선택합니다.

| 선택 | 적합한 상황 | 이력에 남는가 |
|---|---|---|
| 커밋 | 하나의 의미 있는 상태가 완성됨 | 남음 |
| stash | 미완성·실험 변경을 잠시 치움 | 일반 커밋 이력에는 안 남음 |
| 변경 폐기 | 정말 필요 없는 수정 | 남지 않으며 복구가 어려울 수 있음 |

## stash 사용 흐름

```bash
git status
git stash push -m "검색 화면 작업 중"
git stash list
git switch hotfix/urgent
# 긴급 작업 후 원래 브랜치로 복귀
git stash apply stash@{0}
git status
```

- **목적:** 현재 변경을 임시 저장하고 깨끗한 작업 트리로 전환합니다.
- **흐름:** 상태 확인 → 이름 있는 stash 생성 → 목록 확인 → 전환 → 복원입니다.
- **결과:** 미완성 변경을 커밋 이력에 넣지 않고 다시 이어갈 수 있습니다.
- **실무 포인트:** 여러 stash가 있다면 번호만 믿지 말고 메시지와 목록을 확인합니다.

## apply와 pop

`git stash apply`는 복원 후 항목을 유지하므로 안전하게 확인한 뒤 직접 삭제할 수 있습니다. `git stash pop`은 적용과 제거를 한 번에 시도합니다. 중요한 변경이거나 충돌 가능성이 있으면 apply 후 검증하는 방식이 더 신중합니다.

추적하지 않은 새 파일은 기본 stash에 포함되지 않을 수 있습니다. 필요한 경우 옵션의 의미를 확인하고, 비밀정보나 대용량 파일을 stash에 무심코 넣지 않습니다.

## 실습

1. 현재 변경을 메시지와 함께 stash하고 목록을 확인하세요.
2. `apply`와 `pop`의 차이를 설명하세요.
3. 복원 중 충돌이 발생했을 때 확인할 항목을 적으세요.

## 복습 질문 및 답변

### Q1. stash는 커밋을 대신할 수 있나요?

<details>
<summary>답</summary>

장기적인 작업 기록을 대신하지 않습니다. 잠깐 작업 트리를 비울 때 쓰는 임시 보관이며, 중요한 완성 상태는 커밋으로 남기는 편이 안전합니다.

</details>

### Q2. `stash pop`은 언제 주의해야 하나요?

<details>
<summary>답</summary>

복원과 목록 제거를 함께 수행하므로 중요한 stash이거나 충돌 가능성이 높다면 `apply`로 먼저 검증하는 편이 좋습니다.

</details>

### Q3. stash 복원에서도 충돌이 생길 수 있나요?

<details>
<summary>답</summary>

가능합니다. stash를 만든 뒤 대상 브랜치의 같은 부분이 달라졌다면 자동 적용하지 못할 수 있습니다.

</details>

## 요약

stash는 미완성 변경을 잠시 치우는 도구입니다. 상태 확인, 이름 있는 보관, 정확한 항목 선택과 복원 후 검증을 습관화해야 작업을 잃지 않습니다.
