# Pull Request 작성과 리뷰

Pull Request는 완성된 코드만 보여 주는 곳이 아니라 변경의 이유와 검증 근거를 공유하는 대화 공간입니다.

**핵심 키워드:** Base, Head, Reviewer, 피드백, 병합

## 핵심 내용

- PR 생성 전 base와 head 브랜치, 변경 파일과 커밋 범위를 확인합니다.
- 제목은 변경 목적을 한 문장으로, 본문은 배경·변경·검증·영향으로 구성합니다.
- 작성자는 리뷰하기 쉬운 크기로 변경을 나누고 자체 검토를 먼저 수행합니다.
- 리뷰어는 사람보다 코드와 요구사항에 집중하고 근거와 대안을 제시합니다.
- 승인, 자동 검사, 충돌 상태와 팀 병합 정책을 모두 확인한 뒤 병합합니다.

## PR의 구성

| 항목 | 확인할 내용 |
|---|---|
| Base | 변경을 받아들일 대상 저장소와 브랜치 |
| Head | 변경을 제공하는 저장소와 브랜치 |
| Commits | PR에 포함된 작업 이력 |
| Files changed | 최종 코드 차이 |
| Checks | 테스트, 빌드, 린트 등 자동 검사 |
| Reviewers | 검토를 요청할 담당자 |

## 작성자의 흐름

```text
작업 완료 → diff 자체 검토 → 테스트 → 원격 푸시
→ base/head 확인 → PR 설명 작성 → Reviewer 지정
→ 피드백 반영 → 재검증 → 병합 준비
```

- **목적:** 리뷰어가 변경 의도와 위험을 빠르게 판단하도록 돕습니다.
- **흐름:** 코드 검토와 검증을 마친 뒤 설명과 근거를 함께 제출합니다.
- **결과:** 코드와 의사결정 기록이 하나의 PR에 연결됩니다.
- **실무 포인트:** “확인 부탁드립니다”만 쓰지 말고 특히 봐야 할 부분과 실행한 테스트를 구체적으로 적습니다.

## 좋은 리뷰 의견

명령형 표현보다 관찰, 위험, 질문, 제안의 순서가 효과적입니다.

```text
이 입력이 비어 있을 때 예외가 발생할 수 있습니다.
기본값을 두거나 검증 로직을 추가하는 방식은 어떨까요?
```

반드시 수정할 결함과 선택적 제안을 구분합니다. 작성자는 의견을 무조건 수용하거나 방어하기보다 요구사항과 근거를 확인하고 결정 내용을 남깁니다.

## 병합 전 확인

리뷰 승인만으로 충분하지 않을 수 있습니다. 자동 검사 통과, 최신 기준과의 충돌 여부, 배포·마이그레이션 영향, 후속 작업을 점검합니다. 병합 후에는 불필요한 작업 브랜치를 정리합니다.

## 실습

1. 로그인 검증 PR의 제목과 본문 항목을 작성하세요.
2. 모호한 리뷰 의견을 근거와 대안이 있는 문장으로 바꾸세요.
3. 병합 직전 확인할 항목을 다섯 개 적으세요.

<details>
<summary>답</summary>

예: `fix: 빈 로그인 입력 검증`. 본문에는 배경, 변경 내용, 재현·테스트 방법, 영향 범위와 관련 Issue를 적습니다. 병합 전 base/head, 승인, 자동 검사, 충돌, 배포 영향을 확인합니다.

</details>

## 체크리스트

- [ ] PR의 base와 head 방향을 확인했다.
- [ ] 변경 이유와 검증 방법을 적었다.
- [ ] 관계없는 변경을 분리했다.
- [ ] 리뷰 의견에 근거와 대안을 담았다.
- [ ] 승인·검사·충돌·영향을 확인했다.

## 복습 질문 및 답변

### Q1. PR의 Files changed를 꼭 확인해야 하는 이유는 무엇인가요?

<details>
<summary>답</summary>

최종적으로 병합될 실제 차이를 확인해 누락, 디버그 코드, 관계없는 파일이나 비밀정보가 포함되지 않았는지 검토하기 위해서입니다.

</details>

### Q2. 좋은 리뷰는 정답을 바로 지시해야 하나요?

<details>
<summary>답</summary>

항상 그렇지는 않습니다. 문제와 영향을 설명하고 질문이나 대안을 제시하면 작성자가 맥락을 공유하며 더 나은 결정을 내릴 수 있습니다.

</details>

### Q3. 승인된 PR도 병합을 미뤄야 하는 경우가 있나요?

<details>
<summary>답</summary>

자동 검사가 실패했거나 충돌이 생겼거나, 배포 순서와 데이터 변경 같은 운영 조건이 준비되지 않았다면 미뤄야 합니다.

</details>

## 요약

좋은 PR은 작은 변경, 충분한 설명, 재현 가능한 검증과 존중하는 리뷰 대화를 갖습니다. 병합은 승인 버튼이 아니라 모든 품질 조건을 확인한 뒤 내리는 팀의 결정입니다.
