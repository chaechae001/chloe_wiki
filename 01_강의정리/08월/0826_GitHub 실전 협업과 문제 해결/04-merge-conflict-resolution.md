# Merge Conflict 해결

충돌은 실패가 아니라 Git이 자동으로 선택할 수 없는 변경을 사람에게 판단해 달라고 알리는 상태입니다.

**핵심 키워드:** Conflict, HEAD, Incoming, 3-way merge, 검증

## 핵심 내용

- 같은 파일의 같은 영역을 서로 다르게 수정하면 충돌이 발생할 수 있습니다.
- 수정과 삭제가 충돌하거나 같은 함수를 다른 구조로 바꾼 경우에도 충돌할 수 있습니다.
- 충돌 마커의 현재 변경과 들어오는 변경을 읽고 최종 결과를 직접 결정합니다.
- 편집기의 Accept Both는 문법과 의미를 보장하지 않으므로 반드시 다시 다듬습니다.
- 해결 후 충돌 마커 제거, 테스트, 스테이징과 병합 완료를 확인합니다.

## 충돌 마커 읽기

```text
 <<<<<<< HEAD
현재 브랜치의 변경
 =======
병합하려는 브랜치의 변경
 >>>>>>> feature/example
```

| 구간 | 의미 |
|---|---|
| `HEAD` 쪽 | 현재 체크아웃한 브랜치의 내용 |
| 구분선 아래 | 들어오는 브랜치의 내용 |
| 최종 파일 | 사람이 양쪽 의도를 반영해 작성할 결과 |

마커 중 하나를 기계적으로 선택하기 전에 두 변경이 해결하려던 요구사항을 확인합니다. 양쪽 코드를 모두 남겨도 중복 실행, 잘못된 순서, 변수 충돌이 생길 수 있습니다.

## 안전한 해결 순서

```bash
git status
# 충돌 파일을 편집하고 테스트
git add src/example.js
git status
git commit
```

- **목적:** 충돌 파일의 최종 내용을 확정하고 병합 이력을 완료합니다.
- **흐름:** 상태 확인 → 의도 파악 → 편집 → 검증 → 해결 표시 → 완료입니다.
- **결과:** 충돌이 해소된 병합 커밋 또는 진행 중이던 rebase 결과가 만들어집니다.
- **실무 포인트:** 절차를 잘못 시작했다면 파일을 임의로 덮기 전에 `git merge --abort` 또는 해당 작업의 중단 명령을 검토합니다.

## 3-way merge의 관점

3-way merge는 공통 조상(Base), 현재 변경(Current), 들어오는 변경(Incoming)을 비교합니다. 편집기의 결과 영역은 단순히 둘 중 하나를 선택하는 곳이 아니라 세 상태를 참고해 올바른 최종 코드를 만드는 곳입니다.

## 충돌을 줄이는 습관

작업 브랜치를 짧게 유지하고, 큰 포맷 변경을 기능 작업과 분리하며, 공통 파일 담당을 조율합니다. 충돌 자체를 완전히 없앨 수는 없지만 변경 범위를 작게 하면 해결 판단이 쉬워집니다.

## 복습 질문 및 답변

### Q1. 충돌은 같은 파일을 수정하면 항상 발생하나요?

<details>
<summary>답</summary>

아닙니다. 서로 다른 영역의 변경은 자동 병합될 수 있습니다. 같은 영역의 양립하기 어려운 변경처럼 Git이 안전하게 판단하지 못할 때 충돌합니다.

</details>

### Q2. Current Change가 항상 내 코드인가요?

<details>
<summary>답</summary>

현재 체크아웃한 `HEAD` 쪽 변경을 뜻합니다. merge와 rebase 상황에 따라 체감하는 “내 것”과 다를 수 있으므로 브랜치와 진행 중인 작업을 확인해야 합니다.

</details>

### Q3. 충돌 파일을 저장하면 해결이 끝나나요?

<details>
<summary>답</summary>

아닙니다. 테스트하고 파일을 스테이징해 해결되었음을 표시한 뒤 merge 또는 rebase 절차를 완료해야 합니다.

</details>

## 요약

충돌 해결은 코드 선택이 아니라 변경 의도를 통합하는 작업입니다. 상태와 세 가지 기준을 확인하고, 최종 결과를 테스트한 뒤 Git 절차까지 완결해야 합니다.
