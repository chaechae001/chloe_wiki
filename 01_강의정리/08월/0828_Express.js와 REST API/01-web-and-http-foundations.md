# 웹과 HTTP 기초

웹 애플리케이션은 클라이언트가 요청을 보내고 서버가 상태와 데이터를 담은 응답을 돌려주는 반복으로 동작합니다.

**핵심 키워드:** 웹, HTTP, 요청, 응답, CSR·SSR

## 핵심 내용

- 웹은 URL로 자원을 식별하고 HTTP로 요청과 응답을 교환합니다.
- 요청에는 메서드, 경로, 헤더와 선택적인 본문이 포함됩니다.
- 응답에는 상태 코드, 헤더와 표현 데이터가 포함됩니다.
- 프런트엔드는 사용자 인터페이스를, 백엔드는 데이터와 비즈니스 규칙을 주로 담당합니다.
- CSR과 SSR은 화면 HTML을 주로 어디에서 만드는지에 따른 렌더링 전략입니다.

## 요청과 응답

```http
GET /articles/42 HTTP/1.1
Host: example.test
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"id":42,"title":"HTTP 이해하기"}
```

- **목적:** 클라이언트가 특정 자원의 JSON 표현을 요청합니다.
- **흐름:** URL 해석 → 서버 연결 → 요청 처리 → 상태와 본문 응답입니다.
- **결과:** 클라이언트는 상태 코드로 결과를 판단하고 본문을 사용합니다.
- **실무 포인트:** HTTP는 요청마다 의도가 드러나야 하며 성공처럼 보이는 200 응답에 오류 문자열을 넣는 방식을 피합니다.

## 정적 웹과 동적 웹

정적 웹은 준비된 파일을 거의 그대로 전달합니다. 동적 웹은 사용자, 시간, 데이터와 권한에 따라 결과를 생성합니다. 하나의 서비스 안에서도 정적 자산과 동적 API를 함께 사용할 수 있습니다.

| 구분 | CSR | SSR |
|---|---|---|
| 초기 HTML 생성 | 브라우저 JavaScript 중심 | 서버 중심 |
| 초기 표시 | 번들 다운로드 영향이 큼 | 완성된 HTML을 먼저 받을 수 있음 |
| 이후 상호작용 | 클라이언트 상태 전환에 유리 | 하이드레이션이나 추가 요청 필요 가능 |
| 고려사항 | SEO, 초기 로딩, 번들 크기 | 서버 부하, 캐시, 렌더링 비용 |

CSR과 SSR은 우열 관계가 아니라 페이지의 검색 노출, 상호작용, 캐시와 서버 비용에 맞춰 선택하는 전략입니다.

## 백엔드의 역할

백엔드는 요청을 검증하고 인증·권한, 비즈니스 규칙, 데이터 접근을 처리한 뒤 일관된 응답을 만듭니다. Express.js 같은 프레임워크는 이 흐름을 라우팅과 미들웨어로 구조화합니다.

## 복습 질문 및 답변

### Q1. URL과 HTTP 메서드는 각각 무엇을 표현하나요?

<details>
<summary>답</summary>

URL은 주로 대상 자원을 식별하고 HTTP 메서드는 그 자원에 수행하려는 조회, 생성, 수정, 삭제 등의 의도를 표현합니다.

</details>

### Q2. 동적 웹은 항상 SSR을 의미하나요?

<details>
<summary>답</summary>

아닙니다. 브라우저가 API 데이터를 받아 화면을 갱신하는 CSR도 동적 웹입니다.

</details>

### Q3. 상태 코드가 중요한 이유는 무엇인가요?

<details>
<summary>답</summary>

클라이언트와 관측 도구가 본문을 임의로 해석하지 않고 결과의 종류를 표준 방식으로 판단하도록 돕기 때문입니다.

</details>

## 요약

웹 서비스는 HTTP 요청과 응답의 계약 위에서 동작합니다. 자원, 행위, 상태와 표현을 명확히 구분하면 Express.js API 구조도 자연스럽게 이해할 수 있습니다.
