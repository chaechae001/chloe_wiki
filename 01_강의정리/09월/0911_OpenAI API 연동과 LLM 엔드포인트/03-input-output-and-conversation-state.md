# 입력·출력과 대화 상태

> LLM 요청은 단순 문자열처럼 보여도 지침, 현재 입력, 이전 상태와 출력 구조를 명확히 구분해야 합니다.

`stateless` · `conversation state` · `previous_response_id` · `token usage` · `structured contract`

## 핵심요약

- 후속 질문의 맥락은 애플리케이션 또는 API의 상태 연결 기능이 제공해야 합니다.
- 전체 대화를 계속 전송하는 방식은 단순하지만 입력 크기가 커집니다.
- Responses API에서는 이전 response ID를 연결하는 방법을 사용할 수 있습니다.
- 반환값은 사용자용 텍스트와 내부 메타데이터로 나눕니다.
- 토큰 사용량은 비용·지연 관찰에 유용하지만 사용자에게 내부 정보를 과도하게 노출하지 않습니다.

## 1. 상태 없는 요청 이해

“방금 설명한 첫 번째 항목” 같은 입력은 앞선 맥락 없이는 해석할 수 없습니다. 애플리케이션이 history를 저장해 다시 보내거나, 지원되는 상태 연결 식별자를 사용해야 합니다.

<details>
<summary>답</summary>

멀티턴은 UI의 대화 모양이 아니라 각 요청에 필요한 이전 맥락이 모델에 전달되는지로 결정됩니다.

</details>

## 2. 두 가지 상태 전략

```text
A. 앱이 history 저장 → 매 요청에 필요한 메시지 전달
B. 이전 response ID 저장 → 다음 Responses 요청에 연결
```

어느 방식이든 사용자별 격리, 보존 기간, 삭제 요청, 입력 길이 제한이 필요합니다. 이전 response를 연결할 때도 새 `instructions`가 자동 계승된다고 가정하지 말고 요청별 지침을 명시합니다.

## 3. 서비스 응답 계약

```json
{
  "reply": "생성된 답변",
  "request_id": "service-generated-id"
}
```

공급자 객체 전체를 그대로 반환하면 SDK 변경과 내부 정보가 외부 계약에 새어 나갑니다. 서비스가 약속할 필드만 추립니다.

## 코드로 보기 — 상태 식별자

### 코드 목적

후속 요청에 필요한 식별자를 서버 저장소와 연결합니다.

### 코드 흐름

1. 사용자·대화 ID로 이전 상태를 찾습니다.
2. 모델을 호출합니다.
3. 새 response ID를 저장합니다.
4. 클라이언트에는 필요한 결과만 반환합니다.

### 실행 결과 해석

서버를 여러 process로 확장한다면 process 메모리가 아니라 공유 저장소가 필요합니다.

### 실무 연결

보존 기간과 개인정보 삭제 정책은 상태 저장 방식 선택에 직접 영향을 줍니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| 대화 history vs response ID | 내용을 직접 관리하는 방식과 API 상태 연결 식별자를 관리하는 방식입니다. |
| provider ID vs service ID | 외부 공급자의 요청 식별자와 내 서비스가 발급한 추적 식별자입니다. |
| 생성 텍스트 vs metadata | 사용자에게 보여줄 내용과 운영 관찰용 정보입니다. |
