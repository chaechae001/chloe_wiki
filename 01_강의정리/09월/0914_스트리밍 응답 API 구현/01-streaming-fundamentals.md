# 스트리밍 응답의 원리

> 스트리밍은 전체 답변이 끝날 때까지 기다리지 않고, 만들어지는 조각을 먼저 보여 주는 응답 방식입니다.

`TTFT` · `token` · `chunk` · `iterator` · `buffering`

## 핵심요약

- 일반 응답은 완성본 한 번, 스트리밍은 여러 조각을 순서대로 전송합니다.
- 총 생성 시간이 같아도 첫 결과가 빨리 보이면 체감 속도가 좋아집니다.
- token은 모델의 처리 단위, chunk는 전송 단위라서 일대일 관계가 아닙니다.
- 클라이언트는 조각을 즉시 표시하면서 필요하면 완성본도 누적합니다.
- 스트리밍은 중간 실패·취소·부분 출력까지 계약에 포함해야 합니다.

## 1. 두 응답 흐름 비교

```text
일반: 요청 → 전체 생성 대기 → 완성 응답
스트림: 요청 → chunk → chunk → chunk → 완료
```

TTFT(Time To First Token)는 요청부터 첫 글자가 보일 때까지의 시간입니다. 스트리밍은 보통 전체 생성 시간을 마법처럼 없애지는 않지만, 사용자가 진행 중임을 빨리 확인하게 합니다.

긴 답변을 읽을 수 있는 상태가 빨리 시작되므로, 같은 총 대기 시간이라도 UX가 더 빠르게 느껴질 수 있습니다.

## 2. chunk를 완성본으로 모으기

```python
pieces = []
for piece in incoming_pieces:
    if not piece:
        continue
    print(piece, end="", flush=True)
    pieces.append(piece)

full_text = "".join(pieces)
```

표시와 저장은 목적이 다릅니다. 화면에는 조각을 즉시 내보내고, 대화 저장이나 감사 기록에는 `full_text`를 사용합니다. 다만 민감한 대화 원문을 기본 로그에 보관하지 않도록 별도 정책이 필요합니다.

## 3. 적용 판단

대화, 긴 설명, 코드 초안처럼 기다림이 보이는 경험이 중요한 경우에 적합합니다. 반대로 구조화 JSON 전체 검증이나 안전 후처리가 먼저 필요한 경우에는 완성 응답이 단순할 수 있습니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| token vs chunk | 모델 처리 단위와 네트워크 전송 묶음입니다. |
| TTFT vs 총 생성 시간 | 첫 표시까지의 시간과 전체 응답 완료 시간입니다. |
| 표시 vs 저장 | 즉시 UX와 완성 결과 보관은 별도 책임입니다. |
