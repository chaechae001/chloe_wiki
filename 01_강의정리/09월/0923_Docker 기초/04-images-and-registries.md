# 이미지와 레지스트리로 배포 준비하기

> 로컬에서 확인한 실행 환경을 다른 곳에서도 재사용하려면 이미지를 명확한 이름과 버전으로 관리해야 한다.

`Docker Hub` · `pull` · `push` · `tag` · `이미지 캐시`

## 핵심요약

- 이미지는 레지스트리에서 내려받거나 직접 빌드해 로컬 캐시에 보관할 수 있다.
- `pull`은 가져오기, `push`는 등록하기, `tag`는 이미지 버전 식별에 쓰인다.
- 이미지 출처와 태그를 확인하는 습관은 재현성과 보안에 중요하다.

## 1. 이미지를 가져와 실행하기

```bash
docker pull nginx:stable
docker images
docker run -d --name demo-web -p 8080:80 nginx:stable
```

레지스트리에서 가져온 이미지는 로컬에 저장된다. 이후 같은 이미지가 필요할 때는 네트워크에서 매번 내려받지 않고 로컬 캐시를 재사용할 수 있다.

## 2. 태그는 배포의 약속

태그는 이미지가 어떤 버전인지 알려주는 이름표다. 개발용, 검증용, 배포용을 구분할 때도 태그를 활용할 수 있지만, 실제 환경에서는 변경 불가능한 버전 식별자로 배포 대상을 고정하는 편이 좋다.

```bash
docker tag sample-api:dev team/sample-api:1.0.0
docker push team/sample-api:1.0.0
```

## 3. 이미지 출처 확인

공개 레지스트리 이미지는 편리하지만 출처와 유지 상태를 확인해야 한다. 필요한 기능만 담긴 신뢰 가능한 베이스 이미지를 고르고, 주기적으로 취약점 점검과 업데이트 계획을 세운다.

| 점검 항목 | 이유 |
| --- | --- |
| 이미지 출처 | 신뢰할 수 있는 제작·유지 주체인지 확인 |
| 태그·버전 | 같은 배포를 재현할 기준 확보 |
| 이미지 크기 | 다운로드·배포 시간과 공격 표면 감소 |
| 업데이트 정책 | 보안 패치 반영 계획 수립 |

## 직접 해보기

1. 레지스트리에서 이미지를 내려받는 명령을 적어 보세요.
2. `latest` 태그만 사용했을 때의 추적 문제를 설명해 보세요.
3. 로컬 이미지를 다른 이름과 태그로 연결하는 명령을 적어 보세요.

<details>
<summary>정답 보기</summary>

1. `docker pull 이미지:태그` 형식이다.
2. 시간이 지나면 같은 태그가 다른 내용으로 바뀔 수 있어 무엇을 배포했는지 모호해질 수 있다.
3. `docker tag 기존이미지 새이름:새태그`를 사용한다.

</details>

## 헷갈리기 쉬운 포인트

| 비교 | 핵심 차이 |
| --- | --- |
| pull vs push | 레지스트리에서 가져오기 vs 레지스트리에 등록하기 |
| image tag vs container name | 이미지 버전 식별자 vs 실행 인스턴스 식별자 |

### 복습 질문 및 답변

**Q1. 레지스트리는 컨테이너를 저장하나요?**

<details>
<summary>답</summary>

일반적으로 레지스트리는 실행 가능한 이미지와 그 메타데이터를 저장한다. 컨테이너는 특정 호스트에서 이미지로부터 실행된 인스턴스다.

</details>

**Q2. 태그를 바꾸면 이미지 레이어가 복사되나요?**

<details>
<summary>답</summary>

태그는 보통 기존 이미지에 다른 이름표를 붙이는 작업이다. 새로운 레이어를 만드는 빌드와는 다르다.

</details>

**Q3. 이미지가 커지면 어떤 비용이 생기나요?**

<details>
<summary>답</summary>

전송·저장 시간이 늘고 배포가 느려질 수 있다. 불필요한 파일과 의존성을 줄이는 이유다.

</details>

## 한 줄 정리

> 이미지는 레지스트리와 태그를 통해 공유되며, 출처와 버전을 분명히 할수록 배포를 더 잘 재현할 수 있다.
