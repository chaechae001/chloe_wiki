# Agent, Tool, Memory로 확장하는 대화 흐름

> Agent는 답을 바로 쓰기 전에 필요한 도구를 고르고, Memory는 대화가 이어지는 데 필요한 상태를 관리한다.

`Agent` · `Tool` · `Memory` · `상태` · `권한`

## 핵심요약

- Tool은 검색, 계산, 데이터 조회처럼 LLM 밖의 기능을 제공한다.
- Agent는 작업 목표에 맞게 어떤 Tool을 쓸지 판단하는 실행 흐름이다.
- Memory는 대화·작업 상태를 보관하지만, 저장 범위와 개인정보를 함께 설계해야 한다.

## 1. 도구를 쓰는 이유

```mermaid
flowchart LR
    A["사용자 요청"] --> B["Agent 판단"]
    B --> C["Tool 호출"]
    C --> D["관찰 결과"]
    D --> E["최종 응답"]
```

도구 호출은 강력하지만 실행 권한과 입력 검증이 필요하다. 특히 외부 시스템을 바꾸는 도구는 읽기 작업과 쓰기 작업을 구분하고 승인 경계를 둔다.

## 직접 해보기

2. Memory에 모두 저장하지 말아야 하는 정보의 예를 들어 보세요.
3. Agent가 잘못된 Tool을 골랐을 때 필요한 보호 장치를 적어 보세요.

<details>
<summary>정답 보기</summary>

1. 모델의 고정 지식 대신 최신 외부 결과를 조회해야 할 수 있다.
2. 인증 정보나 불필요한 개인정보는 저장 범위를 제한해야 한다.
3. 허용 도구 목록, 입력 검증, 실행 로그, 사람 승인 단계를 둘 수 있다.

</details>

## 헷갈리기 쉬운 포인트

| 비교 | 차이 |
| --- | --- |
| Agent vs Tool | 도구 사용을 판단하는 흐름 vs 실제 기능을 수행하는 인터페이스 |
| Memory vs 모델 학습 | 세션·애플리케이션 상태 저장 vs 모델 자체의 파라미터 변경 |

### 복습 질문 및 답변

**Q1. Tool 결과를 그대로 사용자에게 보여줘도 되나요?**

<details>
<summary>답</summary>

도구 결과의 신뢰성·민감성·형식을 확인하고, 필요한 근거와 한계를 함께 전달해야 한다.

</details>

**Q2. Memory가 길어질수록 어떤 문제가 생기나요?**

<details>
<summary>답</summary>

토큰 비용과 지연이 늘고, 오래된 정보가 현재 요청에 방해가 될 수 있다.

</details>

**Q3. Agent의 권한은 어떻게 시작하는 편이 좋은가요?**

<details>
<summary>답</summary>

필요한 최소 권한만 주고, 위험한 변경 작업은 명시적 승인 뒤에 실행하도록 설계하는 편이 안전하다.

</details>
