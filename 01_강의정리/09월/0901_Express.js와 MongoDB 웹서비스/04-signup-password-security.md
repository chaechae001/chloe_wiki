# 회원가입과 비밀번호 보안

회원가입은 입력 검증, 중복 방지와 비밀번호 해시를 하나의 원자적인 흐름으로 다뤄야 합니다. 비밀번호 원문은 저장하거나 로그에 남기지 않습니다.

**핵심 키워드:** validation, unique index, password hash, salt, bcrypt

## 가입 흐름

```text
입력 정규화 → 형식 검증 → 비밀번호 정책 확인
→ 안전한 해시 생성 → 사용자 저장 → 최소 정보만 응답
```

```javascript
userSchema.pre("save", async function () {
  if (!this.isModified("passwordHash")) return;
  this.passwordHash = await bcrypt.hash(this.passwordHash, 12);
});

userSchema.methods.verifyPassword = function (candidate) {
  return bcrypt.compare(candidate, this.passwordHash);
};
```

예시는 구조를 설명하기 위한 것입니다. 실제 구현에서는 원문 필드와 해시 필드를 명확히 분리하고, 프로젝트의 라이브러리 권고와 성능 기준에 따라 비용 값을 정합니다.

## 중복과 경쟁 조건

가입 전에 이메일을 조회하는 것만으로는 동시에 들어온 요청을 막지 못합니다. 정규화된 이메일에 고유 인덱스를 두고 저장 시 발생하는 중복 키 오류를 사용자 친화적인 충돌 응답으로 변환합니다.

## 해시 선택

SHA-1 같은 빠른 범용 해시는 비밀번호 저장에 적합하지 않습니다. salt와 비용 조절을 제공하는 Argon2id, scrypt 또는 bcrypt 같은 전용 방식을 사용하고 비밀 값은 로그·응답·템플릿에서 제외합니다.

## 체크리스트

- [ ] 서버에서 가입 입력을 검증한다.
- [ ] 비밀번호 원문을 저장·기록하지 않는다.
- [ ] 전용 비밀번호 해시를 사용한다.
- [ ] 고유 인덱스로 중복을 방지한다.
- [ ] 사용자 응답에서 민감 필드를 제외한다.

## 복습 질문 및 답변

### Q1. 단순 SHA 해시가 비밀번호 저장에 부적합한 이유는 무엇인가요?

<details>
<summary>답</summary>

너무 빠르게 계산되어 유출 시 대량 대입 공격 비용이 낮기 때문입니다.

</details>

### Q2. 가입 전 중복 조회만으로 충분하지 않은 이유는 무엇인가요?

<details>
<summary>답</summary>

두 요청이 동시에 조회를 통과할 수 있으므로 데이터베이스의 고유 제약이 최종 방어선이어야 합니다.

</details>

### Q3. 해시가 같으면 원문 비밀번호도 같은가요?

<details>
<summary>답</summary>

적절한 무작위 salt를 쓰면 같은 비밀번호라도 저장된 해시가 달라질 수 있으며, 검증 함수가 salt 정보를 이용해 비교합니다.

</details>
