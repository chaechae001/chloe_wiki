# EBS와 EFS 스토리지

> 저장소는 용량만 비교하는 것이 아니라 접근 방식, 공유 범위, 성능 단위와 장애 경계를 기준으로 선택해야 합니다.

`EBS` · `EFS` · `block storage` · `file storage` · `snapshot`

## 핵심요약

- EBS는 EC2에 디스크처럼 연결하는 블록 스토리지입니다.
- EFS는 여러 인스턴스가 파일 경로로 공유하는 관리형 파일 시스템입니다.
- EBS 볼륨은 AZ와 연결되며 스냅샷으로 백업·복제할 수 있습니다.
- 성능은 IOPS, 처리량, 지연 시간을 워크로드 패턴과 함께 봅니다.
- 영구 저장과 백업은 서로 다른 목적이므로 둘 다 설계해야 합니다.

## 1. 블록과 파일 스토리지

블록 스토리지는 운영체제가 디스크 블록처럼 포맷해 사용하고, 파일 스토리지는 여러 클라이언트가 디렉터리와 파일 이름으로 접근합니다.

<details>
<summary>답</summary>

데이터베이스처럼 낮은 지연과 디스크 제어가 중요하면 블록 스토리지가 자연스럽고, 여러 서버가 같은 콘텐츠 디렉터리를 공유하면 파일 스토리지가 편리합니다.

</details>

## 2. EBS

EBS는 인스턴스와 분리된 영구 블록 볼륨입니다. 인스턴스를 교체해도 볼륨 생명주기를 별도로 관리할 수 있고, 스냅샷을 만들어 백업하거나 다른 위치에 새 볼륨을 생성할 수 있습니다.

| 워크로드 | 우선 비교할 특성 | 예시 선택 방향 |
|---|---|---|
| 운영체제·일반 앱 | 균형 잡힌 가격·성능 | 범용 SSD |
| 트랜잭션 DB | 지속 IOPS와 낮은 지연 | 프로비저닝 IOPS SSD |
| 대용량 순차 처리 | 처리량 | 처리량 최적화 HDD |
| 드문 대용량 접근 | 낮은 저장 비용 | 콜드 HDD |

## 3. EFS

EFS는 네트워크 파일 시스템으로 여러 AZ의 여러 인스턴스가 같은 파일을 공유할 수 있습니다. 각 AZ의 마운트 경로, 네트워크 접근과 보안 그룹을 함께 구성해야 합니다.

## 4. 성능 지표

- **IOPS**: 초당 처리하는 입출력 작업 수입니다.
- **Throughput**: 초당 전송하는 데이터 양입니다.
- **Latency**: 한 작업이 완료되기까지 걸리는 시간입니다.

작은 요청이 많은 데이터베이스는 IOPS와 지연이 중요하고, 큰 파일을 연속 처리하는 분석은 처리량이 더 중요할 수 있습니다.

## 5. 지속성, 백업, 암호화

영구 볼륨이라고 해서 실수 삭제나 데이터 손상까지 자동으로 복구되는 것은 아닙니다. 스냅샷 주기, 보존 정책, 복구 시험과 저장·전송 암호화를 함께 설계합니다.

### 복습 질문 및 답변

**Q1. EBS 볼륨을 만들면 어느 인스턴스에서나 바로 연결할 수 있나요?**

<details>
<summary>답</summary>

볼륨과 인스턴스의 위치와 볼륨 유형의 연결 제약을 확인해야 합니다. 다른 위치로 옮길 때는 스냅샷을 이용해 새 볼륨을 만드는 흐름을 사용합니다.

</details>

**Q2. EFS는 보안 그룹과 무관한가요?**

<details>
<summary>답</summary>

아닙니다. 마운트 경로까지의 네트워크 접근을 보안 그룹으로 제어하고 파일 시스템 권한과 암호화도 함께 적용해야 합니다.

</details>

**Q3. 가장 높은 성능 등급을 고르면 항상 좋은가요?**

<details>
<summary>답</summary>

필요 이상의 성능은 비용 낭비가 됩니다. 실제 입출력 패턴과 지표를 측정해 목표 성능을 만족하는 가장 단순한 구성을 선택합니다.

</details>

## 한 줄 정리

> EBS와 EFS는 접근 방식과 공유 범위가 다르므로 워크로드의 성능·위치·복구 요구로 선택합니다.
