# 로드 밸런싱과 오토 스케일링

> 고가용성은 서버를 많이 두는 것만으로 완성되지 않고, 정상 서버로 트래픽을 보내고 필요한 수를 자동으로 유지해야 합니다.

`ELB` · `ALB` · `NLB` · `Target Group` · `Auto Scaling`

## 핵심요약

- 로드 밸런서는 여러 대상에 트래픽을 분산하고 상태를 확인합니다.
- ALB는 HTTP 계층의 콘텐츠 기반 라우팅에 적합합니다.
- NLB는 TCP·UDP 계층의 낮은 지연과 높은 처리량에 적합합니다.
- Auto Scaling Group은 최소·최대·원하는 용량 안에서 인스턴스 수를 유지합니다.
- 다중 AZ, 헬스 체크와 확장 정책을 함께 구성해야 고가용성이 높아집니다.

## 1. 단일 인스턴스의 한계

한 인스턴스만 사용하면 장애와 배포, 트래픽 급증이 모두 서비스 중단으로 이어질 수 있습니다. 여러 AZ에 복제본을 두고 앞단에서 정상 대상만 선택하면 장애 영향을 줄일 수 있습니다.

<details>
<summary>답</summary>

인스턴스를 여러 개 만드는 것만으로는 부족합니다. 사용자가 접근할 단일 진입점, 대상 상태 확인, 트래픽 분배와 부족한 인스턴스를 보충하는 자동화가 필요합니다.

</details>

## 2. Listener와 Target Group

```text
Client → Listener → Routing rule → Target Group → Healthy instances
```

Listener는 프로토콜과 포트에서 요청을 받고 규칙을 평가합니다. Target Group은 요청을 처리할 대상과 헬스 체크 기준을 묶습니다.

## 3. ALB와 NLB

| 유형 | 계층 | 잘 맞는 상황 |
|---|---|---|
| ALB | HTTP·HTTPS 애플리케이션 계층 | 경로·호스트 기반 라우팅, 웹 API |
| NLB | TCP·UDP 전송 계층 | 낮은 지연, 높은 처리량, 연결 중심 서비스 |

선택은 단순 성능 순위가 아니라 필요한 프로토콜과 라우팅 기능을 기준으로 합니다.

## 4. Auto Scaling Group

Auto Scaling Group은 시작 템플릿을 이용해 인스턴스를 만들고 최소, 최대, 원하는 용량 범위에서 수를 유지합니다. 인스턴스가 비정상이면 교체하고 수요가 변하면 확장하거나 축소합니다.

## 5. 조정 정책과 안정성

- **대상 추적**: CPU나 요청량 같은 지표를 목표값에 맞춥니다.
- **단계 조정**: 경보 수준에 따라 증감 폭을 달리합니다.
- **예약 조정**: 예측 가능한 시간대에 미리 용량을 바꿉니다.

급격한 반복 확장을 막기 위해 준비 시간, 평가 기간, 축소 지연과 최대 용량을 조정합니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| 로드 밸런싱 vs 오토 스케일링 | 기존 대상에 트래픽을 분배하는 일과 대상 수를 조절하는 일입니다. |
| ALB vs NLB | 애플리케이션 내용 기반 라우팅과 전송 계층 연결 처리입니다. |
| 헬스 체크 vs 모니터링 | 트래픽 대상의 생존 판단과 시스템 상태의 폭넓은 관찰입니다. |

### 복습 질문 및 답변

**Q1. 로드 밸런서가 있으면 인스턴스 수가 자동으로 늘어나나요?**

<details>
<summary>답</summary>

아닙니다. 로드 밸런서는 트래픽을 분산하고 Auto Scaling Group이 정책에 따라 인스턴스 수를 조절합니다.

</details>

**Q2. 헬스 체크 실패 대상을 즉시 삭제해야 하나요?**

<details>
<summary>답</summary>

일시적 준비 지연을 장애로 오판하지 않도록 임계값과 유예 시간을 정합니다. 지속적으로 실패하면 트래픽에서 제외하고 교체합니다.

</details>

**Q3. 평균 CPU만으로 모든 확장 정책을 정해도 되나요?**

<details>
<summary>답</summary>

워크로드 병목이 요청 수, 큐 길이, 메모리나 외부 의존성일 수 있습니다. 사용자 경험과 가장 가까운 지표를 함께 선택해야 합니다.

</details>

## 한 줄 정리
