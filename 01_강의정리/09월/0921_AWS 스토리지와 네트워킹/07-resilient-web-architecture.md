# AWS 서비스로 탄탄한 웹 아키텍처 만들기

> 좋은 아키텍처는 서비스를 많이 쓰는 구성이 아니라, 성능·가용성·보안·비용 요구를 가장 단순한 책임 구조로 충족하는 구성입니다.

`architecture` · `multi-AZ` · `three-tier` · `observability` · `cost`

## 핵심요약

- 웹 아키텍처는 DNS·전송·컴퓨팅·데이터·관찰 계층으로 나눕니다.
- 정적 콘텐츠와 동적 요청을 분리하면 원본 부하를 줄일 수 있습니다.
- 애플리케이션과 데이터베이스는 프라이빗 서브넷에 배치합니다.
- Multi-AZ, 로드 밸런싱, 자동 확장과 DB 장애 조치를 함께 검증합니다.
- 보안·복구·비용·관찰 가능성을 설계 초기부터 포함합니다.

## 1. 단순 구조에서 시작하기

초기에는 하나의 애플리케이션과 데이터베이스로 요구를 검증할 수 있습니다. 단일 장애 지점과 용량 한계를 측정한 뒤 책임을 분리하며 발전시키는 편이 복잡한 구조를 먼저 만드는 것보다 안전합니다.

<details>
<summary>답</summary>

관리형 서비스를 많이 연결한다고 자동으로 좋은 구조가 되지는 않습니다. 각 서비스가 해결하는 장애·성능·운영 문제와 추가 비용을 설명할 수 있어야 합니다.

</details>

## 2. 계층별 책임

```text
Route 53
   ↓
CloudFront ── static path → private S3 origin
   ↓ dynamic path
Load Balancer across AZs
   ↓
Private application subnets + Auto Scaling
   ↓
RDS Multi-AZ / Read Replica
```

Route 53은 이름 해석, CloudFront는 엣지 전송, 로드 밸런서는 정상 대상 분배, Auto Scaling은 컴퓨팅 용량 유지, RDS는 관계형 데이터 운영을 맡습니다.

## 3. 가용성과 복구

- 여러 AZ에 컴퓨팅 대상을 분산합니다.
- 헬스 체크 실패 대상을 자동 제외하고 교체합니다.
- 데이터베이스 장애 조치와 애플리케이션 재연결을 함께 시험합니다.
- 백업에서 실제 복원하고 복구 시간과 데이터 손실 목표를 측정합니다.

## 4. 보안과 관찰

인터넷 진입점만 공개하고 내부 계층은 Security Group 참조로 연결합니다. 로그, 지표, 추적, 감사 기록을 수집하고 사용자 지연·오류율·처리량·자원 사용량을 서비스 목표와 연결합니다.

## 5. 비용과 단계적 개선

캐시 적중률, 컴퓨팅 사용률, 데이터베이스 부하, 저장 등급과 데이터 전송을 함께 관찰합니다. 가용성 수준이 높아질수록 중복 자원 비용도 커지므로 사업 영향과 복구 목표에 맞춰 단계적으로 구성합니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| 가용성 vs 확장성 | 장애에도 지속하는 능력과 수요 증가를 처리하는 능력입니다. |
| 정적 경로 vs 동적 경로 | 캐시에 오래 둘 수 있는 응답과 요청 맥락에 따라 계산하는 응답입니다. |
| 모니터링 vs 복구 시험 | 상태를 관찰하는 일과 장애 후 실제로 되살리는 검증입니다. |

### 복습 질문 및 답변

**Q1. 모든 계층을 Multi-AZ로 만들면 무조건 충분한가요?**

<details>
<summary>답</summary>

아닙니다. 애플리케이션 상태, 데이터 복제, DNS 캐시, 외부 의존성과 운영 절차도 장애 시나리오에 포함해야 합니다.

</details>

**Q2. CloudFront가 있으면 로드 밸런서가 필요 없나요?**

<details>
<summary>답</summary>

역할이 다릅니다. CloudFront는 엣지 전송과 캐시를 담당하고, 로드 밸런서는 원본 애플리케이션의 정상 대상에 요청을 분배합니다.

</details>

**Q3. 아키텍처 품질을 어떤 지표로 판단하나요?**

<details>
<summary>답</summary>

사용자 지연과 오류율, 가용성 목표, 복구 시간·데이터 손실, 처리량, 배포 실패율과 단위 비용을 함께 봅니다.

</details>

## 한 줄 정리

> 탄탄한 웹 아키텍처는 계층별 책임을 분리하고 장애·보안·비용을 측정 가능한 목표로 검증합니다.
