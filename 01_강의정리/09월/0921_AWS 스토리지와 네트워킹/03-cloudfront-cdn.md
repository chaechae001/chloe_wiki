# CloudFront와 CDN

> CDN은 원본을 복제하는 기술이 아니라, 사용자 가까운 캐시와 정책으로 전송 경로를 최적화하는 계층입니다.

`CloudFront` · `CDN` · `Edge Location` · `Origin` · `cache`

## 핵심요약

- CloudFront는 Edge Location에서 콘텐츠를 캐시하는 CDN입니다.
- Origin은 S3, 로드 밸런서나 웹 서버처럼 원본을 제공하는 대상입니다.
- 캐시 적중은 원본 부하와 사용자 지연을 줄입니다.
- TTL과 캐시 키는 최신성, 적중률과 비용 사이의 균형을 결정합니다.
- 정적·동적 경로를 구분해 각 요청을 적합한 원본으로 보낼 수 있습니다.

## 1. CDN이 필요한 이유

사용자와 원본 서버의 거리가 멀수록 네트워크 왕복 시간이 늘어납니다. CDN은 자주 요청되는 콘텐츠를 가까운 엣지에 저장해 원본까지 가는 요청 수와 지연을 줄입니다.

<details>
<summary>답</summary>

CDN은 모든 요청을 영구 저장하는 복제 저장소가 아닙니다. 캐시 정책에 따라 응답을 임시 보관하고 필요할 때 원본에서 새 데이터를 가져옵니다.

</details>

## 2. 캐시 흐름

```text
Viewer → Edge cache
           ├─ hit  → cached response
           └─ miss → Origin → cache → response
```

첫 요청이 캐시 미스라면 원본에서 가져온 뒤 캐시에 저장합니다. 이후 같은 캐시 키의 요청은 유효 기간 안에서 엣지 응답을 받을 수 있습니다.

## 3. Origin과 동작 경로

| 요청 유형 | 적합한 Origin | 정책 예시 |
|---|---|---|
| 이미지·스타일 파일 | S3 | 긴 캐시, 파일명 버전 |
| 웹 API | 로드 밸런서·애플리케이션 | 짧거나 선택적 캐시 |
| 다운로드 | S3 | 압축·범위 요청·서명 URL |

## 4. 캐시 키와 무효화

캐시 키에 불필요한 헤더·쿠키·쿼리를 많이 포함하면 같은 콘텐츠가 여러 사본으로 나뉘어 적중률이 낮아집니다. 새 버전은 파일명 변경을 우선하고 긴급한 경우 무효화를 사용할 수 있습니다.

## 5. 보안과 관찰

- HTTPS를 기본으로 사용합니다.
- 원본 직접 접근을 제한합니다.
- 서명 URL·쿠키로 제한 콘텐츠를 보호합니다.
- 접근 로그와 캐시 적중률, 원본 지연, 오류율을 함께 봅니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| Edge cache vs Origin | 사용자 가까운 임시 응답과 원본 데이터 제공자입니다. |
| TTL vs DNS TTL | 콘텐츠 캐시 수명과 이름 해석 결과의 캐시 수명입니다. |
| 정적 vs 동적 콘텐츠 | 같은 요청에 같은 응답이 쉬운 데이터와 요청 맥락에 따라 달라지는 데이터입니다. |

### 복습 질문 및 답변

**Q1. CDN을 쓰면 원본 서버가 필요 없나요?**

<details>
<summary>답</summary>

아닙니다. 캐시에 없는 데이터와 만료된 콘텐츠는 원본에서 가져오며 동적 요청도 원본 처리가 필요할 수 있습니다.

</details>

**Q2. TTL을 길게 하면 무조건 좋은가요?**

<details>
<summary>답</summary>

적중률은 높아질 수 있지만 변경 반영이 늦어집니다. 콘텐츠 변경 방식과 최신성 요구에 맞춰 정합니다.

</details>

**Q3. 캐시 적중률만 높으면 성능이 충분한가요?**

<details>
<summary>답</summary>

오류율, 사용자 지연, 원본 응답 시간과 전송 비용도 함께 봐야 합니다. 잘못된 응답을 오래 캐시하면 높은 적중률이 오히려 문제가 됩니다.

</details>

## 한 줄 정리

> CloudFront는 엣지 캐시와 요청 정책을 통해 원본 부하를 줄이고 전 세계 사용자에게 콘텐츠를 빠르게 전달합니다.
