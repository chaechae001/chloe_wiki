# Amazon RDS와 관리형 데이터베이스

> 관리형 데이터베이스의 핵심 가치는 SQL을 대신 써주는 것이 아니라, 설치·패치·백업·장애 조치 같은 운영 부담을 표준화하는 데 있습니다.

`RDS` · `Read Replica` · `Multi-AZ` · `backup` · `Aurora`

## 핵심요약

- RDS는 관계형 데이터베이스 엔진을 관리형 서비스로 제공합니다.
- Read Replica는 읽기 부하 분산을, Multi-AZ는 장애 대응을 우선합니다.
- 자동 백업과 수동 스냅샷은 복구 목적과 보존 방식이 다릅니다.
- 스토리지 자동 확장은 용량 부족을 줄이지만 쿼리 병목을 해결하지는 않습니다.
- Aurora는 분산 저장 구조와 빠른 장애 조치를 제공하는 관리형 관계형 데이터베이스입니다.

## 1. EC2의 DB와 RDS

EC2에 데이터베이스를 직접 설치하면 운영체제, DB 엔진, 패치, 백업과 고가용성 구성을 사용자가 관리합니다. RDS는 이 중 반복적인 인프라 운영을 서비스가 맡고 사용자는 스키마, 쿼리, 계정과 데이터 품질에 더 집중할 수 있게 합니다.

<details>
<summary>답</summary>

관리형이라는 말은 운영 책임이 완전히 사라진다는 뜻이 아닙니다. 사용자는 접근 권한, 데이터 모델, 쿼리 성능, 백업 보존과 복구 검증을 계속 책임집니다.

</details>

## 2. Read Replica와 Multi-AZ

| 기능 | 주목적 | 복제 방식의 관점 | 평상시 사용 |
|---|---|---|---|
| Read Replica | 읽기 성능 확장 | 복제 지연 가능 | 읽기 요청 처리 |
| Multi-AZ Standby | 고가용성과 장애 조치 | 일관된 장애 대응 우선 | 대기 후 승격 |

Read Replica에 분석·조회 트래픽을 분리하면 기본 인스턴스의 부하를 줄일 수 있습니다. Multi-AZ는 기본 인스턴스나 AZ에 문제가 생길 때 대기 인스턴스로 전환하는 데 초점을 둡니다.

## 3. 백업과 스냅샷

자동 백업은 보존 기간 안에서 시점 복구를 지원하고, 수동 스냅샷은 사용자가 보존 수명주기를 직접 관리합니다. 복구 가능성을 확인하려면 백업 성공 여부뿐 아니라 실제 복원 시험과 복구 시간도 측정해야 합니다.

## 4. 스토리지 자동 확장

저장 공간 사용량이 임계치에 가까워지면 최대 한도 안에서 용량을 늘릴 수 있습니다. 하지만 잘못된 인덱스, 느린 쿼리, 연결 과부하나 CPU 병목은 스토리지 확장만으로 해결되지 않습니다.

## 5. Aurora

Aurora는 MySQL 또는 PostgreSQL 호환 인터페이스를 제공하면서 저장 계층을 여러 AZ에 분산합니다. 읽기 복제본과 장애 조치를 활용할 수 있지만 엔진 호환성, 비용, 운영 기능과 마이그레이션 제약을 검토해야 합니다.

## 헷갈리기 쉬운 포인트

| A vs B | 차이 |
|---|---|
| Read Replica vs Standby | 읽기 확장 대상과 장애 조치 대기 대상입니다. |
| 백업 vs 고가용성 | 과거 데이터 복구와 현재 서비스 지속입니다. |
| 스토리지 확장 vs 성능 튜닝 | 저장 공간 증가와 쿼리·자원 병목 개선입니다. |

### 복습 질문 및 답변

**Q1. Read Replica는 항상 최신 데이터를 반환하나요?**

<details>
<summary>답</summary>

복제 방식에 따라 지연이 생길 수 있습니다. 즉시 일관성이 필요한 요청은 쓰기 기본 인스턴스를 사용하도록 구분해야 합니다.

</details>

**Q2. Multi-AZ를 사용하면 백업이 필요 없나요?**

<details>
<summary>답</summary>

아닙니다. 대기 인스턴스에도 잘못된 변경이 복제될 수 있으므로 삭제·손상·과거 시점 복구를 위한 백업이 별도로 필요합니다.

</details>

**Q3. 데이터베이스 비용을 줄일 때 가장 먼저 볼 것은 무엇인가요?**

<details>
<summary>답</summary>

실제 CPU·메모리·연결·저장소 사용량, 느린 쿼리와 읽기·쓰기 패턴을 측정해 과도한 크기와 불필요한 복제본을 찾습니다.

</details>
